청구 구성 — 청구유형 · 통합분할 · 수익계정 결정

Learning Journey Implementing Sales in SAP S/4HANA Cloud Private Edition · Course 9 / S46150 · 11 Unit · 14 레슨 · Intermediate · 12h 10m
출처: 노션 SAP Learning Hub 노트 9-1 ~ 9-6 변환

결론부터. 청구문서는 SD의 마지막 문서가 아니라 SD가 FI로 넘어가는 유일한 관문입니다. 이 코스에서 배우는 설정은 전부 "돈이 어느 계정에, 몇 장의 송장으로, 언제 찍히는가"를 통제합니다.

그래서 이 노트의 무게중심은 두 곳입니다 — 인보이스 통합/분할(왜 한 장이어야 할 송장이 세 장이 되었는가)과 수익계정 결정(왜 이 매출이 저 G/L로 갔는가). 앞은 운영 문의가 가장 많이 들어오는 자리이고, 뒤는 SD 설정 하나가 회계 결산을 흔드는 자리입니다.

LESSON 1청구문서의 자리 · 조직단위 · 청구유형

Unit 1-3레슨 3개Integrating Billing Documents · Setting Up Organizational Units · Configuring the Billing Process

언제 이걸 알아야 하는가

청구 쪽에서 제일 먼저 오는 문의는 "납품은 끝났는데 VF01에 안 뜹니다"입니다. 답이 갈리는 지점이 세 개뿐입니다 — 아이템카테고리의 청구관련성, 청구차단, 그리고 판매조직이 회사코드에 배정되어 있는지. 앞의 둘은 이 LESSON, 셋째는 조직단위 설정입니다.

청구를 "판매 프로세스의 끝"으로만 보면 이 문의를 풀 수 없습니다. 청구문서는 판매문서·납품문서와 FI 사이의 교차점이고, 양쪽 설정이 모두 맞아야 생성됩니다.

청구문서가 놓이는 자리

표준 청구유형

청구유형(Billing Type)은 청구문서 전체를 통제하는 최상위 키입니다. Customizing 경로는 Sales and Distribution → Billing → Billing Documents → Define Billing Types.

청구유형설명
F2Invoice — 표준 송장. 납품기준 청구의 기본값
F8Pro forma invoice — 견적송장. FI로 넘어가지 않는다
BVCash sale — 현금판매
G2Credit memo — 크레딧메모(고객에게 돌려줌)
L2Debit memo — 데빗메모(고객에게 더 청구)
REReturns — 반품
IV / IGIntercompany billing — 사내간거래 송장 / 크레딧메모
S1 / S2Cancellation — 취소 송장 / 취소 크레딧메모
LR / LGInvoice list / Credit memo list — 송장목록 / 크레딧메모목록

납품기준 vs 오더기준 — 무엇이 기준을 가르나

기준은 "실제로 나갔는지 확인해야 하는가"입니다.

  • 납품기준 청구 — 이미 출하된 것을 확인하고 청구할 때. 원문 예시: 카펫 납품
  • 오더기준 청구 — 납품문서가 아예 생성되지 않는 거래. 원문 예시: 카펫 시공 서비스
  • 물품과 서비스를 함께 청구해야 하면 오더와 납품을 동시에 참조하는 청구도 가능하다
🔰 초보자 설명 — 청구문서를 한 줄로

판매오더가 "무엇을 팔기로 했다", 납품문서가 "실제로 보냈다"라면, 청구문서는 "이제 고객에게 돈을 청구한다"입니다. 이 문서가 생성되어야 비로소 FI의 매출·채권 전표가 만들어집니다.

🔰 초보자 설명 — 회사코드 · 판매조직 · 계정과목표

회사코드는 법적 회계 단위, 판매조직은 영업 단위이고, 둘을 잇는 것이 배정(Assignment)입니다. 계정과목표는 그 회사가 쓰는 회계장부 양식이라고 보면 됩니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트는 회사코드 CL04 하나이고, 판매조직이 CL04에 배정되어 있어야 VF01이 FI 전표를 만듭니다. 판매 형태가 벤더 사입 → 재판매이므로 서비스 아이템이 없고, VL01N 기반 출하납품이 항상 선행합니다 — 즉 기본은 납품기준 F2 한 갈래로 깔면 됩니다.

다만 유통기한 임박품 반품·보상이 생기는 업종이므로, RE(반품)와 G2(크레딧메모)는 초기 IMG 단계에서 같이 열어 두는 편이 낫습니다. 나중에 붙이면 Copying Control과 계정결정을 다시 손봐야 합니다.

LESSON 2클레임 처리와 데이터플로 — Copying Control

Unit 4-5레슨 2개Using Billing Documents in Complaints Processing · Configuring the Data Flow for Billing Documents

언제 이걸 알아야 하는가

"고객이 금액이 틀렸다고 합니다. 송장을 고칠 수 있나요?" — 답은 언제나 아니오입니다. 이미 FI로 넘어간 송장은 고치는 게 아니라 취소하거나(S1) 차액 문서를 붙입니다. 어느 쪽이냐를 가르는 것이 이 LESSON의 문서 흐름입니다.

클레임 처리 문서 흐름

견적송장(Pro Forma Invoice)의 성질

  • 수출 거래용. 오더·납품 어느 쪽을 참조해도 생성 가능
  • 납품기준이라도 재고출고(PGI) 게시 전에 생성 가능
  • 선행문서의 청구상태를 갱신하지 않는다 → 얼마든지 반복 생성 가능
  • FI로 전달되지 않는다 — 회계에 흔적을 남기지 않는 문서

청구의 선행문서 — 무엇이 무엇을 참조하나

청구문서선행문서
Invoice판매문서 또는 납품
Credit / Debit memo크/데빗메모 요청 또는 청구문서
Returns credit memo반품문서
Pro forma invoice판매문서 또는 납품
Cancellation invoice / credit memo청구문서 / 크레딧메모
Invoice list청구문서들
Intercompany billing납품

외부거래 청구를 제외하면 모든 청구문서는 선행문서를 참조해야 합니다. 명시적으로 청구할 때는 선행문서 번호를 직접 입력합니다. 선행문서는 Copying Control 테이블의 헤더 레벨에 소스로 나타납니다.

Copying Control — 무엇이 어떻게 건너가나

레벨키 조합통제하는 것
헤더타겟 = 청구유형 · 소스 = 판매문서유형선행문서 종류, 외환데이터, 배정번호, 참조번호, 아이템번호 결정
아이템타겟 = 청구유형 · 소스 = 판매문서유형 + 아이템카테고리청구수량(오더수량 / 납품수량 중 어느 것), 가격결정 · 환율, 가격순서(조건이 어디서 전달되는지)

Copying Requirements(복사요건)로 헤더·아이템 레벨에서 청구 전제조건을 지정합니다 — 대표적인 것이 "재고출고(PGI) 게시가 선행되어야 함"입니다. 표준 요건으로 부족하면 커스텀 요건을 VOFM에서 직접 정의합니다.

청구수량 계산식

청구 방식청구수량
오더기준 (예: G2)오더수량 − 기청구수량
납품기준 (예: F1 · F2)기납품수량 − 기청구수량
Pro forma F5오더수량
Pro forma F8납품수량

가격결정유형(Pricing Type) — 청구유형 × 아이템카테고리 조합별로 배정

유형동작
A선행문서 조건값을 복사하고 스케일에 따라 갱신
B가격을 전체 재결정
C수동 조건은 복사, 나머지는 재결정
D선행문서 조건값을 그대로 복사(변경 없음)
G조건값 복사 + 세금만 재결정
H조건값 복사 + 운임비만 재결정
확인 필요 — 가격결정유형은 함부로 B로 두지 않는다

B(전체 재결정)로 두면 오더 시점의 합의가격이 아니라 청구 시점의 조건레코드로 금액이 다시 계산됩니다. 오더와 송장 금액이 달라져 고객 클레임이 됩니다. 실제 시스템(winerp01 / MEP)에서 VTFL(납품→청구 Copying Control)의 아이템 레벨 Pricing Type이 무엇으로 설정되어 있는지 확인하고 확정할 것.

🔰 초보자 설명 — Copying Control을 한 줄로

"선행문서의 어떤 정보(수량 · 가격 · 번호)가 청구문서로 어떻게 건너갈지"를 정하는 규칙표입니다. 납품문서 단계의 Copying Control과 완전히 같은 원리가 청구 단계에도 한 번 더 적용됩니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트에 반품·클레임을 붙인다면 대상은 유통기한 임박품 반품입니다. 그런데 프로젝트 원칙이 "회계 영향이 있는 처리는 자동화하지 않는다"이므로, 크레딧메모 요청에 청구차단을 자동설정하고 담당자 릴리즈를 반드시 거치게 하는 그림 2의 경로 A가 원칙에 맞는 구조입니다. 릴리즈 없이 청구문서를 직접 참조하는 우회 경로는 쓰지 않습니다.

Copying Control 관점에서는 ZGATE_INSPECT(GR 101 vs STOR이관 301 차이 → 송장 미발생 건 122 자동반품)가 MM 측 대응물입니다. SD 쪽 같은 자리가 이 LESSON의 Copying Requirements — "PGI 전에는 청구 못 한다"는 전제조건을 코드가 아니라 설정으로 막는 방식입니다.

LESSON 3청구문서 생성 방식 · 인보이스 통합과 분할

Unit 6-7레슨 3개Creating Billing Documents in Various Ways · Analyzing Invoice Combination and Invoice Split · Understanding Special Types of Settlement

언제 이걸 알아야 하는가

이 코스에서 운영 문의가 가장 많이 들어오는 자리가 여기입니다. "납품 3건을 한 장으로 청구해 달라고 했는데 송장이 3장 나왔습니다. 왜 갈라졌습니까?"

분할은 오류가 아니라 자동 판정의 결과입니다. 고칠 대상은 송장이 아니라 헤더 데이터가 왜 달랐는지이고, 그걸 추적하는 방법이 이 LESSON입니다.

청구문서를 만드는 네 가지 방식

방식내용
요청에 의한 청구오더번호 · 납품번호를 직접 입력해 명시 지정. 청구차단 등으로 생성 불가하면 오류로그가 남는다. Item Selection으로 일부 아이템 · 부분수량만 청구 가능 — 단 납품기준 청구에서는 청구관련성 K인 아이템카테고리만 수량 변경 가능
청구대기목록VF04. 개별 / 집합 / 집합 온라인 세 옵션 (아래)
특정일자 청구지정한 날짜로 청구문서를 생성
백그라운드 처리주기 실행(예: 매주 월요일 02:00) 또는 특정 시각 1회. 대기목록을 여러 백그라운드 작업으로 분할해 동시 실행 가능

청구대기목록의 세 옵션

개별

개별청구문서 — 대기목록의 각 문서마다 VF01을 개별 실행. 결합 없음

집합

집합청구문서 — 백그라운드에서 가능한 한 결합해 처리. 아이콘으로 성공 여부 표시

온라인

집합청구문서 온라인 — VF01로 분기하되 동일한 개별/집합 기준으로 결합. 시뮬레이션 모드로 저장 없이 결과만 미리볼 수 있다

대량 청구 성능 — 로그를 켜 둔 채로 돌리지 않는다

로그 · 상세목록이 불필요하면 선택하지 않는 것이 성능에 유리합니다(원문 명시). 집합처리 전체를 취소하는 것도 가능한데, 취소된 청구문서들은 집합처리유형 S의 집합처리번호로 묶여 Billing document → Log에서 확인됩니다. 집합실행 취소는 권한 있는 사용자만 가능합니다 — 권한 오브젝트 확인 없이 배포하지 말 것.

인보이스 통합과 분할 — 무엇이 같아야 합쳐지나

확인 필요 — 분할기준 필드 목록은 시스템마다 다르다

노션 원문은 "헤더 데이터가 서로 다른 경우 분할된다"까지만 기술합니다. 그림 3에 적은 필드 목록은 일반적으로 비교되는 헤더 값이며, 실제 비교 대상은 VTFL/VTFA Copying Control에 배정된 Data Transfer Routine과 VOFM 커스텀 요건에 따라 달라집니다. 실제 시스템(winerp01 / MEP)에서 다음 순서로 확정할 것 — ① 분할된 두 송장의 VBRK 비교 → ② VBRK-ZUKRI 값 확인 → ③ 해당 조합의 VTFL Data Transfer Routine 확인.

특수 정산 유형 세 가지

인보이스 리스트(Invoice List)

단건 청구문서 여러 장을 묶어 하나의 리스트 문서로 만듭니다(VF25, 청구유형 LR/LG). 출력 설정으로 개별 인보이스 생성 시점에 고객에게 발송할지, 리스트 생성 시점까지 보류할지를 고를 수 있습니다.

외부청구문서요청(EBDR) — Convergent Billing

SD 문서와 외부 시스템의 청구데이터를 함께 묶어 단일 고객 인보이스로 만드는 기능입니다. 원문 예시가 이해에 가장 빠릅니다 — IT 회사가 하드웨어(출하납품) · 소프트웨어 라이선스(판매오더) · 컨설팅 서비스(데빗메모 요청) · 클라우드 ML 서비스(EBDR의 외부 사용량 데이터)를 한 장의 인보이스로 묶습니다.

  • 생성 방법: SAP Fiori 앱 Manage Billing Document Requests에서 MS Excel 템플릿 업로드
  • 생성된 EBDR은 청구대기목록(Create Billing Documents 앱)에 함께 나타난다
  • 이렇게 내부/외부 데이터를 함께 청구하는 방식을 Omnichannel Convergent Billing이라 부른다

예비청구문서(Preliminary Billing Document)

사용하려면 비즈니스함수 SD_BIL_PRELIMBILLINGDOC을 활성화해야 합니다. 주의할 동작은 이것입니다 — 예비청구문서가 생성되면 선행문서(예: 납품)의 청구상태가 "청구됨"으로 바뀌어 정식 청구문서 없이도 청구대기목록에서 빠집니다. 거부하지 않는 한 대기목록에서 직접 청구문서를 만들 수 없고, Manage Preliminary Billing Documents 앱에서 최종 청구문서로 전환해야 합니다.

상태설명

Rejected사용자가 수동 거부. 청구문서 전환 불가, 선행문서가 다시 개방된다

청구 앱 — Create Billing Documents

Create Billing Documents – Billing Due List Items 앱은 전통적인 VF01/VF04보다 많은 필터·선택 옵션을 제공합니다. Billing Settings로 자동화할 수 있는 것:

  • 청구 전 청구일 / 청구유형 입력 요청
  • 청구대기목록 아이템별로 별도 청구문서 생성 (= 강제 분할)
  • 생성된 청구문서 자동 전표게시(post)
  • 생성 후 미리보기 표시 — 저장하면 최종 확정, 폐기하면 대기목록으로 복귀
  • 커스텀 필드를 활성화하면 대기목록 필터 · 정렬에도 사용 가능

보조 앱 Manage Billing Documents로 생성된 청구문서를 조회 · 수정 · 게시 · 취소하고 PDF 미리보기를 만들 수 있습니다.

🔰 초보자 설명 — 개별 청구 vs 집합 청구

개별청구는 "문서 하나당 청구서 하나", 집합청구는 "묶을 수 있는 건 묶어서 한 장으로"입니다. 납품 단계의 Order Combination(오더 여러 건을 한 납품으로)과 개념이 거의 같습니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트는 온도군이 갈린 자재를 다룹니다 — 냉동(CHKN/RICE)과 실온(SHAK/PROT/PBAR)은 저장위치가 다르고, 실무적으로 출하 차량이 다르면 납품문서가 갈립니다. 이때 한 고객의 냉동 납품과 실온 납품을 한 장의 송장으로 묶을지 갈라 둘지가 이 LESSON의 판단 지점입니다.

권장은 묶는 쪽입니다 — 고객은 한 번 주문했는데 송장이 두 장 오면 대사(對査)가 번거로워집니다. 반대로 온도군별 매출을 따로 봐야 한다면 굳이 송장을 쪼갤 것이 아니라 수익계정 결정(LESSON 5)에서 자재 계정지정그룹으로 G/L을 나누는 편이 맞습니다. 송장 장수와 계정 분리는 별개 문제입니다.

또 하나 — Billing Settings의 자동 전표게시는 프로젝트 원칙("회계 영향 처리는 자동화하지 않는다")과 정면으로 부딪힙니다. 켜지 않습니다.

LESSON 4청구계획 · 선급금 · 분할납부

Unit 8레슨 3개Setting Up Billing Plans · Processing Down Payments · Processing Installment Payments

언제 이걸 알아야 하는가

"계약은 걸었는데 매달 청구가 자동으로 안 나옵니다." 정기청구는 날짜가 자동으로 무한정 늘어나지 않습니다 — 리포트를 주기적으로 돌려 날짜를 생성해야 합니다. 이 한 줄을 모르면 두 달째부터 청구가 멈춥니다.

청구계획 두 유형

단건 청구일 대신 아이템 레벨에 여러 청구일자를 담은 청구계획을 저장할 수 있습니다. 헤더 레벨에도 정의할 수 있고, 이 경우 그 헤더에 배정된 모든 아이템에 적용됩니다. 거래 유형에 따라 시스템이 둘 중 하나를 자동 제안합니다.

유형용도동작
정기청구
Periodic Billing		임대 · 서비스 계약전액을 주기적으로 반복 청구. 시작일 · 종료일이 기간을 정의하며 가능하면 계약데이터에서 가져온다. 기간이 무제한이면 종료일을 두지 않고 호라이즌(청구계획에 설정된 정산기간 수)까지 날짜를 확장
마일스톤청구
Milestone Billing		플랜트 엔지니어링 · 건설총액을 여러 일자에 분산. 개별 일자마다 청구인덱스에 항목이 생기고 오더기준으로 청구된다
정기청구의 함정 — RVFPLA01

정기청구에서 새 청구일자는 개별 정산기간을 청구한다고 자동 생성되지 않습니다. 리포트 RVFPLA01을 주기적으로 실행해 날짜를 생성해야 합니다. 배치 잡 등록이 빠지면 호라이즌 끝에서 청구가 조용히 멈춥니다 — 실패해도 에러가 아니라 "대기목록에 안 뜸"으로 나타나 발견이 늦습니다.

마일스톤청구의 갱신 규칙

  • 이미 청구된 마일스톤 이후에 발생한 변경(예: 금액 변동)은 남은 청구계획 일자들에 분배된다
  • 이미 생성된 청구문서의 재청구 잔액은 최종인보이스에 포함된다
  • S/4HANA에서 마일스톤은 네트워크의 계획/실적 프로젝트 데이터와 함께 저장되고, 청구계획 일자에 배정되어 마일스톤 완료 확인 전까지 청구차단된다

청구규칙(Billing Rule)

특정 일자에 얼마를 청구할지 결정하는 규칙입니다 — 고정액인지 비율인지, 최종청구인지. 임대료처럼 월별 가격을 정의하는 특수 조건유형을 통해 월별 청구액을 산정할 수도 있습니다.

선급금 처리 — 왜 일반 채권과 섞으면 안 되나

플랜트 엔지니어링 · 건설이나 자본재 거래에서는 보통 고객과 선급금을 약정하고, 이는 판매오더 생성 시점에 이미 설정됩니다. 회계상 성질이 일반 매출채권과 다르기 때문에 계정을 분리합니다.

단계처리
선급금요청서 발송기일에 SD 청구문서로 발송. FI에 통계적(statistical) 항목으로 자동 게시 — 특수 G/L 지표 F, 일반 채권과 구분되는 별도 조정계정
입금 수령F-29. 선급금이 오더 계정에도 배정되며 특수 G/L 지표 A를 갖는다
부분 / 최종 청구선급금이 특수조정계정에서 차감되고 일반조정계정에 입력되어 고객 미수금 총액이 줄어든다

오더에 선급금을 거는 방법

선급금 처리는 청구계획 기능을 통해 수행됩니다. 오더에 선급금 합의를 청구계획 일자로 하나 이상 저장하며, 고정액 또는 아이템액의 비율로 지정합니다.

설정 항목값
청구규칙 4비율 기반 마일스톤청구용 선급금
청구규칙 5금액 기반 마일스톤청구용 선급금
조건유형 AZWR선급금 아이템 전용 조건유형(일반 PR00 대신). 조건카테고리 E · 계산규칙 B(고정액). AZWR이 결정되면 다른 모든 조건유형이 비활성화된다

부분청구와 선급금 정산

  • 부분 / 최종 인보이스 시 이미 수령한 선급금이 청구문서에 정산대상으로 자동 이전된다
  • 전액정산 방식 — 자동으로 차감
  • 비례정산 방식 — 가격화면의 AZWR 조건값을 수정해 정산액을 조절. 최대치는 수령된 선급금 − 이미 정산된 선급금
  • 최종청구 시에는 미정산 선급금이 모두 반영된다

분할납부(Installment Payments)

지불조건(payment terms)을 통해 총금액을 여러 분할납부 일정으로 나누어 청구하는 기능입니다. 원문에서는 데모로만 소개되어 설정 상세는 다루지 않습니다.

🔰 초보자 설명 — 정기청구 · 마일스톤청구 · 선급금 · 분할납부

정기청구는 구독형("매달 1일 임대료"), 마일스톤청구는 공사 단계별("착공 30% · 중도금 40% · 준공 30%"), 선급금은 미리 받은 돈을 따로 관리하다 청구 시 차감, 분할납부는 한 건의 청구를 여러 지불일로 쪼개는 것입니다. 앞의 셋은 청구문서를 몇 개 만드느냐의 문제, 분할납부는 한 청구문서의 지불 일정의 문제입니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트는 벤더 사입 → 즉시 재판매 모델이라 청구계획 · 선급금 · 분할납부가 모두 범위 밖입니다. 억지로 붙일 자리가 없습니다.

다만 이 LESSON에서 가져올 것이 하나 있습니다 — 정기청구의 RVFPLA01처럼 "배치가 안 돌면 조용히 멈추는" 구조는 프로젝트의 ZBATCH_ZONE(잔여 유통기한 30% 미달 시 정상→임박 311 자동이동)과 성질이 같습니다. 잡이 실패해도 아무도 모르면 임박품이 정상 저장위치에 그대로 남습니다. CBO 테이블에 상태필드(W/P/H)를 두기로 한 설계가 이 문제를 막는 장치입니다.

LESSON 5수익계정 결정과 SD-FI 인터페이스

Unit 9-10레슨 2개이 코스의 핵심Setting Up Account Determination · Understanding the Interface Between SD and FI

언제 이걸 알아야 하는가

회계팀에서 오는 문의는 딱 두 종류입니다. "이 매출이 왜 저 계정으로 갔습니까"와 "송장은 있는데 회계전표가 없습니다".

앞은 수익계정 결정(Revenue Account Determination), 뒤는 게시차단 또는 계정결정 오류입니다. 둘 다 SD 설정이 원인인데 증상은 FI에서 나타나기 때문에, SD 담당자가 이 구조를 모르면 "FI 문제 같습니다"로 떠넘기게 됩니다. 이 LESSON이 SD와 FI가 실제로 맞물리는 지점입니다.

수익계정 결정 — 조건기법으로 G/L을 찾는다

청구문서 데이터가 FI로 전달될 때 매출 · 매출차감 · 부가세(VAT) 게상용 G/L 계정이 자동으로 결정됩니다. 이 결정은 가격결정과 똑같은 조건기법(Condition Technique)을 재사용합니다 — 즉 Pricing에서 조건레코드를 찾는 방식 그대로 계정을 찾습니다.

확인 필요 — 조건테이블 조합과 계정키는 시스템 설정을 봐야 확정된다

노션 원문은 "수익계정결정이 Condition Technique로 수행된다"까지만 기술하고, 절차명 · 조건유형명 · 접근순서의 구체적 조합은 다루지 않습니다. 그림 4의 5개 키는 일반적인 조건테이블 구성이며, 실제로 어떤 접근이 몇 번째에 오는지는 시스템마다 다릅니다.

실제 시스템(winerp01 / MEP)에서 다음 순서로 확정할 것 — ① VKOA에서 유지보수 가능한 조건테이블 목록 확인 → ② 계정결정절차에 배정된 조건유형과 접근순서 확인 → ③ 문제가 된 청구문서에서 계정결정 분석(Analysis) 기능으로 어느 접근에서 걸렸는지 역추적. 추측으로 계정을 바꾸지 않습니다.

SD → FI 인터페이스

시스템은 인보이스 · 크레딧메모 · 데빗메모의 청구데이터를 FI로 전송해 올바른 계정에 게시합니다. 중요한 시점 구분이 하나 있습니다 — 청구문서가 FI로 넘어가기 전에는 청구일 · 가격 · 계정결정 · 출력결정 데이터를 변경할 수 있습니다. 넘어간 뒤에는 취소만 남습니다.

게시차단(Posting Block) — 전부 아니면 전무

STEP 1

특정 청구유형에 게시차단을 설정하면 청구문서가 생성되어도 FI로 자동 전송되지 않는다

STEP 2

배포자가 청구문서를 릴리즈(승인)한 후에만 회계전표가 생성된다

STEP 3

덕분에 SD 청구문서 생성 → 인쇄 → FI 전달 순서로 나눠 처리할 수 있어 성능이 개선된다

회계전표가 없는 두 가지 이유 — 둘 다 "부분 생성"은 없다

게시차단이 활성화되어 있거나 계정결정 오류가 있으면 시스템은 회계문서를 전혀 생성하지 않습니다. 일부 라인만 전기되고 나머지가 빠지는 일은 없습니다 — 전부 또는 전무입니다. 그래서 "전표가 아예 없다"는 증상을 보면 원인 후보가 이 둘로 좁혀집니다.

참조번호와 배정번호 — FI가 입금을 매칭하는 근거

번호유형FI에 들어가는 값
A고객참조번호(고객 주문번호)
B판매오더 번호
C납품번호
D외부 납품번호
E청구문서번호
F외부 납품번호가 있으면 그것, 없으면 납품번호

인보이스 리스트를 생성하면 리스트 번호가 개별 청구문서의 참조번호를 덮어씁니다. 이 단일 번호로 입금을 상계처리할 수 있습니다 — 고객이 여러 송장을 한 번에 결제하는 구조에서 쓰는 방식입니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트에서 SD · MM · FI 세 모듈이 실제로 만나는 지점이 바로 이 계정결정입니다. 자재그룹이 CHKN · RICE(냉동/냉장)와 SHAK · PROT · PBAR(실온)로 갈려 있으므로, 자재마스터 판매뷰의 계정지정그룹(그림 4의 ⓓ)을 온도군 또는 제품군 기준으로 부여하면 매출계정을 그 축으로 나눌 수 있습니다. 송장을 쪼개지 않고도 매출을 분리하는 정석 방법입니다.

게시차단은 프로젝트 원칙과 정확히 맞습니다 — "회계 영향이 있는 처리는 자동화하지 않는다". 청구유형 F2에 게시차단을 걸어 두면 VF01로 송장은 나오되 회계전표는 사람이 릴리즈해야 생깁니다. CBO에서 BAPI_BILLINGDOC_CREATEMULTIPLE 류로 청구를 자동 생성하더라도, 전표 생성은 이 릴리즈 단계에서 막힙니다.

이동평균가(V)를 쓰므로 매출원가 쪽은 MBEW-VERPR가 근거가 됩니다. ZPRICE_CHECK(정보레코드가 EINE-NETPR vs 이동평균가 MBEW-VERPR 괴리 알림)가 원가 쪽을 감시한다면, 이 LESSON의 계정결정은 매출 쪽이 어디로 꽂히는지를 정합니다. 두 축이 맞아야 매출총이익이 계정 단위로 읽힙니다.

계약의 선급금 상태와 배송차단

판매계약의 선급금 상태(Not Paid / Partially Paid / Fully Paid)는 마일스톤 청구계획에 설정된 배송차단 사유를 출처로 릴리즈오더의 스케줄라인에 자동 배정됩니다.

부분납부로는 차단이 풀리지 않는다

고객이 선급금을 전액 납부해야(Fully Paid) 배송차단이 자동 해제됩니다. Partially Paid만으로는 해제되지 않습니다. "돈 절반 들어왔는데 왜 출고가 안 되냐"는 문의의 답이 여기입니다 — 설정이 아니라 설계된 동작입니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트에서 직접 쓰는 것은 VA01 · VL01N · VF01 세 개와 VBRK / VBRP / VBFA 세 테이블입니다. 특히 VBFA는 납품 ↔ 송장 연결을 찾는 유일한 경로라, MM 쪽 ZGATE_INSPECT(송장 미발생 건을 찾아 122 반품)의 SD 대응 로직을 짤 때 그대로 쓰입니다.

PRCD_COND는 구 KONV가 아니라는 점을 코딩 전에 기억해 둘 것 — 예전 소스를 그대로 옮기면 KONV 참조에서 걸립니다.

General Billing Interface(순차파일로 외부 청구데이터 투입)는 프로젝트 목표 2번 "AL11 디렉토리 기반 대량 처리 프로그램"과 발상이 같습니다. 표준이 이미 파일 인터페이스를 제공한다는 사실을 인터페이스 설계서에 근거로 남겨 둘 만합니다 — 표준 우선 원칙의 실제 사례입니다.

반드시 지킬 것

· FI로 넘어간 송장은 고치지 않는다. 취소하거나 차액 문서를 붙인다. 회계전표는 되돌릴 수 없다는 전제로 움직인다.
· 송장 분할을 "오류"로 부르지 않는다. 자동 판정의 결과다. VBRK 비교 → ZUKRI 확인 → Copying Control 확인 순서로 원인을 찾는다.
· Pricing Type을 B(전체 재결정)로 두는 순간 오더 금액과 송장 금액이 달라질 수 있다. 바꾸기 전에 반드시 영향 범위를 확인한다.
· 계정결정은 추측으로 손대지 않는다. 계정결정 분석 기능으로 어느 접근에서 걸렸는지 확인한 뒤 VKOA를 고친다.
· 청구 자동 게시(Billing Settings의 자동 post)는 승인 절차 없이 켜지 않는다. 회계 영향이 있는 처리에는 사람의 릴리즈를 남긴다.
· 정기청구·마일스톤청구를 붙이면 배치 잡 모니터링을 같이 설계한다. RVFPLA01이 멈춰도 에러가 아니라 "대기목록에 안 뜸"으로만 나타난다.
