Output Control — Decision Table 기반 출력결정

Learning Journey Implementing Sales in SAP S/4HANA Cloud Private Edition · Course 6 / S46055 · 2 Unit · 4 레슨 · Intermediate
출처: 노션 SAP Learning Hub 노트 6-1 ~ 6-2 변환

결론부터. S/4HANA에서 오더확인서가 나가느냐 마느냐는 프린트 프로그램이 아니라 Decision Table 한 줄이 결정합니다. 문서가 저장되는 순간 시스템은 "무엇을 · 누구에게 · 어떤 채널로 · 어떤 폼으로" 보낼지를 규칙표에서 조회해 Output Parameter(출력 파라미터)로 문서에 박아 넣습니다. 파라미터가 없으면 Output은 발행되지 않습니다.

그래서 이 코스의 실체는 "출력물 만드는 법"이 아니라 규칙표를 읽는 법입니다. 행은 위에서 아래로, 컬럼은 왼쪽에서 오른쪽으로, 컬럼끼리는 AND, 같은 셀 안은 OR — 이 네 줄이 전부이고, 여기에 exclusive 표시 하나가 붙으면 이후 행이 통째로 무시됩니다. Pricing의 Condition Technique과 저장 위치만 다르고 발상은 같습니다.

언제 이걸 알아야 하는가

운영에서 가장 자주 나오는 문의가 "이 오더는 오더확인서가 안 나갑니다"입니다. 폼도 있고 프린터도 살아 있는데 안 나갑니다. 십중팔구 프로그램 문제가 아니라 그 문서에 출력 파라미터가 결정되지 않은 것입니다 — 규칙표에 걸리는 행이 없었던 겁니다.

그래서 이 문의의 조사 순서는 "폼 → 프린터"가 아니라 "어느 프레임워크로 만들어진 문서인가 → Decision Table에 걸렸는가 → Output Relevance가 켜졌는가" 셋입니다. 이 LESSON은 그 첫 번째 질문을, LESSON 2가 나머지 둘을 다룹니다.

왜 Output이 필요한가

ERP의 핵심은 비즈니스 트랜잭션의 문서화입니다. 판매 트랜잭션은 판매문서로, 출하 활동은 납품문서로, 청구·대변전표는 청구문서로 각각 문서화·처리·평가됩니다. 그런데 거래처는 대개 이 시스템에 접근권한이 없습니다. 그래서 문서를 기반으로 Output(출력물)을 발행해 거래처에게 전달합니다.

Output받는 쪽
오더확인서 (Order Confirmation)오더 입력자
납품서 (Delivery Note)수화인 (Ship-to Party)
청구서 (Invoice)청구수신자 (Bill-to Party)

프레임워크가 둘이다 — 어느 쪽으로 만들어진 문서인가

Output을 발행하려면 문서 안에 "어떤 유형의 Output을, 언제, 어떤 거래처에게, 어떤 채널로, 어떤 언어로"를 정의해야 합니다. 이 묶음이 Output Parameter이고, 문서가 생성될 때 자동으로 결정됩니다. SAP S/4HANA Sales에는 이를 담당하는 프레임워크가 두 가지 있습니다.

🔰 초보자 설명 — Output Control을 한 줄로

판매오더 같은 SAP 문서 안의 정보를 "누구에게, 언제, 어떤 방식(출력·이메일·EDI)으로 내보낼지" 자동으로 결정해 주는 규칙 엔진입니다. 오더확인서·납품서·청구서가 저절로 이메일이나 출력물로 나가는 것이 이 기능 덕분입니다.

확인 필요 — 원문에 없는 것

· 조건기법 기반 Output Determination(SD-BF-OC) 쪽의 저장 구조는 원문이 "출력조건레코드"까지만 언급합니다. 메시지 상태 테이블·전송매체 코드 같은 구식 구조의 세부는 강의에 나오지 않으므로 여기 적지 않았습니다.
· 출력 파라미터에 언어가 포함된다고 개념 레슨은 설명하지만, LESSON 2의 결정단계 8개 목록에는 언어에 해당하는 단계가 별도로 없습니다. 언어가 어느 단계에서 확정되는지는 실제 시스템(winerp01 / MEP)의 Output Parameter Determination 앱에서 확인할 것.

핵심 Customizing 객체 5종

커스터마이징은 순서가 곧 논리입니다 — "어떤 프레임워크를 쓸지 → 어떤 종류의 문서인지 → 언제·누구에게 보낼지 → 어떤 방법으로 → 어떤 모양으로". 다섯 단계를 하나씩 설정합니다.

① Framework 선택

Sales_Document라는 application object type에 대해 SAP S/4HANA Output Management를 활성화해야 쓸 수 있습니다. S/4HANA에서는 기본적으로 활성 상태입니다. 반대로 조건기법 기반 Output Determination(SD-BF-OC)을 쓰려면 Customizing에서 Sales_Document에 대해 비활성화합니다.

전환은 소급되지 않는다

활성 상태를 변경해도 신규 문서에만 적용됩니다. 기존 문서는 생성 당시 활성이던 프레임워크로 계속 처리됩니다 — 전환 직후 "어제 오더는 되는데 오늘 오더는 안 된다"(또는 그 반대)는 문의가 나오면 먼저 이걸 의심합니다.

② Output Type 정의

Output Type(출력유형)은 거래처와 정보를 교환하는 행위·문서를 기술합니다. 문서와 Output을 연결하고, 그 문서의 출력 파라미터를 정의하는 축입니다. 하나의 application object type에 여러 Output Type이 배정될 수 있습니다 — Sales_Document의 경우 견적서·오더확인서·계좌이체요청서·판매계약·고객반품 등.

운영에서 Output Type 신규 생성은 SAP 권장사항이 아니다

자체 Callback Class와 함께 쓸 때만 실무적 의미가 있고, 이 코스에서는 Callback Class 정의를 다루지 않습니다. 강의의 신규 생성 시연은 로직 이해를 위한 학습 목적입니다. 프로젝트에서도 표준 Output Type을 먼저 뒤지고, 없을 때만 신규를 검토하는 순서가 맞습니다.

③ Output Parameter Determination을 위한 비즈니스 규칙

특정 비즈니스 문서에 대해 시스템이 출력 파라미터를 어떻게 결정할지 정의하는 핵심 Customizing 활동입니다. 문서 속성을 기반으로 Decision Table의 규칙이 다음을 결정합니다.

  • Output Type · 수신자 · 채널
  • 프린터 설정 — PRINT 채널 한정
  • 발신 / 수신 이메일 주소 — EMAIL 채널 한정
  • PDF 생성용 폼 템플릿
  • Output Relevance(출력관련성)
Pricing의 Condition Technique과 같은 검색 전략이다

원문은 이 활동을 "Output Determination(SD-BF-OC)의 조건기법에 의한 출력조건레코드 검색에 대응한다"고 명시합니다. 즉 "문서의 속성을 키로 규칙표를 뒤져서 값을 문서로 복사한다"는 발상이 Pricing과 동일하고, 저장하는 그릇만 조건레코드 → Decision Table로 바뀐 것입니다.

Access Sequence가 구체적인 조건테이블부터 일반적인 것 순으로 훑는 것과, Decision Table이 구체적인 행을 위에 두고 위→아래로 훑는 것은 같은 전략입니다. 조건테이블·Access Sequence 쪽 구조는 S46200 Pricing 노트 LESSON 1 — 가격이 찾아지는 순서를 같이 보면 대응이 바로 보입니다.

④ Output Channel 배정

Output Channel(출력채널)은 출력물의 전달 매체입니다. SAP S/4HANA Output Control은 Sales_Document에 대해 EMAIL · PRINT · EDI 3가지를 지원합니다.

채널내용제약
EMAIL발신자·수신자를 유연하게 설정하고 이메일 템플릿을 쓸 수 있다—
PRINTSAP Spool System을 통해 출력. 프린터와 출력 매수는 별도 결정단계에서 확정—
EDIIDoc 또는 SOA(XML 메시지) 기술 메시지 포맷으로 거래처에 전송IDoc은 내부 청구(internal billing) 용도로만 지원. XML은 SAP Ariba 연동 전용
EDI 채널을 범용 인터페이스로 오해하면 설계가 무너진다

"S/4HANA Output Control이 EDI를 지원한다"를 "고객·벤더와 임의의 EDI 연동을 이 채널로 할 수 있다"로 읽으면 안 됩니다. IDoc 채널은 내부 청구 외 용도가 지원되지 않고, XML 채널은 Ariba 전용입니다. 일반적인 대외 인터페이스는 이 채널이 아니라 별도 인터페이스(IDoc 프로세스 코드 직접 구성, RFC, API)로 설계해야 합니다.

⑤ Form Template 배정

Form Template(폼 템플릿)은 출력물의 콘텐츠와 레이아웃을 정의합니다. SAP는 각 비즈니스 애플리케이션에 표준 Form Template을 제공하고, 자체 템플릿도 만들어 쓸 수 있습니다 — 단 폼과 대응 프린트 프로그램이 SAP S/4HANA Output Management와 호환되어야 합니다.

"어떤 프레임워크를 쓸지 → 어떤 종류의 문서인지(Output Type) → 언제·누구에게 보낼지(규칙) → 어떤 방법으로(채널) → 어떤 모양으로(폼 템플릿)" 순서로 다섯 단계를 하나씩 설정하는 것이 Output Control 커스터마이징입니다.

📌 개인 E2E 프로젝트와의 연결점

회사코드 CL04에서 오더확인서·납품서·청구서를 자동 발송한다면 이 Output Type → Channel → Form Template 체인이 그대로 설계 뼈대가 됩니다. 프로젝트는 표준 우선 원칙이므로 Output Type은 표준을 그대로 쓰고, 건드리는 것은 ③ 규칙(Decision Table)뿐이라는 선을 먼저 그어 두는 편이 좋습니다.

다만 목표 3번(웹페이지 → RFC로 SAP 호출)을 이 EDI 채널로 붙이려는 시도는 하면 안 됩니다. IDoc은 내부 청구 전용, XML은 Ariba 전용이라 범용 연동 경로가 아닙니다 — 인터페이스 설계서에서는 Output Control과 무관하게 독립 RFC FM으로 정의하는 것이 맞습니다.

언제 이걸 알아야 하는가

이쪽 문의는 "안 나간다"보다 "두 번 나갑니다"가 더 성가십니다. 같은 오더에 대해 이메일도 가고 EDI도 가는데 한쪽만 보내고 싶다 — 이건 버그가 아니라 여러 행이 동시에 걸린(multiple hits) 정상 동작이고, 고치는 곳은 프로그램이 아니라 규칙표의 exclusive 표시입니다.

Decision Table 구조와 8개 결정단계

SAP S/4HANA Output Management는 출력 파라미터마다 별도의 Decision Table을 유지합니다. Output Parameter Determination 애플리케이션에서 다음 8가지 결정단계(Determination Step)로 관리합니다.

#결정단계결정하는 것
1Output Type무엇을 발행할 것인가. 이후 단계에서 이 값 자체가 판단 기준(characteristic)으로 재사용된다
2Recipient누가 받는가. 오더확인서는 보통 Sold-to Party
3ChannelPRINT · EMAIL · EDI(IDoc 또는 SOA/XML)
4Printer SettingsPRINT 채널일 때 프린터와 출력 매수
5E-Mail Settings이메일 설정
6E-Mail Recipient이메일 수신자
7Form Template콘텐츠·레이아웃. 인쇄물·이메일 모두 해당
8Output Relevance파라미터가 아니라 게이트. 지금 정말 발행해도 되는 상태인가

테이블은 조건컬럼(흰색)과 결과컬럼(초록색, 1개 이상)으로 구성됩니다 — 조건이 충족되면 결과, 즉 출력 파라미터가 반환됩니다.

평가 순서 — 왼쪽→오른쪽, 위→아래

Decision Table의 각 항목은 왼쪽에서 오른쪽으로, 위에서 아래로 처리됩니다. 따라서 가장 구체적인 조건 세트를 위쪽에, 더 일반적인 조건 세트를 아래쪽에 배치해야 합니다. 이 순서를 뒤집으면 일반 규칙이 먼저 걸려서 구체 규칙이 의미를 잃습니다.

조건 처리의 일반 규칙

조건은 판매문서의 실제 데이터로 체크됩니다.

STEP 1

1행의 1번째 조건이 충족되면 2번째 조건을 체크한다 — 컬럼들은 논리 AND로 연결된다

STEP 2

한 행의 모든 조건이 충족되면 그 행의 결과가 문서에 반영된다

STEP 3

결과가 exclusive가 아니면 다음 행도 계속 평가한다

STEP 4

조건셀이 비어 있으면 모든 값이 조건을 충족한 것으로 본다

INCLUDE / EXCLUDE 조건

구분규칙
INCLUDE 조건참이어야만 해당 행이 계속 평가된다. 거짓이면 그 행은 더 이상 평가되지 않는다
EXCLUDE 조건거짓이어야만 해당 행이 계속 평가된다. 참이면 결과가 반환되지 않는다

비교연산자(같음·작음·다름 등)로 문서의 실제 값(Test Parameter)과 조건셀에 지정된 값(Comparison Parameter)을 비교합니다.

실전 예시 — SD Document Category + Sales Document Type

Decision Table 1행에 INCLUDE 조건 SD Document Category = C가 있고, AND로 연결된 Sales Document Type 컬럼에 조건 3개(INCLUDE 1개 + EXCLUDE 2개)가 있는 경우입니다.

  • 견적서는 Category B라서 이 행은 평가 자체가 중단됩니다
  • INCLUDE 조건 Sales Document Type ≠ BV — 표준오더 OR이면 참, BV면 거짓
  • 이어지는 EXCLUDE 조건 = SO01은 테스트 파라미터가 OR이므로 거짓 → 계속 평가
  • 그 다음 EXCLUDE 조건은 OR로 연결되어 있어 체크되지 않습니다

결과적으로 SD Document Category C + Sales Document Type OR인 표준오더에는 Output Type Order Confirmation과 Dispatch Time 1 Immediately가 반영됩니다.

Simulation — 예측하지 말고 돌려 본다

각 결정단계마다 Decision Table 평가를 시뮬레이션할 수 있습니다. 조건이 복잡해질수록 어떤 파라미터가 실제로 결정될지 머리로 따라가기 어렵기 때문에, Output Parameter Determination 애플리케이션의 시뮬레이션 기능을 쓰는 편이 안전합니다. 행 순서는 신규·변경 요청에 따라 재배열할 수 있고, 테이블은 Excel로 내보내기·가져오기도 됩니다.

🔰 초보자 설명 — Decision Table을 한 줄로

엑셀 표처럼 생긴 "만약 이 조건이면 이 결과" 규칙표입니다. 위에서부터 순서대로 체크하면서 조건에 맞는 행의 결과를 모으고, exclusive 표시된 행을 만나면 거기서 멈춥니다.

판매오더 출력 파라미터 — 결정 5단계 + 게이트 1개

실제 판매오더에 적용할 때의 흐름입니다. 각 단계는 앞 단계의 결과를 다음 단계의 판단 기준으로 다시 사용한다는 점이 핵심입니다 — 특히 Output Type은 이후 거의 모든 단계에서 characteristic으로 쓰입니다.

1

Output Type 결정 — 오더확인서 같은 Output을 발행하려면 먼저 문서의 Output Type이 정해져야 한다. 이후 단계에서 이 값 자체가 판단 기준이 된다

2

Output Recipient 결정 — 받을 거래처. Order Confirmation은 보통 판매오더의 Sold-to Party. Receiver Determination 단계에서 설정하며 여기서도 Output Type이 기준으로 쓰인다

3

Output Channel 결정 — PRINT · EMAIL · EDI(IDoc 또는 SOA/XML). Channel Determination 단계

4

Printer Settings 결정 — PRINT 채널이면 프린터와 출력 매수를 여기서 정한다

5

Form Template 결정 — 인쇄물·이메일 모두 폼 템플릿이 콘텐츠·레이아웃을 결정한다. Form Template Determination 단계

PDF는 어떻게 만들어지는가

PDF 생성에 쓰이는 Form Template은 데이터소스와 레이아웃 두 조각으로 구성됩니다.

구성요소역할
OData Service판매문서 데이터를 DB에서 가져온다 (데이터소스)
Adobe Livecycle Design Document레이아웃. OData 결과셋과 병합되어 PDF 문서로 렌더링된다

Output Relevance — 마지막 게이트

Output Relevance는 그 자체로 출력 파라미터가 아닙니다. Output이 트리거될 때 체크되는 단계로, 어떤 조건에서 Output이 실제로 발행될지를 통제합니다.

  • 문서가 불완전하면(Incompleteness Check) Output을 발행하지 않도록 지정
  • 자재 가용성이 없으면(Availability Check) Output을 발행하지 않도록 지정
출력관련성을 켜지 않으면 조용히 "준비 중"으로 남는다

Output 항목을 여기서 출력관련성 있음으로 표시하지 않으면 해당 Output은 발행되지 않고 "준비 중(in preparation)" 상태로 머뭅니다. 에러도 덤프도 나지 않기 때문에, "안 나간다" 문의의 조사 마지막 단계는 언제나 이 상태 확인입니다.

🔰 초보자 설명 — 5단계 결정 흐름을 한 줄로

"무엇을 보낼지(Type) → 누구에게(Recipient) → 어떤 방법으로(Channel) → (인쇄라면) 어느 프린터로 → 어떤 모양으로(Form Template)"를 순서대로 정하고, 마지막에 "지금 정말 보내도 되는 상태인지(Relevance)"를 체크하는 흐름입니다.

확인 필요 — 실제 시스템에서 확정할 것

· Output Parameter Determination 애플리케이션의 앱 ID와 IMG 경로가 원문(Learning Hub 본문)에 나오지 않습니다. winerp01 / MEP에서 Fiori Launchpad 앱 검색으로 확인하고 이 노트에 보강할 것.
· 결정단계 5 E-Mail Settings와 6 E-Mail Recipient의 역할 구분은 원문이 단계 이름만 나열하고 세부를 설명하지 않습니다. 실제 앱에서 컬럼 구성을 보고 확정할 것.
· Callback Class는 이 코스에서 다루지 않습니다 — 자체 Output Type을 실제로 쓰려면 반드시 필요한 조각이므로 별도 학습 대상입니다.

📌 개인 E2E 프로젝트와의 연결점

규칙을 코드가 아니라 표에 두는 구조가 이 프로젝트의 CBO 설계에 그대로 옮겨집니다. ZBATCH_ZONE의 "잔여 유통기한 30% 미달 → 정상 SLoc에서 임박 SLoc로 311 이동" 판정에서 30%와 온도군별 SLoc 6개(1100/1900 · 2100/2900 · 3100/3900)를 소스에 하드코딩하면 안 됩니다. Decision Table처럼 자재그룹 · 온도군 · 임계율 · 출발 SLoc · 도착 SLoc 컬럼을 가진 커스텀 설정테이블로 빼고, 구체적인 행(자재그룹 CHKN 지정)을 위에, 일반 행(자재그룹 비움 = 전체)을 아래에 두면 Decision Table의 "구체적 → 일반적" 순서 전략을 그대로 재현할 수 있습니다. 조회 순서를 제어할 PRIO 컬럼 하나를 PK에 넣어 두면 exclusive 대신 쓸 수 있습니다.

Output Relevance = 게이트라는 발상은 ZGATE_INSPECT와 정확히 같습니다. GR(101)과 STOR이관(301) 차이 중 송장 미발생 건만 122 반품 대상으로 거르는 것이, "불완전한 문서에는 Output을 발행하지 않는다"와 같은 구조 — 처리 직전에 상태를 한 번 더 확인하는 단계를 로직에서 분리해 두는 것입니다. 다만 122 반품은 재고·금액에 영향을 주므로, Output Relevance처럼 자동 통과시키지 말고 프로젝트 원칙대로 상태필드 W → 승인 후 P로 끊어 둡니다.

반드시 지킬 것

· Output Type을 운영에서 함부로 신규 생성하지 않는다. Callback Class 없이는 의미가 없고, SAP 권장사항도 아니다 — 표준을 먼저 뒤진다.
· EDI 채널을 범용 대외 인터페이스로 설계하지 않는다. IDoc은 내부청구, XML은 Ariba 전용이다.
· Decision Table은 구체적인 행을 위에 둔다. 일반 행이 위로 올라가면 아래 규칙이 전부 죽는다.
· 결과가 여러 개 나오는 것은 버그가 아니다. 의도한 게 아니면 exclusive로 끊는다.
· 조건이 세 줄 넘어가면 머리로 따라가지 말고 Simulation을 돌린다.
· "안 나간다" 문의는 폼·프린터가 아니라 프레임워크 → Decision Table → Output Relevance 순서로 본다.
