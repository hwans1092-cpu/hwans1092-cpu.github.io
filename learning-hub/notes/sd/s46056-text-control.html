Text Control — 텍스트 유형과 자동 전달

Learning Journey Implementing Sales in SAP S/4HANA Cloud Private Edition · Course 7 / S46056 · 2 Unit · 5 레슨 · Intermediate · 3h 3m
출처: 노션 SAP Learning Hub 노트 7-1 ~ 7-2 변환

결론부터. "송장에 찍혀야 할 문구가 안 나옵니다"라는 문의의 원인은 거의 항상 출력양식(Form)이 아니라 Text Control 설정입니다. 그 문서유형에 Text Determination Procedure가 안 붙었거나, 절차 안에 그 Text Type이 없거나, 있어도 Access Sequence가 텍스트를 못 찾아온 것입니다.

이 코스는 텍스트가 어디에 저장되고(Text Object) → 어떤 종류로 나뉘고(Text Type) → 어느 문서유형에서 쓸 수 있고(Text Determination Procedure) → 어디서 자동으로 채워지는지(Access Sequence)를 순서대로 세웁니다. 이 네 단계가 곧 장애 원인을 좁혀 가는 순서이기도 합니다.

LESSON 1Text Control 기본 구조 — Object · Type · Procedure

Unit 1-2레슨 2개Getting Started with Text Control · Customizing Manual Text Entry

언제 이걸 알아야 하는가

운영에서 이렇게 들어옵니다. "오더에는 메모를 분명히 썼는데 송장에 안 찍힙니다", 혹은 "이 오더에는 특이사항 입력칸이 아예 안 보입니다".

둘 다 출력양식 문제가 아닙니다. 입력칸 자체가 안 보이는 건 그 문서유형에 배정된 Text Determination Procedure에 해당 Text Type이 없다는 뜻이고, 오더엔 있는데 송장에 없는 건 청구유형 쪽 절차에 그 Text Type이 안 담겼거나 전달 설정이 없다는 뜻입니다. 확인 순서는 항상 Text Object → Text Type → Procedure → 배정처입니다.

왜 자유서식 텍스트가 필요한가

판매오더의 정보는 대부분 코드화되어 저장됩니다 — "즉시 순지불" 결제조건은 코드 0001로 들어갑니다. 코드로 못 담는 정보가 남는데, 그게 텍스트입니다.

  • 고객 특이사항 — "이 고객은 문화적 정체성을 고려해 응대해주세요"
  • 견적 아이템의 마케팅 정보 — "이 제품은 월말까지 세트로 특가 판매됩니다"
  • 동료용 내부 메모 — "Markus님, Spedition Müller에 집하 요청 전화 부탁드려요"

Text Object와 Text Type

텍스트는 여러 위치에 저장될 수 있습니다 — 고객마스터 · 자재마스터 · 조건마스터 · SD 문서. 이 "저장될 수 있는 위치"가 Text Object(텍스트객체)입니다.

Text Object무엇의 자리인가
VBBK판매문서 헤더 텍스트
VBBP판매문서 아이템 텍스트
TEXT표준텍스트(Standard Text). SO10으로 유지하며 Text ID로 다시 나뉜다 — 예: SDVD

그 위치 안에서 개별 메모를 구분하는 것이 Text Type(텍스트유형 · 텍스트ID)입니다. 4자리 영숫자 기술명 + 설명을 가지며, 언어별로 텍스트를 따로 유지할 수 있습니다. 표준 Text Type 예시: 0001 Form Header, 0002 Header Note 1, 0005 Purchase Order Text, 0003 Packing Note.

🔰 초보자 설명 — Text Object · Text Type을 한 줄로

Text Object는 "어느 문서/마스터의 어느 위치에", Text Type은 "그 위치 안에서 어떤 종류의 메모인지"입니다. 판매오더 헤더(VBBK)에 붙는 "Header Note"라는 메모지 한 장 — 이런 식입니다. Text Type을 새로 만드는 건 백지 한 장을 더 끼워 넣는 것에 가깝습니다.

Text Determination Procedure — 메모지 묶음

Customizing에는 그 Text Object에 한 번이라도 필요했던 모든 Text Type이 모여 있습니다. 출하납품 · 견적서 · 반품오더 · 표준오더용 헤더 Text Type이 전부 VBBK 아래 쌓여 있는 셈입니다. 그런데 실제 표준오더에 필요한 Text Type과 상업송장에 필요한 Text Type은 다릅니다.

그래서 특정 컨텍스트에서 쓸 Text Type만 골라 담은 바구니가 Text Determination Procedure(텍스트결정절차)입니다.

🔰 초보자 설명 — Text Determination Procedure를 한 줄로

"이 문서유형에는 이런 메모지들을 쓸 수 있어요"라고 정해두는 메모지 세트입니다. 표준오더에는 A·B·C 메모지가, 청구서에는 D·E 메모지가 필요하다면 서로 다른 세트를 만들어 각 문서유형에 배정하는 식입니다.

이론상 Text Object 하나당 Text Type 1개만 있어도 텍스트 입력 자체는 됩니다(한 Text Type 안에 여러 줄을 얼마든지 쓸 수 있으므로). 하지만 그러면 텍스트별로 제어할 수 없습니다 — 어떤 건 출력하고 어떤 건 안 하고, 어떤 건 후속문서로 넘기고 어떤 건 안 넘기고를 구분할 방법이 사라집니다. Text Type을 나누는 이유가 곧 제어 단위를 나누는 것입니다.

배정 — 절차는 어디에 붙는가

SD 문서는 문서유형으로 생성·통제됩니다(청구유형 F2 Invoice, 납품유형 LF Delivery, 판매문서유형 OR Standard Order). 그래서 헤더 텍스트 절차는 이 문서유형들에 배정합니다. 아이템 텍스트 절차는 (판매) 아이템카테고리, 납품 아이템카테고리에 배정합니다.

청구 아이템만 예외다

청구 아이템카테고리라는 오브젝트는 존재하지 않습니다. 그래서 청구 아이템용 Text Type을 담은 절차는 청구유형 자체에 배정합니다 — 청구유형 하나에 헤더용 절차와 아이템용 절차가 함께 붙는 셈입니다. 헤더/아이템 배정 규칙을 기계적으로 외우면 여기서 걸립니다.

Customizing 진입점

STEP 2

확인 필요 — 실제 시스템(winerp01 / MEP)에서 확정할 것

VOTXN 진입 후 Text Object 선택 UI와 절차 배정 탭 구성은 릴리스에 따라 화면이 다릅니다. 또한 Private Edition에서 Fiori 기반 Customizing 앱(SSCUI)으로만 열리는 항목이 섞일 수 있습니다. 실제 시스템에서 VOTXN이 열리는지, IMG 경로가 동일한지 먼저 확인한 뒤 설계서에 반영합니다.

수동 텍스트 입력

절차가 특정 판매문서유형(예: OR)에 배정되면, 그 문서유형으로 만든 판매문서에서 절차에 속한 Text Type만 나타나고 거기에 원하는 언어(예: EN)로 텍스트를 입력할 수 있습니다. 아이템 레벨도 동일합니다 — 아이템카테고리(예: TAN)에 절차가 배정되면 그 아이템카테고리로 통제되는 아이템에 입력할 수 있습니다.

하나의 Text Type 안에 언어키를 지정해 여러 언어 버전을 동시에 유지할 수도 있습니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트는 배치관리 + 유통기한(MCHA-VFDAT) 상품을 다루므로, 납품서·송장에 취급 문구가 반드시 따라가야 하는 구조입니다. 구체적으로는 이렇게 매핑됩니다.

· 아이템 텍스트(VBBP) — 온도군별 취급 문구. 냉동(1100/1900)은 "해동 후 재냉동 금지", 냉장(2100/2900)은 "0~4℃ 유지". 자재그룹 CHKN·RICE에 걸립니다.
· 헤더 텍스트(VBBK) — 배송 특이사항, 내부 메모.
· 배정처 — 판매문서유형(표준오더) + 아이템카테고리, 그리고 납품유형 · 청구유형까지 같이 배정해야 송장까지 따라갑니다. 오더에만 배정하고 끝내면 그림 1의 ④가 비는 상태가 됩니다.

실온 자재그룹(SHAK·PROT·PBAR)은 취급 문구가 필요 없으므로 같은 절차를 쓰되 Text Type만 비워 두면 됩니다 — 절차를 온도군별로 쪼갤 필요는 없습니다. 표준 우선 원칙에 맞습니다.

LESSON 2자동 전달 · 소스 분석 · 특수 기능

Unit 2레슨 3개Customizing Automatic Text Transfer · Analyzing Text Sources · Configuring Special Features

언제 이걸 알아야 하는가

1단계를 다 했는데도 "입력칸은 보이는데 항상 비어 있습니다"라는 문의가 남습니다. 이건 Access Sequence가 없거나, 있어도 텍스트를 못 찾은 것입니다.

그리고 가장 헷갈리는 케이스 — "문의서에 쓴 메모가 오더에는 안 넘어옵니다". 이건 설정 오류가 아니라 설계입니다. 텍스트는 직전 선행문서에서만 복사되기 때문입니다.

자동 전달의 조건 — Access Sequence 배정

판매문서가 생성될 때 특정 Text Type의 텍스트를 다른 Text Object의 Text Type에서 자동으로 가져오게(procure) 만들 수 있습니다. 표준오더의 텍스트가 기반 견적서에서 자동 복사되거나, 판매오더 텍스트가 Sold-to Party의 고객마스터 또는 판매자재의 자재마스터에서 자동 복사되는 식입니다.

자동 전달을 켜는 방법은 하나뿐입니다 — 해당 Text Determination Procedure 안에서 그 Text Type에 Access Sequence(접근순서)를 배정합니다. 절차에 Text Type만 담고 Access Sequence를 안 붙이면 입력칸만 생기고 자동으로 채워지지 않습니다.

Access Sequence — 텍스트 검색전략

Access Sequence는 텍스트에 대한 검색전략입니다. 최소 1개, 보통 여러 개의 Access로 구성되어 순차 처리됩니다. 각 Access에서 "어느 Text Object의 어느 Text Type에서 찾을지"를 정의하고, 언어 같은 추가 요건도 지정할 수 있습니다.

  • 요건을 만족하는 텍스트가 있으면 → 호출한 Text Type(이 Access Sequence가 배정된 Text Type)으로 전달
  • 없으면 → 다음 Access 실행. 같은 Object·Type의 다른 언어, 같은 Object의 다른 Type, 아예 다른 Object 무엇이든 가능
  • Access는 배타적(exclusive) — 한 번 찾으면 이후 Access는 실행되지 않는다
저장했는데 동작하지 않는다면

Access Sequence를 신규 생성하거나 수정한 뒤에는 반드시 Access를 Generate해야 합니다 — VOTXN 메뉴 Texts → Generate access. Customizing 화면상으로는 완벽한데 텍스트가 안 붙는 전형적 원인입니다.

또한 Access에서 접근 가능한 Text Object는 Permitted Text Object(허용된 텍스트객체)로 제한되어 있습니다 — 아무 오브젝트나 지정할 수 없습니다.

🔰 초보자 설명 — Access Sequence를 한 줄로

"이 메모가 비어 있으면 어디 가서 찾아올지"를 순서대로 정해둔 검색 순번표입니다. 첫 번째 후보에서 못 찾으면 두 번째, 세 번째로 넘어가고, 찾으면 그 자리에서 멈춥니다.

직전 선행문서 원칙 — 건너뛰기는 불가능하다

텍스트는 항상 직전 선행문서(direct preceding document)에서만 복사됩니다. 문의 → 견적 → 오더 체인에서 오더는 견적에서만 가져올 수 있고, 문의에서 직접 가져올 수는 없습니다.

STEP 1

문의 생성 — 문의의 판매문서유형에 Text Type 0001이 담긴 절차가 배정되어 있고, 첫 Access가 VBBK·0001을 참조한다. 하지만 문의는 선행문서가 없으므로 아무것도 전달되지 않고 처리자가 직접 입력해야 한다.

STEP 2

견적 생성(문의 참조) — 같은 절차가 배정되어 있어 문의의 0001 텍스트가 견적의 0001로 복사된다.

STEP 3

오더 생성(견적 참조) — 오더 문서유형에도 VBBK 접근을 포함한 절차가 배정되어 있으면 견적에서 오더로 복사된다.

성능 팁 — 헛된 Access를 막는다

STEP 1처럼 선행문서가 없는 문서유형에서는 VBBK 접근이 어차피 빈손으로 끝납니다. 이때 Access Sequence의 해당 Access에 조건 1 Reference doc. header를 걸어 접근 자체를 막을 수 있습니다. 문서 건수가 많을수록 차이가 납니다.

청구문서의 텍스트 소스

납품기준 청구(delivery-related billing)에서 청구문서의 직전 선행문서는 납품문서입니다. 그런데도 기반 판매오더에서 텍스트를 가져오는 것이 가능합니다. 청구유형 Customizing에서 VBBK·VBBP별로 선행문서를 고를 수 있기 때문입니다.

STEP 3

🔰 초보자 설명 — Text Determination Analysis를 한 줄로

"이 메모가 왜 안 채워졌지?" 또는 "이 메모는 어디서 복사돼 오는 거지?"를 추적하는 디버깅 로그 화면입니다. 어느 Access까지 갔고 어디서 멈췄는지가 보입니다.

확인 필요 — 실제 시스템(winerp01 / MEP)에서 확정할 것

Goto → Header → Texts → Display log는 SAP GUI 판매오더 화면 기준 경로입니다. Fiori 앱(Manage Sales Orders 등)에서 같은 분석 화면이 어떤 이름·위치로 제공되는지는 릴리스마다 다릅니다. 운영 매뉴얼에 쓰기 전에 실제 화면에서 경로를 확인합니다.

Reference vs Duplicate

Text Type에 Access Sequence가 배정되어 복사가 가능한 경우, 절차에서 그 텍스트를 복제(duplicate)할지 참조(reference)할지 지정합니다.

방식동작
Duplicate(복제)전달된 텍스트가 DB에 별도 레코드로 저장된다. 원본과 복사본이 완전히 독립적이라 서로 영향 없이 수정 가능. 메모리를 더 사용하므로 기능적으로 꼭 필요할 때만 사용을 권장
Reference(참조)텍스트가 DB에 한 번만 존재 — 원본을 바꾸면 전달된 텍스트도 함께 바뀐다(사실상 같은 것). 문서에서 복사된 텍스트를 직접 수정하면 그 순간 자동으로 복제로 전환되며, 이후 원본 변경은 영향을 주지 않는다
🔰 초보자 설명 — Reference vs Duplicate를 한 줄로

Reference는 "원본과 링크로 연결된 사본"이라 원본이 바뀌면 같이 바뀌고, Duplicate는 "완전히 따로 떨어진 복사본"이라 원본이 바뀌어도 영향받지 않습니다. 문서에서 직접 손대는 순간 자동으로 Duplicate로 바뀝니다.

Text is mandatory — 표시와 불완전성체크

절차에서 Text Type별로 Text is mandatory or should be displayed 필드를 설정할 수 있고, 이 한 필드가 두 가지를 통제합니다.

  • 표시 여부 — 텍스트가 전달될 때 화면에 띄울지. 띄우도록 설정하면 판매문서 처리 중 개요화면에 대화상자가 뜨고 필요하면 즉시 편집할 수 있다
  • 필수 여부 — Incompleteness Check(불완전성체크) 관점에서 필수인지. 필수로 잡힌 Text Type에 텍스트가 전달·입력되지 않으면 문서가 불완전 상태가 된다
확인 필요 — 하드코딩된 불완전 절차 50 · 51

불완전 절차 50·51은 하드코딩되어 있어 트랜잭션 SM31의 뷰 유지보수 V_TVUVF로만 처리 가능합니다(SAP Note 385982). SM31 직접 유지는 권한·변경요청 정책에 걸리는 경우가 많으니, 실제 시스템(winerp01 / MEP)에서 이 뷰가 열리는지와 운영 이관 경로를 먼저 확인합니다. 열리지 않으면 이 방식은 설계에서 뺍니다.

데이터전달루틴(Data Transfer Routine) — VOFM

Access가 찾는 조건을 ABAP으로 직접 프로그래밍하고 싶을 때 데이터전달루틴을 만듭니다. 트랜잭션은 VOFM(Maintain: Requirements & Forms)입니다. 루틴을 Access Sequence의 특정 Access에 배정하면, 그 Access는 프로그래밍된 로직으로 텍스트를 조달합니다.

  • 고객 자체 개발 네임스페이스는 50~99 (2자리 키)
  • 제공되는 샘플루틴 1(Exit sample) · 2(Exit Sample 2)에서 사용 가능한 데이터구조를 확인할 수 있다

표준 제공 루틴 91 — 자재별 표준텍스트 찾기

데이터전달루틴 91은 Text Object TEXT(표준텍스트)의 Text ID SDVD에서, 이름이 ZMAT:* 형식인 표준텍스트를 찾습니다. *는 해당 문서아이템의 현재 자재번호로 치환됩니다.

refer-tdname+5 = FTVOM-MATNR

자재 P650-100이 팔리면 시스템은 이름이 ZMAT:P650-100인 표준텍스트를 찾습니다. 전제조건은 세 가지입니다.

STEP 1

Text Object TEXT · Text ID SDVD에 대한 Access가 존재할 것

STEP 2

그 Access에 데이터전달루틴 91이 배정되어 있을 것

STEP 3

해당 이름의 표준텍스트가 실제로 존재할 것 — SO10으로 유지

📌 개인 E2E 프로젝트와의 연결점

1) 루틴 91이 프로젝트에 그대로 쓸 수 있는 표준입니다. 자재별 취급 문구를 SO10에 ZMAT:<자재번호>로 등록해 두면, 냉동 CHKN·RICE 자재는 "해동 후 재냉동 금지", 실온 SHAK·PROT·PBAR는 별도 문구가 오더 아이템 텍스트로 자동 전달됩니다. CBO 없이 표준만으로 끝나는 구간이므로 "표준 우선" 원칙에 맞습니다.

2) 직전 선행문서 원칙이 제약조건입니다. 오더 → 납품 → 청구 3단 체인에서 문구를 끝까지 보내려면 세 단계 모두에 절차를 배정해야 합니다. 오더와 청구에만 배정하고 납품을 비우면 중간에서 끊깁니다. 청구는 Text Delivery 체크박스로 "납품 경유"와 "오더 직결" 중 하나를 고를 수 있으니, 납품 단계에서 문구를 손댈 일이 없다면 체크를 풀어 오더에서 직접 가져오는 편이 배정 누락에 덜 취약합니다.

3) Reference/Duplicate는 ZBATCH_ZONE과 엮입니다. 잔여 유통기한 30% 미달로 정상→임박 SLoc(1100→1900 등)으로 311 이동이 일어나도, 이미 발행된 납품·송장의 문구는 바뀌면 안 됩니다. 출력물에 찍힌 내용이 사후에 달라지는 것은 증빙 관점에서 사고입니다. 따라서 출력 대상 Text Type은 Duplicate로 잡습니다. 반대로 아직 발행 전인 내부 메모성 Text Type은 Reference로 두어 마스터 수정이 반영되게 해도 무방합니다.

4) 필수(mandatory) 설정은 신중히. 취급 문구 Text Type을 불완전성체크 필수로 걸면 표준텍스트가 하나만 빠져도 오더 전체가 불완전 상태가 되어 납품이 막힙니다. 마스터 정비가 끝나기 전에는 "표시만" 설정으로 두고, 데이터가 안정된 뒤 필수로 올리는 편이 안전합니다.

반드시 지킬 것

반드시 지킬 것

· Access Sequence를 만들거나 고쳤으면 Generate access를 반드시 실행한다. 저장만으로는 동작하지 않는다.
· 문구가 송장까지 가야 한다면 오더 · 납품 · 청구 세 단계 모두에 절차를 배정한다. 한 군데만 비어도 거기서 끊긴다.
· 출력물에 찍히는 Text Type은 Duplicate로 잡는다 — 발행된 문서의 문구가 사후에 바뀌면 증빙 사고다.
· 불완전성체크 필수 설정은 마스터 정비가 끝난 뒤에 켠다. 먼저 켜면 문구 하나 때문에 납품이 전부 막힌다.
· 선행문서가 없는 문서유형에서는 Access에 조건 1 Reference doc. header를 걸어 헛된 접근을 막는다.
· 텍스트가 안 나오면 출력양식부터 보지 말고 Object → Type → Procedure → 배정 순으로 좁힌다.
