Outline Agreement — 일정계약 · 수량계약 · 가치계약

Learning Journey Implementing Sales in SAP S/4HANA Cloud Private Edition · Course 4 / S46051 · 3 Unit · 3 레슨 · Intermediate
출처: 노션 SAP Learning Hub 노트 4-1 ~ 4-2 변환 (Learning Hub 레슨 본문 3개, 다운로드 자료 없음)

결론부터. Outline Agreement(장기계약)는 물건을 내보내는 문서가 아닙니다. 뒤에 올 개별 오더가 갉아먹을 한도를 미리 걸어두는 문서입니다 — 한도의 단위가 수량이면 Quantity Contract, 금액이면 Value Contract, 수량에 납품 스케줄까지 붙으면 Scheduling Agreement입니다.

그래서 이 코스에서 실제로 봐야 할 것은 계약 화면이 아니라 릴리스오더가 계약을 어떻게 물고 들어가는가입니다. Copying Control이 어떤 오더유형을 릴리스로 허용하는지, 시스템이 열린 계약을 얼마나 자동으로 찾아주는지, 아이템 레벨에 배정해야만 계약 잔여가 줄어드는지 — 운영에서 터지는 지점은 전부 이쪽입니다. 계약 자체는 껍데기고, 연결 규칙이 본체입니다.

LESSON 1Outline Agreement의 자리 · Scheduling Agreement와 Quantity Contract

Unit 1-2레슨 2개Introducing the Sales and Distribution Process · Working with Scheduling Agreements and Quantity Contracts

언제 이걸 알아야 하는가

계약을 태운 고객에서 제일 자주 나오는 문의가 "계약 걸어놨는데 오더가 계약을 안 물고 갑니다"입니다. 계약도 살아 있고 유효기간도 남았는데 오더는 그냥 단독 오더로 떨어집니다. 그 다음 문의는 "릴리스를 했는데 계약 잔여가 안 줄어듭니다"입니다.

두 문의의 답은 계약 문서 안에 없습니다. 앞은 Copying Control과 열린 계약 자동검색 옵션, 뒤는 헤더가 아니라 아이템 레벨 배정입니다. 계약 화면만 들여다보면 하루를 씁니다.

판매문서 구조 위에 얹히는 문서

SAP에서 모든 판매 활동은 판매문서(sales document)로 기록되고, 판매·출하·청구 각 단계는 전용 문서유형으로 표현됩니다 — 판매문서유형(문의·견적·표준오더 등), 납품유형(출하납품·반품납품 등), 청구문서유형(청구서·대변전표·차변전표 등).

Outline Agreement도 판매문서유형의 한 종류입니다. 별도 계통이 아닙니다. 모든 문서는 고유 문서번호로 식별되고 처리상태를 반영하는 전체상태(overall status)를 가지며, 판매문서의 일반 구조인 헤더 – 아이템 – 스케줄라인이 Outline Agreement와 그 릴리스오더에도 그대로 적용됩니다. 이 코스 전체가 이 구조 위에서 전개됩니다.

🔰 초보자 설명 — Outline Agreement을 한 줄로

"앞으로 이 조건으로 여러 번 나눠서 살게요"라고 미리 약속해두는 판매문서입니다. 실제 개별 주문(release order, 릴리스오더)은 이 약속을 하나씩 꺼내 쓰는 방식으로 진행됩니다.

계약 3종 — 무엇을 고정하고 무엇을 릴리스하는가

확인 필요 — Scheduling Agreement의 납품 경로

원문(Learning Hub 레슨 본문)은 Scheduling Agreement를 "Quantity Contract에 납품 스케줄을 더한 문서"로만 설명하고, 납품이 릴리스오더를 거치는지 스케줄라인에서 직접 생성되는지는 명시하지 않습니다. 단정하지 않고 넘깁니다 — 실제 시스템(winerp01 / MEP)에서 해당 문서유형의 납품 생성 경로를 확인한 뒤 이 칸을 채울 것.

릴리스오더 생성 — Copying Control이 먼저다

어떤 판매문서유형을 그 계약의 릴리스오더로 쓸 수 있는지는 Copying Control에서 결정됩니다. 여기에 허용되지 않은 조합은 참조 생성 자체가 막힙니다. "계약을 참조할 수 없다"는 증상이 나오면 계약이 아니라 Copying Control부터 봅니다.

허용된 다음, 릴리스오더를 만드는 방법은 네 가지입니다.

1

오더 초기화면에서 Create with reference 선택 — 가장 일반적인 경로

2

판매문서 메뉴에서 Sales document → Create with reference → To contract

3

이미 만든 오더의 아이템을 사후에 계약에 수동 배정 — 오더를 먼저 치고 나중에 계약에 붙이는 경우

4

오더 생성 시 시스템이 열린(open) Outline Agreement을 자동으로 검색하도록 Customizing에서 설정

열린 계약 자동검색 옵션

4번 경로의 동작 강도를 정하는 것이 아래 옵션입니다. 같은 알파벳 쌍에서 앞 글자가 헤더 레벨, 뒤 글자가 아이템 레벨 체크입니다.

옵션동작사용자가 보는 것
Blank체크하지 않음계약이 있어도 아무 일도 일어나지 않는다
A / B헤더 / 아이템 레벨 체크. 고객번호·자재번호를 비교해 열린 계약이 있으면 알린다대화상자가 떠서 목록에서 고르거나, 무시하고 그대로 오더 처리를 계속할 수 있다
C / D헤더 / 아이템 레벨 체크 + 유일하면 자동복사열린 계약이 정확히 1개면 대화상자 없이 자동 생성되고 상태바에 정보메시지만 뜬다
E / F헤더 / 아이템 레벨 체크 + 즉시 선택목록으로 이동대화상자를 건너뛰고 바로 선택목록. 계약이 1개뿐이면 C/D와 동일하게 동작
확인 필요 — 옵션 필드의 위치와 필드명

원문은 옵션 코드(Blank/A·B/C·D/E·F)와 동작만 제시하고, 이 값을 유지하는 Customizing 경로와 필드명은 명시하지 않습니다. 판매문서유형 쪽 설정으로 보이지만 단정하지 않습니다 — 실제 시스템에서 VOV8 계열 화면을 열어 필드 위치를 확정할 것.

계약 → 릴리스오더 → 납품 : 잔여는 언제 줄어드는가

선수금(Down Payment) — 돈을 받아야 물건이 나간다

Quantity Contract에 선수금 처리를 걸 수 있습니다. 원문의 예시는 300유로 판매계약에서 납품 전 100유로를 선불로 요구하는 경우입니다.

🔰 초보자 설명 — 선수금 처리를 한 줄로

"돈을 먼저 받기 전엔 물건을 못 보낸다"는 규칙을 시스템에 걸어두는 것입니다. 계약에 걸어둔 청구계획 금액만큼 고객이 결제하면 자동으로 납품 잠금이 풀립니다.

📌 개인 E2E 프로젝트와의 연결점

지금 프로젝트(회사코드 CL04, 플랜트 GATE·STOR)는 건별 판매오더 중심이라 장기계약 자체는 범위 밖입니다. 다만 두 가지는 그대로 가져올 수 있습니다.

· 자동검색 옵션의 등급 설계 — A·B(알리기만) / C·D(유일하면 자동) / E·F(바로 목록)는 CBO에서 "참조문서를 얼마나 자동으로 물릴지"를 정할 때 쓸 수 있는 3단계 모델입니다. ZGATE_INSPECT가 GR(101)과 STOR이관(301) 차이를 잡을 때 건이 유일할 때만 자동, 여러 건이면 목록으로 가는 게 정확히 C/D 사고방식입니다.

· 납품블록 모델 — 조건이 충족될 때까지 후속 처리를 막고, 조건이 풀리면 시스템이 해제하는 구조는 CBO 상태필드 W(대기) → P(처리) 설계와 같습니다. 회계 영향이 있는 처리는 자동화하지 않는다는 원칙과도 맞습니다 — 막는 것은 자동, 푸는 것은 정산 사실 확인 후.

LESSON 2Value Contract — 금액 한도 · 릴리스 권한 · 계약 날짜

Unit 3레슨 1개Working with Value Contracts · 코스에서 가장 긴 Unit(1시간 40분) · Exercise 시뮬레이션 6개

언제 이걸 알아야 하는가

본사와 계약을 맺고 지점이 주문하는 고객에서 나오는 문의가 "이 지점으로는 계약에서 릴리스가 안 됩니다"입니다. 계약은 본사(Sold-to Party) 이름으로 걸려 있고 오더는 지점이 냅니다.

이건 권한 오류가 아니라 파트너결정절차에 릴리스 권한 파트너가 안 들어간 것입니다. 답은 판매문서유형의 Check partner authorization과 파트너기능 AA에 있습니다.

Value Contract란

Value Contract는 특정 자재 수량이 아니라 총 금액(value) 한도로 약정하는 계약입니다. 릴리스오더는 계약에 합의된 총 금액 중 일부를 소진하는 판매오더의 일종입니다.

🔰 초보자 설명 — Value Contract를 한 줄로

"이 금액만큼 앞으로 이것저것 사겠다"는 통 큰 약정입니다. Quantity Contract가 "이 물건을 이 수량만큼"이라면 Value Contract는 "총 얼마어치를"이라는 차이가 있습니다 — 개별 릴리스 때마다 다른 자재를 섞어 살 수도 있습니다.

릴리스(Release) 처리

항목내용
계약 찾는 방법① 파트너번호로 적합한 계약 검색 / ② 계약번호로 적합한 파트너 검색 — ②는 고객리스트 방식에 한정된다
자재 선택아이템선택 기능으로 유효한 전체 자재 중에서 고르거나, assortment module(구색 모듈)을 펼쳐서 선택
납품수량 · 납품시점계약이 아니라 릴리스오더의 스케줄라인에 저장된다
통화릴리스는 어떤 통화로도 생성 가능. 단 계약의 총액은 계약 통화로 업데이트된다
생성 시 체크계약에 저장된 요건(릴리스규칙 · 유효기간 등) 확인 + 릴리스오더 금액을 계약 잔여금액과 비교
한도 초과 시시스템 반응 방식은 설정 가능 — 표준으로 고정된 동작이 아니다
사후 배정헤더 · 아이템 레벨 모두 가능. 단 아이템 레벨에서 배정해야만 계약의 금액값이 업데이트된다
확인 필요 — 한도 초과 시 반응

원문은 "초과 시 시스템 반응 방식은 설정 가능하다"까지만 말하고 경고 / 오류 / 차단 중 무엇이 선택지인지, 어디서 설정하는지는 밝히지 않습니다. 계약 한도를 넘긴 릴리스가 조용히 통과하면 매출 인식까지 따라 흔들리므로, 실제 시스템(winerp01 / MEP)에서 이 설정 위치와 표준 기본값을 반드시 확정할 것.

청구(Billing)

방식내용
릴리스오더 개별 청구표준 오더유형 OR 사용. 오더기준 또는 납품기준 청구 가능
Value Contract 직접 청구표준시스템의 릴리스용 오더유형 WA 사용. 계약이 오더에 따라 청구된다
  • 청구계획(billing plan)을 쓰면 여러 날짜·부분수량에 걸쳐 한 번에 계약을 청구할 수 있다
  • 이후 계약 아이템의 목표금액을 변경하면 시스템이 열린 청구일정을 자동 조정한다
  • 완전히 릴리스되지 않은 Value Contract는 자동청구 대상이 될 수 없다

계약에서 릴리스할 수 있는 파트너

기본은 Sold-to Party와 그 외 지정된 비즈니스파트너입니다. 이 구조 덕분에 본사가 어느 지사가 계약에서 릴리스할 수 있는지를 결정할 수 있고, Ship-to Party도 여러 개일 수 있습니다.

고객리스트 방식(Rule A)의 릴리스 권한

  • 고객리스트가 있으면 계약문서의 파트너화면에 릴리스 권한 파트너를 직접 저장할 수 있다
  • 표준시스템에서 파트너기능 AA는 관련 파트너결정절차(표준 KAB 절차)의 선택적(optional) 파트너기능으로 정의되어 있다 — 기본으로 켜져 있지 않다
  • 대체 Ship-to Party는 파트너기능 AW로 표현된다
  • 고객마스터에 이미 여러 개의 잠재적 Sold-to Party(SP, AA)가 있으면, 계약 생성 시 시스템이 선택화면을 띄워 한 번에 여러 파트너를 선택·복사하게 한다
  • 릴리스 권한 파트너는 헤더 레벨에서만 체크된다
확인 필요 — 표준 코드값의 존재 여부

오더유형 WA, 요건 002(Header - Diff Customer), 파트너기능 AA·AW, 파트너결정절차 KAB는 모두 원문이 "표준시스템에서"라고 전제한 값입니다. 릴리스 버전과 기존 Customizing 상태에 따라 존재하지 않거나 다른 값으로 대체되어 있을 수 있습니다 — 실제 시스템에서 존재를 확인한 뒤 설계서에 인용할 것. 확인 전에는 하드코딩 금지.

계약 날짜 결정(Determining Dates)

계약을 만들면 시스템이 시작일·종료일 등을 제안합니다. 그 제안을 만드는 것이 Customizing의 날짜결정규칙(date determination rule)입니다.

구성요소역할
날짜결정규칙지정된 기준일(예: 오늘 날짜, 설치일) 중 하나로 문서를 시작시키고, 여기에 지정한 기간(interval)을 더한다. 이렇게 결정된 월의 시작일이나 종료일로 일정을 맞출 수도 있다
Duration Category
(기간범주)		지정하면 시스템이 계약 기간을 자동 생성한다. 계약 종료일 결정 등에서 날짜규칙의 구성요소로 쓰일 수 있다
Contract Profile
(계약프로필)		판매문서유형에 배정하면 계약 관련 기본값을 한 번에 결정 — 시작·종료일 결정규칙, Duration Category, 후속활동, 취소절차

즉 순서는 판매문서유형 → Contract Profile → 날짜결정규칙 · Duration Category → 실제 계약 날짜입니다. 계약 날짜가 이상하게 들어온다는 문의는 계약 화면이 아니라 이 체인의 위쪽을 봐야 합니다.

📌 개인 E2E 프로젝트와의 연결점

· 파트너기능 설계 — 프로젝트에서 이미 파트너기능(SP 등)을 잡아 두었으므로, 다지점 도매 고객을 넣게 되면 파트너결정절차에 AA(릴리스 권한)·AW(대체 Ship-to)를 더하는 것이 그대로 확장 경로가 됩니다. 식품 유통 모델에서 Ship-to가 여러 개인 상황(본사 계약 · 점포별 납품)은 자연스럽게 생깁니다.

· 유효기간 · 날짜결정규칙 — 프로젝트는 배치 유통기한(MCHA-VFDAT)을 기준으로 잔여 유통기한 30% 미달 시 ZBATCH_ZONE이 정상→임박 저장위치로 옮깁니다. "기준일 + 기간 → 종료일"이라는 계약 날짜결정규칙의 계산 구조가 제조일 + 유통기간 → 만료일 → 임계일 계산과 같은 모양입니다. 임계일 계산식을 CBO 안에 하드코딩하지 말고 규칙 테이블로 빼야 한다는 근거로 이 표준 설계를 인용할 수 있습니다.

· 금액 한도 초과 반응은 회계 영향이 있는 지점입니다. 프로젝트 원칙(회계 영향 처리는 자동화하지 않는다)에 따르면, 한도 초과 릴리스는 자동 차단보다 알림 + 승인 대기가 맞습니다 — ZPRICE_CHECK가 EINE-NETPR vs MBEW-VERPR 괴리를 알림까지만 하는 것과 같은 판단입니다.

반드시 지킬 것

· "계약을 참조할 수 없다"는 계약 문제가 아니다. Copying Control부터 본다. 계약 화면을 아무리 봐도 답이 없다.
· 사후 배정은 아이템 레벨로 한다. 헤더에만 붙이면 계약 잔여가 그대로 남아 한도 관리가 통째로 무의미해진다.
· 납품블록을 수동으로 풀지 않는다. 선수금 통제는 정산 사실로 풀리는 것이지 사람 판단으로 푸는 것이 아니다.
· 한도 초과 반응을 표준 기본값에 맡기지 않는다. 매출 인식에 직결되므로 설정값을 눈으로 확인하고 문서에 남긴다.
· WA·002·AA·AW·KAB는 확인 전까지 인용하지 않는다. 원문이 "표준시스템에서"라고 한 값이고 시스템마다 다를 수 있다.
