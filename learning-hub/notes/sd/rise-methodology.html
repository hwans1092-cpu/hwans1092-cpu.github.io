결론부터. 이 코스는 기능 코스가 아니라 "커스텀 코드를 어디에 둘 것인가"를 정하는 코스입니다. SAP가 RISE with SAP를 판매 패키지에서 전환 프레임워크·방법론으로 바꾸면서 그 중심에 놓은 원칙이 Clean Core이고, Clean Core는 개발자에게는 곧 확장을 코어 안에 넣지 말라는 요구입니다.

나머지는 그 원칙을 지키게 만드는 장치들입니다 — 무엇을 언제 할지 정해 주는 표준화 프레임워크, 그 활동을 얹을 통합 툴체인, 사람이 붙는 전문가 가이던스, 그리고 실제로 지켜졌는지 점수로 보여 주는 Dashboard. ABAP 개발자 입장에서 읽을 값은 "표준 오브젝트를 고치면 무엇을 잃는가"와 "그 대안이 어디에 마련돼 있는가" 두 가지입니다.

LESSON 1RISE with SAP Methodology와 Clean Core — 원칙

Unit 1레슨 3개Introducing the SAP Business Suite · Exploring the RISE with SAP Methodology · Exploring Clean Core Fundamentals

언제 이걸 알아야 하는가

개발자에게 이 코스가 걸리는 지점은 딱 한 문장입니다. "이거 표준으로 안 되니까 그냥 표준 프로그램에 한 줄 넣으면 됩니다" — 여기서 결정이 갈립니다. 그 한 줄이 들어가는 순간, 다음 업그레이드마다 그 자리를 다시 열어 보고 회귀 테스트를 해야 하는 채무가 생깁니다.

Clean Core는 그 채무를 만들지 않는 규칙이고, 이 코스의 나머지 전부는 그 규칙을 프로젝트 일정 안에 강제로 끼워 넣는 장치입니다. 답이 어디 있는지만 알면 됩니다 — 원칙은 Unit 1, 강제 장치는 Unit 2, 점수판은 Unit 3.

RISE with SAP의 위치가 바뀌었다

전통적으로 RISE with SAP는 SAP Cloud ERP Private(구 SAP S/4HANA Cloud Private Edition)을 포함하는 특정 판매 패키지였습니다. 클라우드로 전환하는 고객이 늘면서 SAP는 지속적·집중적 지원을 제공하는 방향으로 모델을 진화시켰고, 지금 RISE with SAP는 SAP Business Suite로 가는 전환 프레임워크이자 방법론입니다. SAP Cloud ERP Private는 여전히 많은 고객에게 핵심이며, 이를 지원하기 위해 SAP Business Suite가 자리합니다.

고객은 현재 ERP 구성과 전략 목표에 따라 SAP Business Suite로 가는 경로가 여러 갈래입니다. 포괄적인 현대화를 원한다면 전체 랜드스케이프를 평가해야 하고, 그 평가와 이후 전환을 RISE with SAP 전환 프레임워크가 지원합니다.

Clean Core — 코어를 표준에 가깝게 유지한다

Clean Core는 핵심 시스템을 표준 버전에 최대한 가깝게 유지해 과도한 커스터마이징이 불러오는 업데이트·유지보수 복잡성을 피하는 개념입니다. 그 결과 신규 기능·기술을 저비용으로 최신 상태로 유지할 수 있고, 시스템이 향후 변화에 유연하게 대응합니다.

ERP 시스템의 Core는 5개 차원으로 구성되고, 각 차원은 구현 시 베스트프랙티스·방법론·툴이 효과적으로 적용될 때 "clean"하다고 봅니다.

Clean Core를 떠받치는 장치가 셋 더 있습니다. SAP Activate Methodology 로드맵이 각 차원을 깨끗하게 유지하는 데 필요한 태스크·산출물·액셀러레이터를 구조적으로 안내하고, 운영 쪽에서는 Customer Center of Expertise를 구성해 업그레이드를 감독하고 IT팀과 비즈니스 부서를 연계합니다. 그리고 Enterprise Support 패키지에 포함된 SAP Cloud ALM Operations 앱이 추가 비용 없이 전체 랜드스케이프 상태를 유지합니다.

Clean Core 시스템의 특징 5가지

특징설명
Minimalism불필요·구식 기능 제거, 핵심 컴포넌트에 집중

Scalability성능·안정성 저해 없이 성장·변화에 대응
Maintainability코드베이스 단순화로 개발자의 이해·수정·개선이 용이
Stability and Reliability의존성 감소로 버그·불일치 가능성 축소, 신뢰성 향상
🔰 초보자 설명 — Clean Core를 한 줄로

"SAP 표준 기능은 그대로 두고, 커스터마이징이 필요하면 core 밖(BTP)에 별도로 얹는다"는 원칙입니다. core를 건드리지 않으니 다음 업그레이드가 훨씬 쉬워집니다.

확인 필요 — 확장 계층 용어와 온프레미스 적용 범위

원문(레슨 1-3 · 2-3)은 확장을 "BTP 위에 구축해 코어 ERP와 분리"하는 side-by-side 방향만 명시합니다. 업계에서 흔히 같이 말하는 In-App(키유저 확장 · 릴리즈된 확장 포인트) 계층은 이 코스 본문에 나오지 않으므로, 이 노트에서도 단정하지 않았습니다.

또한 Clean Core Success Plan · Quality Gate · Dashboard는 SAP Cloud ALM 전제입니다. 학습용 온프레미스 시스템(winerp01 / MEP)에는 Cloud ALM도 BTP도 없으므로, 여기서 적용 가능한 것은 "표준 오브젝트를 수정하지 않는다"는 원칙뿐입니다. 실제 적용 범위는 시스템에서 확정할 것.

개발자 관점 — 개인 프로젝트 CBO 3종은 어디에 있나

📌 개인 E2E 프로젝트와의 연결점

프로젝트 개발 원칙 첫 줄이 "표준 우선. IMG로 되는 건 IMG로. CBO는 표준으로 안 되는 지점만"인데, 이게 정확히 이 코스의 Clean Core 원칙입니다. 세 본 다 표준 오브젝트를 건드리지 않은 선택이 왜 맞는지 근거를 코스 용어로 말할 수 있습니다.

· ZBATCH_ZONE — 잔여 유통기한 30% 미달 배치를 정상 SLoc(1100/2100/3100)에서 임박 SLoc(1900/2900/3900)으로 옮길 때, MB1B의 표준 이동유형 311을 호출합니다. 이동 로직을 표준 재고이동 프로그램에 끼워 넣지 않았으므로 Processes 차원은 표준 그대로고, 판정 로직만 Extensions로 나와 있습니다.

· ZPRICE_CHECK — EINE-NETPR와 MBEW-VERPR를 읽기만 하고 전기하지 않습니다. 회계 영향이 있는 처리는 자동화하지 않는다는 원칙이 Clean Core의 Data 차원(마스터·트랜잭션 데이터를 임의로 건드리지 않음)과 같은 방향입니다.

· ZGATE_INSPECT — 반품 전기를 직접 INSERT하지 않고 BAPI로 만듭니다. 표준이 보장하는 검증·업데이트 태스크를 우회하지 않는다는 뜻이고, 이게 Clean Core에서 말하는 "코어의 무결성을 유지한 확장"입니다.

반대로, 같은 요구를 MB_MIGO_BADI나 표준 폼 복사로 해결했다면 그림 1의 왼쪽 경로가 됩니다 — 기능은 같지만 업그레이드 채무가 붙습니다.

언제 이걸 알아야 하는가

Unit 1의 원칙만으로는 아무것도 강제되지 않습니다. 실제 프로젝트에서 "이번만 예외로 표준을 고칩시다"가 나오는 순간을 막는 건 원칙이 아니라 단계마다 놓인 검문소입니다. Unit 2는 그 검문소가 어디에, 누가, 무엇으로 서 있는지를 다룹니다.

① Standardized Framework — SAP Activate 위에 얹는 활동

목적은 기업이 예측 가능하게 go-live하고 클라우드 혁신의 잠재력을 최대한 쓰도록 자신감을 주는 것입니다. SAP Activate 원칙과 RISE with SAP 도입 프레임워크 같은 기존 검증된 베스트프랙티스를 활용하며, 숙련된 파트너 생태계가 뒷받침하는 셀프서비스·지원 서비스·툴을 통해 각 단계에서 전문가 가이던스를 받습니다.

Standardized Framework가 실제로 하는 일은 구현 전 핵심 정보 수집에 초점을 맞춘 활동을 기존 SAP Activate 로드맵 태스크·산출물에 추가하는 것입니다.

Discover — Digital Discovery Assessment

Digital Discovery Assessment로 핵심 정보를 수집하고, 이 결과가 프로젝트 방향을 잡고 고객이 계획한 여정에 대한 인사이트를 줍니다. 온보딩팀과 고객성공관리자(customer success manager)가 이 데이터 수집에서 핵심 역할을 합니다.

Explore ~ Run — Clean Core Success Plan

Clean Core Success Plan은 SAP Cloud ALM을 통해 150개 이상의 권장 Clean Core 태스크를 관리하고 상세 Runbook으로 진행 상황을 추적합니다. 각 단계(Explore · Realize · Deploy · Run)마다 파트너 또는 SAP 소속 프로젝트매니저가 Clean Core Quality Gate로 태스크 완료를 검증하며, Gate는 설문 형태로 Cloud ALM에서 관리되고 제출하면 SAP Enterprise Support팀의 피드백을 받습니다. 피드백 리포트는 설문 응답 기반 권고사항과 시스템 데이터 분석을 담고, RISE with SAP Enterprise Architect와 함께 검토해 업그레이드·혁신에 대한 시스템 준비도를 유지합니다.

② Transformation Preparation Service (TPS)

TPS는 "Suite First"와 "AI First"라는 변화하는 우선순위에 대응해 SAP Business Suite를 제품 전략의 중심에 두는 서비스입니다. RISE with SAP 여정의 일환으로 비전과 실행 사이의 간극을 메워 초기 프로젝트 약속이 측정 가능한 성과로 이어지게 설계되었습니다. SAP Activate의 Prepare 단계에서 SAP 전문가가 주도하는 몰입형 경험으로 제공되며, 엔드투엔드 프로세스 셋업을 통해 AI 역량 통합과 거버넌스 프레임워크 구축을 포함한 후속 계획을 세우게 합니다.

Explore · Realize 단계에서는 Signavio와 Cloud ALM이 프로세스 모델링 · 실행관리 · 지속적 추적성을 지원하며, Cloud ALM은 실현 단계의 프로젝트 넥서스 역할로 진행상황·태스크배정을 추적하고 프로세스 산출물을 프로젝트 요소와 연결합니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트에 Cloud ALM은 없지만, Quality Gate 발상은 그대로 옮길 수 있습니다. MM 설계서 v2가 쓰는 형식 — 표준의 한계 → CBO가 메우는 것 → 테이블 정의 → 우선순위 — 이 사실상 "왜 표준으로 안 되는가"를 CBO 1본마다 통과시키는 게이트입니다. CBO를 늘리기 전에 이 네 칸을 못 채우면 만들지 않는다는 규칙이 Clean Core Runbook이 하는 일과 같습니다.

Toolchain 표에서 이 프로젝트가 실제로 쓰는 칸은 ③ 확장 개발뿐입니다. 나머지 다섯 칸(LeanIX · Signavio · Tricentis · Enable Now · Cloud ALM)은 학습 환경에 없으므로 개념만 알고 넘어가면 됩니다 — 포트폴리오 문서에서 "이 프로젝트에서 구축했다"고 쓰면 안 되는 영역입니다.

LESSON 3Clean Core Dashboard — 지켜졌는지 확인하는 창구

Unit 3레슨 1개Understanding the RISE with SAP Methodology Dashboard

언제 이걸 알아야 하는가

개발자에게 이 Unit이 직접 걸리는 문장은 하나입니다 — System View는 Clean Core 원칙에 부합하지 않는 코드를 식별하고, 그 코드가 운영 시스템으로 이관되지 않도록 돕습니다. 즉 이 대시보드는 보고용 그림이 아니라 이관 게이트에 걸리는 점수판입니다.

Dashboard가 하는 일

RISE with SAP Methodology Dashboard(Clean Core Dashboard라고도 함)는 고객 시스템의 Clean Core 원칙 준수도를 확인 · 평가 · 발전시키는 창구이며, SAP Cloud ALM을 통해 접근합니다.

코스는 여기서 Clean Core의 두 얼굴을 다시 정리합니다 — 표준 프로세스 채택은 운영 일관성·효율성에, 확장 구축은 차별화·유연성에 핵심적입니다. 둘 다 필요하고, 다만 자리가 다를 뿐입니다. Clean Core를 유지하면 민첩성·비용효율성이 올라 더 빠른 혁신·도입 사이클이 가능해집니다.

System View — 지금 세팅이 기준에 맞는가

제공 정보내용
Version insights설치된 SAP S/4HANA 제품버전이 최신인지 확인

System View는 시스템 준수도·최적화 기회 개요, Clean Core 상태 데이터 분석, SAP 권고사항 대비 편차 식별, 업그레이드 대비 확장성 관리를 제공합니다. 개발·테스트·운영 시스템 전체에 대한 인사이트를 포함해 Clean Core 원칙에 부합하지 않는 코드를 식별하고 운영 이관을 막습니다.

Operations View — 매일 지키고 있는가

Operations View는 RISE with SAP 고객에게 제공되며, 시스템 상태 KPI의 일별 인사이트와 과거 데이터로 운영 차원의 Clean Core 준수 목표를 맞추게 합니다. SAP Cloud ALM에 구성·운영 중인 모든 S/4HANA 시스템의 지표를 수집해 매일 특정 임계값과 비교 평가하고, 결과를 KPI·점수로 집계합니다. 지표·임계값·평가 알고리즘은 모든 RISE 고객에게 동일하게 공유되어 일관된 준수도 산정을 보장합니다.

  • 최대 30일치 과거 데이터를 포함한 일별 인사이트, 전일 기준 최신값과 System Health 점수 · KPI
  • 모든 운영 S/4HANA 시스템(Cloud Private Edition · On-Premise)의 System Health 점수 개요
  • KPI 산정에 영향을 준 지표 편차를 식별·분석하는 시스템별 뷰
  • 상세 확인을 위한 표준 SAP Cloud ALM 애플리케이션 바로가기
🔰 초보자 설명 — System View vs Operations View를 한 줄로

System View는 "지금 이 시스템이 Clean Core 기준에 맞게 세팅돼 있는가"를 보는 정적 점검이고, Operations View는 "매일 운영하면서 그 기준을 계속 지키고 있는가"를 보는 일별 모니터링입니다.

확인 필요 — 학습 시스템에는 이 대시보드가 없다

Dashboard는 SAP Cloud ALM 전제이고 Operations View는 RISE with SAP 고객 대상입니다. 온프레미스 학습 시스템(winerp01 / MEP)에서는 그대로 재현할 수 없습니다. 대체 가능한 표준 수단(예: SCI/ATC 코드검사, SPAU/SPDD 모디피케이션 조정 대상 목록)이 어디까지 붙어 있는지는 실제 시스템에서 확정할 것.

📌 개인 E2E 프로젝트와의 연결점

Dashboard를 흉내 낼 수는 없지만, "준수했는지 남기는" 자리는 프로젝트 안에 이미 있습니다. CBO 테이블에 두기로 한 상태필드(W / P / H)와 오류 로그 누적이 그것입니다. 특히 ZPRICE_CHECK는 판정만 하고 전기는 사람이 한다는 구조여서, Operations View가 "편차를 식별해 사람에게 보여 준다"는 성격과 정확히 같습니다 — 회계 영향 처리는 자동화하지 않는다는 프로젝트 원칙의 근거를 이 코스 용어로 설명할 수 있습니다.

반대로 ZBATCH_ZONE은 311 이동을 자동으로 겁니다. 이동평균가(V) 기준 SLoc 간 이동이라 재고 금액 총액은 바뀌지 않지만, 자동 전기인 이상 System View가 말하는 "업그레이드 리스크 있는 확장"과 같은 논리로 실행 이력과 취소 경로는 반드시 남겨야 합니다.

반드시 지킬 것

· 표준 오브젝트를 고치는 선택은 "빠른 길"이 아니라 "이자 붙는 빚"이다. 고치기 전에 확장으로 뺄 수 있는지 먼저 본다.
· 확장을 만들 때는 표준을 호출한다 — 표준 이동유형, BAPI. 직접 INSERT·표준 로직 우회는 코어를 더럽히는 것과 같다.
· 회계·재고 금액에 영향을 주는 판정은 자동 전기하지 않는다. 알림 또는 승인 대기까지가 안전선이다.
· Clean Core는 선언이 아니라 단계별 게이트로 검증된다. CBO 1본마다 "왜 표준으로 안 되는가"를 문서에 남기지 않으면 게이트가 없는 것과 같다.
· 이 노트의 Cloud ALM · BTP · Dashboard는 학습 환경에 없는 영역이다. 포트폴리오에 "구축했다"고 쓰지 않는다 — 개념 이해까지만.
