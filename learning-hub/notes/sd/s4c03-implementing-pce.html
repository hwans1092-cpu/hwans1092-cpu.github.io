언제 이걸 알아야 하는가

개발자가 프로젝트에 투입돼서 제일 먼저 부딪히는 질문이 "이거 지금 어느 시스템 · 어느 클라이언트에서 작업하는 겁니까"입니다. 그 다음이 "이 프로젝트가 신규 구축입니까, ECC에서 넘어오는 겁니까"입니다. 이 둘의 답에 따라 내가 만질 코드의 성격이 완전히 달라집니다 — 신규 구축이면 처음부터 ABAP Cloud로 쓰면 되지만, 컨버전이면 넘어온 Z 프로그램을 뜯어야 합니다.

PCE의 정체 — 클라우드가 아니라 "호스팅된 온프레미스"

이름이 Cloud라 오해하기 쉽지만, SAP S/4HANA Cloud Private Edition은 SAP S/4HANA 온프레미스 소프트웨어를 SAP HANA Enterprise Cloud(HEC)에 호스팅한 것입니다. 이 한 문장에서 나머지 성질이 전부 따라 나옵니다.

  • 온프레미스와 동일한 릴리즈 주기 — 2년 주기 기본 릴리즈
  • 메인스트림 유지보수 기간 7년(기존 5년에서 연장) · 최소 7년에 1회는 반드시 업그레이드해야 유지보수 범위에 남는다
  • 기본 릴리즈 후 6개월마다 FPS(신규 기능, 비파괴적), 다음 기본 릴리즈 출시 후 이전 릴리즈에는 6개월마다 SPS(수정만)
  • RISE with SAP 서비스의 일환으로 고객은 연 1회 업그레이드를 요청할 권리를 가진다. 기술적 업그레이드는 SAP가 수행하고, 계획·준비·테스트는 고객/파트너 책임

Public Edition과 달리 커스터마이징 유연성이 크기 때문에, 산업별 특수요건이 많거나 커스터마이징이 큰 중형~대형 고객이 주 대상입니다. Public Edition과 묶어 2-tier ERP 구조로 배포할 수도 있습니다.

Clean Core — 이 코스 전체를 관통하는 한 단어

고객의 핵심 시스템을 최대한 깨끗하게 유지한다는 개념입니다. 문제 있는 커스텀 코드 때문에 업그레이드를 못 하는 고객이 많았던 것이 출발점입니다. 이 코스의 LESSON 6(확장성)이 결국 Clean Core를 코드 차원에서 구현하는 방법입니다.

RISE with SAP Methodology는 기존 SAP Activate 로드맵 위에 Clean Core 관련 산출물을 덮은 것입니다. SAP Cloud ALM에서는 RISE with SAP Methodology - clean core success plan이라는 이름으로 제공됩니다.

🔰 초보자 설명 — New Implementation vs System Conversion을 한 줄로

New Implementation은 "빈 종이에 다시 그리는 것"(SAP 표준 프로세스로 시작), System Conversion은 "기존 그림을 새 캔버스로 옮기는 것"(현재 프로세스를 그대로 가져감)입니다.

SUM · DMO 용어 정리

  • SUM(Software Update Manager) — DB 마이그레이션 · 소프트웨어 업데이트 · 데이터 변환을 처리하는 도구
  • DMO(Database Migration Option) — 위 3단계를 하나로 통합. 다운타임이 줄어든다
  • DMO with System Move — 새 데이터센터로의 이전까지 함께 처리. ABAP 기반 시스템에만 가능

구현팀 — 누가 무엇을 하는가

용어부터 정리합니다. "고객"은 SAP 소프트웨어를 구매한 조직(또는 그 프로젝트팀 구성원), "파트너"는 SAP와 파트너십을 맺고 구축·판매·서비스·운영을 하는 조직입니다.

📌 개인 E2E 프로젝트와의 연결점

개인 프로젝트는 성격상 New Implementation(그림 1의 첫 행)입니다 — 렌탈 서버 위에 회사코드 CL04, 플랜트 GATE(입고 게이트) · STOR(보관)를 처음부터 IMG로 세웁니다. 승계할 ECC 자산이 없으므로 SUM · SPDD · SPAU · CVI 같은 컨버전 계통 작업은 발생하지 않습니다.

다만 클라이언트 구분은 그대로 걸립니다. ZBATCH_ZONE · ZPRICE_CHECK · ZGATE_INSPECT 세 CBO는 개발 클라이언트(클라이언트 독립)에서 만들어지고, STOR 저장위치 6개(냉동 1100/1900 · 냉장 2100/2900 · 실온 3100/3900) 정의와 이동유형 설정은 커스터마이징 클라이언트(클라이언트 종속)에서 만들어집니다. 전자는 Workbench Request, 후자는 Customizing Request로 갈립니다.

IT Contact(고객 System Admin)는 항상 단 한 명만 지정되며 모든 시스템 프로비저닝 알림을 받습니다. 잘못 지정됐다면 SAP for Me → Services & Support에서 서포트 케이스를 열어 변경 요청합니다(Component: XX-S4C-OPR-SRV). 일반 커뮤니케이션만 받을 Communication Contact은 여러 명 지정 가능합니다.

프로비저닝 순서 — IAS를 가장 먼저

STEP 1

IT Contact가 SAP for Me → Systems & Provisioning에서 SAP Cloud ALM 프로비저닝을 트리거한다. 이때 기존 SAP Cloud Identity Service 연결 여부를 선택하며, 신규 고객은 지역을 골라 자동 생성된다

STEP 2

여러 로그인 안내 메일이 순서에 관계없이 도착한다. 그러나 SAP Cloud Identity Authentication Service(IAS)를 가장 먼저 활성화해야 한다 — IAS 안에서 사용자를 만들고 Cloud ALM 접근 권한을 주기 때문

STEP 3

IT Contact의 트리거 없이 자동 프로비저닝되는 것: SAP Signavio Process Manager · Signavio Process Collaboration Hub · SAP BTP

STEP 4

PCE 시스템 자체는 — 신규구현이면 프로젝트 후반에 별도 프로비저닝, 시스템컨버전이면 각 시스템이 SUM으로 ECC에서 전환되므로 별도 프로비저닝 없음

SAP Fiori Rapid Activation — 컨버전 후 반드시 하는 일

SUM은 Fiori Launchpad를 자동 생성하지 않는다

전환이 끝나도 런치패드 UI는 만들어지지 않습니다. 별도로 Rapid Activation 절차를 돌려야 합니다. 개발시스템에서 런치패드 활성화를 시작해 SAP 제공 템플릿 역할 기반으로 고객 전용 역할 · 카탈로그를 정의하고, 마지막으로 품질시스템에서 고객 전용 비즈니스롤을 활성화해 프로덕션으로 전송합니다.

적용 조건: "Embedded" 아키텍처의 시스템에만 가능 (S/4HANA 1909 이상 권장 아키텍처).

핵심은 태스크리스트 SAP_FIORI_FOUNDATION_S4입니다. 실행하면 기본 역할 SAP_FLP_USER(사용자용) · SAP_FLP_ADMIN(관리자용)이 생성되고, 사용자 지정 접두사(예: Z_)를 붙인 복합역할 2개 Z_FIORI_FOUNDATION_USER · Z_FIORI_FOUNDATION_ADMIN이 함께 만들어집니다. 이 복합역할에 다른 역할을 추가하면 권한 부여가 단순해집니다 — LESSON 3에서 바로 쓰이는 지점입니다.

📌 개인 E2E 프로젝트와의 연결점

개인 프로젝트는 렌탈 서버에 이미 올라간 시스템으로 시작하므로 프로비저닝 · CAL 배포 구간은 해당이 없습니다. 다만 Cloud ALM의 Timeboxes(역산 일정) 개념은 그대로 씁니다 — 렌탈 서버 만료일을 go-live로 놓고 역산하면, SD/MM/FI IMG → CBO 3종 → 병렬처리 프로그램 → RFC 웹페이지의 순서에서 어느 범위를 버려야 나머지가 사는지가 계산됩니다.

그리고 Rapid Activation의 복합역할 구조(Z_ 접두사로 복사본을 만들고 거기에 역할을 붙인다)는 개인 프로젝트에서도 그대로 유효합니다. CBO 3종을 실행할 담당자 역할을 SAP 표준 역할에 직접 붙이지 말고 Z_ 복합역할을 하나 만들어 거기에 모으는 편이 나중에 정리하기 쉽습니다.

언제 이걸 알아야 하는가

개발을 마치고 나면 반드시 나오는 문의가 "권한 줬다는데 타일이 안 보입니다"입니다. 그리고 그 반대 — "타일은 보이는데 누르면 권한 오류가 납니다". 둘은 완전히 다른 원인이고, 고치는 곳도 다릅니다.

S/4HANA의 권한은 "쓸 수 있는가"(권한 축)와 "보이는가"(표시 축)가 분리돼 있습니다. GUI 시절에는 PFCG 역할 하나에 트랜잭션을 넣으면 메뉴에 나오고 실행도 됐지만, Fiori에서는 Business Catalog가 권한을 주고 Space/Page가 화면 배치를 결정합니다. 둘 중 하나만 있으면 위 두 문의 중 하나가 발생합니다.

Spaces and Pages는 S/4HANA 1909에 도입되어 2021부터 Groups를 대체합니다. 하지만 실제 시스템의 릴리즈와 설정에 따라 여전히 Groups가 활성 상태일 수 있습니다.

사용자 생성 — SU01

Fiori Launchpad를 쓰려면 먼저 SU01(User Maintenance)로 User Master Record를 만들어야 합니다. 접속은 아이디/비밀번호(basic authentication) 또는 SSO로 하고, 인증 후 사용자의 권한이 런치패드 앱 실행 또는 SAP GUI 트랜잭션코드 실행 시점에 검증됩니다.

  • User Master Record는 SAP HANA 플랫폼이나 서버 OS에 직접 접근할 권한을 주지 않습니다 — S/4HANA 애플리케이션 내에서의 행동만 통제. HANA 접근이 필요하면 보통 기술 계정으로 처리
  • 최소 필수 필드는 Last Name · Password
  • 런치패드 접근을 위해서는 SAP Fiori 사용자/관리자 역할 + 직무에 필요한 Catalog + (보통) Space가 함께 배정되어야 한다
  • 권한은 SU01에서 유지되는 역할에 기반해 프로파일을 통해 부여된다
"권한 있는데 안 됩니다"의 두 가지 실제 원인

· 실행은 되는데 데이터가 안 보인다 — 트랜잭션/OData 실행 권한은 있지만 데이터 접근 범위 권한이 없다. 둘 중 하나라도 누락되면 오류.
· Space는 받았는데 타일이 없다 — 역할에 Fiori Space가 부여돼도, 그 앱이 사용자가 가진 Catalog에 포함되지 않았다면 타일은 표시되지 않는다.

반드시 지킬 것

· SAP Catalog를 직접 수정하지 않는다. 복사해서 커스텀 Business Catalog로 쓴다 — 그래야 앱 간 네비게이션이 유지된다

· 원본 타일(Technical)과 사용 카탈로그(Business)를 분리해야 재사용성이 확보된다
· 한 스코프 안에서만 작업한다(Configuration 또는 Customizing 중 하나). 섞으면 Catalog가 오래된 상태로 남는다

🔰 초보자 설명 — Catalog vs Space/Page를 한 줄로

Catalog는 "이 사용자가 이 앱을 쓸 수 있는가"(권한)를 결정하고, Space/Page는 "그 앱이 런치패드 화면 어디에 자동으로 보이는가"(표시)를 결정합니다. 둘 다 갖춰야 사용자가 타일을 자동으로 볼 수 있습니다.

📌 개인 E2E 프로젝트와의 연결점

CBO 3종을 만들고 나면 바로 이 구조가 걸립니다. ZBATCH_ZONE(유통기한 30% 미달 건 정상→임박 311 이동) · ZPRICE_CHECK(EINE-NETPR vs MBEW-VERPR 괴리 알림) · ZGATE_INSPECT(GR 101 vs STOR 이관 301 차이 → 송장 미발생 건 122 반품)는 각각 실행 주체가 다릅니다 — 첫째는 물류 담당, 둘째는 구매 담당, 셋째는 입고 게이트 담당.

이것을 SU01에서 개인별로 트랜잭션을 붙이는 방식으로 풀면 나중에 담당자가 바뀔 때마다 다시 만져야 합니다. 그림 2의 왼쪽 축대로 역할 3개(Z_MM_GATE · Z_MM_PURCH · Z_SD_LOGI 같은 이름)를 만들고 각 CBO의 트랜잭션과 권한 오브젝트를 그 역할에 넣는 편이 맞습니다.

특히 ZGATE_INSPECT는 이동유형 122(반품)를 일으켜 재고와 회계에 영향을 줍니다. 프로젝트 원칙상 자동 전기까지 가지 않고 알림·승인 대기까지만 가기로 했으므로, 권한 설계에서도 조회 역할과 승인·전기 역할을 분리해야 합니다 — 같은 역할에 넣으면 승인 절차가 형식만 남습니다.

워크숍 일정 잡기 — 테스트스크립트 페이지 수가 기준

LoB 구성전문가는 테스트스크립트를 처음부터 끝까지 시연합니다(preliminary steps는 생략, test procedures만). 이를 통해 수집하는 것: 구성값 · Business Role 커스터마이징 · key user 인앱 확장 · 출력폼/이메일 커스터마이징 · 분석앱 커스터마이징 · 데이터마이그레이션 값 · 추가 통합 요구사항 · 예상 변화 영향.

  • 소요시간 추정 기준은 테스트스크립트의 Test Procedures 섹션 페이지 수 — 예: Material Requirements Planning(J44)는 약 40페이지, Production Capacity Leveling(3LQ)는 11페이지. 소요시간 차이가 크다
  • 반나절(4시간) 워크숍에 1~2개 프로세스, 종일 워크숍에 2~3개 프로세스가 현실적
  • SAP Signavio Process Navigator에서 각 프로세스의 주요 Business Role을 확인해 같은 역할이 많은 프로세스끼리 묶는다 — 참석자 집중도 유지에 유리
  • 가능하면 계정계획(Chart of Accounts)과 조직구조 워크숍을 먼저. 나머지 LoB 워크숍은 순서 무관 · 병행 가능
  • 하나의 Business Role에 최소 2명 · 최대 4명이 적절 (너무 적으면 관점이 빈약, 너무 많으면 논의가 산만)
  • 고객 LoB 전문가의 참여가 저조하면 파트너 PM이 고객 PM · 경영진 스폰서에게 에스컬레이션한다

워크숍 진행 — "Cloud Mindset"

각 워크숍은 mini kick-off로 시작해 Cloud Mindset을 설명합니다 — 표준 프로세스를 최대한 유지하고, 변경은 반드시 필요할 때만 하며, 앱 내에서 먼저 해결을 시도하고 안 되면 SAP BTP로 분리한다는 개념입니다. LESSON 6의 Tier 모델이 바로 이 문장의 기술적 구현입니다.

필드 하나를 추가해도 매 릴리즈마다 비용이 붙는다

어떤 변경이든 미래 릴리즈 업그레이드 시 유지보수 부담을 늘립니다. 새 필드 하나를 추가해도 매 릴리즈마다 확인 · 후속작업이 필요합니다(RASD 툴로 변경사항 파악은 가능). 그래서 워크숍에서 "반드시 필요(need to have)"와 "있으면 좋음(nice to have)"를 명확히 구분해야 합니다.

모든 워크숍이 끝나면 Realize 단계로 들어갑니다 — lead configuration expert가 개발시스템 클라이언트를 배포하고, 확정된 프로세스를 활성화하며, 조직구조를 구축하고 주요 재무 설정을 선택합니다. 이후 LoB 구성전문가가 BDCQ 설정값을 입력하고 Cloud ALM의 미결 요구사항을 해결해 나갑니다.

🔰 초보자 설명 — Fit-to-Standard vs Design Workshop을 한 줄로

Fit-to-Standard 워크숍은 "표준이 고객에게 맞는지 확인하고 부족한 점(요구사항)을 모으는" 단계, 디자인 워크숍은 "그 부족한 점을 어떻게 구현할지 구체적으로 설계하는" 단계입니다.

  • WRICEF(Workflow · Report · Interface · Conversion · Enhancement · Form)와 개발 요구사항에 대해서는 Realize 단계 견적 산출을 위해 Functional Specification이 필요하다. 시스템컨버전은 기존 명세서를 갱신
  • 마스터데이터 설계문서도 생산된다. 신규구현은 이 문서가 후속 데이터마이그레이션 설계에 재사용된다
  • 설계문서의 상세도 기준 — Realize 단계 작업이 바로 시작될 수 있을 만큼
  • 설계문서에 담기는 것 — 프로세스 간략설명 · 요구사항 · 프로세스플로우(Best Practices 기준선 대비 변경점만) · 구성요약 · 사용자역할 · 권한체계 요건 · 연동 IT 시스템 · 커스터마이징 요구사항 · 개발내역 · 조직측면 · 데이터량

Fiori의 설계 철학 — 왜 앱을 쪼갰나

Fiori는 디자인 언어입니다. PCE 내 앱 간 이동하거나 Cloud ALM 같은 다른 시스템으로 이동해도 일관된 사용자 경험과 동일한 룩앤필을 제공하는 것이 목표입니다. 핵심 원칙 5가지 — 역할기반 · 적응형 · 단순함 · 일관성 · 만족도.

배경은 인력 구조의 변화입니다. 과거에는 한 회사에 20~30년 근속하며 한 번 배운 도구를 계속 썼지만, 오늘날은 이직 · 직무변경이 빈번해 소프트웨어가 직관적이고 빠르게 배울 수 있어야 합니다.

대표 예시가 MIGO입니다. 하나의 앱에 너무 많은 기능이 들어 있어 복잡한데, 이를 개별 작업에 특화된 Fiori 앱으로 분리했습니다(입고 게시, 반품 처리 등). 기존 숙련 사용자는 web GUI로 원래 앱을 계속 쓰고, 신규 직원은 자기 업무에 맞는 개별 Fiori 앱만 씁니다.

비활성 템플릿을 그냥 두지 않는다

Embedded Analytics — HANA → CDS(VDM) → Fiori

S/4HANA Cloud의 분석은 비즈니스 데이터와 같은 소프트웨어 스택 안에 내장돼 있고, SAP Analytics Cloud(SAC)가 실시간 연결로 여러 분석 앱을 구동합니다. 3층 구조로 이해합니다.

  • 최하단 — 비즈니스 데이터가 있는 SAP HANA 데이터베이스
  • 중간층 — Virtual Data Model(VDM), Core Data Services(CDS) 뷰로 구현
  • 최상단 — 사용자가 데이터를 소비하는 Fiori 분석 앱

CDS가 왜 필요했는가에 대한 답이 원문에 나옵니다 — 여러 SAP 클라우드 솔루션이 각자 다른 데이터 구조 · 언어를 가진 독립 회사에서 인수된 경우가 많아, 서드파티 데이터까지 통합 분석할 공통 언어가 필요했습니다.

확장성이란 무엇까지 포함하는가

UI 적응(Adapt UI)

변경 후 "마법지팡이" 아이콘으로 새 버전을 활성화하고, "트럭" 아이콘으로 전송로그에 게시해 Extensibility Inventory에 반영합니다.

Custom Fields

Custom Fields 앱으로 만든 필드는 관련 앱 · 리포트 · 이메일/폼 템플릿 · API에서 공통 사용됩니다. 저장 후 Publish가 필요하며 최대 30분 소요됩니다.

커스텀 필드에 개인정보를 담지 않는다

커스텀 필드는 읽기액세스로깅(Read Access Logging)이 제공되지 않고, 개인정보보호(DP&P) 관련 차단 · 삭제 대상으로 지정할 수 없습니다. 개인정보성 데이터를 커스텀 필드에 넣으면 나중에 규제 대응이 불가능해집니다.

Custom Logic (BAdI)

Custom Logic 앱에서 릴리즈된 BAdI를 선택해 로직을 추가합니다. 코드는 ABAP으로 생성되며 View Documentation 링크로 변경 가능 범위를 확인합니다. 생성 · 게시 후 Code Editor에서 코드를 볼 수는 있지만, 지원되지 않는 변경은 저장 · 게시가 막혀 있어 개발 지식 없이도 안전하게 쓸 수 있습니다.

ABAP Cloud에서 지켜야 할 것

· 릴리즈된 공용 API를 사용한다 — 예: CDS 뷰 I_PRODUCT

이 코스는 Developer Extensibility 자체를 깊게 다루지 않고, SAP Developer Center와 무료 개발자용 Learning Journey를 별도 안내합니다.

Side-by-Side 확장 — 누가 만드는가

별도 플랫폼(SAP BTP)에서 앱 · 확장을 개발한 뒤 대상 S/4HANA Cloud 시스템과 통합하는 방식입니다. 핵심 ERP와 근본적으로 분리된 플랫폼에서 구축되므로 가장 유연하지만, 보통 추가 개발 리소스가 필요합니다.

LoB 구성전문가는 직접 개발하지 않는다

In-App으로 해결되지 않는 요구사항은 PM에게 에스컬레이션해야 하며, 다음 4가지 중에서 결정합니다.

(1) 파트너팀 ABAP 개발 인력 투입 — 구 ERP 경험자
(2) 고객사 내부 ABAP 인력 투입 — 내부 업무 이해도가 높다
(3) 파트너팀 Side-by-Side 인력 — SAP Build 또는 BAS
(4) 고객사 내부 Side-by-Side 인력

전환 후 커스텀 코드 분석 — 컨버전 프로젝트의 본편

시스템컨버전 과정에서 커스텀 ABAP 소스코드는 적응이 필요합니다 — S/4HANA에서 많은 SAP 코드가 단순화되거나 비호환적으로 변경돼 일부 커스텀 객체가 더 이상 유효하지 않거나 구문오류를 냅니다. Simplification Database(S/4HANA 단순화 항목과 관련 SAP Note를 담은 테이블)를 기반으로 SAP가 탐지 도구를 제공합니다.

1) 스코핑 — 옮길 것부터 줄인다

커스텀 코드 스코핑은 자주 사용되어 S/4HANA로 이관되어야 할 코드를 식별하는 작업입니다. 사용되지 않는 코드는 삭제 전송요청으로 제거해 마이그레이션할 객체 수와 적응 작업량을 줄입니다.

Custom Code Migration Fiori 앱(ERP 시스템 또는 SAP BTP에서 실행 가능)이 담당합니다 — S/4HANA 호환성 검사 실행, 미사용 코드 식별, 분석결과를 다운로드해 SAP Readiness Check에 업로드.

프로젝트의 CBO 3종을 그림 5의 순서로 다시 검토하면 이렇게 갈립니다.

ZBATCH_ZONE (잔여 유통기한 30% 미달 시 정상→임박 SLoc 311 이동) — 1번(IMG)에서 걸립니다. 표준 배치 상태관리로는 MCHA-VFDAT 기준 만료 임박을 판정할 수는 있어도, 온도군별 정상/임박 SLoc(1100↔1900 · 2100↔2900 · 3100↔3900) 사이로 물리 이동을 자동 생성하지는 않습니다. 2번(Key User)도 BAdI 범위를 넘습니다. 따라서 3번 — Developer Extensibility가 맞는 자리이고, 전기는 직접 INSERT 대신 BAPI(BAPI_GOODSMVT_CREATE)로 갑니다.

ZPRICE_CHECK (EINE-NETPR vs MBEW-VERPR 괴리 알림) — 전기가 없고 읽기와 통보만 하므로, 엄밀히는 Embedded Analytics(CDS 뷰 + 분석 쿼리)로도 성립합니다. 학습 목적상 ABAP 리포트로 먼저 만들되, "이건 원래 CDS로 갈 수 있는 건이었다"는 판단을 문서에 남겨 둘 것.

ZGATE_INSPECT (GR 101 vs STOR 이관 301 차이 → 송장 미발생 건 122 반품) — 재고와 회계 금액에 직접 영향을 주는 전기입니다. 프로젝트 원칙상 자동 전기까지 가지 않고 CBO 테이블의 상태필드(W/P/H)로 승인 대기까지만 갑니다. Tier 관점에서도 이쪽이 맞습니다 — 자동 전기를 넣으면 나중에 로직을 고칠 때마다 회계 검증을 다시 해야 합니다.

공통으로, 세 CBO 모두 개발 클라이언트 / Workbench Request에서 만들어집니다. Key User 확장(Customizing 클라이언트 / ATO)과는 전송 경로 자체가 다르다는 점을 설계서에 명시해 둘 것.

확인 필요 — 이 시스템이 ABAP Cloud를 쓸 수 있는가

ABAP Cloud 언어버전, 릴리즈된 API 목록, ATO 설정 여부는 릴리즈와 시스템 설정에 따라 갈립니다. 실제 시스템(winerp01 / MEP)에서 확인할 것.

· ADT(Eclipse)에서 ABAP 언어버전 선택지에 "ABAP for Cloud Development"가 있는가
· ATC 변형(variant)에 S/4HANA / ABAP Cloud 검사 세트가 있는가
· ATO가 설정돼 있는가 (미설정이면 Key User 확장이 로컬 객체로 남는다)
· I_PRODUCT 같은 릴리즈된 CDS 뷰가 조회되는가

연동이란 무엇이고 무엇을 먼저 하는가

서로 다른 플랫폼의 애플리케이션을 연결해 데이터를 주고받거나 프로세스를 연동하는 것입니다(예: SuccessFactors Employee Central의 직원 정보를 S/4HANA Cloud 사용자로 자동 반영). 여러 API를 묶어 하나의 작업을 달성하는 묶음을 통합패키지(integration package)라고 부릅니다.

DDA의 연동 목록은 시작점일 뿐이다

사전패키지 연동 콘텐츠 — 먼저 찾아본다

제목에 "integration"이 들어간 Signavio Process Navigator의 비즈니스 프로세스에는 설치안내(Set-up instructions)가 포함됩니다.

시스템컨버전은 Solution Builder를 쓸 수 없다

신규구현은 Solution Builder로 활성화 후 설치안내를 따르면 됩니다. 반면 시스템컨버전은 Solution Builder를 사용할 수 없어, 관련 Fiori 앱만 활성화하고 IMG · SPRO로 LoB 구성전문가가 수동으로 프로세스를 구축해야 합니다. 표준과 동일하게 구축했다면 Signavio의 설치안내를 그대로 활용할 수 있습니다.

SAP Help Portal의 PCE → Integration 섹션에서도 추가 콘텐츠를 찾을 수 있습니다.

CIAS (Cloud Integration Automation Service)

SAP BTP에서 실행되는 무료 서비스로, 지원되는 연동이라면 가이드된 워크플로우로 설치 과정을 부분 자동화해줍니다. SAP Cloud ALM 또는 SAP for Me의 Maintenance Planner(Plan for Cloud Integration Scenario 앱)에서 실행합니다.

태스크 유형내용

태스크를 역할별로 분담해 진행상황도 추적할 수 있습니다. 모든 연동이 CIAS를 지원하는 것은 아니며, 구독(무료) 설정이 사전에 필요합니다.

SAP Business Accelerator Hub (구 API Business Hub)

SAP · 파트너 개발자 생태계가 제공하는 공개 콘텐츠 카탈로그입니다. API는 개방형(open API) 포맷으로 문서화되며, 버전관리 · 호환성을 규정하는 폐기정책(deprecation policy)으로 안정성이 보장됩니다.

LoB 컨설턴트의 책임은 "개발"이 아니라 "리소스 식별"이다

Process Navigator와 Help Portal을 철저히 검색해도 적합한 사전패키지 연동이 없다면 커스텀 개발을 고려합니다. 이때 LoB 컨설턴트의 책임은 직접 개발이 아니라 Business Accelerator Hub에서 개발자가 활용할 수 있는 리소스를 식별해주는 것입니다.

이런 연동을 "customer-driven"이라 부르는 이유가 중요합니다 — 고객 측 개발자가 설계 · 구축에 참여해야 향후 유지보수를 직접 담당할 수 있기 때문입니다.

Cloud ALM for Operations — 연동 모니터링

SAP Cloud ALM은 SAP Enterprise Support for cloud editions에 포함되어 모든 앱이 무료입니다. Landscape Management에 등록된 SAP 시스템의 건강 상태를 모니터링하며, External API Management에 구독 등록하면 외부 시스템도 함께 모니터링할 수 있습니다.

주요 기능 — Business Process Monitoring · Integration & Exception Monitoring · User & Performance Monitoring · Job & Automation Monitoring · Configuration & Security Analysis · Health Monitoring · Business Service Management · Intelligent Event Processing.

데이터 마이그레이션 — Migration Cockpit

Migrate Your Data(Fiori Launchpad 앱)로 Migration Cockpit을 엽니다. 추가비용 없는 내장 도구이며 SAP · 비SAP 레거시 시스템 여러 개를 지원합니다(온프레미스 · 프라이빗 · 퍼블릭 클라우드 전반에 동일 앱이 있고 배포형태별로 기능 · 템플릿이 조금 다름).

마이그레이션 객체 템플릿은 필드가 사전 정의되어 있고, 소스 데이터를 S/4HANA 대상 구조에 자동 매핑하며 백엔드 검증과 함께 단계별 안내를 제공합니다.

앱 권한만으로는 마이그레이션이 안 된다

Migrate Your Data 앱 접근권한과 별도로, 마이그레이션할 데이터 유형마다 그에 해당하는 1회성 생성앱의 권한도 필요합니다 — 같은 API · 기술 검증을 쓰기 때문입니다.

예: 은행 1,000개를 마이그레이션하려면 Manage Banks 앱 권한도 있어야 합니다. 각 마이그레이션 객체는 SAP Help Portal에 문서화되어 있고, Post-Processing 섹션에서 검증에 필요한 앱을 확인할 수 있습니다.

상태 추적과 확장성

  • Custom Fields 앱으로 만든 커스텀 필드는 해당 비즈니스 컨텍스트에서 확장을 지원하는 마이그레이션 객체에 자동 추가된다
  • Migration Object Modeler(SAP GUI for HTML 앱) — 소수의 릴리즈된 객체에 한해 소스/대상 구조 · 매핑을 직접 커스텀화. 엑셀 템플릿을 직접 수정하는 것은 파일 손상 문제로 불가 — 반드시 이 도구로 변경

🔰 초보자 설명 — ISA-M과 Migration Cockpit을 한 줄로

ISA-M은 "어떤 시스템과 어떻게 연결할지"를 계획하는 전략 도구이고, Migration Cockpit은 "기존 데이터를 새 시스템에 한번에 옮겨 넣는" 일회성 도구입니다. 하나는 지속적 연동, 다른 하나는 1회성 이전입니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트 목표 3번 "간단한 웹페이지 → RFC 통신으로 SAP 호출"이 정확히 이 LESSON의 주제입니다. 다만 위치가 다릅니다 — Integration Suite는 BTP 위에서 도는 관리형 플랫폼이고, 프로젝트가 만들 것은 RFC Function Module 직접 호출입니다. 개인 프로젝트에 BTP가 없으므로 그쪽이 맞지만, 설계서에는 "표준이라면 Integration Suite / Business Accelerator Hub의 사전 API를 먼저 찾는 것이 순서인데, 학습 목적상 RFC를 직접 만든다"는 판단 근거를 한 줄 남겨 둘 것.

목표 2번 AL11 디렉토리 기반 대량 처리 프로그램은 이 LESSON의 "로컬 스키마 · 파일 100MB 제한 · 기본 동시작업 8개"와 같은 계통의 문제를 다룹니다. 병렬처리 설계에서 동시 실행 개수와 커밋 단위를 얼마로 잡을지를 정할 때, Migration Cockpit이 8개를 기본값으로 두고 조정 가능하게 만든 이유를 참고할 것.

자재마스터(CHKN · RICE · SHAK · PROT · PBAR)와 벤더 · 고객 마스터는 실제 구축이라면 Migration Cockpit의 마이그레이션 객체로 적재됐을 데이터입니다. 개인 프로젝트에서는 수작업으로 만들지만, 배치관리 + 유통기한(MCHA-VFDAT) 항목처럼 뒤 공정(FEFO 배치결정)이 의존하는 필드는 적재 순서를 먼저 정하고 들어가야 합니다.

ALM 플랫폼과의 역할 분담

SAP Solution Manager · SAP Cloud ALM 같은 기존 ALM 플랫폼과는 개방형 인터페이스로 통합됩니다. 두 ALM 플랫폼 모두 테스트 계획 · 준비, 오케스트레이션 · 리포팅, 수동테스트, 탐색적 테스트를 이미 갖추고 있으며, Tricentis는 자동화 실행을 담당해 서로의 강점에 집중합니다.

즉 SAP ALM 플랫폼은 여전히 애플리케이션 라이프사이클 전체의 오케스트레이터로 남고(다른 서드파티 테스트자동화 도구에도 개방된 상태 유지), Tricentis는 이 구조에 통합되는 실행 엔진입니다.

설치는 — 고객의 Cloud ALM에 Tricentis가 아직 설정되지 않았다면 Administration 섹션에 "Set Up Tricentis Test Automation for SAP" 앱이 보입니다. 마법사(wizard) 형태로 단계별 활성화를 안내합니다.

반드시 지킬 것

· SAP 제공 객체를 직접 수정하지 않는다. Business Role 템플릿 · Catalog · Space · Best Practices 프로세스 · 폼 템플릿 · KPI — 전부 복사본을 만들어 쓴다. 원본을 고치면 업그레이드 확장기능을 받지 못하고, 앱 간 네비게이션도 깨진다
· Key User 확장은 만들자마자 로컬 객체다. ATO 설정 → 패키지 등록 → SE09 릴리즈까지 가야 운영기에 간다. 여기서 멈추면 개발기 전용으로 남는다
· Tier 2 래퍼에는 반드시 기한을 붙인다. 해당 API가 릴리즈되면 Tier 1으로 교체 — 기록해 두지 않으면 영구 Tier 3가 된다
· 커스텀 필드에 개인정보를 담지 않는다. Read Access Logging이 없고 DP&P 차단·삭제 대상 지정이 불가능하다
· 개발자가 만든 DB 테이블은 기본 보안이 없다. ILM · IRF를 쓸 수 없으므로 권한 체크를 코드에서 직접 챙긴다
· ATC quick fix를 한꺼번에 적용하지 않는다. 구문오류부터, 그 다음 반복 실행
· Catalog 하나에 앱 100개 이하, Page당 타일 35개 이하. 성능 문제는 설계 시점에 생긴다
· 승인이 필요한 처리와 조회는 역할을 나눈다. 같은 역할에 넣으면 승인 절차가 형식만 남는다
