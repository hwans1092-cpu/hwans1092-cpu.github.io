SAP Fiori의 3가지 차원

SAP Fiori는 데스크톱·태블릿·스마트폰에서 일관되게 동작하는 엔터프라이즈 애플리케이션 디자인 언어입니다. 2013년 SAPPHIRE에서 25개 앱으로 시작해 SAP S/4HANA 1610부터 Fiori 2.0, 현재 타깃 디자인은 SAP Fiori 3입니다.

차원핵심
Design좋은 UX는 생산성·데이터품질 향상, 교육비용·변경요청 감소라는 금전적 가치와 인재유치·만족도라는 인간적 가치를 함께 낸다. SAP UX Value Calculator로 절감효과 산정 가능. 5대 핵심 디자인원칙 → 페이지 플로어플랜 → UI 엘리먼트 순으로 가이드라인 제공. 2016년 iOS, 2018년 Android 지원. 2023년 7월부터 human-centered AI 접근(예측적·능동적·반응적 가이던스)
Principles여러 클라이언트에서 일관·직관적인 통합 UX. 기능기반(Functional-based) UI → 역할기반(Role-based) UI 전환이 클래식 UI 대비 가장 큰 변화
Technology일관성·지능성·통합성·협업성 있는 UX를 뒷받침하는 기술적 진화
🔰 초보자 설명 — 역할기반이 왜 큰 변화인가

클래식 UI는 기능이 중심입니다. VA01 하나에 오더 생성의 모든 경우가 다 들어 있고, 사용자는 자기에게 필요 없는 필드까지 전부 봅니다. 역할기반 UI는 사람이 중심입니다. "출하 담당자가 오늘 처리할 납품"처럼 한 역할의 한 단계만 앱 하나로 잘라 놓고, 앱 여러 개를 이어 붙여 프로세스를 만듭니다. 그래서 Fiori에서는 "이 트랜잭션이 어디 있냐"가 아니라 "이 역할에 이 앱이 배정됐냐"를 묻게 됩니다.

2025년 6월부터 SAP Fiori 디자인 가이드라인은 AI를 포함한 모든 디지털 콘텐츠를 아우르는 SAP Design System 가이드라인으로 확장되었습니다(sap.com/design-system).

SAP Fiori Launchpad (FLP)

FLP는 사용자 역할(Role) 기준으로 분해된 앱들을 한 화면에 모아 여러 솔루션에 걸친 일관된 UX를 제공합니다. 앱 하나는 특정 역할의 개별 단계이고, 앱 여러 개를 조합해 하나의 완전한 프로세스를 구성합니다.

SAP Fiori Horizon은 S/4HANA Cloud 2208부터 제공되며, 버전 번호 대신 디자인 테마명을 씁니다. 재설계된 My Home 페이지는 To Dos(작업/상황) · Pages(스페이스를 열지 않고 페이지 직접 접근) · 자주쓰는 앱/즐겨찾기 · Insights(분석데이터 타일·카드) 4개 섹션이며 전부 개인화 가능합니다.

User Actions Menu의 기능은 역할별로 구성할 수 있습니다 — 개인화 전면 금지부터 런타임 앱 조정까지 범위가 넓습니다. 최근활동·자주쓰는 앱도 비활성화할 수 있고, Notifications 영역은 역할별 활성화 후 SAP Workflow 또는 ABAP notification framework 기반 알림 제공자가 내용을 생성합니다.

개인화 — 설정 · Spaces/Pages · 타일

User Actions Menu의 Settings에서 계정정보·외관·언어·지역에 접근합니다. 구성에 따라 디자인테마 선택, 스페이스↔홈페이지 전환, 사용자프로파일링 활성화, 기본값 유지보수, 알림 외관/동작, 개인화 검색 구성을 바꿀 수 있습니다.

FLP 기본값과 SU3 파라미터는 같은 것이 아니다

FLP 최초 시작 시 백엔드 사용자계정의 SET-/GET-parameter가 기본값으로 복사되는데 이 복사는 딱 1회입니다. ABAP 트랜잭션은 그 뒤로도 계속 SU3/SU01의 SET-/GET-parameter를 씁니다. 그리고 단일값은 복사되지만 범위(range)값은 복사되지 않습니다. SAP Fiori 안에서는 기본값만 쓰는 편이 안전합니다 (SAP Note 2519765).

Spaces와 Pages

S/4HANA 2020부터 Space(FLP 상단 리본/탭, 하나 이상의 Page를 담는 프레임) 개념을 씁니다. Page는 타일을 보여주는 섹션들로 구성되며 과거 Group 방식을 대체합니다. 타일은 시스템의 Catalog에 조직화되고 → Page에 임베드되어 표시되고 → Page는 Space에 할당되어 사용자의 FLP 구조를 정의합니다.

  • Space와 Page는 시스템에서 중앙 정의된다
  • 역할(Role)에 배정할 수 있는 것은 Space뿐이다 — Page는 직접 배정되지 않는다
  • Section은 Page의 필수 구성요소이며 사용자가 직접 생성할 수 있다
📖 참고 — Group은 이제 Deprecated

S/4HANA 2021 FPS01부터 Group 기반 홈페이지 개념은 Deprecated입니다 (SAP Note 3500249). 신규 구성이라면 Space/Page로 갑니다.

My Home 개인화와 타일 종류

My Home은 To-Dos · Pages · Apps · Insights 4개 섹션이고, 각 섹션헤더 옆 화살표에서 My Home Settings로 들어갑니다. Layout에서 섹션 재배치/숨김, Advanced에서 개인화 콘텐츠 내보내기/가져오기가 가능합니다.

Apps 섹션에 앱을 넣는 경로는 둘입니다 — (1) Apps 섹션의 Add Apps → App Finder에서 카탈로그의 앱 선택(기능 검색 위주), (2) Page에서 Edit Current Page → 타일 컨텍스트메뉴의 Add to My Home(프로세스 접근 위주). 즐겨찾기는 App Group으로 묶을 수 있는데, Delete는 그룹과 즐겨찾기를 모두 삭제하고 Remove All Apps는 그룹만 삭제하고 즐겨찾기는 남깁니다.

클래식 UI와의 통합 — 테마는 SAP GUI에도 적용된다

SAP Belize(Deep, Fiori 2.0) · SAP Quartz Light/Dark(Fiori 3) · SAP Fiori Morning/Evening Horizon 테마는 SAPUI5뿐 아니라 SAP GUI 애플리케이션에도 적용됩니다. 색상·폰트만이 아니라 SAVE·BACK 버튼 위치 같은 UI 구조까지 Fiori 규칙에 맞춰 바뀝니다. 그리고 매핑된 ABAP 시스템의 User Menu/SAP Menu에서 트랜잭션을 FLP 타일로 손쉽게 추가할 수 있습니다.

확인 필요 — 테마 · 커널 · GUI 버전 매트릭스

강의 기준으로 Belize는 SAP GUI for HTML(Kernel 7.49+) / GUI for Windows 7.50+(S/4HANA 1610 이상 연결 시), Windows 7.60부터 전 제품, Quartz는 S/4HANA 1909+ / GUI for Windows 7.70+, Horizon은 S/4HANA 2023+ / GUI for Windows 8.10부터입니다. 다만 이 매트릭스는 릴리스마다 갱신되므로 단정하지 말고 SAP Note 710719와 실제 시스템(winerp01 / MEP)의 커널·GUI 버전으로 확정할 것.

SAP Fiori Apps Reference Library

sap.com/fiori-apps-library에서 라인오브비즈니스·산업·사용자역할·기술 기준으로 모든 Fiori 앱을 탐색합니다. 앱 상세를 보려면 먼저 제품군(Product Suite)과 릴리스를 지정해야 합니다 — 같은 앱이라도 제품/릴리스별로 헤더정보·제품기능·구현정보·관련앱이 전부 달라집니다.

⚠️ Hint — App ID 찾는 지름길

트랜잭션의 App ID는 해당 트랜잭션 코드와 동일합니다. VA01을 라이브러리에서 찾으려면 App ID에 VA01을 넣으면 됩니다.

라이브러리에 로그인하면 SAP Fiori App 분석 기능이 추가로 열립니다 — 기존 랜드스케이프 사용현황을 분석해 (1) 업그레이드가 Fiori 앱에 미치는 영향을 파악하고 (2) 앱 추천을 받습니다.

S/4HANA로 옮겨도 시스템 역할 자체는 그대로입니다 — 클라이언트의 FLP는 여전히 SAP Web Dispatcher를 통해 FES(Front-End Server)에 연결됩니다. 달라지는 건 BES(Back-End Server)의 역량으로, S/4HANA에서는 SAP HANA에 최적화된 코드를 갖습니다.

S/4HANA에서는 모든 애플리케이션 유형이 제공되고, Business Suite와의 결정적 차이는 모든 애플리케이션 유형에 아키텍처가 단 하나뿐이라는 점입니다 — 전부 SAP Gateway를 통해 FES를 경유하는 Transactional 앱처럼 동작하고, BES는 곧 S/4HANA 시스템입니다. 클래식 애플리케이션과 일부 Fiori 검색 시나리오만 S/4HANA에 직접 연결됩니다.

Space와 Page 만들기

Manage Launchpad Spaces는 SAP 제공 Space를 전부 보여주고 고객 Space를 만들게 해 줍니다. 여기서 반드시 알아둘 것 — Space 생성/변경에는 커스터마이징 전송요청이 필수입니다. 로컬 커스터마이징이 안 됩니다. 모든 Space는 ID·설명·제목과 최소 1개 Page를 가지고, 고객 Space ID는 Z 또는 Y로 시작하며 "SP" 약어를 넣는 것이 권장됩니다.

Manage Launchpad Pages에는 함정이 하나 있습니다. Page에 앱을 추가하기 전에 그 Space를 먼저 롤에 할당해야 합니다. 그래야 그 롤에서 파생된 비즈니스카탈로그가 Page의 타일 소스로 나타납니다. "…" 버튼으로 모든 비즈니스카탈로그를 수동 선택할 수도 있지만, 그렇게 넣은 타일은 "Out of role context" 경고가 붙고 미리보기에도 안 나옵니다 — 사용자가 FLP에서 실제로 타일을 보려면 그 카탈로그의 소스가 자신에게 할당된 어떤 롤에라도 들어 있어야 합니다.

카탈로그 관리 — 복사는 "참조"다

FLPCM의 Catalog Management에서 카탈로그를 고르고 Copy하면 비즈니스카탈로그가 손쉽게 만들어집니다(커스터마이징/워크벤치 전송요청 필수). 기술카탈로그를 복사원본으로 고르면 비즈니스카탈로그가 생성됩니다. 고객 카탈로그 ID는 Z 또는 Y로 시작해야 합니다.

여기서 가장 중요한 성질 — 복사된 카탈로그는 원본의 타일·Target Mapping에 대한 "참조(Reference)"로 구성됩니다. SAP가 새 버전 카탈로그를 배포하면 모든 참조가 즉시 새 버전을 쓰게 됩니다. 그래서 SAP 제공 카탈로그를 참조하며 커스텀 카탈로그를 정의하는 것이 좋은 출발점입니다 — 업그레이드 때 손으로 따라가지 않아도 됩니다.

📖 참고 — 두 가지 편의

· 신규 카탈로그 제목 앞에 (솔루션)영역을 하이픈으로 구분해 붙이면 FLP의 App Finder에서 동일 영역 카탈로그가 그룹화되어 보입니다.
· S/4HANA 2023부터는 FLPCM에서 PFCG를 열지 않고도 카탈로그를 기존 롤에 직접 배정할 수 있습니다(카탈로그의 롤 사용현황 화면에 버튼 제공).

Intent-Based Navigation

타일의 가장 중요한 정보는 화면에 보이는 제목이 아니라 내비게이션 정보이고, 그 안에 Target Mapping과 연결되는 Intent가 들어 있습니다. Target Mapping은 어떤 앱을 어떤 파라미터·디바이스유형으로 시작할지 정의하며, Intent = Semantic Object + Action으로 식별됩니다.

Semantic Object는 비즈니스 엔티티(고객·판매오더·제품)를 구현으로부터 추상화해 표준화된 방식으로 참조하게 해 주고, 특정 시나리오를 반영하는 애플리케이션들을 하나로 묶어 줍니다.

트랜잭션용도
/UI2/SEMOBJ_SAPSAP 제공 Semantic Object 목록 조회
/UI2/SEMOBJ고객 자체 Semantic Object 정의. 동일 키로 항목을 정의하면 SAP 제공 Semantic Object의 속성을 오버라이드한다

FLPCM의 Add Tiles/Target Mappings로 시스템 전체 카탈로그에서 원하는 앱을 검색해 타일만 / Target Mapping만 / 둘 다를 참조로 생성할 수 있습니다. 여기서 "타일만" 참조하면 타일은 보이는데 실행이 안 되는 상태가 만들어집니다 — 그림 1의 ④가 이 경우입니다.

확인 필요 — 릴리스에 따라 화면이 다르다

FLPCM·FLPAM·Manage Launchpad Spaces/Pages는 SAP_UI 릴리스에 따라 있고 없고가 갈리고, 콘텐츠 모델(TC·BC·PG·SP·BR)의 명명규칙은 S/4HANA 2023 이후 기준입니다. 실제 시스템(winerp01 / MEP)의 SAP_UI 컴포넌트 버전과 S/4HANA 릴리스를 SPAM·시스템 정보에서 확인한 뒤 이 표를 적용할 것.

📌 개인 E2E 프로젝트와의 연결점

프로젝트에서 만드는 CBO 3종(ZBATCH_ZONE · ZPRICE_CHECK · ZGATE_INSPECT)은 ABAP 리포트로 시작합니다. 이걸 나중에 FLP에 올린다면 새 Fiori 앱을 개발할 필요 없이 클래식 애플리케이션(Transactional App)으로 타일을 만들면 됩니다 — 트랜잭션의 App ID는 트랜잭션 코드와 같으므로 ZPRICE_CHECK 트랜잭션을 만들고 Semantic Object를 /UI2/SEMOBJ에 정의한 뒤 Target Mapping을 붙이는 순서입니다. 다만 이건 최종 목표 3가지(IMG · 병렬처리 · RFC 웹페이지)에 들어 있지 않으므로 범위 밖으로 두고, 웹 호출은 계획대로 RFC로 갑니다.

언제 이걸 알아야 하는가

운영에서 매일 받는 문장은 정해져 있습니다. "어제 저녁부터 그 프로그램이 죽습니다", "이 화면이 갑자기 느려요", "저장을 눌렀는데 아무 반응이 없습니다", "전기했다는데 전표가 없습니다". 네 문장이 각각 다른 도구를 가리킵니다.

도구를 아는 것과 순서를 아는 것은 다릅니다. ST22를 열 줄 아는 사람은 많지만, 덤프 단문을 확보하기 전에 코드부터 고치기 시작하면 같은 장애를 세 번 만납니다. 이 LESSON은 그 순서를 고정하는 데 목적이 있습니다 — 증상에서 출발하고, 근거를 먼저 확보하고, 그 다음에 손을 댄다.

왜 미리 봐야 하는지에 대한 강의의 예시가 정확합니다 — DB 파일시스템이 100%로 차면 비동기 업데이트가 실패하고 전체 메커니즘이 비활성화되어 시스템이 행(hang)됩니다. 사후에 보면 "전표가 안 생겨요" 문의 수십 건이지만, 사전에 보면 디스크 사용률 경고 하나입니다.

System Monitoring 애플리케이션은 System/Host/Database Overview 섹션에서 랜드스케이프 총계와 상태를 녹색=정상 · 노랑=경고 · 빨강=오류 · 회색=데이터없음으로 보여줍니다. 좌측 System Hierarchy에서 시스템 → 인스턴스 → DB → DB인스턴스 → OS 계층별 상태를, 우측 Event/Metrics 뷰에서 알림그룹 순으로 개별 메트릭을 확인합니다.

확인 필요 — 보관 기간과 파라미터는 시스템마다 다르다

ST22 28일 보관, SM21 조회 기본 1~2시간, rslg/max_diskspace/local, rstr/* 값은 전부 프로파일 파라미터로 바뀔 수 있는 기본값입니다. 장애 분석 전에 실제 시스템(winerp01 / MEP)에서 RZ11로 현재값을 확인하고, "덤프가 없다"가 덤프가 안 났다는 뜻인지 이미 지워졌다는 뜻인지를 먼저 가릴 것. Solution Manager MAI 구성 여부도 시스템별로 확인이 필요합니다.

· 증상 기술을 정밀하게 다시 쓴다. "안 됩니다"를 "어느 사용자가 · 언제부터 · 어떤 시스템에서 · 어떤 조작에서"로 바꾸는 것이 1단계다. 이 한 줄이 범위의 절반을 지운다.
