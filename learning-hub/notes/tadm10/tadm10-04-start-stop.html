LESSON 1AS ABAP 시작·중지 개념 — 우선순위와 프로파일

Unit 12레슨 2개Understanding the Concept of Start and Stop Procedures · Introducing Different Tools

파일시스템 구조 — 어디에 무엇이 있는가

인스턴스 데이터는 usr/sap 하위에 조직화되고, <SAPSID> 디렉터리가 해당 SAP 시스템 전용 데이터를 담습니다.

디렉터리내용
SYS/global시스템 전체 관련 정보를 중앙 저장 — SSFS-key 등 보안 데이터, 시스템이 생성한 스냅샷
SYS/profile시작에 사용되는 프로파일 — Default Profile · Instance Profile
SYS/exe글로벌 커널 디렉터리. 설치된 인스턴스 커널의 원본(프로그램·라이브러리)

UNIX/Linux는 SYS가 별도 파일시스템 sapmnt에 있고 각 인스턴스 파일시스템에 링크가 걸립니다. Windows는 PAS 인스턴스 파일시스템에 SYS가 있고 sapmnt 공유로 전 인스턴스가 접근합니다. 인스턴스마다 2자리 인스턴스번호 디렉터리 트리를 가지며, 그 안에 work(시작·중지 시 로그·트레이스가 쌓이는 곳)와 로컬 exe(복제된 커널)가 들어갑니다.

🔰 초보자 설명 — 글로벌 exe와 로컬 exe

커널 바이너리의 원본은 한 곳(SYS/exe/<codepage>/<platform>)에 두고, 시작할 때마다 각 인스턴스가 자기 디렉터리로 복사해서 씁니다. 그래야 인스턴스마다 커널 버전이 달라지는 사고가 안 납니다. 이 복사를 하는 프로그램이 sapcpe입니다. 현재 codepage는 uc(Unicode)만 지원하며, HANA 기반 시스템은 Unicode 전용입니다.

시작 우선순위(Priority)

설치 시 인스턴스 유형별로 부여되는 숫자입니다. 숫자가 낮을수록 먼저 시작합니다.

우선순위인스턴스 유형
0.3SAP HANA DB — 우선순위 메커니즘으로 함께 시작 가능
0.5ERS (Enqueue Replication Server) — 고가용성 구성
1Enqueue 있음 · ABAP Dispatcher 없음 = ASCS
2Enqueue 있음 · ABAP Dispatcher 있음 = 구형 Central Instance
3Enqueue 없음 = PAS · AAS (구형 Dialog Instance)
🔰 초보자 설명 — 1과 2는 같이 못 산다

우선순위 1(ASCS)과 2(구형 Central Instance)는 한 시스템에 공존하지 않습니다. 기술 릴리스에 따라 둘 중 하나입니다. 요즘 시스템은 전부 ASCS 구성입니다.

시작 절차 — 무슨 일이 일어나는가

OS 사용자 <sid>adm(Windows는 서비스 사용자 SAPService<SID>)로 수행됩니다.

STEP 1

모든 인스턴스의 sapstartsrv가 가동됩니다. 인스턴스당 1개, SAP 커널에 포함된 프로그램으로 UNIX/Linux는 데몬(sapinit 스크립트가 시작), Windows는 서비스(SAPService<SAPSID>_<instance_number>)입니다. 호스트 재부팅 시 자동 시작이 기본값입니다.

STEP 2

최고 우선순위(보통 ASCS)의 sapstartsrv가 제어권을 갖고, Default Profile의 전역 파라미터 → Instance Profile의 시작(Start) 섹션 순으로 평가합니다.

STEP 3

ASCS가 sapcpe로 커널을 복제한 뒤 Message Server · Enqueue Server를 시작합니다(옵션: RFC Gateway, 통합 Web Dispatcher). DB는 필요 없습니다.

STEP 4

제어권이 우선순위 3(PAS · AAS)으로 넘어갑니다. 우선순위가 같으므로 동시에 진행됩니다. 각 sapstartsrv가 sapcpe 실행 → DB 상태 확인(동일 호스트인데 안 떠 있으면 시작 스크립트 실행) → ABAP Dispatcher 시작(→ 워크프로세스 시작) → IGS watchdog 시작.

Instance Profile의 시작 파라미터는 Start_Program_<number> / Execute_<number> 접두사를 씁니다(sapcpe · DB · ABAP Dispatcher · IGS 등). 그 외 인스턴스 구성 파라미터(워크프로세스 유형·수, 보안, 메모리)도 같은 파일에 들어갑니다. 저장 위치는 UNIX/Linux /usr/sap/<SAPSID>/SYS/profile, Windows \\<SAPGLOBALHOST>\saploc\<SAPSID>\SYS\profile입니다.

두 가지 함정

· 잘못된 파라미터·값은 시스템 또는 개별 인스턴스 시작 실패로 직결됩니다.
· Instance Profile의 시작 관련 항목을 바꾸면 sapstartsrv를 재시작해야 다음 기동에 반영됩니다. 프로파일만 고치고 "왜 안 먹냐"가 여기서 나옵니다.

LESSON 2AS ABAP 시작·중지 실행과 로그·트레이스

Unit 12레슨 2개Starting and Stopping AS ABAP · Log and Trace Information for System Start and Stop

DB를 올리는 것은 SAP Host Agent다

DB는 SAP 시스템에 직접 속한 구성요소가 아닙니다. 그래서 인스턴스 에이전트(sapstartsrv)가 아니라 호스트마다 별도로 설치되는 SAP Host Agent가 담당합니다. SAP MC가 이 에이전트에 붙어 DB를 시작·중지합니다.

포트용도
1128HTTP
1129HTTPS

Hard vs Soft Shutdown

방식동작
Hard Shutdown즉시 강제 종료. 진행 중인 요청을 기다리지 않는다
Soft Shutdown지정한 타임아웃 동안 진행 중인 요청 완료를 기다린 뒤 종료
Hard Shutdown

진행 중인 트랜잭션이 비정상 종료될 수 있습니다. 가능하면 Soft Shutdown을 쓰고 타임아웃을 적절히 잡습니다. SAP MC의 기본 시작 타임아웃은 300초입니다.

SAPControl 명령 — 실제로 치는 것

sapcontrol -nr <nr> -user <sid>adm <pwd> -function StartSystem ALL
sapcontrol -nr <nr> -user <sid>adm <pwd> -function StopSystem LEVEL 3
sapcontrol -nr <nr> -systempki /usr/sap/<SID>/SYS/profile/<profile> -function StartSystem ALL

LEVEL은 우선순위와 대응합니다. StopSystem LEVEL 3이면 PAS/AAS만 내리고 ASCS는 살려 둡니다. 시작할 때는 낮은 레벨(ASCS·메시지 서버)이 먼저, 그다음 높은 레벨이 순차적으로 올라갑니다.

명령줄에 비밀번호를 넣지 않는다

-user <name> <password>는 프로세스 목록과 셸 히스토리에 그대로 남습니다. 일부 기능은 protected web method라 인증이 필요한데, 이때는 System PKI 기반 -systempki 옵션을 써서 계정정보를 노출하지 않습니다.

인스턴스 상태 — 로그를 읽기 전에

상태의미
shutdown종료됨
stop중지됨
initial초기화 중

Passive부하 분산에서 일시 제외(유지보수용). 기존 요청은 계속 처리하지만 신규 요청은 다른 인스턴스로만 간다

로그온이 되면 SM51 또는 SMMS로 상태를 보고 Passive → active 복귀도 여기서 합니다. 로그온이 안 되면 로그·트레이스 파일로 판단해야 합니다.

로그·트레이스 파일 — 어느 파일을 보는가

핵심 위치는 인스턴스별 work 디렉터리(DIR_HOME)입니다. 문제가 나면 날짜·시간 내림차순으로 정렬해 최신 파일부터 봅니다. 모든 로그 유형이 모든 인스턴스에 있는 건 아닙니다 (ASCS와 PAS/AAS 구성이 다름).

스냅샷(Snapshot)

sapstartsrv 웹서비스 기반으로 SAPControl이 만드는 상황 수집 패키지입니다. 백업의 Storage Snapshot과는 전혀 다른 개념입니다. 자동 트리거되면 각 프로세스가 개발자 트레이스 안에 begin / end / <id> / <reason> 메타데이터가 붙은 스냅샷 섹션을 쓰고, 관련 트레이스를 묶은 아카이브를 만듭니다.

자동 트리거(대표 예, 전체 목록은 아님): Hard Shutdown 발생 · 교착 상태(deadlock) 발생 · 리소스 병목 감지 · 요청 처리가 30초 이상 중단 · 워크프로세스 · ICM · RFC 게이트웨이 크래시.

프로세스덤프되는 내용
ABAP 디스패처요청, 세션, 그 요청을 실행한 프로세스
ABAP 워크프로세스C-STACK, ABAP 스택, critical section 상세

수동 생성은 SAP MC 인스턴스 컨텍스트 메뉴 · SAPControl CreateSnapshot · 트랜잭션 SNAPSHOTS 세 가지입니다. 저장 위치는 UNIX/Linux 기준 /usr/sap/<SAPSID>/SYS/global/sapcontrol/snapshots이고, SAP MC의 File → Load Snapshot...으로 불러와 그래픽으로 볼 수 있습니다. 관련 Webmethod는 CreateSnapshot · ReadSnapshot · ListSnapshots · DeleteSnapshots입니다.

🔰 초보자 설명 — 스냅샷은 인스턴스 단위다

스냅샷은 인스턴스마다 자기 sapstartsrv를 쓰므로 항상 인스턴스 단위로 생깁니다. 시스템 전체를 한 번에 뜨려면 시간·이벤트 기반으로 조율하는 스크립트를 고객이 직접 만들어야 합니다. 커널 7.40부터, SNAPSHOTS 트랜잭션은 SAP_BASIS 7.40 SP7부터 제공되며, 제한 파라미터는 service/max_snapshots · rdisp/snapshot입니다. PAS/AAS가 안 올라와 ABAP 스택에 로그온조차 못 하는 상황에서는 SNAPSHOTS 트랜잭션은 도움이 안 됩니다.

SAP BTP의 Support Log Assistant는 지원 파일을 알려진 이슈·권장사항 DB와 대조해 스캔해 주는 셀프서비스 앱입니다. 2019년 가을 정식 공개, 2021년 6월부터 기계번역으로 6개 언어를 지원하며, 업로드한 파일이 SAP로 전송되지 않는다는 점이 보안상 중요합니다.

구조와 순서 — ABAP과 같고, 이름만 다르다

중지는 priorityLEVEL 역순이고 SCS가 항상 마지막입니다. PAS/AAS는 모두 LEVEL 3이라 서로 간 순서는 의미가 없습니다. 프로파일 개수 공식은 활성 프로파일 수 = 인스턴스 수 + 1(default profile 1개)입니다.

🔰 초보자 설명 — JStart

ABAP은 ABAP Dispatcher가 워크프로세스를 띄웁니다. Java는 Java Startup and Control Framework가 그 역할을 하고, 그 중심이 Java Instance Controller = JStart입니다. sapstartsrv → JStart → ICM · Server Process 순으로 내려갑니다. Server Process가 실제로 Java 애플리케이션을 돌립니다.

Soft Shutdown이 ABAP과 다른 점

Soft Shutdown이 걸리면 해당 인스턴스로 신규 로그온이 막히고 메시지 서버의 부하분산 목록에서 빠집니다. 다만 이미 로그온한 사용자의 요청은 계속 그 인스턴스로 전달됩니다. 각 Server Process는 critical 작업이 없으면 "preparing to stop"으로 전환되고, 활성 세션이 없으면 애플리케이션을 중지하고 종료합니다. 세션이 남아 있으면 전부 끝날 때까지 기다리므로, 보통 300초 같은 상한을 두고 그 뒤 Hard Shutdown으로 전환하는 절충안을 씁니다.

ABAP 개발자가 이 Unit에서 실제로 부딪히는 문의는 두 문장입니다.

"배치가 밤에만 느립니다." — 프로그램은 그대로인데 야간에만 늦어집니다. 십중팔구 그 시간대 백그라운드 워크프로세스 개수가 다른 겁니다. 오퍼레이션 모드가 밤에 대화(DIA) → 백그라운드(BTC)로 재분배되지 않았거나, 반대로 내 잡이 몰리는 시간에 BTC가 다 차 있어 큐에서 기다리는 중입니다. 답은 RZ04·SM63과 SM50·SM37에 있습니다.

"rdisp/max_wprun_time 때문에 죽었습니다." — 대화 작업의 런타임 상한을 넘겨 TIME_OUT 덤프가 난 겁니다. 값을 올려 달라고 하기 전에 RZ11에서 현재 값이 얼마이고, 동적 파라미터인지, 그 값이 어느 프로파일에서 왔는지부터 확인해야 합니다. 그리고 대개 옳은 답은 값을 올리는 게 아니라 배치로 돌리는 것입니다 — 백그라운드 작업에는 이 상한이 걸리지 않습니다.

확인 필요

rdisp/max_wprun_time의 기본값·현재값과 동적 변경 가능 여부는 커널 릴리스에 따라 다릅니다. 최신 커널은 스케줄러 계열 파라미터로 대체·보완되기도 합니다. 실제 시스템(winerp01 / MEP)에서 RZ11로 확정한 뒤 문서에 값을 적습니다. 이 노트에는 값을 적지 않습니다.

직접 편집하려면

OS 에디터로 프로파일 파일을 직접 고칠 수도 있지만, 잘못된 파라미터 하나로 인스턴스가 안 올라옵니다. 반드시 변경 전 백업을 만들고, 무엇을 왜 바꿨는지 문서화합니다. 사고가 나면 백업 파일로 기동해 놓고 분석합니다. OS 프로파일 디렉터리에는 .1부터의 이전 버전이 전부 남습니다(구 릴리스는 .BAK 하나뿐이었음).

RZ10 안에서 되는 점검은 세 가지입니다 — Profile → Check(단일 프로파일, 활성화 전에 돌린다) / Utilities → Check all profiles → Of active servers(알 수 없는 파라미터·수식 덮어쓰기 등 일관성) / Profile → Comparisons → Profile in database → With active profile(DB 버전과 OS 활성 버전 비교).

오퍼레이션 모드 — 시간대별로 WP를 갈아 끼운다

낮에는 대화 사용자가 많아 DIA 워크프로세스가 많아야 하고, 밤에는 사용자가 없어 그 메모리·CPU가 놀게 됩니다. 프로파일의 WP 구성은 보통 대화 응답시간에 최적화되어 DIA가 많고 BTC가 적으므로, 야간에는 배치가 리소스를 다 못 씁니다. 이걸 재기동 없이 시간대별로 재분배하는 것이 오퍼레이션 모드입니다.

전환 시 인스턴스도 WP도 재시작하지 않습니다. 그래서 SAP 버퍼 품질이 유지되고, 각 WP는 현재 요청을 끝낸 뒤 다음 가능한 시점에 유형이 바뀝니다. 프로세스 ID는 그대로 유지되어 SM50에서 확인할 수 있고, 유형 변경은 시스템 로그에 이전·새 유형과 함께 기록됩니다.

Reserved WP와 Dynamic WP

구분내용
Reserved
(standby · restricted)		항상 dialog 유형. rdisp/wp_no_restricted로 정의(기본값 0). 시작 시 함께 떠서 리소스를 점유하지만 정상 운영에서는 쓰이지 않는다. 모든 dialog WP가 Hold 상태일 때만 작동해 교착을 푼다. 하나라도 Hold에서 풀리면 다시 예약 상태로 복귀
Dynamic정상 운영 시 존재하지 않는다. ABAP 디스패처가 필요할 때 띄우고, 필요 없어지면 내려 리소스를 반납한다. 유형은 무엇이든 될 수 있고, dialog뿐 아니라 모든 유형이 Hold일 때 떠서 교착을 막는다. 단, 뜨는 데 시간이 걸린다
🔰 초보자 설명 — Hold 상태와 교착

WP가 어떤 자원을 기다리며 Hold로 잡혀 있고, 그 자원을 풀어 줄 작업이 또 WP를 필요로 하는데 남은 WP가 없으면 시스템 전체가 멈춥니다. Reserved / Dynamic WP는 그 상황을 뚫기 위한 여유분입니다. SM50에서 관찰합니다.

Dynamic WP 개수는 직접 지정하지 않고 간접적으로 결정됩니다. 커널 7.42부터 rdisp/wp_max_no의 기본값은 수식입니다.

rdisp/wp_max_no =
  $(RDISP/WP_NO_DIA) + $(RDISP/WP_NO_VB) + $(RDISP/WP_NO_VB2)
+ $(RDISP/WP_NO_ENQ) + $(RDISP/WP_NO_BTC) + $(RDISP/WP_NO_SPO)
+ MAX( $(RDISP/WP_NO_RESTRICTED), 5 )

rdisp/configurable_wp_no =
  MAX( $(RDISP/WP_MAX_NO) - 5 ,
       $(RDISP/WP_NO_DIA) + $(RDISP/WP_NO_VB) + $(RDISP/WP_NO_VB2)
     + $(RDISP/WP_NO_ENQ) + $(RDISP/WP_NO_BTC) + $(RDISP/WP_NO_SPO) )

즉 구성된 WP 합계 + dynamic 5개가 기본입니다. restricted를 잡아 두면 그만큼 dynamic이 줄어듭니다.

손대지 않는 것이 권장되는 파라미터

특별한 이유가 없으면 rdisp/configurable_wp_no · rdisp/wp_no_enq · rdisp/wp_no_restricted · rdisp/wp_max_no는 어느 프로파일에도 설정하지 않습니다. 교착 대비는 rdisp/wp_no_restricted를 건드리는 대신 오퍼레이션 모드에서 dynamic WP를 구성하는 쪽이 권장됩니다.
커널 7.42부터 이 두 파라미터의 기본값이 문자열 DEFAULT에서 수식으로 바뀌었습니다. 7.42 이상에서 DEFAULT를 쓰면 RZ10 프로파일 점검이 오류를 냅니다(숫자 타입을 요구). 값을 DEFAULT로 두지 말고 파라미터 자체를 프로파일에서 제거합니다.
RZ10의 Basic maintenance도 권장되지 않습니다 — 불필요한 파라미터를 프로파일에 잔뜩 써 넣어 구성 불일치 위험을 키웁니다. Extended maintenance를 씁니다.

그래서 실무에서 만지는 축은 사실상 dialog ↔ background 하나입니다.

설정 절차와 모드 종류

SM63 타임테이블에서 24시간 중 각 모드가 유효한 시간대와 전환 시점을 지정한다

모드성격

ABAP에서는 함수모듈 RZL_PERFORM_BA_SWITCH로도 트리거됩니다. 모니터링도 RZ03에서 — 전체 인스턴스·모드 상태, 분배된 WP 개요, Monitoring → Status details로 현재 활성 모드의 WP 구성, Monitoring → Alert Monitor로 RZ20 이동.

전환이 안 되는 대표 원인 — 불일치

WP 개수가 세 군데에 각각 정의됩니다: OS 레벨 instance profile · DB에 저장된 instance profile · 오퍼레이션 모드 정의. 이 셋이 어긋나면 전환이 막힙니다. 프로파일에서 WP 수를 바꿨다면 인스턴스를 재기동하기 전까지는 전환이 되지 않고, 오퍼레이션 모드 정의도 같이 고쳐야 합니다.
또한 수동 전환은 위험합니다 — dialog를 너무 줄이면 운영이 멈춥니다. Simulation을 먼저 돌립니다.

📌 개인 E2E 프로젝트와의 연결점 — 병렬처리 대량 프로그램

목표 2번(AL11 기반 대량 처리 + 병렬처리)이 이 레슨과 직접 걸립니다. 두 가지만 확정하면 됩니다.

① 런타임 상한. 병렬 처리를 CALL FUNCTION ... STARTING NEW TASK(aRFC)로 돌리면 각 태스크는 대화 WP를 씁니다 → rdisp/max_wprun_time에 걸립니다. 반대로 JOB_OPEN/JOB_SUBMIT으로 배치 잡을 쪼개면 백그라운드 WP를 쓰므로 이 상한에서 자유롭습니다. 어느 쪽으로 갈지에 따라 한 태스크가 처리할 파일 분할 크기(커밋 단위)가 결정됩니다. 상한 안에서 끝나도록 분할하는 것이 설계 제약입니다.

② 동시에 쓸 수 있는 WP 개수. 병렬도(parallel degree)를 프로그램에 하드코딩하면 안 됩니다. 서버 그룹(RZ12)을 쓰거나 최소한 셀렉션 화면 파라미터로 빼고, 기본값은 SM50에서 본 실제 가용 WP 수보다 작게 잡습니다. 전부 점유하면 내 배치가 시스템을 멈춥니다 — Reserved·Dynamic WP가 존재하는 이유가 바로 이 상황입니다.

확인 필요: winerp01 / MEP에서 ⓐ RZ11로 rdisp/max_wprun_time 현재값과 동적 여부, ⓑ RSPFPAR로 rdisp/wp_no_dia · rdisp/wp_no_btc, ⓒ RZ04에 오퍼레이션 모드가 정의되어 있는지(개인 학습 서버는 없을 가능성이 큼)를 확인한 뒤 인터페이스 설계서에 값을 적습니다.

ABAP Task Manager — STC01 · STC02

구성 작업을 사전 정의된 task list로 자동화하는 도구입니다(정식 명칭: ABAP task manager for lifecycle management automation). 최신 AS ABAP 시스템에 900개 이상의 task list step이 들어 있습니다.

T-Code용도
STC01task list 생성·편집·복사·삭제, variant 생성, 실행(대화형 또는 백그라운드 잡)
STC02Task list run monitor — 실행된 run의 로그 표시(Task List Run → Display Log)

대표 사용 사례는 ABAP Initial Setup(로그온 그룹, TMS 구성, 보안 설정, 라이선스), Security Checks(SSL·기본 구성 스모크 테스트), SAP Fiori Setup(Gateway 기본 구성, Launchpad OData·HTTP 서비스 활성화), Embedded Search, ABAP Post-Copy Automation(SAP LaMa/LVM enterprise 라이선스 필요)입니다. SAP_BASIS 7.00 SP14부터 사용 가능하며 요구사항은 SAP Note 1589145입니다.

직접 만든 task list는 리포지토리의 개발 오브젝트입니다 — 고객 네임스페이스에 만들고, 패키지를 지정하고, 트랜스포트 요청에 담아야 다른 시스템으로 갑니다(로컬 오브젝트로 저장하면 이관 불가). run이 오류로 멈추면 실패한 task의 Status 열에서 로그를 보고, 고친 뒤 재개하거나 해당 task를 선택 해제해서 건너뜁니다(그 구성 단계는 수행되지 않습니다).

용어 충돌 — "Instance Profile"이 두 가지다

하나는 OS 상의 프로파일 파일(<SID>_<instance name>_<host>), 다른 하나는 Config Tool에서 인스턴스를 선택하면 보이는 AS Java의 동적 구성 파라미터 모음(Instance Profile 탭)입니다. 이름도 다르게 붙습니다. 대화에서 어느 쪽인지 먼저 확인해야 합니다.

JVM 메모리 — young · tenured · Metaspace

서버 프로세스는 멀티스레드로 요청을 동시 처리하며, 한 인스턴스 안의 서버 프로세스들은 동질적입니다 — 같은 구성 템플릿·같은 컴포넌트 상태를 공유하고, 한 곳에서 컴포넌트 시작이 실패하면 동질성 보장을 위해 모든 서버 프로세스에서 그 컴포넌트가 중지됩니다. 인스턴스 내 VM들은 세션 저장소로 쓰이는 공유 메모리에 접근하며, 이것이 VM 장애 시 안전장치가 됩니다.

영역저장되는 것
young generation애플리케이션이 새로 만든 객체
tenured generation오래 살아남은 객체가 자동으로 승격되어 옮겨온다
Metaspace클래스·메서드처럼 VM이 영구적으로 필요로 하는 것

generation은 시작 시 OS로부터 최대 크기만큼을 확보해 두고 내부적으로 initial → max까지 단계적으로 씁니다. Metaspace는 반대로 최소한만 받고 필요할 때 더 받았다가 다시 줄일 수 있습니다. 기본 -XX:MetaspaceSize는 미지정이며 기본값 21MB가 쓰입니다.

tenured의 초기·최대 크기는 직접 지정할 수 없고 young 파라미터와 -Xmx·-Xms에서 계산됩니다. 시작 중 "perm gen low on memory"가 보이는 것은 Metaspace GC가 애플리케이션과 병렬로 도는 것이라 성능 문제가 아니며, 줄이고 싶으면 -XX:MetaspaceSize를 256m으로 둡니다(구 JVM의 perm generation은 Metaspace로 대체 — SAP Note 2121243).

Config Tool 작업 시

· JVM 설정은 Config Tool로만 유지보수됩니다. 템플릿 레벨에서 만지려면 View → Expert Mode가 필요합니다(런타임 필터도 동일).
· 변경은 File → Apply Changes로 저장하고 시스템 재시작해야 적용됩니다. 저장 전이면 "Connect to DB"로 되돌릴 수 있지만, 저장한 뒤에는 이전 설정을 복원할 수 없습니다. 미리 File → Backup Custom Data로 zip 내보내기를 해 둡니다.
· 서버 프로세스 수는 수식으로도 넣을 수 있는데, 계산 결과가 정수가 아니면 시스템이 시작되지 않습니다. 입력 필드 옆에 정수가 표시되는지 확인합니다(N/A가 보이면 안 됩니다).
· NWA의 Configuration Wizard는 초기 구성 전용입니다. 이미 설정을 바꾼 시스템에서 돌리면 기존 설정을 덮어씁니다.

재시작 후 값이 실제로 먹었는지는 인스턴스 work 디렉터리의 dev_server<n>에서 F SAP JVM arguments: 줄 아래 나열된 파라미터로 확인합니다. NWA 쪽에서는 Configuration → Infrastructure → Java System Properties(퀵링크 /nwa/sys-config)에서 현재 유효값과 Changeable 열(온라인 변경 가능 여부)을 보고, 서버 프로세스 수는 Set Node Count로 바꿉니다. 그중 하나를 디버그용으로 할당하면 시작 시에는 뜨지 않고 부하분산에서도 빠지므로, 일반 사용자는 브레이크포인트 지연을 겪지 않습니다.

반드시 지킬 것

· startsap / stopsap은 쓰지 않는다 — deprecated(SAP Note 1763593). SAP MC 또는 SAPControl.
· SAPControl 명령줄에 비밀번호를 직접 넣지 않는다. 프로세스 목록과 셸 히스토리에 남는다 → -systempki.
· 트레이스 레벨(rdisp/TRACE)은 올렸으면 반드시 내린다. 1을 넘는 값은 분석 중에만.
· 프로파일 파일을 OS에서 직접 고칠 때는 백업 먼저. 파라미터 하나로 인스턴스가 안 올라온다.
· rdisp/wp_max_no · rdisp/configurable_wp_no · rdisp/wp_no_restricted · rdisp/wp_no_enq는 프로파일에 쓰지 않는다. 커널 7.42+ 에서 DEFAULT 문자열은 RZ10 점검 오류가 된다 — 값을 고치지 말고 파라미터를 제거한다.
· 오퍼레이션 모드 수동 전환(RZ03)은 Simulation 먼저. dialog를 줄여 놓고 운영을 세우지 않는다.
· 병렬처리 프로그램에 병렬도를 하드코딩하지 않는다. 서버 그룹 또는 셀렉션 파라미터로 빼고, 가용 WP를 전부 점유하지 않는다.
· 직접 만든 task list(STC01)는 고객 네임스페이스 + 패키지 + 트랜스포트. 로컬 오브젝트로 만들면 이관이 안 된다.
