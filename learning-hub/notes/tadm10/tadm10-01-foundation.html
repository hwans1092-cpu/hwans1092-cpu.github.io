시스템 아키텍처 — 어디에 무엇이 있는가

SAP GUI for Java는 AS Java용이 아니다

이름 때문에 늘 헷갈립니다. SAP GUI 세 변형은 전부 AS ABAP 기반 시스템 전용이고, "for Java"는 단지 구현 기술이 Java라는 뜻입니다. AS Java 기반 애플리케이션은 웹브라우저로만 접근합니다.

Row Storage vs Column Storage

전통 RDBMS는 OLTP에 최적화된 행(Row) 저장을 씁니다. HANA는 행/열 저장을 모두 지원하는 단일 DB이고, OLAP에는 열(Column) 저장이 유리합니다.

  • 열 테이블 — 필요한 컬럼만 메모리에 로드, 값이 연속 배치되어 CPU 스캔 효율적, 별도 인덱스 불필요, 병렬처리 최적화. 단점은 트랜잭션 처리 시 레코드 재구성 비용
  • 행 테이블 — 레코드의 전 컬럼을 한 번에 읽음. 갱신·복사·삭제에 유리
  • 하나의 테이블이 행/열을 동시에 가질 수는 없다 — 용도에 따라 택일

🔰 초보자 설명 — 클라이언트(Client)가 뭔가

SAP의 클라이언트는 "접속 프로그램"이 아니라 시스템 안의 독립된 회사 단위입니다. 한 SAP 시스템에 클라이언트를 여러 개 두고 회사를 병행 운영할 수 있고, 어떤 클라이언트로 로그온했느냐에 따라 보이는 비즈니스 데이터가 달라집니다. 테이블의 첫 필드 MANDT가 바로 이 값입니다.

📌 개인 E2E 프로젝트와의 연결점

프로젝트의 회사코드 CL04는 FI의 법적 실체 단위이지, 여기서 말하는 클라이언트가 아닙니다. 클라이언트는 그보다 한 단계 위 — CL04를 포함한 커스터마이징·마스터데이터 전체가 담기는 그릇입니다. CBO 테이블을 MANDT + 업무키로 잡기로 한 설계 원칙이 그대로 이 구조에서 나옵니다. 클라이언트 필드를 빼면 다른 클라이언트의 데이터가 섞여 보입니다.

언제 이걸 알아야 하는가

ABAP 개발자가 이 유닛을 꺼내야 하는 순간은 대개 셋입니다.

1

"프로그램이 타임아웃으로 죽습니다." — TIME_OUT 덤프. dialog 워크프로세스에는 런타임 제한(rdisp/max_wprun_time)이 걸려 있고, 백그라운드 워크프로세스에는 없습니다. 답은 "코드를 더 최적화하라"가 아니라 어느 워크프로세스에서 돌려야 하는가입니다.

2

"저장은 됐다는데 테이블에 없습니다." — CALL FUNCTION ... IN UPDATE TASK로 쌓아둔 요청이 COMMIT WORK 뒤 update 워크프로세스에서 비동기로 처리되기 때문입니다. 실패했으면 SM13에 defective로 남아 있습니다.

3

"이 문서가 다른 사용자에 의해 잠겼습니다." — DB 락이 아니라 SAP 자체 엔큐 락입니다. SM12/SMENQ에서 보이고, 지우는 조건이 따로 있습니다.

인스턴스와 구성요소

인스턴스(= 애플리케이션 서버)는 하나 이상의 서비스를 묶은 관리 단위입니다. 공통 인스턴스 프로파일로 파라미터를 받고, 자체 RAM 버퍼를 가지며, 3자리 SID + 2자리 인스턴스 번호로 식별합니다. SAP 시스템당 DB는 보통 1개이고 DB SID는 SAP SID와 같습니다.

디스패처가 관리하는 워크프로세스 유형은 dialog · background · update · spool 네 가지이고, 개수는 프로파일 파라미터로 구성합니다. 워크프로세스가 아닌 부가 서비스가 따로 있습니다.

서비스역할개수
ABAP Message Server (MS)분산 디스패처 간 통신. 업데이트 시작·락 요청/해제·백그라운드 트리거 등 내부 통신의 중앙 채널. SAP GUI 로그온 부하분산도 담당시스템당 1
Enqueue Server (ES)ABAP 런타임의 논리적 DB 락(lock table) 관리시스템당 1
RFC Gateway (GW)SAP 시스템 간 · 외부 애플리케이션과의 통신디스패처당 1
Internet Communication Manager (ICM)HTTP · HTTPS · SMTP 등 웹 프로토콜 통신디스패처당 1

메시지 서버가 로그온 그룹으로 부하분산을 하면, SAP GUI는 그 이후 디스패처와 직접 통신하고 로그오프할 때까지 그 애플리케이션 서버에 머무릅니다. 지금 어느 서버에 붙어 있는지는 System → Status...로 확인합니다.

구성요소AS ABAP 경로AS Java 경로
PAS (Primary Application Server)/usr/sap/<SID>/D<nr>/usr/sap/<SID>/J<nr>
Central Services Instance/usr/sap/<SID>/ASCS<nr>/usr/sap/<SID>/SCS<nr>
AAS (Additional Application Server)/usr/sap/<SID>/D<nr>/usr/sap/<SID>/J<nr>

PAS는 처음 설치된 애플리케이션 서버입니다(ASCS가 없으면 enqueue 워크프로세스와 message server도 여기 포함). ASCS는 dialog 로그온이 불가능하고 "애플리케이션 서버"라 부르지 않습니다. PAS와 DB(및 ASCS)가 같은 호스트에 있으면 central system입니다. AS ABAP 7.10부터 central instance → PAS, dialog instance → AAS로 명칭이 바뀌었습니다.

요청 처리 — 내 ABAP 프로그램은 어디서 도는가

디스패처가 고른 dialog 워크프로세스는 사용자 컨텍스트를 roll-in(현재 프로그램 처리상태·사용자 특성 데이터를 인식) → 요청 처리(DB 또는 버퍼 조회) → 결과 반환 후 roll-out → 다음 요청 대기, 순서로 돕니다. 사용자와 워크프로세스가 고정 할당되지 않는다는 점이 핵심입니다 — dialog step마다 다른 워크프로세스가 내 프로그램을 이어받을 수 있습니다.

화면(dynpro = 화면 이미지 + 흐름로직)의 흐름로직은 PBO(Process Before Output, 화면 전송 전)와 PAI(Process After Input, 입력 후)로 나뉘고, dynpro processor가 흐름로직을, ABAP interpreter가 처리로직을 실행합니다.

🔰 초보자 설명 — ABAP SQL과 DB 독립성

ABAP SQL(AS ABAP 7.52까지의 명칭은 Open SQL)은 RDBMS 종류와 무관하게 쓰는 SAP 고유 쿼리 언어이고, DB 인터페이스가 이걸 해당 DB의 Native SQL로 번역해 줍니다. EXEC SQL. ... ENDEXEC.로 Native SQL을 직접 보낼 수도 있지만 그 순간 DB 독립성과 테이블 버퍼를 포기하게 됩니다. 다만 S/4HANA는 HANA 전용이라 DB 독립성이 더 이상 필요 없어져, ABAP 연산 대신 DB 프로시저를 호출하는 방향으로 옮겨가는 중입니다.

Atomic (원자성)완전히 성공하거나 전혀 효과가 없어야 한다 — 부분 결과 저장 금지
Consistent (일관성)비즈니스적으로 정확·일관된 상태에서 다른 정확·일관된 상태로만 전환
Isolated (고립성)트랜잭션 내 변경은 Commit 후에만 다른 트랜잭션에 보인다
Durable (지속성)확정 후 결과는 DB에 영구 저장된다

워크프로세스는 런타임 동안 특정 DB 통신 파트너에 고정 연결되므로, 하나의 DB 트랜잭션 안에서만 DB를 변경할 수 있습니다. 반면 SAP 트랜잭션(SAP LUW)은 여러 dialog step으로 구성된 논리적 업무 단위입니다. 이 둘의 길이가 다르다는 것이 락 관리와 업데이트 처리가 존재하는 이유 전부입니다.

락 관리 — 왜 DB 락으로는 부족한가

DB 트랜잭션은 dialog step 단위로 끊기는데 SAP 트랜잭션은 여러 step에 걸칩니다. 그래서 SAP는 자체 락 관리(enqueue)를 씁니다. 락 테이블은 enqueue 프로세스가 있는 애플리케이션 서버의 메인 메모리에 있습니다.

락 모드설명
Write (Exclusive)한 사용자만 편집. 다른 write/read 요청 거부. 동일 락 소유자는 재설정(cumulate) 가능
Read (Shared)여러 사용자 동시 읽기 가능. 추가 read는 허용, write는 거부
Enhanced write (Exclusive noncumulative)동일 트랜잭션이라도 한 번만 요청 가능. 이후 모든 락 요청 거부
Optimistic처음엔 read처럼 동작하다 저장 시 write로 전환. 다른 non-optimistic 락이 있으면 실패하고, 다른 optimistic 락은 그 과정에서 삭제됨
확인 필요 — 락 조회 트랜잭션이 릴리스로 갈린다

SAP_BASIS 7.52 이하는 SM12, 7.53 이상은 SMENQ이고, 7.55 이상부터는 SM12가 곧 새 SMENQ입니다. 실제 시스템(winerp01 / MEP)의 SAP_BASIS 릴리스를 System → Status...에서 확인한 뒤 어느 쪽을 쓸지 확정할 것.

락을 지우는 방법은 둘인데, 쓰는 조건이 다릅니다.

  • SM04에서 사용자 세션 종료 — 원 소유자가 트랜잭션을 벗어나며 자기 락을 전부 해제합니다. 지우기 전에 그 사용자가 아직 로그온 중인지 반드시 확인
  • SM12/SMENQ에서 수동 삭제 — 소유자가 이미 로그오프했는데 락만 남은 경우에만. 예: 프론트엔드가 죽어서 연결이 끊긴 경우

업데이트 처리 — COMMIT WORK 시점에 벌어지는 일

스풀 · 백그라운드 · RFC

  • Spool — spool 워크프로세스는 dialog/background가 만들어 놓은 spool 요청을 처리할 뿐, 스스로 요청을 만들지 않습니다. local access method가 인쇄 성능에 유리. 조회 SP02, 개인 설정 SU3
  • Background — 리소스 집약적 프로그램을 오프피크에. dialog 런타임 제한(예: 10분)이 없습니다. 스케줄 SM36, 모니터 SM37, 개인 작업 SMX
  • RFC — RFC/CPIC 통신에는 항상 gateway가 관여합니다. inbound RFC는 gateway가 수신하고, outbound는 워크프로세스가 시작합니다

AS Java 쪽은 무엇이 다른가

개발자 입장에서 대비만 잡고 넘어가면 됩니다. 결정적 차이는 AS Java의 server process는 멀티스레드라 하나의 프로세스가 여러 요청을 병렬 처리한다는 점입니다. AS ABAP 워크프로세스는 한 번에 하나의 요청만 잡습니다.

  • 전체 Java 환경(프로세스 + DB 스키마) = Java cluster, 개별 프로세스(ICM·server) = node
  • 서버 프로세스 = managers(Java Enterprise Runtime = 커널) + services(Java EE Engine Components, 애플리케이션에 API 제공)
  • HTTP 처리 경로: ICM → Java EE handler → cluster manager → HTTP provider service → web container(servlet·JSP, 표현로직) → EJB Container(business logic) → JDBC Connector Service → DB, 그리고 동일 경로로 응답
  • 트랜잭션: ACID는 동일하되 Transaction Service가 JTA/JTS 표준을 구현. Java 트랜잭션은 저장 시 즉시 완료되고 하나의 DB 트랜잭션으로 구성됩니다 — V1/V2 같은 비동기 오프로드가 없습니다
  • 영속성: Open SQL for Java framework(Open SQL/JDBC, Open SQL/SQLJ, EJB, JDO). Native SQL을 쓰면 이식성과 테이블 버퍼를 잃습니다
  • 락: Java EE 표준 DB 락을 쓰되, 응답시간 개선과 DB 플랫폼 간 의미 차이 보완을 위해 enqueue service 개념을 도입
  • 관리 도구: SAP NetWeaver Administrator(/nwa, 권한 NWA_READONLY / NWA_SUPERADMIN), UME(사용자·그룹·역할·비밀번호 정책), Config Tool(오프라인 구성), Java Shell Console Administrator. Visual Administrator는 AS Java 7.10부터 미제공(Deprecated)
  • 7.10 이후 아키텍처 변경: Java Dispatcher가 ICM 프로세스로 대체, SDM 프로세스 제거, Java Central Services Instance에 gateway 포함
📌 개인 E2E 프로젝트와의 연결점 — 병렬처리와 RFC가 여기서 갈린다

프로젝트 목표 2번(병렬처리 + AL11 대량처리 프로그램)과 3번(웹 → RFC 호출)이 정확히 이 그림 위에서 돕니다.

· 병렬처리의 상한은 워크프로세스 개수다. CALL FUNCTION ... STARTING NEW TASK ... DESTINATION IN GROUP으로 태스크를 뿌려도 결국 dialog 워크프로세스를 빌려 쓰는 것이라, 동시에 도는 개수는 SM50에 보이는 DIA 개수를 넘지 못합니다. 전부 점유하면 다른 사용자가 로그온조차 못 합니다 — 여유분을 남기는 것이 설계 조건입니다.

· 병렬 태스크는 dialog WP를 쓰므로 런타임 제한에 걸립니다. AL11 파일 한 덩어리를 통째로 한 태스크에 주면 TIME_OUT입니다. 패킷 크기를 한 태스크가 제한 시간 안에 끝나는 양으로 잘라야 합니다.

· 커밋 단위는 그림 3 그대로입니다. 전표는 직접 INSERT 하지 않고 BAPI로 만들기로 했으므로, BAPI 호출 후 BAPI_TRANSACTION_COMMIT(= COMMIT WORK)이 나가야 update WP가 돌고, 그때까지는 DB에 없습니다. 패킷마다 커밋하고 실패 패킷은 CBO 테이블의 상태필드를 W → H로 남겨 재처리 대상으로 만드는 것이 맞습니다.

· RFC 방향: 웹페이지 → SAP는 inbound RFC라 Gateway가 수신합니다(SMGW에서 확인). 반대로 SAP가 외부를 호출하면 워크프로세스가 직접 나갑니다.

· ZBATCH_ZONE이 정상 → 임박 SLoc으로 311 이동을 걸 때, 같은 배치를 SD 출고가 동시에 잡으면 재고가 어긋납니다. ENQUEUE_EMMARCS 계열 락 오브젝트로 자재/플랜트/SLoc를 먼저 잡고 처리해야 합니다 — 그림 3의 ①이 빠지면 안 되는 이유입니다.

병렬처리 설계 전에 실제 시스템에서 다음을 먼저 확정할 것. 추측으로 패킷 크기를 정하면 무조건 틀립니다.

언제 이걸 알아야 하는가

개발자가 가장 자주 부딪히는 문장이 "이관했는데 운영기에 반영이 안 됐습니다"입니다. 원인은 거의 항상 이 셋 중 하나입니다.

1

Export는 됐는데 Import가 안 됐다. 릴리스하면 Export는 자동이지만 Import는 자동이 아닙니다 — 전송관리자가 TMS에서 트리거해야 합니다.

2

로컬 오브젝트로 만들었다. 패키지를 $TMP로 두면 전송 불가(Local) 요청이라 Export 자체가 일어나지 않습니다.

3

커스터마이징이 클라이언트 종속이라 빠졌다. 프로그램은 Workbench Request로 갔는데 IMG 설정은 Customizing Request에 따로 담겨 있었고, 그건 안 넘어간 경우입니다.

여기에 "어제까지 되던 게 안 됩니다"도 자주 같은 계열입니다 — 비활성(inactive) 버전으로 저장만 하고 활성화(Activate)를 안 했으면 런타임은 여전히 예전 활성 버전을 실행합니다.

데이터 구조 — 클라이언트 종속 vs 크로스클라이언트

구분범위설명
사용자 마스터 레코드클라이언트 종속클라이언트별 사용자 데이터 — 자기 레코드가 있는 클라이언트에만 로그온
마스터 / 트랜잭션 데이터클라이언트 종속클라이언트별 비즈니스 데이터
커스터마이징클라이언트 종속특정 클라이언트에만 적용되는 설정
커스터마이징 (일부)크로스클라이언트모든 클라이언트에 공통 적용 — 예: 공휴일 캘린더, 시스템 변경 옵션
리포지토리 오브젝트크로스클라이언트ABAP Workbench로 다루는 전부 — 테이블, 데이터엘리먼트, 도메인, ABAP 프로그램, 메뉴, 화면

클라이언트는 비즈니스·조직·데이터 측면에서 독립 단위이고, 클라이언트 종속 데이터는 서로 연관되어 있어 커스터마이징 설정과 불일치하면 시스템이 데이터를 거부합니다. 반대로 리포지토리는 클라이언트 독립이라, 한 클라이언트에서 고친 프로그램은 같은 시스템의 모든 클라이언트에서 그대로 바뀝니다. 리포지토리 오브젝트는 패키지(Package)로 묶이고, 각 패키지는 하나의 소프트웨어 컴포넌트에 고유하게 속합니다.

왜 다단계 랜드스케이프인가

  • SAP·고객이 계속 트리거하는 유지보수(코드·커스터마이징 변경)는 사전 테스트가 필요하다
  • 감사(Audit)를 위해 전송요청의 상세 로깅이 필요하다
  • 리포지토리 오브젝트는 클라이언트 간 공유되므로 운영 시스템에서 직접 개발·커스터마이징하는 것은 금지다 — 테스트 클라이언트에서 고쳐도 운영 클라이언트가 같이 바뀐다

전송 절차와 역할

Transport Organizer(SE09)가 변경을 로깅합니다. 리포지토리·클라이언트독립 커스터마이징 변경은 Workbench Request, 클라이언트종속 커스터마이징 변경은 Customizing Request로 가고, 둘을 합쳐 Transport Request라 부릅니다. 번호 형식은 <SID>K9<nnnnn>(예: DEVK900123)입니다.

역할책임
Development Project Leader프로젝트 생성·전송관리 통합 활성화, 최소 개수의 전송요청 생성, 개발자 배정, 요청 최종 릴리스
Developer배정된 전송요청에 대해 개발 시스템에서 개발 수행
Tester품질보증 시스템에서 기술적 승인(Acceptance) 수행
Transport Administrator전송 개념(Concept) 수립, 구조화된 방식으로 Import 수행
역할 분리는 소규모라도 두 군데는 지킨다

소규모 환경에서 4개 역할을 겸할 수는 있지만, 개발자와 테스터가 동일인이면 안 되고, 개발자와 전송관리자도 분리되어야 합니다. 자기가 만든 걸 자기가 승인하고 자기가 운영기에 밀어 넣는 구조는 감사에서 그대로 걸립니다.

요청이 개발자에게 배정되면 Transport Organizer가 각 담당자에게 Task를 자동 생성합니다. 개발자가 릴리스 → 전 개발자 Task 릴리스 완료 → 프로젝트 리더가 요청 릴리스 → 전송 가능(Transportable) 요청은 Export 자동 트리거(로컬 요청은 Export 없음).

ABAP Workbench와 Dictionary

SAP 표준을 바꾸는 길은 두 갈래입니다 — 커스터마이징(SAP Reference IMG, SPRO)이거나 리포지토리 오브젝트 생성/편집이고, 후자는 Modification – Enhancement – Customer Development 순으로 확장 강도가 갈립니다.

개발 대상은 개발 오브젝트(프로그램·트랜잭션·화면)와 패키지(논리적으로 연관된 오브젝트 묶음)로 나뉘고, Object Navigator(SE80)가 통합 진입점입니다.

ABAP Dictionary(SE11)는 단순 문서가 아니라 능동적(active) 사전입니다 — ABAP Interpreter와 Dynpro Processor가 런타임에 빈번하게 참조합니다. 정보는 한 번만 정의되고 시스템 전체에서 항상 유효합니다.

오브젝트설명
테이블 (Table)DB 독립적으로 정의. 활성화 시 동일 구조의 물리 테이블이 DB에 생성됨. 기본키로 각 행을 고유 식별
뷰 (View)하나 이상의 테이블을 논리 조합(보통 정적 조인 조건). Open SQL에서 DB 테이블처럼 사용
락 오브젝트 (Lock Object)여러 사용자의 동일 데이터셋 접근을 조율. 함수모듈(ENQUEUE_/DEQUEUE_)이 생성되어 프로그램에서 호출
도메인 (Domain)기술적으로 유사한 목적의 필드를 그룹화하고 값 범위를 정의
🔰 초보자 설명 — 2단계 도메인 개념

필드 하나는 두 겹으로 정의됩니다. 도메인이 기술적 속성(길이·타입·출력속성·값 제한), 데이터엘리먼트가 의미적 속성(짧은 설명·F1 도움말·필드 레이블)입니다.

이게 왜 이득이냐면 — 도메인 하나가 수많은 필드에 속성을 전파하므로 도메인만 고치면 개별 필드를 일일이 손댈 필요가 없고, 같은 도메인 기반 필드끼리는 값 비교 시 변환이 필요 없습니다. 어떤 정의가 어디에 쓰이는지는 SE11의 Where-Used List로 확인합니다.

CDS Views는 그 다음 단계입니다. Dictionary 뷰는 DB 부하를 줄이고 DB 종류와 무관하게 동일 결과를 보장하려고 일부러 제한적으로 설계됐습니다. 그런데 HANA의 병렬처리와 최적화된 데이터 구조를 살리려면 고비용 연산·집계를 애플리케이션 서버가 아니라 DB에서 직접 하는 편이 유리합니다 — 이것이 code-to-data 패러다임이고, 그래서 DB 위에 직접 메타모델 리포지토리를 올린 것이 SAP CDS입니다.

ABAP 언어와 에디터

모든 문장은 키워드로 시작해 마침표로 끝납니다.

REPORT first_program.
WRITE 'My first ABAP program!'.

주요 키워드: PARAMETERS(선택화면), WRITE(리스트 출력), SELECT(테이블 접근), CALL SCREEN(화면 호출). 언어 특징은 다국어 지원(언어별 텍스트 엘리먼트 분리 저장), 간편한 GUI 개발, 객체지향(ABAP Objects), 플랫폼 독립성(Open SQL + DB 인터페이스), 효율적 데이터 구조 접근입니다.

저장 ≠ 활성화

SE38/SE80에서 저장하면 항상 비활성(inactive) 버전으로 리포지토리에 들어갑니다. 활성화 전까지 런타임은 최신 활성 버전을 실행합니다. "고쳤는데 그대로 돌아요"의 가장 흔한 원인입니다. 활성화해야 시스템 전체에서 쓰이는 활성 버전이 생성됩니다.

에디터는 구문검사, 키워드 대문자 변환, F1 구문도움말을 지원하고 다른 도구(ABAP Dictionary, Screen Painter, Menu Painter)로 더블클릭 Forward Navigation이 됩니다. F8로 Direct processing(테스트 실행), 예제 프로그램 모음은 ABAPDOCU에 있습니다.

ADT — ABAP in Eclipse

Eclipse 기반의 최신 ABAP IDE입니다. Application Lifecycle Management, 서버기반 개발, 완전한 통합, 테스트/트러블슈팅 도구를 Eclipse UI와 결합했고, CDS 엔티티 생성을 지원하며 SAP HANA Studio·SAP UI5 tools·Java와 긴밀히 연동됩니다.

🔰 초보자 설명 — 온라인 개발 모델

Git 같은 체크아웃/체크인이 없습니다. ADT 개발자는 로그온을 유지한 채 작업하고 오브젝트는 백엔드에만 저장됩니다(성능용 소규모 읽기전용 캐시 제외). Eclipse에서 오브젝트를 열면 클라이언트에 enqueue 락이 설정되고 최신 버전을 백엔드에서 가져오며, 활성화/저장은 SAP 시스템에 직접 반영됩니다. 오프라인 개발은 지원하지 않습니다.

  • 프로젝트 유형: Classic Project(온프레미스 시스템) / Cloud Project(SAP BTP ABAP 환경)
  • 다룰 수 있는 오브젝트: ABAP 프로그램, Dictionary 오브젝트(테이블 정의·데이터타입), 화면, Web Dynpro 컴포넌트, 함수그룹/함수모듈, 클래스/인터페이스
  • Eclipse 기반 에디터가 없는 오브젝트는 SAP GUI 기반 도구가 별도 탭에서 열립니다(Package Builder, ABAP Dictionary, 텍스트 엘리먼트 유지보수)
  • 오브젝트 전송은 기존과 동일 — SE09 · STMS
📌 개인 E2E 프로젝트와의 연결점 — CBO 3종을 어떤 요청에 담을 것인가

· 요청 종류가 갈린다. CBO 테이블(ZBATCH_ZONE·ZPRICE_CHECK·ZGATE_INSPECT의 상태 테이블)과 프로그램·함수모듈·락 오브젝트는 전부 리포지토리라 Workbench Request입니다. 반면 저장위치 1100/1900 · 2100/2900 · 3100/3900, 자재그룹 CHKN RICE SHAK PROT PBAR, 이동유형 311/122 관련 IMG 설정은 클라이언트 종속이라 Customizing Request로 따로 갑니다. 둘을 같이 안 넘기면 프로그램만 가고 설정이 없어서 운영기에서 바로 덤프납니다.

· 패키지를 $TMP로 만들지 않는다. 렌탈 서버가 단일 시스템이라 어차피 이관할 곳이 없다고 $TMP로 두면, 그 순간 이 프로젝트는 "운영 이관 불가 구조"의 실물 예시가 됩니다. Z 패키지를 하나 만들고 전송 가능 요청에 담는 것까지 해 둬야 포트폴리오에서 설명할 거리가 생깁니다.

· CBO 테이블 설계가 2단계 도메인 개념 위에 있다. 상태필드(W / P / H)는 도메인에 값 범위(고정값)를 정의해 두는 것이 맞습니다. 프로그램에서 IF lv_status = 'W'로 하드코딩된 문자를 비교하는 대신, 도메인 고정값 + 데이터엘리먼트로 F4와 텍스트까지 같이 얻습니다.

· 락 오브젝트를 SE11에서 먼저 만든다. ZBATCH_ZONE이 자재/플랜트/배치를 잡아야 한다면, 락 오브젝트를 정의하면 ENQUEUE_EZ... / DEQUEUE_EZ... 함수모듈이 자동 생성됩니다. 직접 UPDATE 하기 전에 이걸 호출하는 것이 LESSON 2의 그림 3 ①에 해당합니다.

· CDS는 지금 쓰지 않는다. ZPRICE_CHECK가 EINE-NETPR과 MBEW-VERPR을 비교하는 정도라면 조인 하나로 끝나므로, 학습 목적으로 단순화해 ABAP SQL 조인으로 갑니다. code-to-data가 값을 내는 건 집계 규모가 커질 때입니다.

확인 필요 — 단일 시스템에서 트랜스포트를 어디까지 실습할 수 있나

렌탈 서버가 1개 시스템이면 DEV → QAS → PRD Import는 실행할 수 없습니다. 다만 아래까지는 단일 시스템에서도 확인 가능하니, 실제 시스템에서 어디까지 되는지 먼저 확정할 것.

· SE09 — Workbench / Customizing 요청과 Task 구조, 오브젝트 목록
· SE10 — 요청 릴리스 시 오브젝트 락 해제와 버전 생성 확인
· SE11 → Utilities → Versions — 릴리스 전후 버전 비교
· STMS — 전송 경로(Transport Route)가 구성돼 있는지, 클라이언트가 2개 이상인지
· SCC4 — 클라이언트별 변경 옵션, SE06 — 시스템 변경 옵션(크로스클라이언트)

한 장 요약

질문답
내 ABAP 프로그램은 어디서 도나디스패처가 배분한 dialog(DIA) 또는 background(BTC) 워크프로세스. 사용자와 WP는 고정 할당되지 않는다
왜 타임아웃이 나나dialog WP에만 런타임 제한(rdisp/max_wprun_time)이 있다. BTC에는 없다
워크프로세스 4종dialog · update · background · spool. enqueue는 WP일 수도 ASCS의 일부일 수도 있다
WP가 아닌 서비스Message Server · Enqueue Server · RFC Gateway · ICM
COMMIT WORK 하면 DB에 들어가나아니다. update WP를 트리거할 뿐이고 실제 반영은 비동기다. 실패는 SM13
V1과 V2 차이V1 = 시간 critical(재고·오더), 순차 처리 단일 WP / V2 = 비critical(통계), V1에 종속
왜 DB 락으로 부족한가DB 트랜잭션은 dialog step 단위, SAP LUW는 여러 step에 걸친다. 그래서 enqueue 락이 따로 있다
락은 어떻게 지우나SM04 세션 종료(아직 로그온 중일 때) / SM12·SMENQ 수동 삭제(이미 로그오프했는데 락만 남았을 때)
클라이언트 종속이 아닌 것리포지토리 오브젝트 전부, 공휴일 캘린더, 시스템 변경 옵션
Workbench vs Customizing Request리포지토리·크로스클라이언트 커스터마이징 = Workbench / 클라이언트 종속 커스터마이징 = Customizing
Export와 ImportExport는 릴리스 시 자동, Import는 자동이 아니고 전송관리자가 TMS에서 트리거
저장했는데 안 바뀐다저장은 항상 inactive 버전. 활성화(Activate)해야 런타임이 바뀐다
도메인과 데이터엘리먼트도메인 = 기술적 속성(길이·타입·값범위) / 데이터엘리먼트 = 의미적 속성(설명·F1·레이블)
AS Java가 AS ABAP과 다른 점server process가 멀티스레드, 클라이언트 개념 없음, 브라우저로만 접근, V1/V2 같은 비동기 업데이트 없음
반드시 지킬 것

· 병렬 태스크를 뿌리기 전에 SM50을 먼저 본다. DIA를 전부 점유하면 다른 사용자가 로그온조차 못 한다. 여유분을 남기는 것은 배려가 아니라 설계 조건이다.
· 대량 처리에서 커밋 없이 끝까지 가지 않는다. 패킷 단위로 COMMIT WORK하고, 실패 패킷은 상태필드로 남겨 재처리 대상으로 만든다. 롤백 범위는 마지막 커밋까지다.
· SM12 수동 삭제는 소유자가 로그오프한 뒤에만. 아직 붙어 있는 사용자의 락을 지우면 그 사용자가 저장하는 순간 데이터가 깨진다.
· 갱신 전에 ENQUEUE. 락 오브젝트를 SE11에서 만들고 ENQUEUE_EZ...를 호출한다. DB 락만 믿으면 dialog step 사이에 남이 끼어든다.
· 패키지를 $TMP로 만들지 않는다. 로컬 오브젝트는 Export 자체가 일어나지 않아 영원히 개발기에 남는다.
· 운영기에서 직접 고치지 않는다. 리포지토리는 크로스클라이언트라, 운영기의 테스트 클라이언트에서 고쳐도 운영 클라이언트가 같이 바뀐다.
· 활성화를 확인한다. 저장만 하고 "왜 안 바뀌냐"고 묻지 않는다 — 설계상 안 바뀐다.
