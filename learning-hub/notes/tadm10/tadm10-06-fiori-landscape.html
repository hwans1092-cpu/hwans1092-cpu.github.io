배포 옵션 — 무엇이 어디에 설치되는가

Fiori 랜드스케이프 설계의 첫 갈림길은 SAP Fiori front-end server(FES)를 어디에 두느냐입니다. SAP S/4HANA에는 embedded FES가 권장이고, 여러 시스템을 묶는 SAP Business Suite 시나리오에는 여전히 중앙 hub 옵션이 권장됩니다.

배포 옵션설명
Embedded (S/4HANA 단일)S/4HANA용 embedded FES가 권장 구성. Launchpad · 앱 · 비즈니스 역할 설정을 자동화하는 task list가 제공된다
전용 FES hub (S/4HANA별)특정 사용 사례에서만 선택지가 된다
FES hub (다중 Business Suite)Fiori UI 컴포넌트 · Launchpad 콘텐츠 · Gateway 서버가 중앙 FES에 번들. 전통 UI와 비즈니스 로직은 백엔드에 남는다. 여러 릴리스의 백엔드를 FES 하나에 연결 가능
혼합 (S/4HANA + 기존 Suite)기존 중앙 FES hub를 유지한 채 S/4HANA를 추가. 신규 S/4HANA에는 embedded FES를 두고, 중앙 Launchpad에서 URL 타일로 로컬 Launchpad를 연결한다. 기존 hub 배포에 영향이 없는 것이 장점

여기서 걸리는 지점이 하나 있습니다. FES 2023은 S/4HANA 2023의 일부로만 설치됩니다. 낮은 릴리스에서 FES 컴포넌트만 2023으로 올릴 수 없다는 뜻이고, FES 2023의 UI 기술 혁신을 쓰려면 전체 시스템 업그레이드가 필요합니다.

확인 필요

위 표는 2022년 7월 기준 정리입니다. 개인 프로젝트 서버의 실제 조합(S/4HANA 릴리스 · SAP_UI · SAP_GWFND SP)은 SPRO가 아니라 System → Status → Component Information에서 직접 확인해야 합니다. 노트 값으로 단정하지 않습니다.

제품 버전 관점에서 FES는 신규 기술 컴포넌트가 아니라 "필요한 스택 조합을 정의한 번들"입니다. S/4HANA 2023이면 FES 2023 = SAP Gateway Foundation 7.58 + User Interface Technology 7.58 + UI for Basis Applications 7.58 조합이고, FES의 DB는 SAP HANA · SAP ASE · SAP MaxDB 중 하나여야 합니다(ABAP 백엔드는 SAP HANA 2.0). 상세는 SAP Note 3336823 · 3307222.

🔰 초보자 설명 — Web Dispatcher 용어 주의

SAP Web Dispatcher 문서에서는 FES도 "백엔드(back-end)"라고 부릅니다. Fiori 용어의 백엔드(BES, 비즈니스 로직 시스템)와 다른 말이니, 파라미터를 읽을 때 어느 쪽 용어인지 먼저 구분해야 합니다. 클라이언트↔Web Dispatcher 구간은 HTTPS(SAP Note 908097).

SAP Build Work Zone와 콘텐츠 페더레이션

SAP의 전략 방향은 BTP 위의 중앙 진입점 SAP Build Work Zone, standard edition(구 SAP Launchpad service)입니다. 온프레미스·클라우드를 가리지 않는 UX 통합자 역할이고, 연결된 시스템은 라이프사이클·권한·콘텐츠 구조 면에서 여전히 독립 개체로 남습니다. 통합 방법은 두 가지입니다.

수동

SAPUI5 · Web Dynpro ABAP · SAP GUI for HTML 템플릿으로 앱을 개별 통합. 웹 애플리케이션은 동적 URL 런처로도 가능하고, iFrame 인플레이스 또는 새 탭 실행을 고를 수 있다

페더레이션

SAP 제품이 콘텐츠 제공자가 되어 역할·앱·메타데이터를 노출. 교환 포맷은 Common Data Model(CDM)이며, 각 제공자 시스템이 CDM에 맞춰 자기 콘텐츠를 노출할 책임을 진다

배포 위치에 따라 OData 경로도 갈립니다. 온프레미스면 UI 컴포넌트가 FES(hub 또는 embedded)에 설치되고 FES의 Gateway가 백엔드 OData 구현을 호출합니다. BTP에 배포하면 UI는 BTP에, 연결은 SAP Cloud Connector로 가고 OData 처리는 동일합니다. Business Suite 백엔드라면 경량 대안으로 BTP의 OData Provisioning service가 있지만 완전한 Gateway Server보다 범위가 제한적입니다.

Fiori 앱과의 접점이 여기 있습니다. Fiori 앱은 프론트엔드 · 백엔드 · (해당 시) HANA 컴포넌트를 각각 별도 제품으로 요구하는데, SAP Fiori apps reference library에서 앱을 고르면 Maintenance Planner로 바로 넘어가 필요한 패키지를 한 트랜잭션으로 내려받을 수 있습니다. 라이브러리의 Relevance and Readiness Analysis는 "내 프로세스에 관련 있는 앱"(Relevance)과 "지금 쓸 수 있는가"(Readiness)를 나눠 보여 줍니다 — 이미 설치된 앱, 업데이트·DB 마이그레이션이 필요한 앱, 필요한 설치 사항까지.

Fiori 검색은 SAP Enterprise Search on HANA를 쓰며, HANA를 기반으로 트랜잭션 테이블에 직접 접근합니다. 주의할 전제가 하나 있습니다 — Object Page 앱은 동작 자체에 검색 모델이 필요하지 않지만, 검색에서 앱을 시작하려면 기저 검색 커넥터가 활성화되어 있어야 합니다. 즉 Fiori 검색 설정은 Object Page 사용의 전제조건입니다.

Single Sign-On — 초기 인증 한 번, 백엔드는 신뢰 RFC

Fiori 인증 개념은 두 토막입니다.

1

초기 인증 — 앱 실행 요청이 Launchpad에서 ABAP front-end server로 가고, FES가 지원 메커니즘 중 하나로 사용자를 인증한다. 이후 클라이언트↔FES 사이에 보안 세션이 수립된다

2

백엔드 요청 인증 — 보안 세션이 선 뒤 트랜잭션 앱의 OData 요청은 FES를 거쳐 BES로 간다. 이 구간은 신뢰(trusted) RFC로 전달되며 추가 인증이 필요 없다

예외가 검색입니다. Launchpad 검색은 클라이언트에서 HANA로 InA 검색 요청을 직접 보내며, 이건 Kerberos/SPNego · X.509 클라이언트 인증서 · 로그온 티켓으로 인증합니다.

메커니즘쓸 곳과 제약
User ID / Password구성 복잡도가 낮고 기본 보호는 되지만, 시스템이 많아지면 반복 로그온 부담이 그대로 사용자에게 간다
X.509 Client CertificatesPKI가 있으면 백엔드(ABAP · HANA)를 인증서 수락으로 구성. 로그온 시 발급 시스템 접근이 필요 없어 인터넷 노출 시나리오에 적합. SAP GUI 로그온에도 지원돼 SSO 설정이 단순해진다. 모바일은 MDM으로 중앙 배포
Kerberos / SPNego사내망 접근에 적합. Active Directory 등 인프라가 이미 있으면 Windows 로그온 자격 증명을 재사용한다. 로그온 시 발급 시스템 접근이 필요해 대부분의 인터넷 노출 시나리오에는 못 쓴다 — 외부는 VPN이 필요할 수 있다
SAML 2.0페더레이션 기능이 풍부해 federated user domain · 다중 사용자 도메인에 적합(사용자명·이메일 속성 기반 매핑). 대신 신뢰 구성이 복잡하고, 인터넷 노출 시 IdP가 사외에서도 안전하게 접근 가능해야 한다
SAP Logon TicketsFES가 발급하거나 기존 포털이 발급. 백엔드도 수락하도록 구성해야 하며 ABAP 사용자명과 HANA DB 사용자명이 동일해야 하고 매핑을 지원하지 않는다. 쿠키로 전달되므로 모든 시스템이 같은 DNS 도메인에 있어야 쓸 수 있다

X.509 — Web Dispatcher가 끼어 있을 때

Web Dispatcher는 보통 SSL을 종료(terminate)한 뒤 재암호화해 AS ABAP으로 보냅니다. 그래서 AS ABAP이 보는 SSL 연결은 "Web Dispatcher의 인증서로 시작된 연결"이지 브라우저의 것이 아닙니다. 원본 클라이언트 인증서는 HTTP 헤더(기본값 SSL_CLIENT_CERT)에 실려 전달되어야 합니다.

그렇다고 AS ABAP이 헤더의 인증서를 그냥 믿으면 탈취한 인증서를 그대로 쓸 수 있게 됩니다. 그래서 신뢰할 수 있는 중개자가 전달한 것만 수락합니다. 구성은 세 부분입니다.

1

클라이언트(브라우저)가 자기 인증서를 보낸다

2

SAP Web Dispatcher가 클라이언트 인증서를 수락하고 전달한다

3

AS ABAP이 전달된 인증서를 수락한다 — 프로파일 파라미터 icm/trusted_reverse_proxy_<n>에 SUBJECT · ISSUER를 지정해 신뢰할 프록시를 등록 (다수 프록시는 SAP Note 2052899)

콘텐츠 모델 — 카탈로그 · 그룹 · 스페이스 · 페이지

먼저 종속 관계 세 줄입니다. UI 엔티티가 사용자에게 보이는 앱을 정의하고, OData 서비스가 표시할 동적 데이터를 조회하며, 앱을 시작·사용하는 데 필요한 권한은 OData 서비스로 정의됩니다. 권한이 UI가 아니라 서비스에 걸린다는 점이 핵심입니다.

엔티티역할

Group진입 페이지 자체를 정의. 그룹 안의 앱은 카탈로그에 할당된 앱의 부분집합이다. 그룹에 있어도 카탈로그로 권한이 없으면 타일이 안 보인다

Cache Buster — 업그레이드 후 "화면이 옛날 것"일 때

브라우저는 JS · CSS · 이미지를 캐시합니다. 업그레이드로 서버 리소스가 바뀌었는데 사용자가 캐시를 지우지 않으면 옛 화면이 나옵니다. cache buster는 리소스 URL에 버전 토큰을 붙여, 업데이트 후에는 새 토큰이 붙은 URL이 되고 브라우저가 그걸 초기 요청으로 취급해 서버에서 새로 받게 만듭니다.

장점은 캐시 유효기간을 짧게 줄이는 방식이 아니라는 점입니다. 실제로 리소스가 바뀐 경우에만 캐시가 무효화되므로 평소 성능을 그대로 유지합니다.

알림(Notification) — Hub 쪽 구성

Launchpad는 SAP_GWFND의 일부인 SAP Gateway Notification Channel에서 알림을 소비합니다. 알림은 Launchpad에서 기본적으로 꺼져 있고, 관련 UI 요소도 보이지 않습니다. 알림 센터는 사용자 역할별로 켤 수 있고, 알림은 SAP Workflow 또는 ABAP notification framework 기반의 알림 프로바이더가 생성합니다. 알림에서 quick action을 제공하거나 해당 주제의 앱을 바로 띄울 수도 있습니다.

1

OData V4 활성화 — SICF에서 /sap/opu/odata4가 활성이어야 한다 (SAP_GW_FIORI_ERP_ONE_CLNT_SETUP의 Activate HTTP Services for NW Gateway (SICF) task가 처리)

2

서비스 그룹 게시 — FES의 /IWFND/V4_ADMIN에서 시스템 별칭 LOCAL로 /IWNGW/NOTIFICATION을 게시한다. 게시는 순수한 구성 작업이라 ABAP 리포지토리 오브젝트를 만들지 않는다 — 라이프사이클 아티팩트가 생기지 않는다. 게시된 서비스 그룹의 서비스만 소비자가 호출할 수 있다 (SAP_FIORI_FOUNDATION_S4의 Publish Service Groups Foundation task)

3

APC WebSocket — 알림은 ABAP Push Channels를 쓴다. SICF에서 /sap/bc/apc/iwngw/notification_push_apc가 활성이어야 하고, SPRO → ABAP Platform → Notification Channel → Notification Channel Hub → Administration → Push Channel Settings → Activate and Maintain Push Channels에서 푸시 채널 ID SAP_WEBSOCKET을 유지보수·활성화한다

4

FLP에서 켜기 — NOTIFICATIONS=true · NOTIFICATIONS_UI=true (/UI2/FLP_SYS_CONF 또는 /UI2/FLP_CUS_CONF)

타깃 매핑 방식(Shell-reconfigure 인텐트)을 쓸 때 조정하는 파라미터:

파라미터의미
services/Notifications/config/enabledNotification UShell 서비스 활성화. 기본값 false
services/Notifications/config/serviceUrlNotification OData 서비스 루트 URL — 호스트명 + 게시된 서비스 그룹 + 리포지토리 ID + 서비스명 + 버전의 조합

🔰 초보자 설명 — 표준 카탈로그로 빠르게

언제 이걸 알아야 하는가

"프로그램에서 메일이 안 나갑니다." 배치 프로그램을 돌린 사람이 가장 자주 들고 오는 문의이고, 개발자 쪽에서 제일 자주 오진하는 문의이기도 합니다. 프로그램은 성공 리턴을 받았으니 소스에는 문제가 없어 보이는데, 받는 쪽에는 아무것도 안 갑니다.

이유는 단순합니다. ABAP 프로그램의 "보내기"는 실제 발송이 아니라 큐에 넣는 것이기 때문입니다. 실제 발송은 별도의 발신 작업이 나중에 합니다. 그래서 확인해야 할 지점이 프로그램 밖에 최소 네 군데 더 있고, 그 순서를 알면 원인이 5분 안에 좁혀집니다.

메시지 흐름 — BCS · PPF · Output Control

ABAP 기반 시스템에는 메시지를 만드는 경로가 여럿입니다. 중심에 있는 것이 Business Communication Services(BCS)로, 애플리케이션 안에서 내부·외부 메시지 발송을 통합하게 해 주고 발신·수신 제어와 광범위한 상태 처리를 담당합니다. 애플리케이션 오브젝트에 대한 모든 발신 정보가 BCS에 있습니다.

애플리케이션은 BCS를 직접 부르거나, 먼저 Post Processing Framework(PPF)를 거칩니다. PPF는 특정 조건(배송전표 인쇄, 오더 확인서 팩스, 승인 프로세스 트리거)에 대해 액션을 생성하는 통일 인터페이스이며 message control의 후속입니다. BCS는 Smart Forms(및 SAPscript), PDF 기반 Print Forms(Adobe)에서도 씁니다. 수동 작성은 Business Workplace(SBWP, 구 SAP Office)입니다.

S/4HANA는 여기에 새 출력 관리(SAP S/4HANA Output Control)를 더했습니다. SD Output Control · FI Correspondence · FI-CA Print Workbench · CRM Post-Processing의 후속이 될 예정이지만 기존 프레임워크도 여전히 쓸 수 있고, 새 출력 관리 사용이 필수는 아닙니다. 기본 서비스(인쇄 · 폼 렌더링 · 이메일 발송) 위에 파라미터 결정 · 첨부파일 출력 · 출력 이력을 더한 구조이고, Form Data Provider(CDS + Gateway 기반 동적 데이터 인터페이스)와 Output Forms(Adobe 렌더링으로 PDF · PCL · Postscript 생성)가 짝을 이룹니다. 상세는 SAP Note 2228611 · 2791338 · 2470711 · 3097507.

SAPconnect — 외부 통신의 중앙 인터페이스

SAPconnect는 팩스 · 문자(페이저 · SMS) · 이메일 · X.400, 프린터 전송, 시스템 간 전송을 지원하는 중앙 인터페이스입니다. 인터넷과는 ICM의 SMTP 플러그인으로 직접 연결합니다. BCS가 외부 메시지를 SAPconnect로 넘기는 구조입니다.

수신 방향과 MTA

이메일이 발송되면 먼저 MTA(sendmail 같은 프로그램)에 도달합니다. MTA는 메일을 분석해 로컬 사용자(MUA)에게 주거나 다른 MTA로 전달합니다. 여기서 반드시 기억할 한 줄:

SAPconnect는 MTA가 아니다

SAPconnect는 자신에게 향하지 않은 수신 메일을 다른 메일 서버로 자동 전달할 수 없습니다. "SAP을 메일 중계로 쓸 수 있느냐"는 요구가 들어오면 여기서 끊어야 합니다.

발신 방향은 AS ABAP 7.02부터 한 클라이언트에서 만든 메일을 여러 메일 서버로 보낼 수 있고, SMTP 노드 정의에서 메일 서버의 호스트 주소와 포트를 지정합니다(SAP Note 2348016). 수신 방향은 임의 개수의 메일 서버로부터 받을 수 있으며, 각 클라이언트가 SICF에서 구성된 별도의 가상 메일 서버(호스트명 · 포트)로 접근합니다. 시스템과 클라이언트를 지정하는 가장 좋은 방법은 클라이언트마다 별도 서브도메인을 쓰고, 메일 서버 라우팅 규칙으로 호스트명·포트에 할당하는 것입니다.

팩스·문자도 SMTP로 교환할 수 있는데, 이 경우 이메일로 패킹됩니다. 수신 시 프로바이더는 시스템 도메인이 포함된 주소(예: FAX=+1212541234@crm-prod.company.com)로 메일을 보냅니다.

POPPost Office Protocol. 상시 연결을 보장 못 하는 시스템에서도 수신 가능하게 한다. POP3는 서버 메시지를 삭제·유지·즉시 삭제 중 고를 수 있고, 계층형 메일박스·필터는 프로토콜이 제공하지 않아 클라이언트 기능이나 IMAP이 필요하다
IMAP서버에서 메일을 처리하게 하는 프로토콜. 서버에 폴더(원격 메일박스)를 만들어 분류하고, 필요할 때만 전송하도록 설계돼 사용자가 받을 데이터를 고를 수 있다
SMTP서버 간 이메일 교환 표준. 메일 클라이언트는 발신에만 쓰고 수신에는 쓰지 않는다

📌 개인 E2E 프로젝트와의 연결점 — ZPRICE_CHECK의 알림 경로

CBO 3종 중 ZPRICE_CHECK는 정보레코드가(EINE-NETPR)와 이동평균가(MBEW-VERPR)의 괴리를 알림만 내고 끝내는 설계입니다 — 회계 영향이 있는 처리는 자동화하지 않는다는 원칙 때문에 전기도, 마스터 수정도 하지 않습니다. 그러면 남는 질문이 "그 알림을 무엇으로 내보내느냐"인데, 표준 경로가 이 LESSON의 SAPconnect입니다.

설계 시 이 노트에서 그대로 가져올 것 세 가지:

· 발송은 BCS로. CL_BCS 계열을 쓰고 SO_NEW_DOCUMENT_SEND_API1 같은 구형 FM은 피합니다. 전표를 BAPI로 만드는 원칙과 같은 이유 — 표준이 제공하는 상태 처리를 버리지 않기 위해서입니다.
· "보냈다"를 성공으로 기록하지 않는다. 그림 4의 ①까지만 보장되므로, CBO 테이블 상태필드는 큐 적재 = P(처리중)로 두고 SOST 결과를 확인한 뒤에야 H(완료)로 넘깁니다. 발송 실패를 조용히 삼키면 "괴리 알림이 안 왔다"는 사고가 그대로 지나갑니다.
· 수신자를 하드코딩하지 않는다. 구매그룹·자재그룹(CHKN · RICE · SHAK · PROT · PBAR)별 담당자를 CBO 테이블이나 표준 조직 데이터에서 읽습니다. 담당자 한 명의 메일 주소가 소스에 박히면 운영 이관 시점에 반드시 문제가 됩니다.

확인 필요 — 프로젝트 서버의 메일 환경

렌탈 서버에 실제로 SMTP 노드가 구성되어 있는지, 외부로 나가는 25/587 포트가 열려 있는지 확인되지 않았습니다. SCOT에서 SMTP 노드 존재 여부와 SMICM에서 PROT=SMTP 포트를 먼저 확인하고, 외부 발송이 불가능하면 수신자를 SAP 내부 사용자(SBWP 수신)로 두는 구성으로 범위를 줄입니다 — 알림 로직 검증에는 그것으로 충분합니다.

· Web Dispatcher 뒤에서 X.509를 쓸 때 헤더의 인증서를 무조건 신뢰하지 않는다. icm/trusted_reverse_proxy_<n>로 프록시를 등록한다.
· "프로그램이 성공 리턴했다"를 메일 발송 성공으로 쓰지 않는다. 큐에 넣은 것까지만 보장된다.
· SAPconnect 설정은 대부분 클라이언트 종속이다. 다른 클라이언트에서 되는 것은 근거가 아니다.
