결론부터. 브라우저에서 SAP를 부르는 일은 "SAP가 웹서버 노릇을 한다"는 한 문장으로 요약됩니다. 그 웹서버가 ICM이고, 들어온 URL을 어느 ABAP 클래스로 보낼지 정하는 라우팅 테이블이 ICF(SICF)이며, 그 위에 비즈니스 데이터를 REST로 얹은 것이 SAP Gateway(OData), 맨 앞에서 부하를 나누고 SSL을 끊는 것이 SAP Web Dispatcher입니다.

언제 이걸 알아야 하는가

웹에서 SAP를 부르려고 할 때 제일 먼저 막히는 질문이 "그래서 뭘로 붙습니까"입니다. ITS, BSP, Web Dynpro ABAP, SAPUI5/OData — 이름은 많은데 어느 것이 지금 쓸 물건인지 판단이 안 섭니다. 답은 릴리스별 계보에 있습니다. 새 개발은 SAPUI5/OData 쪽이고, 나머지는 기존 자산을 유지하는 데 필요합니다.

운영 쪽에서는 "웹 화면이 갑자기 안 뜹니다"가 자주 옵니다. 이때 제일 먼저 볼 곳은 ABAP 프로그램이 아니라 SMICM입니다 — ICM 프로세스가 죽었거나 Maintenance Mode로 내려가 있으면 ABAP은 멀쩡해도 아무것도 안 열립니다.

ICM은 SAP 안에 들어 있는 웹서버입니다. Apache나 nginx가 하는 일(포트를 열고 HTTP 요청을 받아 처리기에 넘김)을 SAP 커널이 직접 하는 것이고, 운영체제에서 보면 icman이라는 프로세스입니다. ABAP 디스패처가 이 프로세스를 띄우고 감시합니다.

ICM 프로세스 구조

AS ABAP는 웹 서버(server role)와 웹 클라이언트(client role) 양쪽이 다 됩니다. 이 레슨이 다루는 것은 server role — 임의의 웹 클라이언트로부터 HTTP(S) 요청을 받아 처리하고 응답을 돌려주는 쪽입니다. ICM은 리스닝 중인 서버/포트 조합으로 들어온 URL을 보고 적절한 로컬 핸들러를 호출하며, 워크로드는 스레드로 병렬 처리합니다.

Internet Server Cache (ISC)

성능 관점에서 ICM의 핵심은 ISC입니다. 클라이언트로 보내기 전 HTTP(S) 객체를 저장해 두고, 만료 전이면 다음 요청을 캐시에서 바로 처리합니다. 프로파일 파라미터는 icm/HTTP/server_cache*이고, SAP 시스템에서 모니터링·무효화할 수 있습니다.

특징내용
2단계 계층 구조메인 메모리의 속도와 하드디스크의 용량을 둘 다 활용
Dynamic Caching일반 HTTP 프록시는 이미지 등 정적 콘텐츠만 캐싱하지만, ISC는 JSP·BSP 같은 동적 콘텐츠도 캐싱

시작 절차와 SMICM

프로파일 파라미터 rdisp/start_icman이 인스턴스 시작 시 ICM을 함께 띄울지 결정합니다(미지정 시 기본 true). ICM 파라미터는 대부분 icm/으로 시작하며, 특히 icm/server_port_<xx>가 어느 프로토콜을 어느 포트로 받을지와 타임아웃 등 프로토콜 속성을 결정합니다.

확인 필요 — rdisp/start_icman은 이미 없을 수 있다

SAP Note 2560792에 따르면 커널 7.72부터 AS ABAP 인스턴스는 항상 icman과 함께 시작되며, 이 파라미터는 더 이상 존재하지 않고 무시됩니다. 실제 시스템(winerp01 / MEP)에서 RZ11 또는 SMICM → Goto → Parameters로 존재 여부를 먼저 확인하고, 없다고 해서 잘못된 것이 아님을 기억할 것.

어느 애플리케이션 서버가 ICM과 함께 돌고 있는지는 SM51에서 빠르게 봅니다. 스레드 ID 같은 상세 정보와 실제 관리 작업은 ICM Monitor(SMICM)에서 합니다. 표시 데이터는 SM50과 마찬가지로 인스턴스 종속적입니다 — 로그온한 인스턴스 것만 보입니다.

ICM의 SSL 구성

AS ABAP와의 HTTP 연결 보호에는 SSL을 씁니다. SSL은 공개키 기술 기반이므로 전제조건이 키 쌍과 공개키 인증서입니다. 서버는 두 세트를 가집니다.

  • SSL server PSE — 서버 컴포넌트로서 자신을 식별하는 키 쌍·인증서
  • SSL client PSE — 자신이 클라이언트 역할로 나갈 때 쓰는 별도 키 쌍·인증서

이들은 서버의 PSE(Personal Security Environment)에 저장됩니다. 상세 절차는 SAP S/4HANA Product Assistance의 Configuring the ABAP Platform to Support TLS와 SAP Note 510007을 따릅니다.

📌 개인 E2E 프로젝트와의 연결점 — 목표 3번의 출발점

목표 3번은 "간단한 웹페이지 → RFC 통신으로 SAP 호출"입니다. RFC로 붙든 OData로 붙든, 웹페이지가 SAP에 닿으려면 ICM이 살아 있고 포트가 열려 있어야 합니다. 작업 순서는 이렇습니다.

① SMICM에서 ICM 상태 확인 → ② Goto → Parameters에서 icm/server_port_<xx>의 실제 HTTP 포트 번호 확보 → ③ 그 포트로 브라우저에서 아무 URL이나 때려 보고 응답 자체가 오는지 확인. 여기서 응답이 없으면 그다음 단계(SICF·Gateway)는 볼 필요가 없습니다. 회사코드 CL04 시스템의 실제 포트 번호는 확인 필요 — 렌탈 서버 방화벽에서 해당 포트가 열려 있는지도 같이 봐야 합니다.

LESSON 2ICF — URL과 ABAP 클래스를 잇는 자리

Unit 16레슨 1개Using the Internet Communication Framework (ICF)

언제 이걸 알아야 하는가

"URL을 쳤는데 404가 납니다." 이 Unit에서 가장 자주 나오는 증상이고, 원인 1순위는 거의 항상 하나입니다 — SICF 서비스가 활성화되어 있지 않다. 설치 시점에는 모든 ICF 서비스가 비활성이고, 전송(transport)으로 넘어온 서비스도 처음에는 비활성이며, Support Package 적용·업그레이드 후 다시 비활성으로 돌아가기도 합니다.

그래서 순서가 중요합니다. ABAP 코드를 보기 전에 SICF에서 해당 노드가 검정색인지부터 봅니다. 회색이나 파란색이면 코드는 볼 필요가 없습니다.

ICF가 하는 일

ICF는 ABAP 워크프로세스 안에서 웹 요청을 처리하는 환경이며, SAP 커널(C)과 ABAP 애플리케이션 프로그램 사이의 다리입니다. ABAP 클래스와 인터페이스로 구성되어 있어 Web Dynpro ABAP 애플리케이션 등에서 그 객체·메서드에 접근할 수 있습니다. AS ABAP 7.40부터는 추가 프로그래밍 라이브러리가 필요 없지만, HTTPS에는 별도 구성 단계가 필요합니다(SAP Note 510007).

요청을 실제로 처리하는 애플리케이션 로직은 각각 HTTP request handler로 구현됩니다. 기술적으로는 인터페이스 IF_HTTP_EXTENSION과 메서드 HANDLE_REQUEST를 구현한 ABAP 클래스이며, SAP가 제공하는 것도 있고 고객이 SE24·SE80으로 직접 만들 수도 있습니다. 대표적인 SAP 제공 핸들러가 BSP용 CL_HTTP_EXT_BSP입니다.

HTTP(S) 요청 처리 9단계

STEP 1

사용자의 웹브라우저에서 HTTP(S)로 ICM에 요청이 전송된다

STEP 2

ICM이 수신 데이터를 memory pipe(공유 메모리)에 저장하고 ABAP 디스패처에 통지한다

STEP 3

디스패처가 요청을 큐에 넣고(상태 유지 컨텍스트가 없으면 새 컨텍스트 생성) 처리할 dialog 워크프로세스를 선택한다

STEP 4

워크프로세스의 task handler가 memory pipe에서 데이터를 읽어 ICF controller(함수모듈 HTTP_DISPATCH_REQUEST)로 넘긴다

STEP 5

ICF controller가 요청을 ICF manager(CL_HTTP_SERVER)로 전달. 서버 제어 블록을 만들어 ICM에서 받은 요청 데이터로 채운다

STEP 6

클라이언트 인증 — 여러 로그온 옵션 중 서비스에 설정된 절차 순서대로 검사

STEP 7

앞서 결정된 HTTP request handler가 호출되어 요청 데이터 처리·애플리케이션 호출·응답 객체 접근을 마치고 제어를 ICF controller에 반환

STEP 8

task handler가 응답을 memory pipe에 기록(response serialization)하고 ICM에 완료를 통지

STEP 9

ICM이 응답을 웹브라우저로 반환

ICF 서비스와 활성화 개념

ICF 서비스의 역할은 딱 하나입니다 — 특정 URL과 HTTP request handler를 연결하는 것. 중앙 유지보수 트랜잭션은 SICF이고, 모든 서비스가 계층 트리로 표시됩니다. 서비스의 전체 경로(예: /sap/bc/icf/info)가 프로토콜·서버명·포트와 합쳐져 호출 URL이 됩니다.

상태SICF 색상의미
Active검정색서비스 호출 가능
Inactive회색명시적으로 비활성화됨
Inactive (암묵적)파란색상위 레벨에 명시적 비활성 서비스가 있어서 덩달아 비활성. 그 상위(회색)를 활성화하면 함께 살아난다

노드 활성화는 Service/Host → Activate 또는 우클릭 컨텍스트 메뉴로 하며, 이때 선택한 서비스만(Yes) 살릴지 하위 전부(트리 아이콘이 붙은 Yes)까지 살릴지를 고릅니다.

반드시 짚을 것 — 활성화는 곧 공격면이다

활성화된 ICF 서비스는 네트워크 구성에 따라 인트라넷·인터넷에서 HTTP(S)·SMTP로 직접 접근 가능합니다. 즉 활성화 하나하나가 공격면입니다. "안 되니까 상위 노드를 하위까지 통째로 Activate" 하는 습관이 가장 위험합니다 — 필요한 서비스만 켜고 권한 객체 S_ICF로 접근을 제한하는 것이 원칙입니다.

관련 노트: SAP Note 1447439(전송 후 비활성화되지 않는 문제), 1555208(업그레이드·SP 후 ICF 서비스 비활성화), 517484(전송된 서비스는 처음에 비활성).

대량 처리는 리포트 두 본으로 합니다. RS_ICF_SERV_ADMIN_TASKS가 시스템 내 모든 활성(또는 비활성) HTTP 서비스를 확인해 CSV로 기록하고, RS_ICF_SERV_MASS_PROCESSING이 그 CSV에 나열된 서비스를 모든 가상 호스트에 대해 활성화(또는 비활성화)합니다(SAP Note 1498575).

전송(transport) 시 로그온 데이터는 지워진다

로그온 데이터가 정의된 ICF 서비스를 전송하면 보안상 전송 중 로그온 데이터가 삭제됩니다. 대상 시스템에 그 사용자가 있다는 보장도 없으므로 대상에서 따로 유지보수해야 합니다(SAP Note 732218). 개발기에서 잘 되던 것이 품질·운영기에서 401이 나는 전형적인 원인입니다.

ICF Alias

  • 내부 별칭 — SICF의 Define Services 화면에서 서비스 생성 시 Alias to Existing Service 선택. 핸들러를 정의하는 대신 Target 탭에서 참조할 대상 핸들러를 트리에서 지정. 기존 서비스를 건드리지 않고 다른 로그온 데이터·절차로 호출할 때 쓴다. 단, SAP 서비스(/sap/ 네임스페이스)에 대한 내부 별칭은 가급적 만들지 않는다
  • 외부 별칭 — Maintain external aliases 화면에서 설정. 기술적이지 않은 의미 있는 이름으로 서비스를 부르고 싶을 때 쓰며, 내부 별칭과 달리 이름에 슬래시(/)를 포함할 수 있다. 전송 설정을 빼면 처리 방식은 동일

웹 아키텍처의 핵심은 컴포넌트 통신에 추상 인터페이스를 쓴다는 것입니다. 이 인터페이스를 커넥터라 하고, 클라이언트와 서버가 각자 커넥터를 두며 그 사이에 문서·포맷·동작을 정하는 계약이 있습니다. SAP Gateway가 바로 SAP 백엔드 쪽 커넥터로, ABAP API와 OData 엔티티 사이를 변환합니다. 덕분에 클라이언트와 서버는 서로 거의 독립적이고 교체 가능해집니다.

OData는 REST(Representational State Transfer) 패러다임을 따릅니다 — 리소스는 주소 지정 가능한 데이터이고, 표준 주소 표현은 URI입니다. 클라이언트가 URI로 요청하면 서버가 이를 내부 주소로 바꿔 데이터에 접근·조작하고 응답을 조립합니다.

이름이 같아서 생기는 사고 — SAP Gateway ≠ gateway 프로세스

SAP Gateway(OData 제공자)와 커널의 gateway 프로세스(RFC 통신용, gwrd)는 완전히 다른 물건입니다. "게이트웨이가 안 뜬다"는 말이 오갈 때 어느 쪽인지부터 확인해야 합니다. RFC가 안 되면 커널 gateway, OData가 안 되면 SAP Gateway Foundation입니다.

SAP Gateway는 SAP Business Suite·S/4HANA 같은 ABAP 기반 시스템의 비즈니스 데이터에 접근하는 단일 진입점을 제공합니다(2014년 말까지는 SAP NetWeaver Gateway). SAP HANA 쪽에서는 HANA XS가 같은 역할의 또 다른 OData 제공자입니다. 데이터 소비에 SAP 지식이 필요 없다는 점이 핵심 가치입니다.

컴포넌트 연혁: AS ABAP 7.00~7.31에서는 개별 애드온 조합이었습니다 — 런타임은 GW_CORE + IW_FND(서비스 등록·런타임), 디자인·서비스 프로바이더 런타임은 IW_BEP(서비스 구현 도구). 추가로 IW_PGW(Workflow) · IW_GIL · IW_SPI가 설치 가능했습니다. AS ABAP 7.40부터 GW_CORE·IW_FND·IW_BEP·IW_HDB가 SAP_GWFND로 통합되고, 7.51부터 IW_PGW도 합쳐졌습니다. 나머지 SAP Gateway 애드온은 전부 deprecated이며 삭제 대상입니다.

Soft State

OData 통신은 기본이 stateless입니다. 그런데 성능을 위해 캐싱이 필요한 시나리오가 있어서, SAP Gateway 2.0 SP09(SAP_GWFND 7.40 SP08)부터 soft state가 도입되었습니다. 한 ABAP 애플리케이션 서버 세션에서 여러 요청을 stateful처럼 처리하되, 세션 타임아웃 후의 동작만 다릅니다 — 예외로 중단하는 대신 새 세션을 만들어 평소대로 처리합니다. 소비자가 느끼는 차이는 캐싱 데이터를 다시 읽느라 응답이 느려지는 것뿐입니다.

ICF가 유지하는 세션은 RFC를 통해 백엔드에서도 세션을 유지하게 되고, 거기서 디자인타임이 처리한 데이터(변수)가 data provider cache에 캐싱됩니다. FES에는 SQRC(Soft State Based Query Result Cache)가 있어, 클라이언트가 결과 집합을 단순 탐색만 할 때 불필요한 BES 호출을 막아 줍니다.

활성화는 /IWFND/MAINT_SERVICE에서 서비스별로 하며, 전제조건은 ICF 노드의 session timeout이 0보다 클 것(같은 화면의 ICF Node 버튼에서도 설정 가능). 전체 시스템은 /IWFND/SOFTSTATE로 켭니다.

SQRC는 조건이 다 맞을 때만 쓴다

SQRC를 쓰는 첫 요청은 훨씬 느립니다 — 전체 데이터를 DB에서 한 번에 읽어 캐싱하기 때문입니다. 이후 요청은 캐시에서 다음 부분을 읽어 애플리케이션 시간이 0에 가까워지고 BES와의 RFC 통신도 사라집니다. 그래서 ① 데이터 조회가 매우 느리고 ② 대용량 캐싱을 피해야 하고 ③ 캐싱 데이터가 자주 안 바뀌고 ④ 메모리가 충분할 때만 씁니다.

세션이 살아 있는 동안 시스템 리소스가 점유되므로, soft state로 병렬 실행되는 서비스가 많으면 리소스가 영구 점유됩니다 — 타임아웃을 매우 짧게 잡아야 합니다. 활성화 전 SAP Note 1986626 확인 필수.

언제 이걸 알아야 하는가

"사내에서는 잘 되는데 인터넷에서는 안 열립니다." 또는 "서버 이름·포트번호가 그대로 사용자에게 노출됩니다." 둘 다 애플리케이션 문제가 아니라 앞단에 리버스 프록시가 없어서 생기는 일입니다. SAP가 그 자리에 놓으라고 무료로 주는 물건이 SAP Web Dispatcher입니다.

Web Service(SOAP)는 다른 축의 이야기입니다 — OData가 REST 계열이라면 이쪽은 XML·SOAP 계열이고, 기존 RFC/BAPI를 바깥에 그대로 내보낼 때 씁니다. 기존 함수모듈을 밖에서 부르고 싶다는 요구가 오면 여기가 답입니다.

Web Service 패러다임

Web Service는 독립적·모듈화·자기설명적인 애플리케이션 기능입니다. XML 표준 기반이라 표준 인터넷 프로토콜로 설명·제공·검색·변환·호출됩니다. 하나가 하나의 기능을 캡슐화합니다 — 가격 조회, 재고 가용성 확인, 전화번호 조회, 신용카드 검증, 환전, 급여 처리 같은 것들.

Provider
서비스 제공자 = 서버
서비스 접근을 제공하고 그에 대응하는 WSDL 문서를 가진다. Web Service 자체는 제공자가 호스팅한다
Registry
Service Registry = 전화번호부
제공자가 자기 정보와 서비스 설명을 게시하는 곳. 설명만 담고 실제 구현과 독립된 추상화 계층을 이룬다
Requester
service requester = 클라이언트
대개 사람이 아니라 애플리케이션. 런타임에 클라이언트 프록시를 동적으로 만들어 붙을 수도 있다

제공자와 호출 상세를 이미 알고 있다면 Registry를 거치지 않고도 Web Service를 쓸 수 있습니다.

SAP Web Dispatcher — 무엇이고 왜 두는가

SAP의 리버스 프록시이자 소프트웨어 로드밸런서입니다. 랜드스케이프 안의 시스템·애플리케이션 서버 간 HTTP(S) 요청을 필터링·라우팅·분배합니다. SAP 고객에게 무료이고 TCO가 낮으면서 SAP 시스템의 부하분산·라우팅을 기본적으로 완벽히 지원합니다. AS ABAP, AS Java, HANA XS 등 HTTP 서비스 기반 SAP 솔루션에 모두 씁니다.

필수는 아닙니다(일부 특정 시나리오 제외). HTTP는 표준 프로토콜이라 다른 웹 인프라 제품도 됩니다 — 이미 하드웨어 로드밸런서에 투자했거나 극단적으로 높은 성능이 필요하면 하드웨어 쪽이 유리합니다. 다만 서드파티는 추가 비용과 SAP 통합 제약이라는 단점이 따라옵니다.

SAP Web Dispatcher의 내부 구조는 ICM 프로세스와 매우 유사합니다. 실제로 파라미터 이름도 icm/server_port_<xx>, icm/max_conn, icm/HTTP/admin_<xx>처럼 ICM 것을 그대로 씁니다. ICM을 알면 Web Dispatcher는 절반은 아는 셈입니다. 별도 DB 같은 의존 소프트웨어 없이 독립 실행형 프로그램이라 별도 호스트에도, 애플리케이션 서버 중 하나에도 올릴 수 있습니다.

설치와 프로파일

SAP Web Dispatcher는 하위 호환입니다 — 릴리스가 SAP 시스템(커널) 릴리스보다 높거나 같으면 되고 패치 레벨도 백엔드와 달라도 됩니다. 허용 조합은 SAP Note 908097에 나열됩니다.

설치 옵션내용
실행 파일 + 프로파일호스트에 실행 파일 sapwebdisp와 프로파일만 두면 끝. 실행 파일은 SAP Support Portal(SAP Technology Components)의 sapwebdisp.sar, 프로파일은 보통 sapwebdisp.pfl. 시작: sapwebdisp pf=<profile file>
실행 파일 + -bootstrap프로파일 없이 시작. sapwebdisp -bootstrap을 실행하면 sapwebdisp.pfl이 없을 때 대화형 입력으로 생성되고, icmauth.txt가 없으면 Web Administration용 사용자와 함께 생성된 뒤 그 프로파일로 기동된다
SWPM / SAPinstSoftware Logistics Toolset(SL Toolset)으로 제공되는 설치·업데이트 도구. SWPM 1.0과 2.0이 있고, non-Unicode 버전을 명시적으로 설치하려면 1.0을 써야 한다. 필요한 아카이브: SAP Web Dispatcher, SAP Host Agent. 옵션 경로는 Generic Options → SAP Web Dispatcher → SAP Web Dispatcher (Unicode), Parameter Mode는 Typical / Custom

핵심 파라미터는 둘입니다 — 어느 포트로 받을지(icm/server_port_<xx>)와 어느 메시지 서버에 붙을지(wdisp/system_<xx>). 메타데이터를 HTTPS로 교환하려면 추가 단계가 필요합니다.

구성 점검 — 띄우기 전에 확인한다

sapwebdisp pf=<profile> -checkconfig

이 한 줄이 다음을 검증합니다.

  • OS의 최대 소켓 수가 구성된 연결 수를 감당하는지
  • 애플리케이션 서버 정보가 파일과 wdisp/server_info_location에 구성되어 있는지 — 파일의 구문·의미 검사
  • 메시지 서버 쪽 구성 — HTTP 포트 연결 테스트, 구성된 URL로 데이터 확인, 모든 애플리케이션 서버로의 연결 확인
  • wdisp/group_info_location에 파일이 있으면 그룹 파일 검사, 없으면 /sap/public/icf_info/icr_groups로 확인하고 ICF 노드가 활성인지 검사
  • wdisp/url_map_info_location에 파일이 있으면 검사, 없으면 /sap/public/icf_info/icr_urlprefix로 확인하고 ICF 노드 활성 여부 검사

업데이트는 커널 업데이트와 비슷합니다 — 해당 OS·주요 릴리스의 아카이브를 받아 sapcar -xvf <sapwebdisp.sar>로 풀고 재시작(SAP Note 908097). 현재 버전 확인은 sapwebdisp -v, 개발자 트레이스 dev_webdisp 분석, SAP MC/MMC의 Version Info 중 아무 것이나.

Web Administration 인터페이스

icm/HTTP/admin_0 = PREFIX=/sap/wdisp/admin,DOCROOT=$(DIR_DATA)$(DIR_SEP)icmandir,AUTHFILE=$(icm/authfile),PORT=8008
  • 위 icm/HTTP/admin_<xx>를 프로파일에 정의 — 관리 URL 접두사를 /sap/wdisp/admin으로, 제어 파일 경로를 ./admin으로 설정
  • icm/server_port_<xx>로 이 포트를 인바운드 포트로 지정
  • 관리자 사용자와 해시된 비밀번호가 담긴 인증 파일 icmauth.txt 생성 (wispmon -a로 내용 확인·수정)
  • 최초 기동 후 DOCROOT 디렉토리에 인터페이스 파일이 있는지 확인 (없으면 sapcar -xvf wdispadmin.SAR로 admin 하위 디렉토리에 수동 압축 해제)

접근 URL은 http(s)://<WD host>:<admin port>/<admin prefix>이고 기본 접두사는 /sap/wdisp/admin입니다. 기능은 모니터링 · 파라미터 설정 표시 · 통계 · 트레이스 파일 평가 · 사용자 관리 · Maintenance mode. 명령줄 wdispmon으로도 같은 일을 할 수 있습니다(icmon과 사용법 유사).

반드시 지킬 것 — 관리 인터페이스는 HTTP로 열지 않는다

HTTP로 쓰면 관리자 비밀번호가 평문으로 흘러 도청됩니다. 반드시 HTTPS를 쓰고, 추가로 전용 포트 + localhost 제한을 겁니다(파라미터로 포트·로컬 호스트명·외부 호스트명 기준 제한 가능). AUTHFILE=backend 옵션으로 백엔드 ABAP 사용자로 인증하게 할 수도 있습니다(SAP Note 2011786).

파라미터 변경 방법내용
프로파일 변경 후 (재)시작텍스트 에디터로 인스턴스 프로파일 수정. 시작은 SAP MC/MMC, sapcontrol -function StartSystem ALL, sapwebdisp pf=<InstanceProfile>. 재시작은 sapcontrol -function RestartSystem ALL 또는 Web Admin의 Shutdown / Soft Shutdown
프로파일 변경 후 재구성실행 중인 상태로 반영. 전제조건: wdisp/config_reload = TRUE(기본 FALSE). 트리거는 sapwebdisp pf=<InstanceProfile> -reconfig profile
Web Administration에서 변경Core System → Parameters → Edit Parameters. 이름 입력 후 Get Value로 설명·타입 확인. 대부분(전부는 아님) 동적 변경 가능 — 임시 변경은 RZ11처럼 즉시 적용되지만 재시작 시 사라진다. 영구 변경을 고르면 인스턴스 프로파일에 반영되고 이전 프로파일 백업이 프로파일 경로의 backup 하위에 생긴다
📌 개인 E2E 프로젝트와의 연결점 — 프로젝트에서는 안 쓰되 알고 안 쓴다

렌탈 서버 1대짜리 환경에서는 Web Dispatcher를 두지 않고 ICM에 직결하는 것이 맞습니다. 인스턴스가 하나면 부하분산할 대상이 없고, 설치·SSL 구성에 드는 시간이 목표 1·2번을 깎아먹습니다. 프로젝트 원칙 "밀리면 범위를 줄인다"에 맞는 선택입니다.

다만 인터페이스 설계서에는 한 줄 남겨 두는 편이 좋습니다 — "운영 랜드스케이프라면 Web Dispatcher를 DMZ에 두고 SSL을 여기서 종단하며, AS ABAP는 인트라넷에 둔다. 이 프로젝트는 단일 인스턴스라 생략했다." 면접에서 "왜 없냐"는 질문이 나올 때 모르고 뺀 것과 알고 뺀 것의 차이가 여기서 갈립니다.

Web Service(SOAP) 쪽도 같습니다. 목표 3번을 RFC로 가기로 했으므로 SOAMANAGER는 범위 밖이지만, "Inside-Out으로 BAPI를 그대로 Web Service화할 수도 있었다"는 대안은 설계서에 근거로 남길 가치가 있습니다.

언제 이걸 알아야 하는가

"https로 열면 브라우저가 인증서 경고를 띄웁니다." 사용자는 "무시하고 계속"을 누르고 넘어가지만, 그 순간 SSL이 지켜 주기로 한 인증(authentication)이 사라집니다. 암호화는 남고 "상대가 진짜 그 서버인가"만 없어지는 것입니다. 경고가 왜 나는지 알려면 왜 인증서가 필요한가부터 알아야 합니다.

운영 쪽에서는 "특정 시간대에만 503이 납니다"도 이 레슨 소관입니다 — Web Dispatcher의 연결·요청 제한에 걸린 것이고, 시스템 로그의 메시지 ID로 확정합니다.

암호화 3방식

HTTP가 타고 가는 TCP/IP는 잠재적으로 안전하지 않은 전송 메커니즘입니다. 같은 네트워크에 붙은 사람은 어느 정도의 노력과 지식만 있으면 패킷과 내용을 도청할 수 있습니다. Alice(브라우저)가 요청하고 Bob(서버)이 고객 데이터를 응답하는 동안 Mallory가 전부 듣습니다. 해법은 전송 데이터 자체를 암호화하는 것입니다.

방식내용대표 알고리즘
대칭키 암호화송수신자가 secret key라는 비밀을 공유하고 같은 키로 암·복호화. 특정 길이의 값(예: 256비트). 대부분의 브라우저·웹서버가 널리 사용. 빠르다DES, Triple DES, AES, IDEA, RC4, RC5, Blowfish
비대칭키 암호화서로 대응하는 개인키·공개키 쌍. 공개키로 암호화한 것은 대응하는 개인키로만 복호화된다. 공개키는 배포해도 되고 개인키는 비밀. 단점 — 대칭키보다 느리고, 키 쌍 하나로는 한 방향만 된다RSA, Diffie-Hellman
하이브리드 암호화둘의 장점을 결합. 클라이언트가 ICM 또는 Web Dispatcher에 접속 → 서버가 공개키 전송 → 클라이언트가 secret key를 만들어 그 공개키로 암호화해 전송 → 서버가 개인키로 복호화 → 핸드셰이크 → 이후 통신은 빠른 secret key로 암호화SSL / TLS가 이 방식

인증과 디지털 인증서

암호화만으로는 부족합니다. Mallory가 통신에 끼어들어 Bob 행세를 하며 "이게 내 공개키"라고 내밀면 Alice는 구분할 수 없습니다. 이 문제를 다루는 것이 Authentication이고, 그 기반이 디지털 인증서입니다.

🔰 초보자 설명 — 인증서는 여권이다

디지털 인증서는 인터넷상의 디지털 신분증입니다. 여권처럼 소유자·발급자·일련번호·유효기간을 담고, 형식은 X.509 표준을 따릅니다. 인증서에는 키 쌍의 공개 부분만 들어가고 개인키는 절대 들어가지 않습니다 — 개인키는 안전한 곳에 따로 둡니다.

여권을 국가가 발급하듯 인증서는 CA(Certification Authority)가 발급합니다. CA가 인증서에 디지털 서명함으로써 "이 공개키는 이 서버의 것"을 보증하고, 그래서 위조가 안 됩니다. 이 발급·검증 인프라 전체를 PKI라 합니다. 잘 알려진 CA: Verisign Inc., TC Trust Center.

SSL / TLS

SSL은 보안 기능이 없는 다른 프로토콜을 투명하게 강화하는 프로토콜입니다. HTTP 전용이 아니라 TCP 계층과 LDAP·SMTP·HTTP 같은 애플리케이션 프로토콜 사이에 놓입니다. SSL로 확장된 HTTP가 URL에서 https 식별자를 갖습니다. 정확히는 Web Dispatcher와 ICM이 지원하는 것은 SSL의 후속인 TLS지만, 관례상 SSL이라 부릅니다.

SSL은 하이브리드 암호화를 쓰고, 암호화 외에 서버 인증 · 클라이언트 인증 · 상호 인증을 제공합니다. 서버 인증 절차는 다음과 같습니다.

절대 URL 생성 — HTTPURLLOC

단순한 랜드스케이프에서는 AS ABAP와 브라우저가 같은 네트워크에 있으니 AS ABAP가 자기 이름으로 절대 URL을 만들어도 됩니다. 그런데 앞에 리버스 프록시가 서면 브라우저는 프록시의 이름으로 통신하고 있으므로, AS ABAP가 자기 이름을 쓰면 브라우저가 닿을 수 없는 URL이 나옵니다. 생성될 URL에 리버스 프록시의 이름·포트가 들어가도록 구성 테이블 HTTPURLLOC으로 지정합니다(SAP Note 750292).

  • 할당된 그룹이 없으면 내장 그룹을 씁니다 — !DIAGS(https 요청용) · !DIAG(http 요청용). 각각 해당 프로토콜을 제공하는 ICM이 도는 모든 인스턴스로 구성됩니다

📌 개인 E2E 프로젝트와의 연결점 — 웹페이지가 인증서에서 막힐 때

목표 3번에서 웹페이지를 HTTPS로 띄우고 SAP를 부르면 브라우저가 먼저 인증서를 본다는 사실이 실무적으로 걸립니다. 렌탈 서버는 대개 자체 서명 인증서라 브라우저가 경고를 내고, 자바스크립트 fetch는 경고를 띄우지 않고 그냥 실패합니다 — 화면에는 아무것도 안 나오고 콘솔에만 오류가 찍힙니다.

대응은 셋 중 하나입니다. ① 개발 단계에서는 HTTP로 붙이고 인증서는 범위 밖으로 둔다(가장 현실적) ② 자체 서명 인증서를 브라우저 신뢰 저장소에 예외 등록한다 ③ 실제 CA 인증서를 받는다. ①을 고르되 왜 골랐는지 설계서에 한 줄 남기는 것이 프로젝트 원칙("학습 목적으로 단순화한 부분은 왜 단순화했는지 기록")에 맞습니다.

여기서 얻는 또 하나: 웹페이지를 SAP와 다른 호스트에서 띄우면 AS ABAP가 만들어 주는 절대 URL이 브라우저가 닿을 수 없는 주소일 수 있습니다(HTTPURLLOC 이야기). 인터페이스 설계서에 웹페이지 호스트 · 중간 서버 호스트 · SAP 호스트를 각각 명시해 두면 이 함정을 피합니다. 실제 호스트명·포트는 확인 필요.

반드시 지킬 것

· 층을 먼저 가른다. 404·401은 ICF, 500은 핸들러·애플리케이션, 503은 Web Dispatcher. 이걸 안 가르고 ABAP부터 열면 며칠이 날아간다.
· ICF 서비스는 필요한 것만 켠다. 활성화 = 인터넷에서 직접 닿을 수 있음. "안 되니까 하위까지 통째로 Activate"가 가장 위험한 습관이고, 접근 제한은 S_ICF로 건다.
· /IWBEP/ALL은 운영에 게시하지 않는다. 백엔드의 모든 서비스를 한 번에 노출하는 것이다.
· 관리 인터페이스는 HTTPS 전용 + 전용 포트 + localhost 제한. HTTP로 열면 관리자 비밀번호가 평문으로 흐른다.
· ICF Recorder는 끄고 나온다. 켜 둔 채로 두면 성능이 떨어진다.
· Soft state는 타임아웃을 짧게. 세션이 사는 동안 리소스가 점유되고, 병렬 서비스가 많으면 영구 점유가 된다.
· 개발기에서 되던 것이 운영기에서 401·404 나면 전송 특성부터 의심한다 — 로그온 데이터는 전송 중 삭제되고, 전송된 서비스는 처음에 비활성이다.
