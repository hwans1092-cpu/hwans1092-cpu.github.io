결론부터. SAP의 권한은 "무엇을 금지하는가"가 아니라 "무엇을 허용하는가"로만 정의됩니다. 명시적으로 허용되지 않은 모든 것은 자동으로 금지입니다 — 그래서 권한 문의의 답은 언제나 "무엇이 빠졌는가"이고, 그것을 알려주는 도구가 SU53과 STAUTHTRACE입니다.

통신 기술도 같은 구조입니다. 시스템끼리 붙는 통로는 RFC Destination 하나로 수렴하고, 그 위에 BAPI가 얹히고 다시 그 위에 ALE·IDoc이 얹힙니다. 이 노트는 운영에서 손대는 순서(권한 요청 → 조사 → PFCG → User Comparison)와 인터페이스를 설계할 때 고르는 순서(무엇을 보장할 것인가 → RFC 유형 선택)를 중심으로 정리했습니다.

LESSON 1AS ABAP 사용자·권한 — SU01 · PFCG · SU53

Unit 6레슨 4개사용자 마스터레코드 · 역할과 권한 프로파일(PFCG) · 비밀번호·로그온 파라미터 · 사용자정보시스템(SUIM)

언제 이걸 알아야 하는가

운영에서 제일 자주 들어오는 문의는 이겁니다. "ME23N 권한 좀 열어주세요" 또는 "그 프로그램 돌리니까 권한이 없다고 나옵니다."

여기서 바로 PFCG를 열면 안 됩니다. 트랜잭션 코드를 역할 메뉴에 넣는다고 권한이 생기는 게 아니기 때문입니다. 실제로 막힌 것은 트랜잭션이 아니라 그 안에서 체크되는 권한 오브젝트의 특정 필드값(예: 회사코드, 플랜트, 구매조직)인 경우가 대부분입니다.

그래서 순서는 언제나 ① 무엇이 막혔는지 확인 → ② SU53/STAUTHTRACE로 빠진 오브젝트·값 특정 → ③ SUIM으로 기존 역할 검색 → ④ PFCG 수정·Generate → ⑤ User Comparison입니다. 이 다섯 단계를 건너뛰면 "열어줬는데 여전히 안 된다"가 반복됩니다.

사용자 마스터레코드 (SU01)

SAP에서 "사용자"는 사용자ID·비밀번호 등으로 구성된 사용자 마스터레코드를 말합니다. OS·DB·SAP 각 레벨은 권한 개념이 따로이며, SAP 사용자/비밀번호가 OS나 DB 로그온을 보장하지 않습니다. 사용자·권한 데이터는 클라이언트 종속적입니다 — 100번에서 만든 사용자는 200번에 없습니다.

생성 시 최소 필수 입력은 Address 탭의 Last name과 Logon Data 탭의 초기 비밀번호(2회) 둘뿐입니다.

🔰 초보자 설명 — 사용자그룹이 두 개 있다?

이름이 비슷해서 헷갈리는 지점입니다. Logon Data 탭의 "User Group for Authorization Check"는 권한 오브젝트 S_USER_GRP로 "누가 이 사용자를 관리할 수 있는가"를 통제합니다(공란이면 아무 관리자나 관리 가능). 반면 Groups 탭의 그룹은 SU10 대량 변경용 묶음일 뿐 권한 체크에 쓰이지 않습니다. 그룹 생성은 SUGR.

사용자 유형 — 왜 이 계정으로는 로그온이 안 되는가

유형설명
Dialog1인이 쓰는 일반 대화형 사용자. 만료/초기 비밀번호 체크, 본인이 비밀번호 변경 가능. 다중 로그온은 체크·로깅됨
System시스템 내 무대화(dialog-free) 통신·백그라운드용 — ALE, Workflow, TMS, CUA 등 RFC 통신 계정이 여기. 대화형 로그온 불가, 비밀번호 유효기간 규정 미적용, 관리자만 비밀번호 변경
Communications Data시스템 간 무대화 통신용. 대화형 로그온 불가, 비밀번호 유효기간 규정은 적용됨
Service익명의 다수가 쓰는 대화형 사용자. 만료/초기 비밀번호 체크 없음, 다중 로그온 허용. 제한된 권한만 부여할 것
Reference개인에 종속되지 않는 일반 사용자. 로그온 불가 — 대화형 사용자에게 추가 권한을 얹는 용도로만 (Roles 탭에서 지정)
인터페이스 계정이 만료돼서 야간 배치가 죽는 전형적인 사고

RFC 통신용 계정을 Communications Data로 만들면 비밀번호 유효기간 규정이 적용됩니다. 어느 날 갑자기 비밀번호가 만료되고 인터페이스가 전부 끊깁니다. 시스템 간 통신 계정은 System 유형이어야 유효기간 규정에서 빠집니다.

📖 참고 — S/4HANA의 비즈니스 사용자

S/4HANA에서는 비즈니스 파트너와 1:1 연결된 "비즈니스 사용자" 개념이 도입되어 중복 관리를 줄입니다. 비즈니스 파트너가 할당되지 않은 사용자는 "User with Classic Address"로 표시됩니다. S/4HANA 1909부터 SU01에서 비즈니스 사용자와 기술 사용자(Technical User, 주소 탭 없음)를 구분합니다. 관련 SAP Note 2570961.

권한 개념 — 포지티브(Positive) 모델

AS ABAP에서 데이터·액션 접근은 SAP가 제공하는 권한 오브젝트(Authorization Object)로 보호되고, 오브젝트는 Object Class로 묶입니다. 하나의 권한 오브젝트는 최대 10개의 권한 필드를 가지며, 여러 조건을 AND로 연결한 복합 체크가 가능합니다.

예: S_USER_GRP(사용자 마스터 관리)는 필드 ACTVT(Activity)와 CLASS(User Group)를 가집니다. 같은 오브젝트에서 서로 다른 "권한(Authorization)"을 여럿 만들 수 있습니다 — 권한 A는 그룹 SUPER의 생성/변경/조회 허용, 권한 B는 A-SUPEQ로 시작하는 그룹의 조회만 허용, 하는 식입니다.

"금지" 권한은 존재하지 않는다

모든 권한은 허용만 있습니다. 명시적으로 허용되지 않은 모든 것은 금지입니다. 그래서 "이 사람한테서 이 권한을 빼달라"는 요청은 '금지 권한 추가'가 아니라 해당 값을 포함한 역할을 회수하거나 필드값 범위를 좁히는 작업이 됩니다.

런타임 — user buffer와 AUTHORITY-CHECK

로그온 시 그 사용자의 권한이 애플리케이션 서버 메인메모리의 user buffer(user context)에 적재됩니다. 내용은 SU56으로 확인합니다. 신규 권한을 할당해도 재로그온해야 반영될 수 있는 이유가 이것입니다(SAP Note 452904).

코드 안에서는 AUTHORITY-CHECK 명령이 런타임 체크를 수행하고, 리턴코드 0이면 통과입니다.

AUTHORITY-CHECK OBJECT 'M_MSEG_WWE'
         ID 'ACTVT' FIELD '01'
         ID 'WERKS' FIELD lv_werks.
IF sy-subrc <> 0.
  MESSAGE e001(zmm) WITH lv_werks.   " 조용히 넘기지 않는다
ENDIF.

역할 관리 (PFCG) — 신호등과 Generate

PFCG(구 Profile Generator)에서 관련 트랜잭션을 역할로 묶으면, 선택된 트랜잭션에서 체크되는 권한 오브젝트에 필요한 필드값이 자동 제안됩니다. 하나의 역할은 여러 사용자에게 할당되므로 역할을 고치면 그 역할을 가진 전원에게 영향이 갑니다. 사용자 메뉴는 할당된 역할들의 메뉴 합집합입니다.

메뉴 탭에는 트랜잭션·Web Dynpro·SAP Fiori 오브젝트(카탈로그/그룹, S/4HANA 2020부터 Space도)를 넣을 수 있고, 리포트·웹주소·파일 링크도 삽입 가능합니다(파일은 URL 대신 저장 경로).

권한 탭의 신호등이 실질적인 작업 지점입니다.

신호등의미해야 할 일
녹색시스템이 제안한 기본값이 있다검토만 — 그대로 둬도 생성된다
노란색기본값이 없어 수동 유지보수가 필요하다필드값을 직접 채운다
빨간색조직수준(Organizational Level)이 유지되지 않았다회사코드·플랜트 등 조직값을 지정

자주 등장하는 필드는 조직수준으로 묶여 한 번에 유지보수됩니다(예: 회사코드). 모든 권한을 정리한 뒤 Generate를 눌러야 권한 프로파일이 생성되고, 생성 후에는 프로파일 이름을 바꿀 수 없습니다.

📖 참고 — 프로파일 네임 레인지

프로파일명의 2번째 문자에 언더스코어(_)는 쓸 수 없습니다. 고객 네임 레인지 규칙 — SAP Note 16466.

User Comparison — 여기서 빠뜨려서 다시 문의가 온다

역할↔사용자 할당은 PFCG의 User 탭 또는 SU01에서 합니다(할당 시작일 = 오늘, 종료일 = 12/31/9999가 기본, 변경 가능). 사용자는 여러 역할에 연결될 수 있습니다.

역할 할당 ≠ 권한 부여

역할을 할당하는 것만으로는 권한이 사용자 마스터레코드에 붙지 않습니다. 프로파일이 사용자 마스터에 반영되는 과정이 User Comparison입니다.

· 개별 역할: PFCG → User 탭 → User comparison
· 대량: PFUD → Utilities → Mass comparison
· 정기 자동: PFCG에서 백그라운드 잡 PFCG_TIME_DEPENDENCY 스케줄 (기본 매일 1회 전체 비교)

여기까지 하고도 안 되면 재로그온입니다 — user buffer가 갱신되지 않은 상태입니다.

보안 정책 (SECPOL) — 파라미터보다 세밀하게

프로파일 파라미터는 시스템 전체에 걸립니다. 사용자·클라이언트별로 다른 로그온/비밀번호 정책을 주고 싶으면 SECPOL로 보안 정책을 만듭니다.

STEP 1

SECPOL → New Entries로 정책 생성

STEP 2

Attributes 노드에서 속성값 지정 — 공란인 속성은 표준 프로파일 파라미터 동작을 따른다

STEP 3

SU01(또는 SU10) Logon Data 탭에서 사용자에게 정책 할당

📖 참고 — SECPOL은 커스터마이징이다

보안 정책 생성은 커스터마이징 작업이므로 커스터마이징 전송요청이 필요하고, 클라이언트 종속적이며 전송(transport) 가능합니다. 개발기에서 만들고 운영으로 넘기는 경로를 타야 한다는 뜻입니다.

유지보수 중 로그온 차단

login/server_logon_restriction동작
0제한 없음
1SERVER_LOGON_PRIVILEGE=1 속성의 보안정책 보유자만 로그온 가능
2어떤 사용자도 로그온 불가
3외부 로그온은 SERVER_LOGON_PRIVILEGE=1 보유자만 가능
4외부 로그온 전면 불가

RZ11에서 동적 변경(재시작 불필요), 영구 저장은 RZ10입니다. 누구에게 SERVER_LOGON_PRIVILEGE 정책이 할당됐는지는 SUIM → Where-Used List → Security Policies → In Users로 확인합니다.

대안으로 SMAINTENANCE에서 유지보수 기간(Maintenance Period)을 정의하면 TENANT_RUNLEVEL_PRIVILEGE=1 보유자만 로그온 가능하고 관리용 배치 작업만 실행됩니다. 비활성 사용자 일괄 잠금은 리포트 RSUSR_LOCK_USERS(온라인/백그라운드, 로컬 잠금만 설정).

AS Java는 사용자·그룹 저장을 서비스 프로바이더("user store")로 추상화합니다: DBMS provider(시스템DB) · UDDI provider(외부 서비스) · UME provider(통합 User Management Engine). UME provider는 설치 시 항상 구성되며, 사용자·권한 개념을 유연하게 구축하는 유일한 방법입니다.

UME 계층역할

지원 데이터소스는 시스템DB · 디렉터리서비스(LDAP) · ABAP 기반 SAP 시스템(SAP Web AS 6.20부터)입니다.

LDAP과 AS ABAP을 동시에 데이터소스로 쓸 수 없다

· LDAP: 비밀번호를 LDAP에서 관리하고 싶을 때(Windows 통합인증 재사용 등), 비SAP 시스템과 LDAP을 공유할 때
· AS ABAP: Java 애플리케이션이 ABAP의 서비스·사용자데이터에 접근해야 할 때. CUA 랜드스케이프에서는 중앙시스템(읽기/쓰기) 또는 자식시스템(읽기전용 권장) 중 선택

데이터소스 변경은 불일치를 유발해 제한적으로만 지원됩니다(SAP Note 718383). 시스템DB → LDAP/ABAP 전환은 가능(동일 고유속성의 사용자/그룹이 없어야 함), ABAP 데이터소스는 변경 불가, 디렉터리서비스는 고유ID가 유지되면 구조변경 가능.

데이터 파티셔닝은 속성 기반(전역속성은 LDAP, 앱 특화 속성은 DB) · 사용자 기반(자가등록/내부사용자 구분) · 타입 기반(사용자/그룹/역할/계정별) 셋으로 나뉩니다. SAP가 사전구성 조합을 제공하므로 특별한 이유가 없으면 그대로 씁니다.

ABAP 데이터소스 연동 — 이 대목이 시험에도 운영에도 걸린다

ABAP 클라이언트를 데이터소스(dataSourceConfiguration_abap.xml)로 쓰면 이렇게 보입니다.

  • ABAP 사용자가 ABAP 비밀번호로 AS Java에 로그온 가능
  • ABAP 롤이 동일한 이름의 UME 그룹으로 표시
  • ABAP 사용자 → ABAP(복합)롤 할당이 UME에서는 사용자 → 그룹 할당으로 나타남

여기서 설계 의도가 드러납니다. ABAP+Java 컴포넌트를 모두 가진 애플리케이션(예: SAP PI)에서 권한 관리를 한 곳으로 모으기 위한 것입니다. PFCG 롤이 UME에서 그룹으로 보이므로, 그 그룹(=PFCG 롤)에 UME 롤을 할당해 두면 사용자가 ABAP에서 PFCG 롤을 받는 순간 Java 권한도 자동으로 따라옵니다.

연동은 Java Connector(JCo)로 이뤄지고, ABAP 통신 사용자(보통 이름에 SAPJSF 포함)의 ABAP 권한이 UME가 ABAP 사용자마스터를 읽기만 할지 쓰기까지 할지를 결정합니다.

AS ABAP를 데이터소스로 쓸 계획이면, AS Java 설치 전에 통신사용자(권장명 SAPJSF_<SID>)가 AS ABAP에 이미 존재하고 초기 비밀번호까지 설정돼 있어야 합니다.

Principle — User · User Account · Group · Role

UME에서 User · User Account · Group · Role을 통칭해 Principle이라 부릅니다. 사용자가 실제로 보유하는 역할은 세 경로의 합입니다.

1

사용자에게 직접 할당된 역할

2

사용자가 속한 그룹에 할당된 역할

3

그 그룹의 상위 그룹에 할당된 역할 (계층 상속)

🔰 초보자 설명 — "역할이 안 보인다"의 대부분은 검색 옵션이다

Identity Management에서 간접 할당된 Principle을 보려면 검색 시 "Search Recursively"를 체크해야 합니다. 체크하지 않으면 직접 할당분만 나와서 "권한이 없는 것처럼" 보입니다.

권한 개념 — JEE Security Role vs UME Permission

AS Java의 권한 체크는 세 갈래이고, 어느 방식을 쓸지는 개발자가 결정합니다.

체크 유형설명
애플리케이션 접근 보호요청 사용자에게 필요한 JEE Security Role이 있는지 체크 (없으면 거부)
개별 활동 보호특정 활동(예: Delete) 요청 시 필요한 JEE Security Role 또는 UME Action 보유 여부 체크
오브젝트 사용 보호ACL(Access Control List)로 폴더·문서 등 오브젝트 단위 보호

체크 방식은 선언적(Declarative)과 프로그래밍적(Programmatic)으로 나뉩니다. 선언적은 Java 컨테이너가 개발자 코딩 없이 강제하며(어노테이션 또는 배포서술자에 정의) JEE Security Role에 주로 씁니다. UME Permission은 항상 프로그래밍적으로 체크됩니다 — ABAP의 AUTHORITY-CHECK와 성격이 같습니다.

개념설명
PermissionJava 코딩에서 정의되는 가장 세밀한 권한. 사용자에게 직접 할당할 수 없다
ActionPermission의 집합. 개발자가 actions.xml에 정의하고, Identity Management에 표시됨
UME Role하나 이상 애플리케이션의 Action을 묶은 것. 관리자가 사용자/그룹에 할당하는 단위

즉 개발자는 세밀한 Permission을 정의하되 소수의 Action으로 복잡성을 숨기고, 관리자는 Action을 UME Role로 조합합니다. JEE Security Role도 UME Role에 Action으로 포함시킬 수 있습니다(Identity Management에는 하위호환 때문에 J2EE 타입 Action으로 표시됩니다).

직무분리(SoD) — 조합하면 안 되는 Action

Manage_Role_Assignments_SoD(자신 외 모든 사용자에게 역할 할당 가능)와 Manage_Roles_SoD(자신에게 할당된 역할 외 모든 역할 생성/관리 가능)는 Manage_Users · Manage_Groups · Manage_Roles · Manage_all_Companies와 함께 조합하지 않습니다. 조합하는 순간 "스스로에게 권한을 주는" 경로가 열립니다.

🔰 초보자 설명 — Everyone의 무게

Authenticated Users + Anonymous Users = Everyone입니다. 그리고 Everyone에는 앞으로 생성될 사용자까지 포함됩니다. 여기에 권한을 붙이면 전사에 붙는 것이고, 나중에 만든 계정에도 자동으로 붙습니다. 기본 역할 Everyone이 이 그룹에 할당되어 모든 사용자에게 기본 최종사용자 권한을 줍니다.

기본 역할은 Administrator(광범위한 Java 권한, Administrators 그룹에 연결)와 Everyone(기본 최종사용자 권한) 둘입니다. 관리자 계정은 무제한 접근권한이므로 소수에게만, 강한 비밀번호로. 게스트는 익명 접근용이라 보통 잠겨 있고 삭제하지 않습니다.

비상 사용자 (Emergency User, SAP*)

사용자관리가 잘못 구성되어 아무도 로그온할 수 없거나 모든 관리자 계정이 잠긴 경우에만 켭니다. 모든 애플리케이션·구성도구에 로그온 가능한 완전관리자이며, 보안상 기본 비밀번호가 없어 활성화 시 직접 설정합니다.

언제 이걸 알아야 하는가

인터페이스 쪽 문의는 문장이 거의 정해져 있습니다. "어제 데이터가 안 넘어왔습니다" 또는 "같은 전표가 두 번 들어왔습니다."

이 둘은 서로 다른 문제가 아니라 같은 질문의 앞뒷면입니다 — "이 인터페이스는 무엇을 보장하기로 하고 만들었는가"입니다. 동기 호출은 실패하면 그 자리에서 끝이고 아무도 재시도하지 않습니다. 트랜잭셔널 RFC는 정확히 한 번을 보장하지만 순서는 보장하지 않습니다. 큐 RFC라야 순서까지 갑니다.

그래서 인터페이스를 만들 때 코드보다 먼저 정하는 것은 ① 호출자가 결과를 기다려야 하는가 ② 중복 실행이 회계에 영향을 주는가 ③ 선후관계가 있는가 세 가지이고, 그 답이 RFC 유형을 결정합니다. 이 결정을 문서에 안 남기면 나중에 "왜 이렇게 만들었냐"에 아무도 답을 못 합니다.

RFC — 모든 SAP 상위 인터페이스의 바닥

SAP 인터페이스는 SAP 고유 인터페이스와 개방형 인터페이스로 나뉘고, TCP/IP·CPI-C 같은 기술적 연결부터 BAPI·IDoc 같은 비즈니스 오브젝트 특화 인터페이스까지 층이 있습니다. 그런데 비즈니스 오브젝트/프로세스에 접근하는 SAP 고유 상위 인터페이스는 전부 RFC 기술 위에 서 있습니다.

RFC(Remote Function Call)는 CPI-C·TCP/IP 기반의 SAP 인터페이스 프로토콜로, 원격(또는 동일) 시스템의 사전정의된 함수를 호출·실행하고 통신·파라미터전달·오류처리를 관리합니다. 짚어둘 점 둘.

  • RFC는 인터페이스를 기술하는 말이지 프로그래밍 언어가 아닙니다. 비SAP 시스템의 함수도 호출할 수 있습니다
  • 양방향(bidirectional)입니다 — 외부 프로그램이 SAP의 함수를 RFC로 호출하는 것도 성립합니다

함수모듈은 Function Builder(SE37)에서 만들고 import/export 파라미터를 정의합니다. 호출 문법은 다음과 같습니다.

CALL FUNCTION 'Z_GET_STOCK'
  DESTINATION lv_dest          " SM59 에 정의된 RFC Destination
  EXPORTING   iv_matnr = lv_matnr
              iv_werks = 'STOR'
  IMPORTING   ev_labst = lv_labst
  EXCEPTIONS  communication_failure = 1  MESSAGE lv_msg
              system_failure        = 2  MESSAGE lv_msg.
EXCEPTIONS 를 빼면 조용히 죽는다

communication_failure · system_failure를 받지 않으면 상대 시스템이 내려가 있어도 프로그램은 아무 말 없이 다음 줄로 넘어갑니다. "어제 데이터가 안 넘어왔습니다"의 절반은 여기서 나옵니다. RFC 호출은 반드시 예외를 받고 로그를 남깁니다.

RFC Destination (SM59) — 시스템이 아니라 클라이언트를 가리킨다

RFC 호출에는 두 시스템 간 기술적 연결인 RFC Destination이 필요합니다(SM59, 메뉴 Tools → Administration → Administration → Network → RFC Destinations).

성질내용
가리키는 대상SAP 시스템 전체가 아니라 특정 클라이언트. 그래서 100번용과 200번용 Destination이 따로 필요하다
접근 범위소스 시스템의 모든 클라이언트에서 접근 가능 (권한이 있으면)
복수 정의동일 대상에 여러 Destination 가능 — 각기 다른 로그온 사용자를 지정할 수 있다
양방향양방향 RFC가 필요하면 대상 시스템에도 동등한 두 번째 Destination이 있어야 한다
자격증명미리 지정하지 않으면 런타임에 로그온 데이터 입력을 요구한다
📖 참고 — Trusted RFC

신뢰관계(Trusted RFC)가 설정된 SAP 시스템 간에는 호출측 사용자가 양쪽에 정의되어 있으면 비밀번호 없이 호출됩니다. 편리한 만큼 신뢰관계 + 강한 권한 조합은 침투 경로가 되므로, 신뢰 대상 시스템과 S_RFCACL 값을 좁게 잡아야 합니다.

RFC 유형 — 무엇을 보장할 것인가로 고른다

확인 필요 — 그림 3은 강의 본문 밖의 보충이다

노션 원본(Unit 8 Lesson 1)은 RFC를 하나의 기술로만 설명하고 sRFC/aRFC/tRFC/qRFC 구분은 다루지 않습니다. 그림 3은 인터페이스 설계를 위해 보충한 내용이며, 실제 시스템(winerp01 / MEP)에서 SM58 · SMQ1 · SMQ2 화면과 bgRFC(SBGRFCMON) 사용 여부를 확인해 확정할 것. 릴리스에 따라 tRFC/qRFC가 bgRFC로 대체되어 있을 수 있습니다.

BOR과 BAPI

BAPI(Business Application Programming Interface)는 SAP 비즈니스 프로세스·데이터에 대한 내/외부 표준 접근 인터페이스입니다. Business Object Repository(BOR)에 SAP 비즈니스 오브젝트의 메서드로 정의되어 객체지향적 관점을 제공합니다.

핵심은 기술 레벨이 아니라 비즈니스 레벨에서 통합한다는 점입니다. 그래서 연결 안정성(릴리스가 올라가도 인터페이스가 유지됨)과 통신기술 독립성을 얻습니다.

SWO1Business Object Builder → Business Object Repository → BAPI
BAPIBAPI Explorer — 비즈니스 오브젝트별 BAPI 목록

ALE로 연결 가능한 SAP 시스템의 제약은 적습니다 — RFC/HTTP를 지원하고 포맷(IDoc/XML)을 해석할 수만 있으면 서로 다른 릴리스의 시스템도 연결됩니다.

AS Java의 타 시스템 연결 — Destination Service · JCo RFC Provider

AS Java가 EIS(Enterprise Information System — 다른 AS Java나 AS ABAP)에 붙는 방식은 두 갈래입니다: 애플리케이션이 직접 아웃바운드 연결을 열거나, Destination Service 같은 서비스가 연결을 수립하거나(서비스는 다른 서비스의 연결을 재사용할 수도 있습니다).

아웃바운드 — Destination Service

Destination Service는 EIS로의 HTTP·RFC 연결을 모두 관리합니다. AS ABAP 대상은 보통 RFC 타입, AS Java 대상은 보통 HTTP 타입입니다. 생성·관리 위치는 NWA → Configuration → Infrastructure → Destinations.

타입지정하는 것
HTTPURL로 EIS·서비스 결정. 대상이 AS ABAP이면 SID·언어·클라이언트를 Destination 데이터에 지정. 인증방식은 user/password · X.509 인증서 · assertion ticket · logon ticket · user mapping
RFCTarget Host · System Number · SID · 게이트웨이 데이터. Gateway Host는 보통 대상서버와 동일, Gateway Service는 33<인스턴스번호> 또는 sapgw<인스턴스번호>

RFC 연결은 항상 게이트웨이를 통과합니다(대부분 AS ABAP 인스턴스의 게이트웨이). AS Java 7.10부터는 AS Java Central Services Instance의 RFC 게이트웨이도 쓸 수 있습니다.

Hint — 인증방식

보안 지침상 user/password보다 assertion ticket 등 다른 인증방식을 우선 검토합니다. RFC 트레이스를 켜면 인스턴스 OS 레벨 서버디렉터리에 jrfc<서버프로세스PID>_<Nr>.trc와 개발자트레이스 dev_jrfc.trc가 생성됩니다.

인바운드 — JCo RFC Provider

반대 방향, 즉 AS ABAP → AS Java 인바운드 RFC를 처리하는 서비스가 JCo RFC Provider입니다. 통신을 시작(Initiator)하는 쪽은 AS ABAP이고, AS Java가 데이터를 받으려면 사전에 게이트웨이와의 연결이 수립되어 있어야 합니다. 관리 위치는 NWA → Configuration → Infrastructure → JCo RFC Provider이며, 연결은 Program ID 아래 등록됩니다.

설정 위치해야 할 일
AS ABAP (SM59)연결타입 "T"의 RFC Destination 생성 → Registered Server Program으로 JCo RFC Provider의 Program ID 지정. 관례상 Destination명 = Program ID
AS Java (서버 구성)게이트웨이 데이터와 병렬연결 수(Server Count) 지정. Local JCo Servers 활성 시 서버프로세스 하나가 Server Count만큼 연결, 비활성 시 각 서버프로세스가 각각 Server Count만큼 연결
AS Java (Repository Configuration)"Use RFC Destination" 미체크면 이 탭에서 ABAP 시스템 데이터 직접 유지, 체크하면 Destination Service의 Destination 참조 (이 경우에도 게이트웨이에는 Program ID가 등록됨)
양쪽 게이트웨이 데이터가 어긋나면 연결이 안 붙는다

동일한 게이트웨이 데이터가 JCo RFC Provider(AS Java 측)와 RFC Destination(AS ABAP 측) 양쪽에 일치하게 유지되어야 합니다. "등록은 했는데 호출이 안 간다"의 대부분이 이 불일치입니다.

📌 개인 E2E 프로젝트와의 연결점 — 목표 3번 "웹페이지 → RFC로 SAP 호출"

이 LESSON이 목표 3번의 설계 근거 전부입니다. 정해야 할 것을 순서대로 적으면 이렇게 됩니다.

· 방향 — 웹페이지가 SAP를 부르는 인바운드입니다. 즉 외부 프로그램 → SAP 방향이고, RFC가 양방향이라는 성질을 쓰는 자리입니다. 반대로 SAP가 웹을 부를 일이 생기면 그때는 SM59의 별도 Destination이 필요합니다.
· RFC 유형 — 화면에서 재고·유통기한을 조회하는 용도라면 결과를 기다려야 하므로 sRFC(동기)가 맞습니다. 반면 전표를 만드는 호출이라면 중복 실행이 곧 회계 영향이므로 동기 호출에 그대로 태우지 않고 tRFC 계열(정확히 1회)이나 승인 대기 큐를 한 단계 둡니다 — 프로젝트 원칙인 "회계 영향 처리는 자동화하지 않는다"가 여기서 그대로 적용됩니다.
· 함수모듈 — SE37에서 Remote-Enabled Module로 만들고, 내부에서 전표는 직접 INSERT 하지 않고 BAPI를 호출합니다(그림 4의 "전기 함수모듈"과 같은 구조). 성공 시 BAPI_TRANSACTION_COMMIT까지 명시적으로 부릅니다.
· 계정 — 웹이 쓰는 SAP 계정은 System 유형으로, 권한은 그 FM에 필요한 오브젝트만. 플랜트는 GATE/STOR로 한정합니다. Dialog 계정을 웹에 심지 않습니다.
· Destination이 클라이언트를 가리킨다는 점 — 개발 클라이언트로 붙여두고 운영 이관 시 못 바꾸는 사고가 흔합니다. 클라이언트·Destination명을 코드에 하드코딩하지 않고 커스터마이징 테이블이나 변수로 뺍니다.

ALE/IDoc은 이 프로젝트 범위에는 넣지 않습니다(벤더·고객이 전부 가상이라 실제 파트너 연동이 없음). 다만 AL11 파일 기반 대량 처리 인터페이스(목표 2번)를 설계할 때 그림 4의 상태 코드로 추적하는 구조는 그대로 빌려옵니다 — CBO 테이블의 상태필드 W(대기) / P(처리완료) / H(보류)가 IDoc 상태 코드와 정확히 같은 발상입니다.

반드시 지킬 것

· 권한 요청에 SAP_ALL을 붙여 해결하지 않는다. 원인을 영원히 모르게 되고, 회수 시점도 아무도 기억하지 못한다.
· SU53·STAUTHTRACE 없이 추측으로 권한을 열지 않는다. 트랜잭션 코드만 넣어놓고 "열어줬다"고 답하면 다시 문의가 온다.
· 새 역할을 만들기 전에 SUIM으로 기존 역할을 먼저 찾는다. 역할 수가 늘수록 SoD 점검과 감사 비용이 같이 늘어난다.
· 인터페이스용 계정은 System 유형으로 만든다. 만료로 야간 배치가 통째로 죽는 사고를 미리 막는 유일한 방법이다.
· RFC 호출에 EXCEPTIONS를 반드시 받고 로그를 남긴다. 실패해도 조용히 넘어가는 인터페이스가 가장 고치기 어렵다.
· Destination명·클라이언트·회사코드를 프로그램에 하드코딩하지 않는다. 그 순간 운영 이관이 막힌다.
· UME 설정을 바꾸기 전에 Download Configuration ZIP을 받아둔다. 롤백용은 아니지만 무엇을 바꿨는지 대조할 유일한 근거다.
