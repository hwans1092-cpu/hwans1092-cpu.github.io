결론부터. SAP 안에서 일어나는 모든 일은 세 층으로 설명됩니다 — 회사를 시스템에 그려 넣은 엔터프라이즈 구조, 오래 변하지 않는 마스터 데이터, 그리고 매번 새로 생기는 트랜잭션 데이터·문서.

세 층의 관계도 한 줄입니다. 조직단위는 커스터마이징에서 정의되고, 마스터 데이터는 조직단위 레벨별로 유지되며, 문서는 생성될 때 항상 하나 이상의 조직단위에 할당되고 마스터 데이터로부터 값을 제안받습니다. "이 값은 어디서 왔나"라는 질문의 답이 전부 이 그림 안에 있습니다.

LESSON 1엔터프라이즈 구조 — 회사를 시스템에 그려 넣기

Unit 33-1Defining the Enterprise Structure Using the Example of a Bike Company

언제 이걸 알아야 하는가

"왜 이 자재는 이 플랜트에서 안 나옵니까", "왜 이 전표가 저 회사코드로 갔습니까" — 이런 문의는 프로그램 버그처럼 들리지만 대부분 조직단위 할당(assignment) 문제입니다.

엔터프라이즈 구조는 일상 업무가 아니라 시스템 설정(커스터마이징)의 일부입니다. 그래서 응용 화면을 아무리 뒤져도 답이 없고, IMG 쪽 할당 관계를 봐야 풀립니다. 이 레슨은 그 할당 관계에 어떤 이름들이 붙어 있는지를 세웁니다.

엔터프라이즈 구조란

기업의 비즈니스 프로세스·부문·조직 단위를 반영·관리하는 포괄적인 조직 프레임워크입니다. 답을 주는 질문이 이런 것들입니다 — 제품을 어디서 생산하는가? 원자재 구매 책임자는 누구인가? 판매 가격은 누가 계산하는가?

회사를 SAP에 모델링할 때 고려하는 것은 둘입니다. ① 부서가 일상 업무(자재 주문, 제품 판매)를 수행하는 애플리케이션, ② 각 애플리케이션과 조직 구조에 대한 비즈니스 프로세스 설정, 즉 커스터마이징. 엔터프라이즈 구조 정의는 ②에 속합니다.

확인 필요 — On-Premise 기준 설명이다

강의가 설명하는 엔터프라이즈 구조는 SAP S/4HANA On-Premise 기준입니다. 대부분 Cloud와 동일하고 사용 목적·필요성도 같지만, Cloud Public Edition에서는 설정 가능 범위와 설정 도구가 다릅니다. 실제 시스템(winerp01 / MEP)에서 IMG 경로를 열어 확인할 것.

구성요소 — 영역별로 묶어서

최상위는 Client입니다. SAP 시스템 내 최상위 계층 구조로, 마스터 레코드와 테이블을 포함하며 하나의 기업 그룹을 대표합니다.

헷갈리기 쉬운 셋만 다시 짚으면 — Distribution Channel은 "어떤 경로로 파는가"(온라인몰/도매/직판), Division은 "어떤 제품군을 파는가"(식품 사업부/의류 사업부), Storage Location은 한 공장 안의 창고 구역(냉동창고/상온창고)입니다.

LESSON 2조직단위 · 마스터 데이터 · 문서의 3층 관계

Unit 33-2Relating Enterprise Structures, Master Data, Transaction Data, and Documents

오브젝트 3종

SAP에서 비즈니스 데이터를 표현·조직하는 엔티티를 통틀어 오브젝트라고 부릅니다. 엔터프라이즈 구조도 그중 하나이고, 나머지 셋이 이것입니다.

오브젝트정의예시
마스터 데이터시간이 지나도 비교적 변하지 않는 핵심 기초 데이터. 비즈니스의 명사고객(이름·주소·연락처), 제품(제품명·설명·가격), 직원, 공급업체
트랜잭션 데이터일상 운영·거래로 생성되는, 자주 변하는 데이터. 비즈니스의 동사판매오더, 인보이스, 결제, 배송, 채용·퇴사
문서마스터·트랜잭션 데이터 맥락에서 비즈니스 운영 정보를 캡처·저장하는 구조화된 기록마스터 데이터 문서(고객 레코드, 제품 정보, 벤더 파일) / 트랜잭션 데이터 문서(판매오더 문서)

마스터 데이터는 왜 조직단위별로 갈리나

강의의 예시가 명확합니다. 자전거 회사는 4개 생산 플랜트에서 동일한 자전거를 생산합니다. 제품 마스터를 모든 플랜트에 걸쳐 중앙에서 유지할 수 있는가? 그런데 플랜트별로 다른 데이터(예: 입고 처리 시간)도 유지하고 싶다. 그래서 조직단위별로 차등화된 데이터 유지가 가능해야 합니다.

문서 흐름 — 값은 어디서 와서 어디로 가는가

판매오더 생성 같은 프로세스 단계의 데이터는 결과적으로 문서로 저장되고, 이 문서는 평가(리포팅)에도 쓰입니다. 예를 들어 특정 고객과의 매출 합계는 그 고객 관련 매출 문서들의 합으로 구성됩니다. 그리고 문서 생성 시 항상 하나 이상의 엔터프라이즈 구조에 할당됩니다.

확인 필요 — 총중량 수치

강의 설명은 15 KG/PC × 10 PC 공식이지만, 화면 캡처상의 총중량 수치는 소스 자료 확인이 필요합니다. 중요한 것은 수치가 아니라 "중량은 입력값이 아니라 마스터에서 계산된 값"이라는 점입니다.

🔰 초보자 설명 — 마스터 데이터 vs 트랜잭션 데이터

마스터 데이터는 메뉴판, 트랜잭션 데이터는 그날그날의 주문 영수증입니다. 메뉴판은 자주 안 바뀌지만 영수증은 주문할 때마다 새로 생깁니다.

이 프로젝트로 바꿔 말하면 — "냉동 닭가슴살 100g"이라는 상품 자체 정보(이름·중량·보관온도·원가)가 마스터, "9월 14일에 닭가슴살 100박스를 A업체에 팔았다"가 트랜잭션입니다.

📌 개인 E2E 프로젝트와의 연결점

실습의 Client / Plant / Storage Location 3단 구조가 이 프로젝트의 자재마스터 설계와 그대로 겹칩니다.

· Client 레벨 — CHKN RICE SHAK PROT PBAR 각 품목의 Product Type · Base Unit · 자재그룹. 배치관리 체크(MARA-XCHPF)도 이 레벨이라 한 번 켜면 전 플랜트에 걸린다
· Plant 레벨 — GATE와 STOR 각각의 회계 뷰. Price Control을 V(이동평균가)로 두는 것이 여기, MBEW-VERPR가 생기는 자리도 여기다
· Storage Location 레벨 — 온도군 × 정상·임박 6개. 실습의 101A/101B 자리에 1100/1900…이 들어간다

그림 3의 문서 흐름에 이 프로젝트의 CBO를 얹으면 자리가 분명해집니다. ZBATCH_ZONE은 문서가 아니라 마스터·재고를 보고 움직이고(MCHA-VFDAT 판정 후 311), ZGATE_INSPECT는 자재문서 두 건의 차이(101 vs 301)를 보며, ZPRICE_CHECK는 마스터 두 개의 차이(EINE-NETPR vs MBEW-VERPR)를 봅니다. 세 CBO가 각각 다른 층을 읽는다는 점을 설계서에 적어두면 테이블 설계 근거가 됩니다.

LESSON 3마스터 데이터 동기화 — MDI와 MDG

Unit 33-3Describing the Effects of the Central Objects on Different SAP Applications

왜 동기화가 문제가 되는가

SAP는 E2E 운영을 위해 여러 솔루션을 통합합니다 — Recruit to Retire에는 SAP SuccessFactors, Procure to Pay에는 SAP Ariba. 그런데 S/4HANA의 핵심 오브젝트(엔터프라이즈 구조 · 마스터 데이터 · 트랜잭션 데이터 · 문서)는 다른 솔루션에도 그대로 중요합니다. 그래서 데이터는 여러 솔루션에 걸쳐 제대로 통합·동기화되어야 합니다.

약어풀이역할
MDIMaster Data Integration여러 소스의 데이터를 통합해 단일하고 신뢰할 수 있는 뷰 제공
MDGMaster Data Governance데이터 품질·보안·컴플라이언스 감독

둘은 부서·시스템 간 데이터의 일관성·정확성·책임성을 보장하기 때문에 E2E 프로세스 운영에 필수입니다. 함께 작동해 데이터 사일로·오류·중복을 줄이고 의사결정과 효율성을 개선합니다.

🔰 초보자 설명 — MDI와 MDG의 차이

여러 시스템(SAP 본체, 인사 시스템, 구매 시스템)을 같이 쓰면 "같은 고객"이나 "같은 상품"인데 시스템마다 이름·코드가 다르게 저장되는 문제가 생깁니다.

· MDI = 흩어진 같은 데이터를 하나의 진짜 정답으로 합쳐서 보여주는 것 — "정보를 하나로 모으는 것"
· MDG = 그 데이터를 누가, 어떻게 수정할 수 있는지 규칙을 정하고 품질을 관리하는 것 — "정보를 깨끗하고 정확하게 유지하는 규칙"

📌 개인 E2E 프로젝트와의 연결점

이 프로젝트는 단일 S/4HANA 시스템 안에서 SD-MM-FI가 도는 구조라 별도 MDI/MDG 솔루션은 필요 없습니다. 하지만 개념은 그대로 적용됩니다 — 자재마스터가 SD(판매)와 MM(구매) 양쪽에서 동일하게 참조되어야 재고 수량·평가가 어긋나지 않습니다.

더 직접적인 연결은 목표 3번, 웹페이지 → RFC 호출입니다. 외부에서 SAP를 호출하는 순간 이 프로젝트도 "두 시스템"이 되고, MDG가 말하는 "누가 어떻게 수정할 수 있는지"가 곧 RFC FM의 권한 체크 문제가 됩니다.

인터페이스 설계서에 미리 고정해 둘 것 — ① RFC FM에서 AUTHORITY-CHECK를 어느 오브젝트로 걸 것인가(M_MSEG_WMB 계열 · V_VBAK_VKO 계열), ② 외부에서 넘어온 조직단위(회사코드·플랜트)를 그대로 믿지 않고 서버에서 재검증할 것, ③ 마스터를 외부에서 변경하는 FM은 만들지 않을 것(조회와 트랜잭션 생성만).

반드시 지킬 것

· 조직단위 문의를 응용 화면에서 풀려고 하지 않는다. 답은 커스터마이징의 할당 관계에 있다.
· 이 레슨의 구조 설명은 On-Premise 기준이다. Cloud Public Edition의 설정 범위는 다르므로 실제 시스템에서 확인한다.
· Segment와 Valuation Level은 선택 축이다. 계층 트리에 억지로 끼워 넣어 설명하지 않는다.
· 실습 캡처의 수치(총중량, Sales Order #53 등)는 강의 환경 값이다. 개념만 가져오고 수치는 인용하지 않는다.
· 배치관리 체크는 Client 레벨이다. "이 플랜트만 배치관리"는 자재마스터 기본 설정으로는 안 된다는 뜻이므로, 설계 시 이 제약을 먼저 확인한다.
