대외 연계 대량 데이터 처리 아키텍처

AL11 파일 Staging + 비동기 병렬 분할 처리 — 실무 표준 4단계 패턴
선행 문서: ABAP 병렬처리 표준편(aRFC 문법·라이프사이클·LUW) · ZCSR00630 코드 워크스루

결론부터. 수십만~수백만 건을 대외 시스템과 연동하는 실무 환경에서 "파일 수신(AL11) 및 Staging"과 "비동기 병렬 분할 처리(배치)"를 분리하는 것은 매우 흔한 전형적 아키텍처입니다.

이유는 단순합니다. 외부에서 넘어오는 대용량 데이터를 동기식(Synchronous)으로 직접 처리하면 타임아웃(TIME_OUT)이나 프로세스 락 경합이 반드시 터지기 때문입니다. 수신과 처리를 시간축에서 떼어놓으면 두 문제가 동시에 해결됩니다.

목차

  1. 동기 직접 처리가 실패하는 3가지 지점
  2. 전체 아키텍처 4단계
  3. STEP 1 — 파일 수신과 인터페이스 계약
  4. STEP 2 — Master Job: 디렉토리 감시와 파일 잠금
  5. STEP 3 — 파일 읽기: OPEN DATASET과 인코딩
  6. STEP 4 — 청킹 전략: 행 수가 아니라 락 키
  7. STEP 5 — 병렬 디스패치와 결과 취합
  8. STEP 6 — 파일 후처리와 로그 설계
  9. 재처리·멱등성 — Staging 상태머신
  10. 실패 시나리오와 체크리스트

LESSON 1동기 직접 처리가 실패하는 3가지 지점

외부 시스템이 sRFC로 데이터를 넘기고 SAP이 그 자리에서 전표를 전기하는 구조. 건수가 적을 땐 잘 돌지만 대량이 되면 정확히 세 군데에서 무너집니다.

터지는 지점증상과 원인
① 게이트웨이
타임아웃		 호출자가 결과를 기다리는 동안 gw/keepalive, rdisp/max_wprun_time이 먼저 끊습니다. SAP은 처리를 계속하고 있는데 외부 시스템은 이미 실패로 판정합니다 → 중복 재전송 사고
② 락 경합 여러 인터페이스 세션이 동시에 같은 마스터(동일 계정·자재·공급업체)를 잡으면 FOREIGN_LOCK. 동기 구조에서는 재시도할 여유가 없어 그대로 롤백되고 데이터가 사라집니다
③ 데이터 유실 네트워크 단절이나 덤프 발생 시 원본이 어디에도 남지 않습니다. 외부 시스템에 재전송을 요청해야 하는데, 그쪽 로그가 이미 지워졌다면 복구 불가
파일 Staging이 세 문제를 한 번에 푸는 방식
  • ① 파일 수신은 즉시 끝나는 I/O입니다. 무거운 로직은 배치로 넘기므로 타임아웃 자체가 성립하지 않습니다.
  • ② 처리 시점을 SAP이 통제하므로, 락이 겹치지 않도록 데이터를 재배열한 뒤 돌릴 수 있습니다.
  • ③ AL11에 원본 파일이 남습니다. 몇 번이든 재처리 가능한 Fallback이 확보됩니다.

여기에 부수적으로 부하 분산이 따라옵니다. 피크 타임에 트래픽이 몰려 온라인 사용자 성능이 떨어지는 대신, 배치 스케줄러로 야간·유휴 시간대에 프로세스 수를 제한해가며 돌릴 수 있습니다.

LESSON 2전체 아키텍처 4단계

각 단계 한 줄 요약

  1. 파일 수신 (Staging) — 외부가 RFC 또는 SFTP로 SAP 파일시스템(AL11)에 원본을 적재. 파일로 먼저 떨어뜨려 두면 네트워크 단절·트랜잭션 충돌 시에도 데이터 유실 없이 재처리 가능합니다.
  2. Master Job — 주기 Background Job이 디렉토리를 감시(Polling)해 미처리 파일을 OPEN DATASET으로 읽습니다.
  3. 청크 분할 + 병렬 실행 — 적정 단위로 쪼개 CALL FUNCTION … STARTING NEW TASK … DESTINATION IN GROUP으로 분기합니다.
  4. 결과 취합 + 후속 조치 — 콜백에서 결과를 모으고, 처리가 끝난 파일은 archive 디렉토리로 이동하거나 삭제합니다.

LESSON 3STEP 1 — 파일 수신과 인터페이스 계약

이 단계에서 개발 이전에 문서로 합의해야 할 것들이 있습니다. 여기서 대충 넘어가면 운영 중에 반드시 사고가 납니다.

합의 항목실무 권장
파일명 규칙 <인터페이스ID>_<YYYYMMDDHHMMSS>_<일련번호>.csv
타임스탬프가 있어야 순서 보장과 중복 판정이 가능합니다
완료 마커 본 파일 전송이 끝난 뒤 .ok 또는 .done 빈 파일을 하나 더 만들게 합니다.
이게 없으면 전송 중인 파일을 배치가 읽어 반쪽 데이터를 처리합니다 — 실무에서 가장 흔한 사고
인코딩 UTF-8 고정 권장. BOM 유무까지 명시. 한글이 있으면 반드시 문서에 박아둘 것
구분자·개행 구분자(| 권장, 콤마는 데이터에 섞임), 개행(CRLF vs LF), 텍스트 인용부호 처리
헤더 라인 있는지 없는지. 있다면 컬럼 순서 변경 시 통보 절차
건수 트레일러 마지막 줄에 총 건수를 넣게 하면 파일이 잘렸는지 즉시 검증됩니다
디렉토리 in/ · work/ · archive/ · error/ 4개를 미리 만들어 둡니다
완료 마커가 없으면

10MB 파일을 SFTP로 밀어넣는 중에 Master Job이 깨어나면, 그 시점까지 쓰인 만큼만 읽고 "정상 처리 완료"로 판정합니다. 나머지 데이터는 영영 처리되지 않고, 파일은 archive로 옮겨져 흔적도 안 남습니다.

대안: 외부가 .tmp로 쓰고 완료 시 원자적 rename하도록 합의. 마커 파일보다 깔끔합니다.

LESSON 4STEP 2 — Master Job: 디렉토리 감시와 파일 잠금

디렉토리 목록 조회

DATA: lt_dir  TYPE STANDARD TABLE OF eps2fili,
      ls_dir  LIKE LINE OF lt_dir,
      lv_cnt  TYPE epsf-epsfilsiz.

CALL FUNCTION 'EPS2_GET_DIRECTORY_LISTING'
  EXPORTING  iv_dir_name   = '/interface/in'
             file_mask     = 'ORD_*.csv'
  IMPORTING  file_counter  = lv_cnt
  TABLES     dir_list      = lt_dir
  EXCEPTIONS invalid_eps_subdir     = 1
             sapgparam_failed       = 2
             build_directory_failed = 3
             no_authorization       = 4
             read_directory_failed  = 5
             too_many_read_errors   = 6
             empty_directory_list   = 7
             OTHERS                 = 8.

IF sy-subrc = 7.        " 처리할 파일 없음 — 정상 종료
  MESSAGE s001 WITH '대상 파일 없음'. RETURN.
ENDIF.

SORT lt_dir BY name.   " ★ 파일명 타임스탬프 순 = 처리 순서
디렉토리 물리경로 vs 논리경로

경로를 소스에 하드코딩하지 말고 논리 파일명(FILE 트랜잭션)으로 관리하세요. DEV/QAS/PRD의 마운트 경로가 다른 경우가 대부분입니다.

CALL FUNCTION 'FILE_GET_NAME'
  EXPORTING logical_filename = 'ZIF_ORDER_IN'
  IMPORTING file_name        = lv_path.

파일 잠금 — 이중 실행 방지

Master Job이 30분 주기인데 처리가 40분 걸리면, 두 번째 잡이 같은 파일을 다시 집습니다. 두 가지를 겹쳐 막습니다.

  1. 잡 레벨 세마포어 — 프로그램 자체의 동시 실행 차단 
    CALL FUNCTION 'ENQUEUE_E_TRDIR'
  EXPORTING  mode_trdir = 'E'
             name       = sy-cprog
             _scope     = '1'
  EXCEPTIONS foreign_lock = 1 OTHERS = 2.
IF sy-subrc <> 0.
  MESSAGE s001 WITH '이전 배치가 아직 실행 중입니다'. RETURN.
ENDIF.
  2. 파일 레벨 이동 — 읽기 전에 in/ → work/로 옮겨버립니다. 옮겨진 파일은 다음 잡의 Polling 대상에서 자동으로 빠집니다. 잡이 죽어도 work/에 남아 있으므로 수동 복구가 쉽습니다.
ABAP에는 파일 MOVE 문장이 없습니다

OPEN DATASET으로 읽어서 새 경로에 쓰고 DELETE DATASET으로 원본을 지우는 것이 표준 방식입니다. OS 명령(SXPG_COMMAND_EXECUTE)은 Basis 승인과 권한 설정이 필요하고 감사 대상이 되므로, 되도록 ABAP 안에서 해결하세요.

LESSON 5STEP 3 — 파일 읽기: OPEN DATASET과 인코딩

인코딩 모드 3종 구분

구문언제
IN TEXT MODE ENCODING UTF-8 기본 선택. 외부와 UTF-8로 합의했다면 이것. 유니코드 시스템 표준
IN LEGACY TEXT MODE CODE PAGE '8300' 레거시가 EUC-KR/CP949로 보낼 때. 8300이 한국어 코드페이지입니다
IN BINARY MODE 인코딩을 직접 판정해야 하거나 첨부파일을 그대로 넘길 때
한글이 깨지는 전형적 원인 3가지
  • 파일은 UTF-8인데 IN LEGACY TEXT MODE로 읽음 (또는 그 반대)
  • UTF-8 BOM(EF BB BF)이 첫 필드 앞에 붙어 첫 컬럼 비교가 전부 실패
  • 내부테이블 필드 길이가 바이트 기준으로 부족 — 한글 1자가 UTF-8에서 3바이트

스트리밍 읽기 — 메모리를 지키는 방식

수백만 건 파일을 APPEND로 전부 내부테이블에 올리면 TSV_TNEW_PAGE_ALLOC_FAILED가 납니다. 라인 단위로 읽어 버퍼를 채우고, 청크가 차면 즉시 넘긴 뒤 버퍼를 비웁니다.

DATA: lv_line   TYPE string,
      lt_buffer TYPE tt_record,
      ls_rec    TYPE ty_record,
      lv_cnt    TYPE i,
      lv_total  TYPE i.

OPEN DATASET lv_path FOR INPUT
     IN TEXT MODE ENCODING UTF-8
     MESSAGE lv_msg.
IF sy-subrc <> 0.
  " 권한·경로 오류 → error 처리 후 종료
  RETURN.
ENDIF.

DO.
  READ DATASET lv_path INTO lv_line.
  IF sy-subrc <> 0. EXIT. ENDIF.   " EOF

  lv_total = lv_total + 1.
  IF lv_total = 1 AND p_header = 'X'.
    CONTINUE.                          " 헤더 라인 skip
  ENDIF.

  " BOM 제거 (첫 데이터 라인)
  REPLACE FIRST OCCURRENCE OF cl_abap_char_utilities=>byte_order_mark_utf8
          IN lv_line WITH space.

  SPLIT lv_line AT '|' INTO ls_rec-kunnr ls_rec-matnr
                             ls_rec-menge ls_rec-datum.
  APPEND ls_rec TO lt_buffer.
  lv_cnt = lv_cnt + 1.

  IF lv_cnt >= p_chunk.                " 청크가 찼다
    PERFORM dispatch USING lt_buffer.    " LESSON 7
    CLEAR: lt_buffer, lv_cnt.           " ★ 버퍼 비우기
  ENDIF.

ENDDO.

IF lt_buffer IS NOT INITIAL.            " 마지막 잔여분
  PERFORM dispatch USING lt_buffer.
ENDIF.

CLOSE DATASET lv_path.
이 루프에 숨은 함정 하나

PERFORM dispatch 안에서 aRFC를 던지는 순간 암묵적 DB COMMIT이 발생합니다(표준편 LESSON 3). OPEN DATASET 자체는 DB 커서가 아니라 괜찮지만, 같은 루프 안에서 SELECT … ENDSELECT를 돌리고 있었다면 런타임 오류가 납니다.

→ DB 조회가 필요하면 청크를 다 모은 뒤 FOR ALL ENTRIES로 한 번에 하거나, 아예 태스크 쪽에서 조회하도록 넘기세요.

LESSON 6STEP 4 — 청킹 전략: 행 수가 아니라 락 키

이 문서에서 가장 중요한 장입니다. 병렬처리 실패의 절대다수가 여기서 나옵니다.

단순 행 수 분할이 만드는 사고

파일을 5,000줄씩 기계적으로 자르면, 같은 고객·같은 자재·같은 전표의 행이 서로 다른 청크로 흩어집니다. 그 청크들이 동시에 돌면서 같은 객체에 ENQUEUE를 걸려고 하면 FOREIGN_LOCK이 나고, 그때마다 롤백이 발생합니다.

병렬도를 올릴수록 충돌 확률이 올라가므로, 병렬을 늘렸는데 오히려 느려지고 실패 건만 쌓이는 현상이 나타납니다.

키 그룹핑 청킹 구현

" ① 비즈니스 키로 정렬 — 같은 키가 반드시 붙어 있게
SORT lt_all BY bukrs kunnr.

DATA: lv_prev_key TYPE ty_key,
      lv_cnt      TYPE i.

LOOP AT lt_all INTO ls_rec.

  ls_key-bukrs = ls_rec-bukrs.
  ls_key-kunnr = ls_rec-kunnr.

  " ② 키가 바뀌는 경계에서만 자른다 (같은 키를 절대 쪼개지 않음)
  IF lv_cnt >= p_chunk AND ls_key <> lv_prev_key.
    PERFORM dispatch USING lt_buffer.
    CLEAR: lt_buffer, lv_cnt.
  ENDIF.

  APPEND ls_rec TO lt_buffer.
  lv_cnt      = lv_cnt + 1.
  lv_prev_key = ls_key.

ENDLOOP.

IF lt_buffer IS NOT INITIAL.
  PERFORM dispatch USING lt_buffer.
ENDIF.

p_chunk는 하한선으로 동작합니다. 키 경계를 만날 때까지 조금 넘칠 수 있는데, 그게 정상이고 의도된 동작입니다.

청크 크기는 얼마가 적당한가

상황권장 크기
BAPI 전표 전기 (무거움)200 ~ 500건. 건당 커밋이 있어 처리 시간이 길다
CBO 테이블 단순 적재2,000 ~ 5,000건. MODIFY … FROM TABLE 한 방이면 커도 괜찮다
마스터 갱신 (중간)500 ~ 1,000건
청크 수 ≫ 병렬도

청크 크기를 전체건수 ÷ 병렬도로 잡으면 태스크 하나가 딱 한 번 돌고 끝나 슬롯 재사용이 일어나지 않습니다. 데이터 편차가 있으면 늦은 태스크 하나가 전체를 잡아먹는 롱테일이 생깁니다.

→ 고정 크기로 잘게 잘라 청크 수가 병렬도의 5~10배 이상이 되게 하세요. 먼저 끝난 슬롯이 다음 청크를 집어가면서 편차가 자연히 흡수됩니다.

LESSON 7STEP 5 — 병렬 디스패치와 결과 취합

골격은 표준편 LESSON 5와 동일합니다. 여기서는 파일 처리 문맥에서 달라지는 부분만 짚습니다.

FORM dispatch USING pt_buffer TYPE tt_record.

  " 빈 슬롯이 생길 때까지 대기 = 콜백에게 실행 기회를 준다
  WAIT FOR ASYNCHRONOUS TASKS
       UNTIL gv_running < gv_max
       UP TO 600 SECONDS.

  gv_chunk_no = gv_chunk_no + 1.
  lv_task     = |ZIF_{ gv_ifid }_{ gv_chunk_no }|.

  " ★ 청크 원장을 먼저 남긴다 — 태스크가 통째로 죽어도 추적 가능
  APPEND VALUE #( ifid    = gv_ifid
                    filename = gv_file
                    chunk_no = gv_chunk_no
                    cnt      = lines( pt_buffer )
                    status   = 'S' )      " S = Sent
         TO gt_chunklog.

  DO 10 TIMES.
    CALL FUNCTION 'Z_IF_PROCESS_CHUNK'
      STARTING NEW TASK    lv_task
      DESTINATION IN GROUP p_group
      PERFORMING collect ON END OF TASK
      EXPORTING  iv_ifid     = gv_ifid
                 iv_filename = gv_file
                 iv_chunk_no = gv_chunk_no
      TABLES     it_data     = pt_buffer
      EXCEPTIONS communication_failure = 1
                 system_failure        = 2
                 resource_failure      = 3.

    CASE sy-subrc.
      WHEN 0.
        gv_running = gv_running + 1.
        EXIT.

      WHEN 3.          " 자원 부족 → 일시적 상황. 재시도한다
        WAIT FOR ASYNCHRONOUS TASKS
             UNTIL gv_running < gv_max
             UP TO 5 SECONDS.

      WHEN OTHERS.    " 통신/시스템 오류 → 청크를 실패로 확정
        PERFORM mark_chunk_failed USING gv_chunk_no.
        EXIT.
    ENDCASE.
  ENDDO.

ENDFORM.
보정 RESOURCE_FAILURE 재시도에 WAIT UP TO를 쓰면 안 됩니다

흔히 WAIT UP TO 1 SECONDS 후 재시도하라고 소개되는데, WAIT UP TO는 콜백을 실행하지 않는 단순 sleep입니다(항상 sy-subrc = 0). 1초를 자고 깨어나도 끝난 태스크가 회수되지 않아 슬롯은 그대로이고, 자원 상황도 그대로입니다.

→ WAIT FOR ASYNCHRONOUS TASKS UNTIL <조건> UP TO n SECONDS를 쓰면 대기하는 동안 콜백이 실행되어 실제로 슬롯이 비고, 조건이 충족되는 즉시 깨어납니다. 재시도 성공률이 완전히 달라집니다.

콜백 — 청크 단위 상태 확정

FORM collect USING p_task TYPE clike.

  DATA: lv_chunk TYPE i, lv_ok TYPE i, lv_err TYPE i,
        lt_err TYPE tt_error, lv_msg TYPE char200.

  RECEIVE RESULTS FROM FUNCTION 'Z_IF_PROCESS_CHUNK'
    IMPORTING  ev_chunk_no = lv_chunk
               ev_ok_cnt   = lv_ok
               ev_err_cnt  = lv_err
    TABLES     et_error    = lt_err
    EXCEPTIONS communication_failure = 1 MESSAGE lv_msg
               system_failure        = 2 MESSAGE lv_msg
               resource_failure      = 3.

  gv_running = gv_running - 1.        " ★ 무조건 먼저 감소

  IF sy-subrc <> 0.
    " 태스크가 죽었다 → 청크 전체를 재처리 대상으로
    PERFORM mark_chunk_failed USING p_task lv_msg.
    RETURN.
  ENDIF.

  READ TABLE gt_chunklog ASSIGNING FIELD-SYMBOL(<ls>)
       WITH KEY chunk_no = lv_chunk.
  IF sy-subrc = 0.                  " ★ subrc 확인 후 수정
    <ls>-ok_cnt  = lv_ok.
    <ls>-err_cnt = lv_err.
    <ls>-status  = COND #( WHEN lv_err = 0 THEN 'C'   " Completed
                            ELSE 'P' ).                " Partial
  ENDIF.

  APPEND LINES OF lt_err TO gt_error.
  gv_total_ok  = gv_total_ok  + lv_ok.
  gv_total_err = gv_total_err + lv_err.

ENDFORM.
태스크 FM에 청크 번호를 넘기고 되받는 이유

콜백은 taskname만 받습니다. 태스크 이름에서 번호를 파싱해도 되지만, FM 인터페이스로 명시적으로 주고받는 편이 훨씬 안전합니다. 어느 청크가 실패했는지가 곧 재처리의 단위이기 때문입니다.

     UNTIL gv_running = 0

CASE sy-subrc.

파일 이동 구현 (MOVE 문장이 없으므로)

FORM move_file USING p_from TYPE string p_to_dir TYPE string.

  DATA: lv_to TYPE string, lv_line TYPE string.

  " 타임스탬프를 붙여 덮어쓰기 방지
  lv_to = |{ p_to_dir }/{ gv_fname }.{ sy-datum }{ sy-uzeit }|.

  OPEN DATASET p_from FOR INPUT  IN TEXT MODE ENCODING UTF-8.
  OPEN DATASET lv_to  FOR OUTPUT IN TEXT MODE ENCODING UTF-8.

  DO.
    READ DATASET p_from INTO lv_line.
    IF sy-subrc <> 0. EXIT. ENDIF.
    TRANSFER lv_line TO lv_to.
  ENDDO.

  CLOSE DATASET: p_from, lv_to.

  DELETE DATASET p_from.        " ★ 복사 성공 확인 후 삭제
  IF sy-subrc <> 0.
    " 삭제 실패 → 다음 배치가 중복 처리한다. 반드시 알람!
  ENDIF.

ENDFORM.

LESSON 9재처리·멱등성 — Staging 상태머신

병렬처리는 전체 롤백을 포기하는 구조입니다(표준편 LESSON 8). 그 대가를 치르는 방법이 멱등성 + 재처리이고, 파일 연동에서는 이것이 3중 방어선으로 구현됩니다.

3중 방어선

계층수단막는 사고
① 파일 ZIF_FILELOG에 파일명 존재 여부 확인 → 있으면 skip 외부 시스템의 중복 재전송
② 청크 ZIF_CHUNKLOG 상태가 C면 skip 배치 재실행 시 성공분 중복 처리
③ 건 대상 객체에 처리 플래그(예: ZZIF_FLAG = 'X') 또는 참조번호 저장 같은 데이터가 다른 파일로 다시 들어온 경우
③번이 진짜 방어선입니다

①②는 SAP 안에서의 중복만 막습니다. 외부가 어제 파일을 다른 이름으로 다시 보내면 뚫립니다. 최종 대상 데이터에 "이 건은 어느 인터페이스의 어느 참조번호로 처리됐다"를 남기는 것이 유일하게 확실한 방법입니다.

BAPI 전기라면 전표의 참조필드(XBLNR, BKTXT)에 인터페이스 참조번호를 넣고, 전기 전에 그 번호로 기존 전표 존재 여부를 조회하는 패턴이 표준입니다.

재처리 배치는 별도 프로그램으로

  • 실행 대상: ZIF_CHUNKLOG에서 status = 'E' 또는 'S'(디스패치는 됐는데 회수 안 된 것)
  • 데이터 출처: ZIF_ERRLOG에 저장해둔 원본 라인. 파일이 archive로 옮겨졌거나 지워졌어도 돌아갑니다
  • 재시도 횟수 상한(예: 3회)을 두고, 초과하면 'F'(Fatal)로 확정해 사람이 보게 합니다. 무한 재시도는 장애를 숨깁니다

설계 확정 전 체크리스트

  • □ 파일명 규칙 · 완료 마커 · 인코딩 · 구분자 · 트레일러를 문서로 합의했는가
  • □ in / work / archive / error 디렉토리와 논리 파일명을 만들었는가
  • □ 청킹 키가 실제 ENQUEUE 단위와 일치하는가
  • □ 청크 수가 병렬도의 5배 이상인가 (롱테일 방지)
  • □ Master Job의 동시 실행 차단(ENQUEUE 또는 work/ 이동)이 있는가
  • □ 스트리밍 읽기이며 청크 후 버퍼를 CLEAR하는가
  • □ RESOURCE_FAILURE가 재시도로 처리되는가
  • □ 모든 WAIT에 UP TO가 있고 join 후 sy-subrc를 로그하는가
  • □ 파일·청크·건 3단계 로그 테이블이 설계됐는가
  • □ 건 단위 멱등성 근거(플래그 또는 참조번호)가 있는가
  • □ 재처리 배치가 별도로 있고 재시도 상한이 있는가
  • □ DELETE DATASET 실패 시 알람이 나가는가

수신은 파일로 안전하게, 처리는 배치로 통제하며, 분할은 락 단위로, 실패는 재처리로 수렴시킨다.
