SAP 실행 환경 기초 — 워크프로세스와 RFC 지도

"워크프로세스가 뭐지?" "RFC는 또 뭐지?"에서 막히지 않기 위한 바닥 다지기
대상 시스템: winerp01 / MEP · 캡처 6장 예정

결론부터. ABAP 프로그램은 혼자 도는 게 아니라 서버에 있는 한정된 개수의 "일하는 손"(워크프로세스) 중 하나를 빌려서 돈다. 성능·병렬처리·배치·인터페이스 이야기는 전부 이 문장 하나에서 갈라져 나온다.

이 노트는 다른 노트를 읽기 전에 깔아두는 선행 노트다. 깊이 들어가지 않고, 용어가 무엇을 가리키는지와 어느 T-code로 확인하는지까지만 다룬다.

LESSON 1SAP는 어디서 도는가 — 시스템 · 인스턴스 · 서버

왜 알아야 하나. "다른 서버에서 돌았다"는 말이 나오는 순간 파일이 안 보이거나 모니터링 화면에 태스크가 안 뜬다. SAP 한 대인 줄 알았는데 실은 여러 대인 경우가 흔하다.

용어무엇인가비유
SAP 시스템SID로 식별되는 논리적 단위 하나. DB 하나를 공유한다 회사 하나
인스턴스
= 애플리케이션 서버		 실제로 프로그램을 실행하는 서버 프로세스 묶음. 한 시스템에 여러 개일 수 있다 지점 사무실 여러 곳
워크프로세스인스턴스 안에서 실제 작업을 수행하는 단위 각 사무실의 직원
세션(모드)사용자가 여는 화면 단위. /o로 새로 연다 직원에게 맡긴 일감

DB는 하나지만 파일시스템은 인스턴스마다 따로다. 이 차이가 나중에 크게 작용한다.

AL11 디렉토리는 시스템 공용이 아니다

AL11에서 보이는 경로는 지금 접속해 있는 인스턴스의 로컬 디스크다. 서버 A에 올린 파일이 서버 B에서는 안 보인다 — 공유 마운트(NFS 등)로 묶여 있지 않다면. 내 프로그램이 지금 어느 서버에서 돌고 있는지는 sy-host로 확인한다.

WRITE: / '시스템:', sy-sysid,   " SID
       / '서버:',   sy-host,    " 지금 이 코드가 도는 인스턴스
       / '클라이언트:', sy-mandt.

어떤 서버들이 있는지는 SM51(서버 목록)에서 본다. 한 줄만 보이면 단일 인스턴스, 여러 줄이면 분산 구성이다.

LESSON 2워크프로세스 — 일하는 손이 몇 개인가

핵심 한 문장. ABAP 프로그램 하나는 워크프로세스 하나를 점유한다. 서버 CPU에 코어가 32개여도, 내 프로그램 하나는 손 하나만 쓴다. 병렬처리란 손을 여러 개 빌리는 기술이고, 그래서 항상 "지금 빈 손이 몇 개냐"가 따라붙는다.

유형 6가지

유형하는 일언제 신경 쓰나
DIA사용자 화면의 다이얼로그 스텝 실행 병렬처리(aRFC)도 여기서 돈다 — 다 쓰면 다른 사람 화면이 멈춘다
BTC백그라운드 잡 실행SM36/SM37 배치
UPDV1(시간 임계) 업데이트LUW · 업데이트 태스크
UP2V2(비임계) 업데이트통계성 후처리
ENQSAP 락 오브젝트 설정·해제락 경합 조사
SPO스풀(출력) 처리인쇄
개수는 고정이 아니다

유형별 개수는 프로파일 파라미터 rdisp/wp_no_dia, rdisp/wp_no_btc 등으로 설정하지만, 운영 모드 전환으로 운영 중에도 바뀐다. (예: 야간에 DIA를 줄이고 BTC를 늘림) 그래서 파라미터 값이 아니라 SM50에 지금 실제로 몇 개가 있는지를 봐야 한다.

병렬처리는 DIA를 쓴다

"배치니까 BTC를 쓰겠지"가 아니다. CALL FUNCTION ... STARTING NEW TASK로 뜬 태스크는 DIA에서 돈다. 그래서 병렬 프로그램을 크게 돌리면 같은 서버에 접속한 다른 사용자의 화면이 느려지거나 멈춘다. 가용 DIA를 전부 점유하지 않는 것이 실무 매너다.

LESSON 3다이얼로그 스텝과 300초 제한

안 알면 뭐가 터지나. 프로그램이 잘 돌다가 갑자기 죽는데 로직에는 문제가 없다. TIME_OUT 덤프다. 코드가 아니라 시간 때문에 죽은 것이다.

다이얼로그 스텝이란

사용자가 Enter나 실행 버튼을 눌러서 화면이 다시 그려질 때까지의 한 구간이다. SAP은 이 구간 단위로 WP를 빌려주고 돌려받는다. 그래서 한 스텝이 너무 길면 강제로 끊는다.

파라미터기본의미
rdisp/max_wprun_time300초 DIA 워크프로세스에서 한 스텝이 돌 수 있는 최대 시간
배치(BTC)에는 이 제한이 없다

대량 처리를 SM36 배치 잡으로 돌리는 이유가 여기 있다. 그런데 병렬 태스크는 DIA에서 돈다. 배치 잡 안에서 병렬처리를 해도 태스크 하나하나는 300초 제한을 받는다.

그래서 병렬처리에서 "몇 건씩 나눌까"의 답은 한 덩어리가 300초 안에 끝나는 건수이지 보기 좋은 숫자가 아니다.

실행 시간을 재는 법

DATA: lv_start TYPE i, lv_end TYPE i, lv_sec TYPE p DECIMALS 3.

GET RUN TIME FIELD lv_start.   " 1회차 = 타이머 초기화, 값은 0
" ... 측정할 로직 ...
GET RUN TIME FIELD lv_end.     " 2회차 = 경과 마이크로초

lv_sec = ( lv_end − lv_start ) / 1000000.
WRITE: / '소요(초):', lv_sec.   " WRITE에 계산식은 못 쓴다

단위는 마이크로초(1초 = 1,000,000). 필드는 TYPE i여야 한다. SY-UZEIT 차이로 재면 초 단위라 소수점이 안 보이고, 자정을 넘기면 음수가 나온다.

LESSON 4RFC 지도 — 5종을 한 장에

RFC란. Remote Function Call — 다른 세션이나 다른 시스템의 함수를 불러 쓰는 방식이다. "원격"이라고 해서 꼭 다른 회사 서버일 필요는 없다. 같은 시스템의 다른 워크프로세스도 원격이다.

변형이 5가지나 되는 이유는 요구사항이 다르기 때문이다. 결과를 받아야 하는가 / 순서를 지켜야 하는가 / 지금 실행해야 하는가 세 질문으로 갈린다.

변형구문결과보장주 용도
sRFC 동기DESTINATION dest받음 —조회, 즉시 응답
aRFC 비동기STARTING NEW TASK콜백으로 받음 —병렬처리
tRFCIN BACKGROUND TASK못 받음 한 번만전송 보장 (구세대)
qRFCtRFC + 큐 이름 지정못 받음 한 번 + 순서순서 필요한 연계 (구세대)
bgRFC클래스 API못 받음 T=한 번 / Q=순서신규 개발 권장

RFC 함수 모듈의 제약 — 한 뿌리에서 나온다

원격 호출은 메모리 주소를 공유할 수 없다. 다른 워크프로세스, 경우에 따라 다른 서버에서 돌기 때문에 값을 직렬화해 복사해 보내는 수밖에 없다. 아래는 전부 여기서 파생된 규칙이다.

  • SE37 속성에서 원격 사용 가능 모듈로 지정돼 있어야 한다
  • 파라미터는 값 전달(pass by value)만 허용된다 — 테이블 파라미터는 암묵적으로 값 전달
  • 파라미터 타입은 DDIC 타입이어야 한다 (프로그램 로컬 구조 불가)
  • CHANGING 파라미터를 쓸 수 없다
SE37에서는 되는데 병렬에서만 안 되던 이유

원격 사용 가능 모듈은 자기 시스템 안에서는 일반 FM처럼도 호출된다. DESTINATION / STARTING NEW TASK / IN BACKGROUND TASK 없이 부르면 로컬 호출이다.

뒤집으면, 원격 플래그가 없는 FM도 SE37 단독 실행과 동기 호출은 멀쩡히 된다. STARTING NEW TASK를 붙이는 순간에만 CALL_FUNCTION_NOT_REMOTE로 터진다. "단독은 되는데 병렬만 안 된다"면 이걸 먼저 의심한다.

LESSON 5SM59와 RZ12는 다른 것이다

둘 다 "RFC 설정"이라 헷갈리는데, 가리키는 대상이 다르다.

SM59 — RFC DestinationRZ12 — RFC 서버그룹
무엇의 목록인가어디로 보낼지 (상대 시스템) 어느 서버들에 나눠 돌릴지 (내 시스템 안)
방향바깥 (다른 SAP, 외부 프로그램)안쪽 (같은 시스템의 인스턴스들)
ABAP 구문DESTINATION 'PRD100'DESTINATION IN GROUP grp
테이블RFCDESRZLLITAB (GRPTYPE = 'S')
타입—DDIC RZLLI_APCL

서버그룹이란 병렬 태스크를 던질 서버들의 명단이다. RZ12에서 만들고 이름을 붙인다. DESTINATION IN GROUP에 그 이름을 넘기면, SAP이 명단 안에서 여유 있는 서버를 자동으로 골라 태스크를 배정한다.

* 등록된 서버그룹 확인
SELECT SINGLE classname FROM rzllitab INTO lv_group
 WHERE grouptype EQ 'S'.
지정동작
IN GROUP grpRZ12 등록 그룹 안의 서버로만 분배
IN GROUP DEFAULT현재 시스템의 가용 서버 전부를 그룹으로 사용
변수가 INITIALDEFAULT와 동일하게 동작
프로그램 하나에 서버그룹 하나

한 프로그램 안에서는 RFC 서버그룹을 하나만 쓸 수 있다. 첫 aRFC 호출 시점에 그 그룹이 초기화되고, 이후 호출은 그 안에서 서버가 자동 선택된다.

aRFC는 외부 시스템으로 못 나간다

동기·비동기 호출은 상대 서버가 살아 있어야 성립한다. 그리고 비동기 호출은 SM59의 TCP/IP 연결(외부 프로그램)로는 쓸 수 없다. "보내두면 나중에 알아서" 방식이 필요하면 tRFC/bgRFC 쪽이다.

SM59에는 RFC 말고 연결 유형 G(HTTP Connection to External Server)도 있다. RFC가 아니라 HTTP로 밖에 나가는 통로이고, 화면 구성부터 다르다. 외부 REST API 호출과 SAP를 HTTP 서버로 여는 쪽은 → SAP HTTP 인터페이스 실습

LESSON 6LUW 맛보기 — 어디까지가 한 덩어리인가

LUW(Logical Unit of Work)는 전부 반영되거나 전부 취소되는 작업 한 덩어리다. "중간까지만 저장"이 없어야 하는 범위를 말한다.

경계일어나는 일
COMMIT WORK여기까지를 확정. 새 LUW 시작
ROLLBACK WORK이번 LUW를 통째로 취소
다이얼로그 스텝 끝암묵적 커밋이 일어날 수 있다
병렬처리에서 반드시 알아야 할 두 가지

① aRFC 호출은 호출하는 쪽에서 DB 커밋을 유발한다. 메인에서 DB를 건드리다가 중간에 aRFC를 던지면 그 시점에 커밋이 끊긴다.

② 원격 태스크는 독립 LUW다. 메인의 글로벌 변수에 접근할 수 없고, BAPI_TRANSACTION_COMMIT은 태스크 안에서 호출해야 한다. 따라서 "5개 태스크 중 3번만 실패"를 전체 롤백으로 되돌릴 수 없다. 보상 트랜잭션을 따로 설계해야 한다 — 이건 코딩이 아니라 업무 설계 영역이다.

번들링, 업데이트 태스크(V1/V2), ENQUEUE의 _SCOPE 같은 자세한 내용은 별도 노트에 있다.
