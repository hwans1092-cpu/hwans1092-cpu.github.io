SAP LUW 완전 정리 — 트랜잭션 · 번들링 · 락

"왜 SAP은 DB 커밋만으로 부족한가"에서 출발해 번들링 · Update Task · Enqueue까지
연관 문서: 병렬처리 확장편(aRFC 라이프사이클) · ABAP 디버깅 실무 노트(Update Debugging)

한 문장으로. LUW는 "모두 반영되거나, 하나도 반영되지 않거나" 둘 중 하나만 허용하는 작업 단위입니다.

DB는 이 보장을 COMMIT 한 번 단위로만 해 줍니다. 그런데 SAP의 업무 한 건은 화면을 여러 번 넘나들고, 그때마다 워크 프로세스가 바뀌면서 DB 커밋이 내 의사와 무관하게 일어납니다. 그래서 SAP은 DB LUW 위에 SAP LUW라는 한 겹을 더 쌓고, 실제 DB 변경을 마지막 한 순간까지 미뤄 두는(번들링) 기법을 제공합니다. 이 노트는 그 구조 전체를 그림으로 따라갑니다.

LESSON 1LUW란 무엇인가 — 원자성과 ACID

LUW(Logical Unit of Work, 논리적 작업 단위)는 "업무상 한 덩어리로 취급되어야 하는 데이터 변경의 묶음"입니다. 이름 그대로 논리적이라는 말이 핵심입니다. 기술적으로는 UPDATE 문 세 개일지 몰라도, 업무적으로는 "송금 한 건"이기 때문에 쪼개지면 안 된다는 뜻입니다.

ACID 중 LUW가 책임지는 부분

원칙누가 보장LUW 관점에서의 의미
Atomicity
원자성		LUW의 핵심 LUW 안의 모든 변경은 전부 반영되거나 전부 취소된다. SAP LUW가 직접 설계로 보장해야 하는 영역이며, 이 노트의 대부분이 여기에 해당한다.
Consistency
일관성		개발자 + DB LUW 전후로 데이터가 업무 규칙을 만족해야 한다. 제약조건은 DB가, 업무 규칙(예: 재고가 음수 불가)은 ABAP 로직이 지킨다.
Isolation
고립성		DB 락 + SAP 락 동시에 도는 LUW들이 서로의 중간 상태를 보지 못하게 한다. SAP은 DB 락만으로 부족해 Enqueue(Lesson 8)를 따로 둔다.
Durability
영속성		DBMS 커밋된 변경은 장애가 나도 살아남는다. DB의 트랜잭션 로그(리두 로그)가 책임진다.
시험·면접 포인트

"LUW는 ACID 중 무엇을 보장하나?" → 원자성(Atomicity). 고립성은 락이, 영속성은 DBMS가 담당한다고 나눠서 답하면 정확합니다.

LESSON 2DB LUW vs SAP LUW — 화면 전환의 함정

여기가 SAP LUW를 이해하는 가장 중요한 길목입니다. 두 개념의 정의만 외우면 시험은 통과하지만, 왜 SAP LUW라는 별도 개념이 필요한지를 모르면 실무에서 데이터를 깨뜨립니다.

정의부터

구분DB LUWSAP LUW (= ABAP LUW)
관점데이터베이스업무(비즈니스)
범위하나의 DB 커넥션에서 커밋과 커밋 사이업무 한 건 전체. 화면 여러 개 · 프로그램 여러 개에 걸칠 수 있음
시작직전 커밋/롤백 직후새 내부 세션(Internal Session) 시작 시, 또는 직전 COMMIT WORK 직후
종료DB COMMIT / ROLLBACKCOMMIT WORK / ROLLBACK WORK (명시적) 또는 암묵적 커밋(Lesson 7)
포함 관계SAP LUW 하나 안에 DB LUW가 여러 개 들어간다 (1 : N)

왜 DB LUW만으로는 안 되는가

SAP의 다이얼로그 프로그램은 화면 하나를 처리하고 사용자 입력을 기다리는 순간, 붙잡고 있던 워크 프로세스를 놓아줍니다(roll-out). 사용자가 다음 버튼을 누르면 전혀 다른 워크 프로세스가 그 작업을 이어받습니다. 워크 프로세스가 바뀐다는 것은 DB 커넥션이 바뀐다는 뜻이고, SAP은 이 전환 직전에 반드시 암묵적 DB 커밋을 넣습니다.

실무에서 가장 자주 보는 사고

화면 100의 PAI에서 MODIFY zheader를 해 버린 코드. 사용자가 화면 300에서 "취소"를 눌러도 헤더는 이미 DB에 들어가 있습니다. 다음 날 품목 없는 고아 헤더가 조회 리포트에 잡히고, 원인 추적에 반나절이 걸립니다.

LESSON 3무대 이해하기 — 디스패처와 워크 프로세스

LUW는 추상 개념이 아니라 SAP 인스턴스 안에서 실제로 돌아가는 프로세스들의 약속입니다. 등장인물을 먼저 알면 뒤의 모든 설명이 쉬워집니다.

구성요소LUW 관점에서 하는 일
Dispatcher들어온 요청을 유형에 맞는 WP에 배분한다. 화면 전환 때 다른 WP를 배정하는 주체이므로, 암묵적 커밋의 원인 제공자이기도 하다.
Dialog WPABAP 코드를 실행한다. 단, DB 변경을 직접 하지 않고 "변경 요청"만 등록하는 것이 SAP 표준 설계다.
Update WP (V1/V2)COMMIT WORK 시점에 등록된 변경 요청을 꺼내 실제 DB 변경을 수행한다. Lesson 5에서 자세히 본다.
Enqueue ServerSAP 전역 락을 판정·보관한다. 여러 DB LUW에 걸친 SAP LUW를 보호하는 유일한 수단이다.
Message Server인스턴스 간 통신·부하분산. Enqueue 요청의 전달 경로이기도 하다.
DBMS커밋된 데이터를 영속화하고, 행 단위 DB 락으로 DB LUW 내부의 동시성을 지킨다.

LESSON 4번들링 기법 5종 — 변경을 미루는 방법

Lesson 2의 결론은 "DB 변경을 마지막 한 순간까지 미뤄야 한다"였습니다. 그 미루는 기술을 SAP에서는 번들링(Bundling)이라고 부릅니다. 다섯 가지 수단이 있고, 각각 실행 주체와 시점이 다릅니다.

다섯 가지 번들링 수단

기법실행 주체특징과 용도
CALL FUNCTION ...
IN UPDATE TASK
가장 표준		 Update WP
(V1/V2)		 업데이트 함수 모듈을 등록한다. COMMIT WORK 시 Update WP가 별도 프로세스에서 실행. 대량 변경, 전표 생성 등 본 업무에 사용. 함수 속성이 Update Module이어야 한다.
PERFORM ... ON COMMIT 같은 WP
(Dialog)		 서브루틴을 커밋 시점으로 미룬다. 같은 워크 프로세스에서 동기 실행되므로 가볍고 빠르지만 파라미터를 넘길 수 없다(전역 변수 사용). 소규모 후처리에 적합.
PERFORM ... ON ROLLBACK 같은 WP 롤백 시에만 실행되는 정리 루틴. 임시 파일 삭제, 외부 자원 해제 등에 쓴다.
CALL FUNCTION ...
IN BACKGROUND TASK
tRFC		 원격 시스템 tRFC(Transactional RFC)로 원격 호출까지 LUW에 묶는다. COMMIT WORK 시 전송되며, 실패해도 SM58에 남아 재전송 가능. 인터페이스 연계의 기본기.
메모리에 모았다가
마지막에 한 번 저장		 같은 WP 내부 테이블에 계속 쌓아 두었다가 저장 시점에 INSERT ... FROM TABLE 한 번. 가장 단순하고 성능도 좋다. 단, 여러 프로그램에 걸친 경우에는 쓸 수 없어 ABAP Memory/SAP Memory를 병행해야 한다.
고르는 기준 — 한 줄 요약

업무 데이터 변경이면 IN UPDATE TASK, 가벼운 후처리면 PERFORM ON COMMIT, 원격 전송이면 IN BACKGROUND TASK. 한 프로그램 안에서 끝나는 단순 처리는 내부 테이블에 모았다가 마지막에 한 번이 제일 낫습니다.

LESSON 5Update Task 해부 — V1 · V2 · VBLOG

업데이트 함수 모듈은 종류가 나뉘고, 어느 종류로 만드느냐에 따라 실패했을 때의 결과가 완전히 달라집니다. SE37의 Attributes 탭에서 고르는 그 라디오 버튼이 여기 해당합니다.

업데이트 모듈 유형 (SE37 → Attributes)

유형재시작언제 쓰나
V1 — Update module
Start immediately		가능 기본값이자 대부분의 선택. 실패 시 SM13에 남아 재처리 가능. 업무 데이터는 여기에.
V1 — 즉시 시작, 재시작 불가
Immediate start, no restart		불가 중복 실행되면 안 되는 로직(번호 채번 등). 실패하면 그대로 폐기된다.
V2 — Start delayed가능 통계·집계처럼 늦어도 되고, 실패해도 본 업무에 지장이 없는 것.
Collective run (V3)가능 모아 두었다가 배치로 일괄 처리(RSM13005). LIS 갱신 등 대량 집계에 사용.

업데이트 실행 방식 3가지

" ① 비동기(기본) — Dialog WP 는 등록만 하고 즉시 반환, Update WP 가 처리
CALL FUNCTION 'Z_SD_ORDER_UPDATE' IN UPDATE TASK
  EXPORTING is_header = ls_header
  TABLES    it_item   = lt_item.
COMMIT WORK.                " 반환 즉시 다음 줄로 — 결과는 아직 모른다

" ② 동기 — Update WP 가 끝날 때까지 기다린다
COMMIT WORK AND WAIT.       " sy-subrc = 0 이면 업데이트까지 성공
IF sy-subrc <> 0.
  " 업데이트 실패를 이 자리에서 알 수 있다 → 화면에 에러 표시 가능
ENDIF.

" ③ 로컬 업데이트 — Update WP 를 안 쓰고 현재 WP 에서 바로 실행
SET UPDATE TASK LOCAL.        " COMMIT WORK 전에 선언
CALL FUNCTION 'Z_SD_ORDER_UPDATE' IN UPDATE TASK ...
COMMIT WORK.                " 같은 WP · 같은 DB LUW 에서 실행됨
방식결과를 아는가주 용도와 주의점
COMMIT WORK
비동기		모른다 응답이 빠르다. 대신 실패는 SM13/워크플로 알림으로만 알 수 있다. 대화형 화면의 기본.
COMMIT WORK AND WAIT
동기		안다 (sy-subrc) 결과를 즉시 확인해야 할 때. BAPI 호출 후, 배치 프로그램에서 주로 쓴다. 응답이 느려지므로 대량 루프에서는 신중히.
SET UPDATE TASK LOCAL
로컬		안다 Update WP를 거치지 않아 디버깅이 쉽다. 또한 Update WP 부족 상황을 피할 수 있다. 단 현재 WP가 붙잡히므로 장시간 처리에는 부적합.
디버깅 팁 — Update 모듈에 브레이크포인트가 안 걸릴 때

업데이트 함수는 다른 워크 프로세스에서 돌기 때문에 일반 BP로는 안 잡힙니다. 두 가지 방법이 있습니다.

  • 디버거 메뉴에서 Settings → Update Debugging 체크 (표준 프로그램 디버깅 시)
  • 테스트 프로그램이라면 SET UPDATE TASK LOCAL을 임시로 넣어 같은 WP에서 실행시킨 뒤 일반 BP로 추적

LESSON 6COMMIT WORK / ROLLBACK WORK 정밀 동작

두 문장이 "정확히 무엇을 하는지"를 순서대로 알아 두면, 예상 못 한 동작의 90%는 스스로 설명할 수 있습니다.

COMMIT WORK 가 하는 일 — 순서대로

순서동작
1PERFORM ... ON COMMIT으로 등록된 서브루틴을 등록 순서대로 실행한다 (같은 WP).
2V1 업데이트 모듈들을 Update WP로 넘긴다. AND WAIT이면 끝날 때까지 대기.
3tRFC(IN BACKGROUND TASK) 호출들을 전송 대기열에 올린다.
4현재 열린 모든 DB 커넥션에 실제 DB COMMIT을 건다 → 현재 DB LUW 종료.
5_SCOPE = 2로 잡힌 SAP 락을 Update WP에 인계하거나 해제한다 (Lesson 8).
6새 SAP LUW를 즉시 시작한다. 즉 COMMIT은 "끝"이 아니라 "구분선"이다.

ROLLBACK WORK 가 하는 일

  • 등록만 되어 있던 모든 업데이트 모듈 · ON COMMIT 서브루틴 · tRFC 호출을 삭제한다 (실행 자체를 안 한다).
  • PERFORM ... ON ROLLBACK으로 등록된 루틴을 실행한다.
  • 열린 DB 커넥션에 DB ROLLBACK을 건다 → 현재 DB LUW에서 이미 실행된 직접 SQL도 취소된다.
  • SAP 락을 해제하고 새 SAP LUW를 시작한다.
가장 흔한 오해

"ROLLBACK WORK 하면 화면 100에서 한 UPDATE도 취소되겠지" → 아닙니다. 화면 전환 시 암묵적 커밋으로 이미 다른 DB LUW가 종료됐기 때문에, 현재 DB LUW 밖의 변경은 되돌아오지 않습니다. 이것이 Lesson 4의 번들링을 쓰는 이유입니다.

✕ 이렇게 쓰면 안 된다
LOOP AT lt_order INTO ls_order.
  PERFORM post_document USING ls_order.
  COMMIT WORK.  " 루프 안 커밋
ENDLOOP.
  • 중간에 실패하면 앞부분만 반영된 상태로 남는다
  • 매 커밋마다 락이 풀려 다른 세션이 끼어든다
  • 롤백으로 복구가 불가능해 수작업 정정이 필요해진다
○ 이렇게 쓴다
LOOP AT lt_order INTO ls_order.
  PERFORM validate USING ls_order
                CHANGING lv_err.
  CHECK lv_err IS INITIAL.
  PERFORM collect USING ls_order.
ENDLOOP.
IF lv_err IS INITIAL.
  COMMIT WORK AND WAIT.
ELSE.
  ROLLBACK WORK.
ENDIF.
  • 검증을 먼저 끝내고 전부 또는 전무로 처리
  • 대량이라 한 번에 무리라면 업무 단위(전표 1건)로 끊어 커밋하고 처리 결과를 로그 테이블에 남긴다
대량 배치에서의 현실적인 타협

100만 건을 한 LUW로 묶으면 롤백 세그먼트가 터지고 락이 과도해집니다. 실무 기준은 "업무적으로 쪼갤 수 있는 최소 단위"로 LUW를 끊고, 건별 성공/실패를 로그 테이블에 남겨 재처리 가능하게 만드는 것입니다. 즉 원자성의 단위를 전표 1건으로 재정의하는 것이지, 루프 안에서 아무렇게나 커밋하는 것과는 다릅니다.

LESSON 7암묵적 커밋 — 나도 모르게 끊기는 지점

내가 COMMIT WORK를 쓰지 않았는데도 SAP LUW가 끊기는 지점들이 있습니다. 이 목록을 아느냐 모르느냐가 초급과 중급을 가릅니다.

상황암묵적 커밋비고
다이얼로그 단계 종료(화면 전환)발생WP roll-out 직전. 가장 빈번한 원인
CALL FUNCTION ... DESTINATION (sRFC)발생동기 원격 호출. tRFC/qRFC는 해당 없음

LESSON 8SAP 락(Enqueue)과 _SCOPE — LUW의 파트너

LUW가 "내 변경을 언제 반영할지"의 문제라면, 락은 "내가 작업하는 동안 남이 못 건드리게 하는" 문제입니다. 두 개념은 반드시 짝으로 이해해야 합니다.

_SCOPE 파라미터 — 락과 LUW를 잇는 다리

락 오브젝트(SE11에서 EZ*로 생성)를 만들면 ENQUEUE_EZxxxx / DEQUEUE_EZxxxx 함수가 자동 생성됩니다. 이때 _SCOPE는 "이 락을 누가 언제까지 책임질 것인가"를 정하는 파라미터로, 실무 사고의 상당수가 여기서 나옵니다.

CALL FUNCTION 'ENQUEUE_EZ_VBAK'
  EXPORTING
    mode_vbak      = 'E'       " E=배타적(누적불가) X=배타적·누적 S=공유
    vbeln          = lv_vbeln
    _scope         = '2'       " 기본값: COMMIT/ROLLBACK 시 자동 해제
    _wait          = 'X'       " 잠깐 기다렸다 재시도
  EXCEPTIONS
    foreign_lock   = 1                " 다른 사용자가 이미 점유 → sy-msgv1 에 사용자ID
    system_failure = 2
    OTHERS         = 3.

IF sy-subrc <> 0.
  MESSAGE e001(zsd) WITH lv_vbeln sy-msgv1.  " 누가 잠갔는지 알려 주는 것이 친절한 설계
ENDIF.

" ... 업무 처리 · 업데이트 함수 등록 ...

COMMIT WORK AND WAIT.   " _scope=2 이므로 여기서 락까지 정리된다

세션 A가 자재를 잠그고 고객을 요청, 세션 B가 고객을 잠그고 자재를 요청하면 서로 무한 대기합니다. DB 레벨 데드락은 DBMS가 한쪽을 강제 롤백(예: Oracle ORA-00060)하고 해당 프로그램은 ST22에 덤프로 남습니다. 예방책은 단순합니다 → 모든 프로그램이 락을 거는 순서를 통일한다(예: 항상 헤더 → 품목 → 파트너 순).

LESSON 9RFC · BAPI와 LUW

시스템 경계를 넘는 순간 LUW는 더 이상 하나로 보장되지 않습니다. 어떤 RFC를 쓰느냐에 따라 보장 수준이 달라집니다.

종류LUW 보장동작과 용도
sRFC
동기		암묵적 커밋 호출 즉시 원격 실행하고 결과를 기다린다. 호출 시점에 로컬 LUW가 끊긴다는 점이 핵심. 조회성 호출에 적합.
aRFC
비동기		없음 STARTING NEW TASK. 병렬처리용. 호출자와 완전히 별개의 LUW로 돈다. 결과는 콜백으로 받는다.
tRFC
트랜잭션		LUW에 포함 IN BACKGROUND TASK. COMMIT WORK 시점에 전송되고, 실패하면 SM58에 남아 재전송된다. 정확히 한 번(exactly once) 보장.
qRFC
큐		LUW + 순서 tRFC에 순서 보장을 더한 것. TRFC_SET_QUEUE_NAME으로 큐를 지정. 모니터는 SMQ1(아웃바운드) / SMQ2(인바운드).

BAPI 호출 시의 철칙

BAPI는 내부에 COMMIT WORK를 넣지 않는다는 것이 SAP의 설계 규약입니다. 여러 BAPI를 연달아 호출하면 모두 하나의 SAP LUW로 묶이고, 종료는 호출자가 명시적으로 해야 합니다.

CALL FUNCTION 'BAPI_SALESORDER_CREATEFROMDAT2'
  EXPORTING  order_header_in = ls_header
  IMPORTING  salesdocument   = lv_vbeln
  TABLES     return          = lt_return
             order_items_in  = lt_item.

" ① 반드시 RETURN 을 먼저 검사한다 — sy-subrc 로는 실패를 알 수 없다
READ TABLE lt_return TRANSPORTING NO FIELDS
     WITH KEY type = 'E'.
IF sy-subrc = 0.
  CALL FUNCTION 'BAPI_TRANSACTION_ROLLBACK'.   " 등록된 변경 전부 취소
  MESSAGE e002(zsd).
ELSE.
  CALL FUNCTION 'BAPI_TRANSACTION_COMMIT'      " = COMMIT WORK
    EXPORTING wait = 'X'.                     " = AND WAIT — 업데이트 완료까지 대기
ENDIF.
놓치기 쉬운 세 가지
  • RETURN 미검사. BAPI는 오류가 나도 sy-subrc = 0입니다. 반드시 lt_return의 TYPE = 'E'/'A'를 확인해야 합니다.
  • WAIT = 'X' 누락. 커밋 직후 방금 만든 전표를 다시 SELECT하면 아직 없습니다. 비동기 업데이트라 DB 반영 전이기 때문입니다.
  • 커밋 누락. BAPI만 부르고 끝내면 아무것도 저장되지 않습니다. 반대로 BAPI 사이에 COMMIT을 끼워 넣으면 뒤 BAPI 실패 시 앞 건이 남아 데이터가 깨집니다.

분산 트랜잭션에 대하여

SAP은 애플리케이션 레벨에서 2PC(2-Phase Commit)를 제공하지 않습니다. 시스템 A와 B에 걸친 "하나의 LUW"는 존재할 수 없다는 뜻입니다. 실무에서는 대신 이렇게 풉니다.

  • tRFC / qRFC로 "정확히 한 번" 전송을 보장하고, 수신 측에서 자체 LUW로 커밋한다.
  • 수신 측에 멱등성(idempotency)을 둔다 — 같은 참조번호가 이미 처리됐으면 무시.
  • 불일치는 대사(reconciliation) 배치로 주기적으로 잡아낸다.
  • ALE/IDoc은 위 구조를 표준화해 둔 것이며, 상태(WE02/WE05)로 재처리 지점을 관리한다.

LESSON 11모범 사례 · 체크리스트 · T-code

설계 원칙 6가지

  1. 다이얼로그에서 직접 SQL을 쓰지 않는다. 변경은 전부 번들링으로 등록하고 COMMIT WORK에서 한 번에 반영한다.
  2. 검증을 먼저, 변경을 나중에. 커밋 이후에 나오는 오류는 되돌리기 어렵다. 모든 유효성 검사는 커밋 전에 끝낸다.
  3. 루프 안에서 커밋하지 않는다. 불가피하면 업무 단위(전표 1건)로 끊고 건별 처리 로그를 남긴다.
  4. 락은 필요한 만큼만, 짧게. _SCOPE = 2를 기본으로 두어 커밋 시 자동 해제되게 하고, 락 획득 순서를 프로젝트 전체에서 통일한다.
  5. 암묵적 커밋 지점을 피해 간다. LUW 안에 sRFC·WAIT·대화형 MESSAGE를 넣지 않는다.
  6. 실패를 알 수 있게 만든다. 비동기 업데이트는 성공 여부를 사용자에게 알려 주지 않으므로, 중요 업무는 AND WAIT이나 별도 모니터링을 붙인다.

코드 리뷰 체크리스트

  • □ 화면 PAI에서 직접 INSERT/UPDATE/DELETE를 하고 있지 않은가
  • □ 업데이트 함수가 V1인지 V2인지 의도대로 설정돼 있는가
  • □ 커밋 직후 방금 저장한 데이터를 다시 읽는다면 AND WAIT이 붙어 있는가
  • □ LOOP 내부에 COMMIT WORK가 있지 않은가
  • □ ENQUEUE 실패(foreign_lock) 시 누가 잠갔는지 사용자에게 알려 주는가
  • □ _SCOPE = 1을 썼다면 모든 경로에서 DEQUEUE가 호출되는가 (예외 경로 포함)
  • □ BAPI 호출 후 RETURN 테이블의 E/A 메시지를 검사하는가
  • □ BAPI 사이에 불필요한 커밋이 끼어 있지 않은가
  • □ LUW 안에 sRFC · WAIT · MESSAGE TYPE 'I'가 들어 있지 않은가
  • □ 외부 시스템 연계는 tRFC/qRFC이며 수신 측 멱등성이 있는가
  • □ 롤백 시 정리해야 할 자원이 있다면 PERFORM ... ON ROLLBACK이 있는가
