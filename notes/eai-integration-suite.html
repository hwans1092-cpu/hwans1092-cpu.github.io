01SAP BTP란 무엇인가

SAP Integration Suite는 독립 제품이 아니라 SAP Business Technology Platform(BTP) 위에서 동작하는 하나의 서비스입니다.

02Integration Suite 전체 구조

SAP 공식 정의 : "industry-leading, enterprise-grade integration platform-as-a-service".
핵심은 단일 제품이 아니라 캐퍼빌리티(capability)의 묶음이라는 점 — 각 캐퍼빌리티는 BTP 코크핏에서 개별 활성화합니다.

캐퍼빌리티역할
Cloud Integration iFlow 기반으로 A2A/B2B/B2G 시나리오의 메시지를 설계·실행 — 이 노트의 핵심 축 (Lesson 03~08)
API Management API를 안전하게 게시·관리·거버넌스 (Lesson 09)
Event Mesh 이벤트 기반 비동기 통신 (Lesson 10)
Open Connectors 160개 이상의 비-SAP 애플리케이션용 사전 제작 커넥터
Integration Advisor 크라우드소싱·머신러닝 기반으로 B2B 매핑/인터페이스 자동 생성
Trading Partner Management B2B 거래처(trading partner) 프로필·계약 관리
Edge Integration Cell 고객이 직접 관리하는 하이브리드 환경에서 통합 실행

🔰 초보자 설명

Integration Suite를 계약했다고 모든 기능이 자동으로 켜지는 게 아닙니다. BTP 코크핏에서 "Cloud Integration 캐퍼빌리티를 활성화한다" 같은 식으로 필요한 것만 켜서 씁니다. 이 노트는 ABAP/SD 개발자가 실무에서 가장 먼저 마주치는 Cloud Integration을 중심에 두고, API Management와 Event Mesh는 개념 이해 수준으로 다룹니다.

03Cloud Integration 개요

SAP 공식 정의 : "Support end-to-end process integration through the exchange of messages."
클라우드/온프레미스 애플리케이션을 다른 SAP·비-SAP 애플리케이션과 연결하고, 실시간 시나리오의 메시지를 처리합니다.

🔰 초보자 설명

Cloud Integration은 Integration Suite 안에서 실제로 통합 로직(iFlow)을 그려서 돌리는 개발 환경입니다. Integration Suite가 "여러 도구가 담긴 상자"라면, Cloud Integration은 그중 ABAP 개발자가 실무에서 제일 먼저·제일 자주 만지는 "메인 도구"에 해당합니다.

3가지 실행 환경

환경설명
NeoSAP 초기 클라우드 환경 — 레거시, 신규 구축에는 잘 쓰지 않음
Cloud Foundry현재 표준. 대부분의 신규 프로젝트가 여기서 진행됨
KymaKubernetes 기반 확장 환경

Neo에서 설계한 통합 콘텐츠는 일부 제약과 함께 Cloud Foundry에서도 호환됩니다.

핵심 기능

  • A2A(Application-to-Application)와 B2B(Business-to-Business) 시나리오의 프로세스·데이터 통합
  • SAP/비-SAP, 온프레미스/클라우드를 아우르는 사전 구축 어댑터 세트로 다중 엔드포인트 연결
  • 사전 패키지 통합 콘텐츠로 빠른 프로젝트 착수, 필요 시 커스터마이징
  • Adapter SDK로 커스텀 어댑터 개발 가능
  • 동기·비동기 통신 모두 지원, 큐잉 기반 신뢰성 있는 메시징(decoupling)

04iFlow의 해부학

iFlow(Integration Flow)는 Cloud Integration이 메시지를 어떻게 처리할지 명세하는 단위입니다.
발신자·수신자, 그 사이의 처리 스텝을 그래픽 UI로 설계합니다.

SAP 공식 튜토리얼의 4단계 예제 (난이도 순)

#시나리오내용
1Smoke Test ScenarioTimer로 시작, "Hello World!" 메시지만 생성. 수신자 없음. 테넌트 정상 동작 확인용
2Smoke Test + External Data Source1번에 OData API 호출 추가, 외부 데이터로 메시지 바디 구성
3Timer + Mail Receiver2번 결과를 이메일 수신자로 전송
4Sender-Initiated (HTTPS)유일하게 발신 시스템(HTTP 클라이언트로 시뮬레이션)이 있는 시나리오

앞의 세 시나리오는 Timer로 시작하고 발신자가 없다는 공통점이 있습니다 — 발신 시스템 연결 설정을 생략할 수 있어 진입장벽이 낮습니다.

📌 ABAP 개발자 관점

iFlow는 ABAP의 REPORT 프로그램과 비슷한 위상입니다 — "실행 단위"라는 점에서. 다만 코드를 타이핑하는 대신 팔레트에서 스텝을 끌어와 그래픽으로 배치합니다. 메시지 처리 로그(MPL)를 확인하는 모니터링 화면은 ABAP의 ST22/디버거처럼 "지금 이 메시지가 어디서 멈췄는지"를 보여주는 창구라고 생각하면 됩니다.

05Adapter — 연결의 언어

어댑터는 "sender 또는 receiver를 테넌트에 연결할 때 어떤 기술 프로토콜을 쓸지" 지정하는 컴포넌트입니다.
SAP 제공 어댑터는 40종을 훌쩍 넘습니다 — 카테고리로 묶어서 이해하는 편이 실무에 더 도움이 됩니다.

카테고리대표 어댑터주 용도
웹/API 계열HTTPS SOAP OData (V2/V4)REST/SOAP/OData 기반 시스템 간 동기 호출
파일 전송SFTP FTP서버 간 파일 폴링·업로드 (배치성 연동)
SAP 전용 연결IDoc RFC ProcessDirect온프레미스 ABAP 연결(Cloud Connector 경유), iFlow 간 내부 연결
메시징/큐JMS AMQP Kafka비동기 큐 기반 메시징, Event Mesh·Kafka 연동
메일Mail (IMAP/POP3/SMTP)이메일 수신·발신을 통합 흐름에 연결
데이터베이스JDBC (HANA/Oracle/MSSQL/PostgreSQL)DB에 직접 SQL 실행
B2B 표준AS2 AS4 XI거래처 간 표준 프로토콜로 문서 교환
SaaS 커넥터SuccessFactors Salesforce Ariba특정 클라우드 애플리케이션 전용 연결

대부분의 어댑터는 Sender(수신용)와 Receiver(발신용) 두 방향으로 나뉩니다 — SFTP Sender는 원격 서버에서 파일을 "읽어오고", SFTP Receiver는 파일을 원격 서버에 "써줍니다".

🔰 초보자 설명

어댑터를 "번역기+통신 케이블"로 생각하면 쉽습니다. iFlow 내부 로직은 어댑터의 프로토콜이 무엇이든 동일한 메시지 형태(Camel Exchange)로 다룹니다. SFTP로 파일을 읽어오든 OData로 데이터를 받아오든, 일단 iFlow 안으로 들어오면 이후의 Mapping·Router 스텝은 똑같은 방식으로 동작합니다 — 이것이 iFlow가 이기종 프로토콜을 통일된 방식으로 처리할 수 있는 이유입니다.

06Message Mapping

발신 측 메시지 구조를 수신 측이 기대하는 구조로 변환하는 스텝입니다.
실무 가이드라인의 핵심 두 가지 : Set the Mapping Context(적용 범위 지정), Use a Message Mapping to Map XML to JSON(형식 변환).

time = ${date:now:yyyy-MM-dd HH:mm:ss} — Content Modifier의 Expression 타입으로도 동일하게 구현 가능

실무에서는 그래픽 매핑 툴 대신 Content Modifier + Groovy/JavaScript Script 조합으로 매핑을 처리하는 경우도 많습니다 — 로직이 복잡하거나 조건 분기가 많을 때 특히 그렇습니다.

07Router · Filter · Content Modifier

메시지를 "어디로" 보낼지, "무엇을" 담을지 결정하는 3종 스텝 — 실무에서 가장 자주 쓰입니다.

Router — 조건에 따라 경로를 나눈다

조건에 맞는 경로가 없으면 Default Route가 처리됩니다 — ABAP의 CASE ... WHEN OTHERS와 같은 위상입니다.

* 조건이 true일 때만 이 경로가 태워짐
${property.custom_extension_enabled} = 'true'

Filter — XPath로 메시지의 일부만 남긴다

네임스페이스 프리픽스가 있으면, iFlow의 Runtime Configuration 탭에서 프리픽스-네임스페이스 매핑을 별도로 정의해야 합니다.

* XPath Expression 필드에 입력
/p2:Messages/p2:Message1/p1:Order_MT

Content Modifier — 헤더 · 바디 · 프로퍼티를 편집한다

Source Type설명
Constant고정값 입력
XPath수신 메시지에서 XPath로 값 추출 (예: /Order/Customer/CustomerNumber)
ExpressionCamel Simple Expression 사용 (예: ${exchangeId})
Header / Property기존 헤더·프로퍼티 값을 재참조
Global Variable같은 테넌트의 다른 iFlow에서도 공유되는 변수

실무에서 자주 걸리는 함정

Header는 수신 시스템까지 전달되지만, Property는 iFlow 내부에서만 쓰이고 외부로 나가지 않습니다. HTTP 기반 수신 어댑터를 쓸 때 헤더가 너무 많이 쌓이면(보통 4~16KB 제한) 수신 시스템이 요청을 거부할 수 있습니다 — 마지막에 Content Modifier로 불필요한 헤더를 삭제해야 합니다.

08예외 처리와 모니터링

SAP 공식 가이드라인 : "Handle exceptions by extending an integration flow with an exception subprocess."

Exception Subprocess의 3가지 종료 이벤트

종료 이벤트메시지 상태용도
End EventCOMPLETED발신자에게 커스텀 에러 메시지로 응답 (커스텀 상태 정의 가능)
Error End EventFAILED처리 로그에 추가 정보를 남기고 실패로 확정
Escalation End EventESCALATED별도 상태로 검색·필터링 가능하게 함

Message Status — MPL 상태값 전체

상태의미
COMPLETED수신자에게 정상 전달 완료
PROCESSING처리 진행 중
RETRY에러 발생 후 자동 재시도가 시작된 상태
ESCALATED에러 발생, 재시도 없이 (동기 메시지의 경우) 발신자에게 에러 응답
FAILED최종 실패 — 더 이상 재시도 불가, 전달되지 않음
CANCELLEDJMS 큐 엔트리를 수동으로 취소
DISCARDEDTimer 기반 iFlow에서 워커 노드 재시작 등으로 중복 실행된 이전 메시지
ABANDONED재배포·노드 셧다운 등으로 처리가 중단됨 (재시도 설정 시 재개 가능)

📌 ABAP 개발자 관점

Message Processing Log(MPL) 화면은 ABAP의 SM37(잡 모니터)이나 SLG1(애플리케이션 로그)과 목적이 같습니다 — "이 실행 건이 성공/실패/재시도 중 무엇인지, 어느 스텝에서 멈췄는지"를 추적하는 창구입니다. FAILED 상태를 발견했을 때 원인을 좁혀가는 방식(첨부 페이로드 확인 → 스텝별 로그 확인 → 예외 서브프로세스 로직 점검)도 ABAP 디버깅 습관과 크게 다르지 않습니다.

09API Management

"API 보안·거버넌스에 관한 모든 엔터프라이즈 요구사항을 다루는 완결형 솔루션."
API를 그냥 공개하지 않고, 앞단에 API 프록시(API Proxy)를 두고 정책(Policy)을 적용해 트래픽을 통제합니다.

Aspect 1

API Governance

발견·등록·문서화·게시·버저닝, 정책 템플릿 적용, "Product" 단위 그룹핑.

40여 종 정책 템플릿
Aspect 2

API Facade

커스텀(vanity) URL로 내부 구조를 숨기고, ABHE 개발자 포털로 문서·코드 스니펫과 함께 노출.

API Business Hub Enterprise
Aspect 3

API Security

API Key, SAML, OAuth 2.0, JWT 정책. IP 접근 제어, JSON/XML 위협 방지, DoS 방지.

OpenID Connect 호환
Aspect 4

Transforms

헤더 수정, 값 추출, XML↔JSON 변환, 외부 콜아웃, Python/JS 스크립트 확장.

API 프록시 정책
Aspect 5

API Insights & Analytics

실시간 모니터링·대시보드, API 수익화(monetization)까지 지원.

SAP Subscription Billing 연계

🔰 초보자 설명

iFlow는 "메시지를 어떻게 변환·라우팅할지", API Management는 "누가·얼마나·어떤 조건으로 호출할 수 있는지"를 통제합니다. 실무에서는 iFlow 로직을 API Management 프록시로 한 번 더 감싸 외부에 노출하는 경우가 많습니다.

10Event Mesh — 이벤트 기반 통합

"SAP Event Mesh allows applications to communicate through asynchronous events."
"요청→응답" 대신, 사건(event)이 발생했다는 사실만 발행(publish)하면 구독(subscribe)한 시스템이 알아서 가져갑니다.

  • Publish business events — SAP·비-SAP 소스에서 하이브리드 랜드스케이프 전반에 이벤트 발행
  • Consume business events — SAP Extension Suite, Integration Suite 등 SAP 이벤트 생태계 전반에서 소비
  • Connect seamlessly — 디커플링된 통신으로 확장/통합 시나리오의 신뢰성 있는 데이터 전송

Cloud Integration에서는 AMQP for SAP Event Mesh Sender/Receiver 어댑터(Lesson 05)로 iFlow와 직접 연결할 수 있습니다. 더 큰 규모의 이벤트 브로커링에는 Solace 기반 Advanced Event Mesh라는 상위 옵션도 있습니다.

🔰 초보자 설명

Event Mesh는 "게시판"에 가깝습니다. A는 게시판에 공지만 붙이면 끝 — 구독자가 몇 개인지, 존재하는지조차 몰라도 됩니다. 이 점이 "상대 주소를 알고 직접 호출"하는 iFlow의 동기 방식과 근본적으로 다릅니다.
