ABAP 디버깅 실무 노트

진입 · 멈추기 · 값 바꾸기 — 운영에서 실제로 손이 가는 것만, 작업 화면 캡처와 함께
대상 시스템: winerp01 / MEP · 캡처 23장, 조작 지점 표시 · 계속 추가 중

결론부터. 디버깅의 8할은 값을 들여다보는 일이 아니라 어디서 멈출지 정하는 일입니다. 그래서 이 노트는 기능 설명이 아니라 세 가지 질문으로 구성했습니다.

① 디버거를 어떻게 켜는가 · ② 원하는 지점에서 어떻게 잡는가 · ③ 재현이 안 될 때 값을 어떻게 만드는가.

모든 캡처는 실제 작업 화면이고, 빨간 박스와 번호가 눌러야 할 지점입니다.

목차

  1. 진입 — 디버거를 어떻게 켜는가
  2. 멈추는 법 — 소스 위치를 모를 때
  3. 값 바꾸는 법 — 재현이 안 될 때
  4. 상황별 처방 치트시트
  5. 반드시 지킬 것

LESSON 1진입 — 디버거를 어떻게 켜는가

진입 방법은 딱 하나의 기준으로 갈립니다. 멈출 위치를 아는가. 모르면 /h, 알면 브레이크포인트입니다.

1-1  /h — 위치를 모를 때

명령창에 /h 를 입력하고 Enter. 화면 하단에 "디버깅 켜짐" 메시지가 뜨고, 그 다음 화면 전환부터 디버거가 뜹니다. 즉 /h 를 누른 직후가 아니라 다음 액션(실행 · 저장 · 버튼 클릭)에서 잡힙니다.

대소문자 무관

/h, /H 둘 다 동작합니다. 한 번 켜면 다음 한 번만 유효하고, 디버거에서 나오면 다시 꺼집니다.

명령범위쓰는 때
/h세션 디버깅 — 내 ABAP 코드 수준에서 정지. 표준 · 시스템 코드는 건너뜀평소 쓰는 것
/hs시스템 디버깅 — 시스템 프로그램 · 표준 FM 내부까지 진입표준 로직을 파야 할 때만. 스텝 폭증 + 권한 필요

1-2  브레이크포인트 — 멈출 위치를 알 때

소스에서 라인을 직접 지정하는 방식입니다. 종류가 세션 BP와 외부(External) BP 두 개인데, 겉보기는 같고 유효 범위가 다릅니다. 이 차이를 모르면 "BP를 걸었는데 안 멈춘다"에서 30분을 태웁니다.

어떻게 거는가 — 커서를 두고 툴바 버튼을 누른다

SE38 · SE80 소스 편집기 상단, 패턴 버튼 바로 왼쪽에 빨간 정지 표지 아이콘 두 개가 붙어 있습니다. 멈추고 싶은 행에 커서를 두고 이 버튼을 누르면 그 행에 BP가 걸립니다. 한 번 더 누르면 해제.

소스에서 우클릭해도 됩니다 — Create Session Breakpoint(세션) · Create User Breakpoint(외부)가 컨텍스트 메뉴에 있습니다 (→ 그림 19).

커서 위치가 곧 BP 위치입니다. 엉뚱한 행에 걸렸다면 커서가 그 행에 있었던 것. 또 실행문이 아닌 행(주석, DATA 선언, 빈 줄)에는 걸어도 무시되거나 다음 실행문으로 밀립니다.

1-3  외부 디버깅 사전 설정 — 웹 ID를 맞춰야 걸린다

외부 BP를 찍기만 하면 되는 게 아닙니다. 어느 사용자 ID로 들어오는 요청을 잡을지를 설정에서 먼저 지정해야 합니다. 여기가 비어 있거나 다른 ID면 BP를 걸어도 아무 일도 일어나지 않습니다.

동작 원리 — ID가 조건의 절반

외부 BP는 "소스의 이 줄"이 아니라 "이 사용자 ID로 들어오는 외부 요청이 이 줄을 지날 때"를 조건으로 겁니다. 줄만 맞고 ID가 틀리면 조건이 성립하지 않으므로 그냥 지나갑니다 — 에러도 경고도 없습니다.

1-4  F5 · F6 · F7 · F8 — 어디로 가는가

네 키의 차이는 하나로 정리됩니다. 호출문(PERFORM · CALL FUNCTION · LOOP)을 만났을 때 안으로 들어가느냐, 그리고 어디까지 한 번에 실행하느냐.

F5
단일 스텝 (Step Into)
무조건 바로 다음 문장으로. 호출문이면 그 안으로 들어갑니다 — FORM 내부, FM 내부, LOOP 첫 회차로. 가장 세밀하고 가장 느림.
F6
실행 (Step Over)
호출문을 통째로 실행하고 다음 줄로. PERFORM · CALL FUNCTION · LOOP 내부는 통과합니다. 관심 없는 서브루틴을 건너뛸 때.
F7
복귀 (Step Out)
현재 있는 FORM · FM · METHOD를 끝까지 실행하고 밖으로. 잘못 들어왔을 때, 또는 안은 볼 필요 없어졌을 때 탈출.
F8
계속 (Continue)
다음 브레이크포인트까지 실행. BP가 없으면 프로그램 끝까지 달립니다. 조건에 맞는 다음 히트를 볼 때.

도해 — 같은 지점에서 세 키가 가는 곳

1-5  내 세션이 아닐 때

운영에서 실제로 막히는 지점은 대부분 여기입니다. 내 화면에서 재현이 안 되는 건들 — 남의 세션에서 도는 것, 밤에 배치로 도는 것, 저장 이후에 벌어지는 것.

SM50 — 지금 돌고 있는 프로세스에 붙기

SM50은 이 앱 서버의 워크프로세스 현황판입니다. 누가 어떤 프로그램을 돌리는 중인지 보이고, 그 프로세스에 디버거를 붙일 수 있습니다.

항목내용
붙는 법
(디버깅)		대상 프로세스 행 선택 → 메뉴 관리(A) > 프로그램(R) > 디버깅(D) → 확인 팝업에서 예. 툴바가 아니라 메뉴바에 있습니다. (→ 그림 22)
세부 조회
(디버깅 아님)		행 선택 후 세부사항 버튼 — 그 프로세스의 DB · 세션 · 메모리 통계를 봅니다. 디버거를 붙이는 기능이 아닙니다. (→ 그림 20)
상태 읽는 법대기 = 놀고 있음 · 실행 = 처리 중 · 보류 = 멈춤(디버깅 · 락 대기 등)
덤으로상단 요약에 다이얼로그 50/46(총/가용) 처럼 프로세스 여유가 보입니다. "시스템이 느리다" 신고가 오면 여기부터
STEP 1

대상 프로세스 행을 클릭해서 선택합니다.

STEP 2

메뉴 관리(A) > 프로그램(R) > 디버깅(D)

STEP 3

"프로그램을 디버그하겠습니까?" → 예

예를 눌렀는데 화면이 그대로일 때 — 원인 4가지
  1. 대상이 이미 끝났다. SM50 목록은 스냅샷입니다. 목록을 띄운 순간엔 실행이었어도 메뉴를 여는 사이 대기로 돌아갔으면 붙을 ABAP 컨텍스트가 없습니다. 새로 고침 후 다시 확인하세요.
  2. 시스템 프로세스를 골랐다. 사용자가 SAPSYS, 클라이언트 000, 레포트가 SAPLHTTP_... 같은 행은 커널·시스템 처리입니다. 내 업무 프로그램이 아니라 볼 것이 없거나 /hs(시스템 디버깅)가 필요합니다.
  3. 이미 다른 사람이 디버깅 중이다. 상태 보류 + 대기중 Debug 인 행(그림 9의 ①).
  4. 권한이 없다. S_ADMI_FCD(PADM) · S_DEVELOP의 DEBUG 권한이 필요합니다.
확실히 재현해서 연습하는 법
  1. 명령창에 /o 로 GUI 세션을 하나 더 엽니다.
  2. 새 세션에서 오래 도는 Z 프로그램을 실행합니다 (큰 SELECT나 LOOP가 있는 것).
  3. 원래 세션에서 SM50 → 새로 고침 → 사용자이름이 내 ID이고 상태가 실행이며 레포트가 그 프로그램인 행을 고릅니다.
  4. 관리 > 프로그램 > 디버깅 → 예. 이러면 확실히 디버거가 뜹니다.

덤으로 — 세부 조회로 "왜 느린가" 보기

프로세스를 선택하고 세부사항을 누르면 그 프로세스 한 건의 통계가 나옵니다. 디버깅과는 다른 기능이지만, "이 프로그램이 왜 이렇게 오래 도나"를 볼 때는 디버거보다 이쪽이 빠릅니다.

남의 프로세스에 붙으면 그 사람 작업이 멈춥니다

운영 중인 업무 세션에 붙기 전에 반드시 당사자에게 알릴 것.

SM37 + JDBG — 끝난 배치 잡을 다시 디버깅

배치에서만 실패하는 건은 화면에서 재현이 안 됩니다. JDBG는 이미 끝난 잡을 디버깅 모드로 다시 태우는 명령입니다.

STEP 1

SM37 실행 → 선택 화면에서 조회 조건을 넣습니다.

STEP 2

목록에서 대상 작업에 체크하고, 명령 필드에 JDBG 입력 후 Enter.

JDBG는 "기록 재생"이 아니라 "재실행"입니다

잡 스텝이 실제로 다시 돌기 때문에 DB 변경 · 전표 생성 · 인터페이스 전송이 또 일어납니다. 운영기에서는 결과를 되돌릴 수 있는지 먼저 판단하세요. 안전하게는 QA에서.

Update Debugging — 저장 이후를 보는 법

CALL FUNCTION ... IN UPDATE TASK 로 등록된 로직은 COMMIT WORK 시점에 별도 업데이트 프로세스에서 실행됩니다. 그래서 일반 디버깅으로 끝까지 따라가도 그 안이 안 보입니다. "저장은 성공했다는데 DB 값이 다르다"의 정체가 대개 여기입니다.

STEP 1

디버거에서 Shift+F1 → 다이얼로그에서 Update Debugging 체크.

STEP 2

F8 로 진행 → COMMIT WORK 를 지나면 업데이트 태스크가 새 디버거 창으로 뜹니다.

외부 BP — 웹 · RFC · 인터페이스

BSP · RFC · HTTP 호출 건은 1-3 외부 디버깅 사전 설정에서 다룹니다. User 필드를 실제 호출 주체 ID로 맞추는 것이 전부입니다.

" 메시지 클래스 ID · 번호 확인하는 법
화면 하단 메시지 더블클릭  또는  우클릭 > 기술 정보(Technical Information)
  → Message Class / Message Number 를 그대로 입력
첫 히트가 원인이 아닐 수 있습니다

같은 메시지를 여러 곳에서 던지면 처음 멈춘 곳이 진짜 원인이 아닐 수 있습니다. F8로 다음 히트도 확인하세요.

2-3  Watchpoint — 값이 바뀌는 순간

브레이크포인트는 위치, 워치포인트는 값입니다. 어느 줄에서 깨지는지 모를 때 쓰는 유일한 방법입니다.

STEP 1

디버거 상단 Watchpoint 버튼 또는 Shift+F4 → Create Watchpoint 팝업.

자주 쓰는 조건식

SY-TABIX      =  100          " LOOP 100번째 회차만
GS_ITEM-MATNR =  '1000123'    " 특정 자재만
SY-SUBRC      <> 0            " 실패한 순간
LV_AMOUNT     >  1000000      " 금액이 튀는 지점
STEP 2

설정한 BP·WP는 Break./Watchpoints 탭에서 한번에 확인·관리합니다.

이 화면이 진짜 쓸모 있는 이유

목록에 Condi...(조건)와 Skip (Nu...(건너뛸 횟수) 컴럼이 있습니다. 이미 걸어둔 BP에 조건식과 "몇 번째 히트부터 멈추기"를 나중에 붙일 수 있다는 뜻입니다. LOOP 안에서 500번째만 보고 싶을 때 F8을 500번 누를 필요가 없습니다.

Table 탭이 더 빠를 때가 많습니다

내부테이블 필드는 Table 탭에서 직접 조회 · 필터하는 편이 빠릅니다. Watchpoint는 매 변경을 감시하므로 무거운 기능입니다.

LESSON 3값 바꾸는 법 — 재현이 안 될 때

데이터가 없어 재현이 안 되거나, 분기를 타지 않아 확인이 안 될 때. 원인 규명용이지 결론용이 아닙니다.

3-1  SE16N 데이터 직접 수정 — GD-EDIT / GD-SAPEDIT

SE16N 실행 → /h → 변수 GD-EDIT, GD-SAPEDIT 에 X 입력 → F8. ALV가 편집 가능 상태로 조회되고, 값 변경 후 저장 버튼으로 반영됩니다.

VIEW는 저장 시 덤프가 발생합니다

반드시 실 테이블 기준으로 수정하세요.

운영기(PRD)에서는 원칙적으로 금지

변경 로그도, 정합성 검증도 없이 DB가 바뀝니다. DEV / QA에서만.

3-2  흐름 강제 제어

방법용도
SY-SUBRC 조작실패 분기를 성공으로 밀어넣어 이후 로직을 태워봅니다. 원인 확인용
플래그 · 권한 변수AUTHORITY-CHECK 직후 SUBRC, 편집 가능 플래그 등을 바꿔 화면 상태 재현

필드 Hex 편집길이 초과 · 특수문자 값 재현. 변수창 Hexa 컬럼에서 직접 입력

Goto Statement — 커서 위치로 건너뛰기

소스에서 우클릭으로 바로 쓸 수 있습니다. 건너뛰고 싶은 줄에 커서를 두고 우클릭 → Goto Statement. 그 줄부터 실행이 이어집니다.

사이 코드가 통째로 안 돌아간다는 뜻

건너뛴 구간에서 채워져야 할 변수가 빈 채로 남습니다. 그 상태로 진행하면 엉뚱한 곳에서 터져서 진짜 원인을 더 찾기 어려워집니다. 분기 확인용으로만 쓰세요.

값을 바꿔 통과시킨 결과는 재현이 아닙니다

원인 규명 후에는 정상 데이터로 다시 검증해야 합니다.
