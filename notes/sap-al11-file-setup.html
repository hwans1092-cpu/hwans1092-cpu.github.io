AL11 · FILE 세팅 — 서버 디렉토리와 논리 파일 경로

파일 인터페이스를 만들기 전에 반드시 깔아야 하는 두 가지 설정
대상 시스템: winerp01 / MEP · 캡처 8장 예정

결론부터. ABAP 코드에 서버 경로를 직접 쓰면 안 된다. DEV에서 만든 프로그램을 QA·PRD로 이관하는 순간 경로가 달라서 깨지기 때문이다. 그래서 SAP은 경로를 코드 밖으로 빼는 장치를 두 개 제공한다.

AL11은 서버에 어떤 디렉토리가 있는지 보는 창이고, FILE은 "논리 이름 → 실제 경로" 변환표다. 이름이 비슷해 헷갈리지만 역할이 완전히 다르다.

먼저 알아야 할 것

애플리케이션 서버 — 프로그램이 실제로 실행되는 서버. 한 시스템에 여러 대일 수 있다.
OPEN DATASET — 애플리케이션 서버의 파일을 여는 ABAP 구문. PC 파일이 아니다.
프로파일 파라미터 — 인스턴스 설정값. DIR_HOME 같은 디렉토리 경로도 여기 들어 있다.
Syntax group — 경로 표기법 묶음. UNIX는 /, Windows는 \를 쓰는 차이를 흡수한다.

LESSON 1왜 경로를 코드에 쓰면 안 되는가

안 지키면 뭐가 터지나. DEV에서는 잘 도는데 이관 후 PRD에서만 파일을 못 찾는다. 소스를 고쳐야 하므로 다시 이관해야 하고, 그때마다 같은 일이 반복된다.

* 이렇게 쓰면 안 된다
OPEN DATASET '/interface/dev/po/in/PO_20260914.txt' FOR INPUT ...
" DEV 전용 경로가 소스에 박혔다. QA·PRD에서는 존재하지 않는다.
문제구체적으로
시스템마다 경로가 다르다 DEV /interface/dev/… · PRD /interface/prd/…
OS마다 표기가 다르다 UNIX /usr/sap/… · Windows C:\usr\sap\…
날짜·순번이 파일명에 들어간다 매번 CONCATENATE로 조립하는 코드가 흩어진다
경로가 바뀌면 소스를 고쳐야 한다 운영 중 디렉토리 이전 = 프로그램 수정 + 이관

해결은 코드에는 이름만 쓰고, 실제 경로는 설정에서 찾아오는 것이다. 설정은 이관 대상이 아니므로 시스템별로 다른 값을 가질 수 있다.

* 이렇게 쓴다
CONSTANTS lc_logfile LIKE filename-fileintern VALUE 'Z_PO_IN'.

CALL FUNCTION 'FILE_GET_NAME'
  EXPORTING logical_filename = lc_logfile
  IMPORTING file_name        = lv_path.   " 시스템에 맞는 실제 경로가 나온다

OPEN DATASET lv_path FOR INPUT ...

LESSON 2AL11 읽는 법 — 두 종류의 디렉토리

AL11은 무엇인가. 애플리케이션 서버의 디렉토리와 파일을 SAP GUI에서 들여다보는 조회 화면이다. OS에 직접 접속하지 않고도 파일이 왔는지, 내용이 어떤지 확인할 수 있다. 실제 프로그램은 RSWATCH0이다.

목록에 뜨는 디렉토리는 출처가 두 가지다. 이걸 구분해야 "내 폴더를 어떻게 추가하나"의 답이 나온다.

자주 보는 표준 디렉토리

파라미터용도
DIR_HOME인스턴스 작업 디렉토리. 상대 경로의 기준점이 된다
DIR_TRANS이관(트랜스포트) 디렉토리. 보통 시스템 간 공유
DIR_TEMP임시 파일
DIR_GLOBAL인스턴스 간 공유 디렉토리

ABAP에서 값을 직접 읽을 수도 있다. AL11(RSWATCH0)이 쓰는 방식과 같다.

DATA: lv_dir(200).

CALL 'C_SAPGPARAM' ID 'NAME'  FIELD 'DIR_HOME'
                   ID 'VALUE' FIELD lv_dir.
AL11 경로는 시스템 공용이 아니다

보이는 경로는 지금 접속해 있는 인스턴스의 로컬 디스크다. 서버가 여러 대인 시스템에서는 A에 올린 파일이 B에서 안 보인다 — 공유 마운트(NFS 등)로 묶여 있지 않다면. 파일 인터페이스 설계에서 가장 먼저 확인할 항목이다.

LESSON 3AL11에 내 디렉토리 등록하기

인터페이스용 폴더를 목록에 띄우는 작업이다. 조회 편의를 위한 등록이지, 이것만으로 프로그램이 그 경로를 알게 되는 건 아니다 — 그건 LESSON 4의 FILE이 담당한다.

1

AL11 실행 → 툴바의 Configure User Directories (Shift+F1)

2

신규 항목을 추가하고 아래를 입력한다.

필드입력비고
Name of Directory ParameterDIR_Z_PO_IN 관례상 DIR_ 접두사. 이게 AL11 목록에 뜨는 이름
Directory Name/interface/po/in 애플리케이션 서버의 전체 경로
Server Nameall 또는 서버명 all이면 모든 인스턴스에서 보인다
3

저장 후 목록으로 돌아와 방금 만든 항목을 더블클릭. 파일 목록이 나오면 성공이다.

등록했는데 안 열린다면

AL11 등록은 경로를 만들어주지 않는다. 이름표만 붙이는 작업이다. OS 레벨에 그 디렉토리가 실제로 존재하고 SAP 시스템 사용자에게 읽기·쓰기 권한이 있어야 한다. 없으면 Basis에 생성을 요청해야 한다.

등록 결과는 테이블 USER_DIR에 저장된다. ABAP에서 직접 조회할 수도 있다.

SELECT SINGLE dirname FROM user_dir INTO @DATA(lv_path)
 WHERE aliass EQ 'DIR_Z_PO_IN'.
다만 이 방식은 권하지 않는다

USER_DIR을 직접 읽으면 결국 코드가 특정 이름에 묶인다. 날짜·순번 조립도 직접 해야 하고, 시스템별로 다른 값을 주기도 어렵다. 프로그램에서는 FILE 트랜잭션 방식을 쓴다. AL11 등록은 사람이 눈으로 확인하는 용도다.

LESSON 4FILE — 논리 경로와 논리 파일명

FILE이 하는 일. 코드에 쓴 이름을 실행 시점에 실제 경로로 바꿔주는 변환표다. 변환표는 설정이므로 시스템마다 다른 값을 가질 수 있고, 프로그램은 손댈 필요가 없다.

왜 3단인가

층무엇을 담나왜 분리하나
논리 파일명
Logical file name		 코드에 쓰는 이름 + 물리 파일명 규칙 파일마다 이름 규칙이 다르다
논리 경로
Logical file path		 이름만 있는 중간 껍데기 여러 파일이 같은 폴더를 공유한다
물리 경로
Physical path		 OS별 실제 디렉토리 경로 UNIX와 Windows의 표기가 다르다

정리하면 파일명 규칙과 디렉토리 규칙을 따로 관리하기 위한 구조다. 인터페이스 파일이 10종이어도 폴더가 하나면 논리 경로는 하나만 만들면 된다.

예약어 — 꺾쇠 안의 값은 런타임에 치환된다

예약어치환되는 값
<FILENAME> 논리 파일명이 만들어낸 실제 파일명. 물리 경로에 반드시 포함
<SYSID>시스템 ID
<DATE>, <YYYY>, <MM>, <DD> 실행 시점 날짜
<PARAM_1> ~ <PARAM_3> FILE_GET_NAME의 PARAMETER_1 등으로 넘긴 값
물리 경로에 <FILENAME>이 없으면 안 된다

물리 경로는 디렉토리 + <FILENAME> 형태여야 한다. 이 자리에 논리 파일명이 만들어낸 파일명이 끼워진다. 입력 필드에 커서를 두고 F1을 누르면 쓸 수 있는 예약어 목록이 나온다.

LESSON 5세팅 절차 — 순서대로

FILE 첫 화면 왼쪽의 Navigation 블록에서 항목을 골라 이동한다. 아래→위 순서로 만드는 것이 편하다. 참조 대상이 먼저 있어야 하기 때문이다.

1

논리 파일 경로 정의 (Logical File Path Definition)

Logical pathZ_IF_IN
Name인터페이스 수신 디렉토리

이름만 만들고 저장한다. 이 단계에는 실제 경로가 없다.

2

물리 경로를 논리 경로에 할당 (Assignment of Physical Paths to Logical Path)

Logical pathZ_IF_IN
Syntax groupUNIX
Physical path/interface/po/in/<FILENAME>

Windows 서버라면 syntax group을 바꿔 한 줄 더 만든다. 시스템별로 다른 경로를 주는 지점이 바로 여기다 — DEV·QA·PRD에서 각각 다른 값을 넣으면 된다.

3

논리 파일명 정의 (Logical File Name Definition, Cross-Client)

Logical fileZ_PO_IN코드에 쓸 이름. 대문자
NamePO 수신 파일
Physical filePO_<PARAM_1>.txt파일명 규칙
Data formatASC텍스트
Logical pathZ_IF_IN①에서 만든 것
4

SE37에서 변환 테스트 — 프로그램에 넣기 전에 여기서 확인한다.

FILE_GET_NAME을 단독 실행하고 FILE_NAME에 기대한 경로가 나오는지 본다. 이때 "대/소문자 구분" 지시자를 반드시 켠다. OPERATING_SYSTEM 필드가 대소문자를 가리고, 논리 파일명은 전부 대문자여야 한다.

구문이 맞다고 파일이 열리는 건 아니다

FILE 정의가 문법적으로 완전해도, 그 경로가 서버에 실제로 존재하지 않으면 파일 접근은 실패한다. 정의를 만든 뒤 AL11에서 그 경로가 실제로 열리는지 확인하는 것이 LESSON 3 등록의 진짜 쓸모다.

FILE과 SF01, 그리고 SF04

유지보수 테이블은 클라이언트 종속이다. 그래서 트랜잭션이 나뉘어 있다.

FILE — 클라이언트 공통(cross-client) 정의. 보통 이걸 쓴다.
SF01 — 클라이언트별 정의가 필요할 때.
SF04 — 운영체제와 syntax group의 연결 관계를 보는 곳.

IMG 경로는 SAP NetWeaver → Application Server → System Administration → Platform-Independent File Names.

LESSON 6ABAP에서 쓰기

FILE_GET_NAME — 논리명을 실제 경로로

CONSTANTS lc_logfile LIKE filename-fileintern VALUE 'Z_PO_IN'.

DATA: lv_path TYPE string.

CALL FUNCTION 'FILE_GET_NAME'
  EXPORTING
    client           = sy-mandt      " 정의 테이블이 클라이언트 종속
    logical_filename = lc_logfile    " 반드시 대문자
    operating_system = sy-opsys      " syntax group 결정
    parameter_1      = '01'       " <PARAM_1> 자리에 치환
  IMPORTING
    file_name        = lv_path
  EXCEPTIONS
    file_not_found   = 1
    OTHERS           = 2.

IF sy-subrc NE 0.
  MESSAGE |논리 파일명 { lc_logfile } 정의를 찾을 수 없습니다| TYPE 'E'.
ENDIF.
파라미터역할
LOGICAL_FILENAME변환할 논리 파일명. 대문자
OPERATING_SYSTEM 어느 syntax group으로 만들지 결정. 보통 sy-opsys
PARAMETER_1~3물리 파일명·경로의 <PARAM_n> 자리에 치환
INCLUDING_DIR'X'면 디렉토리까지 포함한 경로를 돌려준다
FILE_NAME결과 — 이걸 OPEN DATASET에 넘긴다

화면 입력을 받을 때는 FILE_VALIDATE_NAME

사용자가 선택화면에 경로를 직접 입력하는 구조라면, 그 값이 허용된 디렉토리 안에 있는지 검증해야 한다. 검증 없이 받으면 임의 경로 접근을 허용하는 셈이 된다.

* 기본값은 FILE_GET_NAME으로 만들어 주고
INITIALIZATION.
  CALL FUNCTION 'FILE_GET_NAME'
    EXPORTING logical_filename = lc_logfile
              including_dir    = 'X'
    IMPORTING file_name        = pa_file
    EXCEPTIONS OTHERS          = 1.

* 사용자가 바꿔 넣었다면 검증한다
AT SELECTION-SCREEN.
  CALL FUNCTION 'FILE_VALIDATE_NAME'
    EXPORTING logical_filename = lc_logfile
    CHANGING  physical_filename = pa_file
    EXCEPTIONS OTHERS          = 1.

OPEN DATASET — 실제 읽기

DATA: lv_line TYPE string,
      lv_msg  TYPE char100.

OPEN DATASET lv_path
     FOR INPUT IN TEXT MODE ENCODING UTF-8
     MESSAGE lv_msg.            " ★ 실패 사유를 문자열로 받는다

IF sy-subrc NE 0.
  MESSAGE |파일 열기 실패: { lv_msg }| TYPE 'E'.
ENDIF.

DO.
  READ DATASET lv_path INTO lv_line.
  IF sy-subrc NE 0. EXIT. ENDIF.
  " 파싱 · 검증
ENDDO.

CLOSE DATASET lv_path.
MESSAGE 절을 꼭 붙인다

OPEN DATASET이 실패하면 sy-subrc 숫자 하나만 남는다. 권한 문제인지, 경로가 없는 건지, 파일이 잠긴 건지 구분이 안 된다. MESSAGE lv_msg를 붙이면 OS가 준 사유가 문자열로 들어온다.

모드용도
FOR INPUT읽기
FOR OUTPUT쓰기 — 기존 내용을 지운다
FOR APPENDING이어 쓰기
IN TEXT MODE ENCODING UTF-8텍스트. 한글이 있으면 인코딩 명시 필수
IN BINARY MODE바이너리

LESSON 7권한 — S_DATASET · SPTH · S_PATH

파일 접근은 권한 오브젝트로 통제된다. 여기서 막히면 코드가 완벽해도 sy-subrc가 0이 아니다.

오브젝트 / 테이블통제 단위비고
S_DATASET파일 단위 필드: 활동, 프로그램명, 파일명. 디렉토리 단위가 아니다
SPTH (테이블)경로에 권한그룹 부여 디렉토리 단위로 가르려면 여기서 시작
S_PATHSPTH의 권한그룹 SPTH와 짝으로 동작
권한 체크는 자동이다 — 코드에 넣지 말 것

OPEN DATASET 계열 구문은 실행 시 권한 검사를 자동으로 수행한다. 프로그램에 AUTHORITY-CHECK OBJECT 'S_DATASET'을 따로 넣을 필요가 없다.

S_DATASET에 프로파일 파라미터는 못 쓴다

<P=DIR_HOME>/* 같은 표기는 치환되지 않는다. 권한에서는 파라미터 치환을 지원하지 않으므로 실제 경로를 직접 적어야 한다. 랜드스케이프 전체에 같은 롤을 쓰고 싶다면 SPTH 쪽을 검토한다.

AL11은 디렉토리 목록을 가리지 않는다

AL11은 기본적으로 설정된 모든 디렉토리를 보여준다. S_DATASET은 파일 접근을 막을 뿐 디렉토리가 목록에 뜨는 것 자체는 막지 못한다. 운영에서 AL11 권한을 폭넓게 주면 의도치 않은 파일이 노출될 수 있다. 롤에 S_DATASET 값이 *로 열려 있지 않은지 확인할 것.

LESSON 8병렬처리와 엮을 때

파일 수신을 병렬로 돌리려 할 때 가장 먼저 밟는 지뢰가 있다.

[서버 A]  /interface/po/in/PO_001.txt   ← 파일은 여기만 있음
[서버 B]  /interface/po/in/            ← 비어 있음

TASK-1 → 서버 A → OPEN DATASET 성공
TASK-2 → 서버 B → OPEN DATASET 실패 (sy-subrc = 8)

DESTINATION IN GROUP은 태스크를 그룹 안의 아무 서버로나 던진다. 그런데 AL11 경로는 서버 로컬이다. 실행할 때마다 결과가 달라져 재현이 안 된다.

해결방식적합도
①NFS 등 공유 마운트 디렉토리 사용 운영 시스템은 대개 이미 이 구조
②IN GROUP 대신 단일 서버 고정 병렬 효과가 서버 1대로 제한
③파일 I/O는 메인에서 직렬, 가공만 병렬 권장 — 서버 종속이 사라진다

③이 성능 관점에서도 맞다. 파일 읽기는 I/O 바운드라 병렬화 이득이 작고, 무거운 건 파싱·검증·BAPI 호출이다.

sy-host를 결과에 남긴다

파일 처리 결과 테이블에 sy-host를 넣어두면 어느 서버에서 읽었는지가 ALV에 그대로 보인다. 서버 로컬 문제를 의심할 때 가장 먼저 확인할 값이다.

* AL11 디렉토리의 파일 목록 조회
DATA: lt_dir TYPE TABLE OF salfldir.

CALL FUNCTION 'RZL_READ_DIR_LOCAL'
  EXPORTING name = lv_path
  TABLES    file_tbl = lt_dir
  EXCEPTIONS argument_error = 1
             not_found      = 2
             OTHERS         = 3.

LOOP AT lt_dir INTO DATA(ls_dir).
  CHECK ls_dir-name NE '.' AND ls_dir-name NE '..'.
  CHECK ls_dir-name CP 'PO_*.txt'.     " CP = Contains Pattern
ENDLOOP.

그때 그냥 따라 했던 것들 — 이유

1

Step 3(AL11 등록)이 왜 optional인가

프로그램은 FILE 정의만 읽는다. AL11 등록은 추출된 zip이 어디 쌓였는지 사람이 확인하기 위한 것이라 안 해도 추출은 정상 동작한다. LESSON 3에서 "조회 편의를 위한 등록"이라고 한 게 이 말이다. 반대로 Step 2(FILE)는 optional이 아니다 — 저장할 곳을 프로그램이 알아내는 유일한 통로다.

2

Physical file을 공란, Data format을 DIR로 둔 이유

이 논리 파일명은 파일 하나를 가리키지 않는다. 디렉토리만 돌려받으려고 쓴다. 추출 결과는 청크 크기(PWCXTRACT50_CHUNKSIZE 기본 10MB)로 쪼개져 여러 zip이 되고, 파일명 끝의 카운터는 프로그램이 /PWC/XTR60_FILES 테이블로 관리하며 직접 붙인다. 파일명 규칙을 FILE에 적을 수가 없으니 공란으로 두고, 용도를 DIR로 표시한 것이다.

DIR은 Data format 값 중 하나다. 해당 옵션이 없는 버전이면 그냥 비워두라고 가이드가 안내한다.

3

Logical file과 Logical path 이름을 똑같이 ZPWCXTRACT50으로 맞추라는 이유

LESSON 1의 원칙은 "경로를 코드에 쓰지 말라"였지 이름까지 자유롭다는 뜻은 아니다. 프로그램 안에 ZPWCXTRACT50이 상수로 박혀 있고 그걸 FILE_GET_NAME에 넘긴다. 경로는 설정이 정하지만, 이름은 프로그램과 설정 사이의 계약이다. 철자가 하나라도 다르면 FILE_NOT_FOUND가 난다 — LESSON 5-④에서 대소문자를 강조한 이유와 같은 지점이다.

4

S_DEVELOP이 왜 권한 목록에 있나

가이드 설명은 "Logical file path validation"이고 값이 DEVCLASS/OBJNAME = SFIL, OBJTYPE = FUGR이다. 경로 검증 로직이 함수그룹 SFIL에 들어 있고, FILE_GET_NAME의 인터페이스를 동적으로 다루기 위해 그 오브젝트 조회 권한이 필요하다. 개발 권한을 주려는 게 아니라 경로 검증 때문에 붙은 항목이다 — 값이 03-Display인 것도 그래서다.

5

S_CTS_ADM CTS_ADMFCT = EPS1은 무엇인가

애플리케이션 서버의 파일 목록을 읽기 위한 권한이다. 함수모듈 EPS2_GET_DIRECTORY_LISTING(TMS 컴포넌트)을 호출하는데 필요하다. LESSON 8에서 쓴 RZL_READ_DIR_LOCAL과 목적은 같고, 이쪽은 이관 시스템 쪽 FM이라 권한 오브젝트가 다르다.

6

S_DATASET에 06-Delete까지 들어간 이유

가이드가 "추출 파일을 PwC에 전달한 뒤에는 서버에서 삭제하라"고 안내한다. 읽기·쓰기만으로는 그 정리를 못 하기 때문에 삭제 활동까지 포함된다. FILENAME 값은 <물리 경로> + * 형태로 좁히라고 되어 있다 — LESSON 7에서 말한 "파일 단위 통제"를 그대로 적용한 예다.

7

Step 5에서 DIR_TRANS를 찾아본 이유

이관 파일(K9*·R9*)을 업로드할 위치를 알아야 해서다. DIR_TRANS는 LESSON 2의 표준 디렉토리 — AL11에서 값만 확인하고 CG3Z로 헤더는 \cofiles\, 바디는 \data\에 올린다. 이후 STMS에서 그 요청이 Import Queue에 잡힌다.

예시 경로가 E:\usr\sap\trans\tmp인 것을 그대로 따라 쓰지 말 것

가이드 화면은 이관 디렉토리 밑을 쓰고 있지만, 같은 가이드가 "본 프로그램 전용의 별도 Directory 사용을 권장"한다고 적어 뒀다. 이유는 두 가지다.

권한을 좁힐 수 없다. S_DATASET의 FILENAME을 <경로>/*로 주는 순간 이관 디렉토리 전체가 열린다.
공유 디렉토리다. DIR_TRANS는 보통 시스템 간 공유라 추출 데이터가 다른 시스템에서도 보인다. 추출물에 민감 정보가 들어갈 수 있다는 점을 가이드도 짚고 있다.

Step 7 Config Check가 점검하는 항목 = 이 노트 체크리스트

/PWC/XTR60_CONFIG 리포트가 보는 것은 네 가지다.

a. 논리 file/path가 존재하는가 → APPENDIX 체크리스트 4
b. 올바르게 구성되었는가 (<FILENAME>·syntax group) → 4
c. 사용자가 물리 경로에 읽기·쓰기 권한이 있는가 → 6
d. SAP_BASIS 700 이상 · 필수 FM 존재 → 설치 전제

직접 만든 파일 인터페이스에는 이런 점검 리포트가 없다. 그래서 SE37에서 FILE_GET_NAME을 한 번 돌려보는 것(LESSON 5-④)이 그 자리를 대신한다.
