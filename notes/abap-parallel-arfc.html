aRFC 병렬처리 — 골격부터 덤프 도감까지

순차 6.036초를 3초로 줄이기까지 밟은 덤프 6종과 그 공통 뿌리
대상 시스템: winerp01 / MEP · 캡처 14장 예정 · 계속 추가 중

결론부터. 병렬처리에서 실제로 어려운 건 STARTING NEW TASK 한 줄이 아니라 ① 언제 끝났는지 판정하는 일과 ② RFC가 메모리를 공유하지 못한다는 제약 두 가지다. 이 노트에서 밟은 덤프 6종은 전부 ②에서 나왔고, 결과가 0건으로 나오던 현상은 전부 ①에서 나왔다.

실습 프로그램: ZTEST_PARALLEL_PROCESS + RFC FM YFM_PARALTEST (함수그룹 YSTUDY_HSH) + DDIC 구조 ZTEST_PARAL_S

먼저 알아야 할 것

워크프로세스(WP) — SAP에서 실제로 일을 수행하는 단위. 한 프로그램은 기본적으로 WP 하나만 쓴다.
DIA — 화면 응답을 담당하는 WP 유형. aRFC 병렬 태스크도 여기서 돈다.
RFC — 다른 세션·서버의 함수를 호출하는 방식. aRFC는 그중 결과를 기다리지 않는 비동기 변형.
서버그룹 — 병렬 태스크를 던질 서버들의 명단. RZ12에서 만든다.
청크 — 전체 데이터를 태스크 하나가 처리할 만큼 잘라낸 묶음. 이 노트에서만 쓰는 말.
태스크 — 병렬로 떠서 청크 하나를 처리하는 실행 단위.

LESSON 1왜 병렬인가 — 코어 32개인데 1개만 쓰는 프로그램

언제 이걸 쓰는가. 배치가 밤새 돌다 업무 시작 시간을 넘길 때, 혹은 rdisp/max_wprun_time(기본 300초) 제한에 걸려 중단될 때다. 안 쓰면 서버에 코어가 아무리 많아도 프로그램 하나는 워크프로세스 1개, 즉 사실상 코어 1개만 쓰고 끝난다.

실습 측정값이다. 10건을 5건씩 2청크로 나누고, 청크 하나당 3초 걸리게 만들었다.

방식태스크소요설명
순차16.036초3초 × 2청크, 정직하게 더해진다
병렬23초대두 청크가 동시에 돈다
병렬103초대더 안 빨라진다 — 청크가 2개뿐이라 8개가 논다
청크 크기를 정하는 진짜 기준

aRFC는 DIALOG 워크프로세스에서 돈다. 따라서 청크 하나가 rdisp/max_wprun_time(기본 300초)을 넘기면 그 태스크만 강제 종료된다. "몇 건씩 나눌까"의 답은 한 청크가 300초 안에 끝나는 건수이지 보기 좋은 라운드 숫자가 아니다.

LESSON 2준비물 3가지 — 서버그룹 · 워크프로세스 · 상한

안 챙기면 뭐가 터지나. 서버그룹이 없으면 호출 자체가 안 되고, 워크프로세스를 다 쓰면 같은 시스템을 쓰는 다른 사용자 화면이 멈춘다. 학습용 프로그램이 운영 장애를 내는 가장 흔한 경로다.

① RFC 서버그룹 (RZ12)

DESTINATION IN GROUP에 넘기는 그룹명이다. 등록 현황은 테이블 RZLLITAB에서 GRPTYPE = 'S'로 조회된다. 파라미터 타입은 DDIC의 RZLLI_APCL을 써야 한다.

* 화면 입력을 존중하고, 비어 있을 때만 등록분을 가져온다
IF pa_group IS INITIAL.
  SELECT SINGLE classname FROM rzllitab INTO pa_group
   WHERE grouptype EQ 'S'.
ENDIF.
지정동작
IN GROUP grpRZ12에 등록된 그룹 안의 서버로만 분배
IN GROUP DEFAULT현재 시스템의 가용 서버 전부를 그룹으로 사용
변수가 INITIALDEFAULT와 동일하게 동작
프로그램 하나에 서버그룹 하나

한 프로그램 안에서는 RFC 서버그룹을 하나만 쓸 수 있다. 첫 번째 aRFC 호출 시점에 그 그룹이 초기화되고, 이후 호출은 그 그룹 안에서 가장 적합한 서버가 자동 선택된다. 중간에 그룹을 바꿔 호출하면 안 된다.

② 가용 워크프로세스 확인 — SPBT_INITIALIZE

선택사항이지만 넣어두면 디버깅이 훨씬 쉬워진다. 호출하기 전에 "지금 이 그룹에 WP가 몇 개 있는지"를 숫자로 알 수 있다.

CALL FUNCTION 'SPBT_INITIALIZE'
  EXPORTING group_name  = pa_group
  IMPORTING max_pbt_wps  = lv_max_wp
            free_pbt_wps = lv_free_wp
  EXCEPTIONS
    invalid_group_name          = 1
    internal_error              = 2
    pbt_env_already_initialized = 3
    " ... 이하 생략
    OTHERS                      = 7.

* SUBRC 3(이미 초기화됨)은 정상 — 같은 세션 재실행 시 항상 발생한다
IF sy-subrc NE 0 AND sy-subrc NE 3.
  MESSAGE |병렬 처리 환경 초기화 실패 ({ sy-subrc })| TYPE 'E'.
ENDIF.
SUBRC 3을 에러로 막으면 두 번째 실행이 안 된다

PBT_ENV_ALREADY_INITIALIZED는 실패가 아니다. 다만 이때는 lv_free_wp가 채워지지 않으므로, 이 값으로 태스크 수를 조정하는 로직에 lv_free_wp > 0 가드를 반드시 걸어야 한다. 안 걸면 pa_tasks = 0이 되어 아무것도 안 돈다.

③ 상한 — 이게 매너다

실습 중 PA_TASKS = 50으로 돌린 적이 있다. 이 서버의 DIA WP는 10여 개라 안전장치가 7로 깎아줬지만, 없었다면 131초 동안 다른 사용자 화면이 멈췄을 것이다. 실무 병렬 프로그램에는 거의 예외 없이 이런 상한이 들어간다.

* 가용 WP를 전부 점유하지 않는다 — 절반, 그리고 절대 상한
DATA(lv_limit) = lv_free_wp / 2.
IF lv_limit GT 5. lv_limit = 5. ENDIF.

IF lv_limit GT 0 AND pa_tasks GT lv_limit.
  pa_tasks = lv_limit.
ENDIF.
IF pa_tasks LT 1. pa_tasks = 1. ENDIF.

LESSON 3RFC FM 제약 4개는 전부 한 뿌리다

뿌리 한 문장. 원격 호출은 메모리 주소를 공유할 수 없다. 다른 워크프로세스, 경우에 따라 다른 서버에서 돌기 때문에 값을 직렬화해서 복사해 보내는 수밖에 없다. 아래 제약들은 전부 여기서 파생된다. 이 문장 하나를 잡고 있으면 나머지는 외울 필요가 없다.

제약일반 FMRFC FM어기면
원격 릴리즈불필요필수CALL_FUNCTION_NOT_REMOTE
값 전달선택필수FL381
파라미터 타입로컬 타입 가능DDIC만활성화 거부
flat 구조 (TABLES)TYPELIKEFL039
CHANGING가능불가—
STRING 인자대체로 통과불가CALL_FUNCTION_CONFLICT_TYPE

SE37 설정 — 이 3개만 맞으면 된다

1

Attributes 탭 → Processing Type을 Remote-Enabled Module(원격 사용 가능 모듈)로. 여기가 Regular Function Module로 남아 있으면 SE37 단독 실행과 동기 호출은 멀쩡히 되는데 STARTING NEW TASK만 덤프난다.

2

Import 탭 → 모든 파라미터의 값 전달(Pass Value) 체크. 원격으로 전환한 직후 활성화하면 FL381이 뜨는데, 이 체크가 빠져서다.

3

Tables 탭 → Typing을 LIKE로. TYPE으로 두면 FL039가 뜬다. TABLES 파라미터에는 값 전달 체크박스가 아예 없다 — 항상 값 전달이기 때문이다.

실습에 쓴 인터페이스

*"  IMPORTING
*"     VALUE(IV_TASKNAME) TYPE  CHAR10
*"  TABLES
*"      CT_DATA STRUCTURE  ZTEST_PARAL_S

DDIC 구조 ZTEST_PARAL_S는 PERNR / TASKNAME / SUBRC 세 필드다. SUBRC를 초기값 4로 채워 보내고 FM에서 0으로 바꿔 돌려받는 식으로, 어느 건이 실제로 처리됐는지를 결과에서 눈으로 구분할 수 있게 했다.

TABLES는 obsolete인데 왜 쓰나

SE37이 TABLES parameters are obsolete! 경고를 띄우지만, RFC FM은 CHANGING을 쓸 수 없다. 하나의 테이블로 보내고 받으려면 TABLES 외에 방법이 없다. 경고를 피하려면 테이블 타입을 만들어 IMPORTING it_data + EXPORTING et_data로 쪼개면 되는데, 코드가 늘어나는 대신 제약이 사라진다.

LESSON 4골격 — 태스크 풀과 카운터 불변식

왜 필요한가. aRFC는 던지고 끝이라 "지금 몇 개가 돌고 있는지"를 시스템이 알려주지 않는다. 직접 세야 한다. 이 숫자가 틀어지면 프로그램이 타임아웃까지 멈춰 있거나, 결과가 빈 채로 끝난다.

카운터를 올리는 위치에 규칙이 있다

변수올리는 위치이유
gv_sent호출이 성공했을 때만 (sy-subrc = 0) 호출 실패한 태스크는 콜백이 오지 않는다. 올리면 WAIT가 안 풀린다
gv_recv콜백 폼 맨 첫 줄 RECEIVE가 예외로 빠져도 "돌아온 건 돌아온 것"이다
* 호출 측 — 성공 분기에서만
CASE sy-subrc.
  WHEN 0.
    ls_task-status = 'I'.
    gv_sent    = gv_sent    + 1.
    gv_running = gv_running + 1.
  WHEN 3.  " RESOURCE_FAILURE — 하나 끝나길 기다렸다 재시도
    WAIT UNTIL gv_running LT pa_tasks UP TO pa_time SECONDS.
    PERFORM call_function.
    RETURN.
  WHEN OTHERS.
    ls_task-status = 'E'.
    " 카운터를 올리지 않는다. 미처리분은 결과에 그대로 편입
    APPEND LINES OF gt_taskdata TO gt_result.
ENDCASE.

청크 분할 — 꺼내고 지우고

인덱스 변수를 굴리면 오프바이원 실수가 나고, 정수 나눗셈이 0이 되면 무한루프에 빠진다 (1건 / 3태스크 = 0). 원본을 고갈시키는 방식이 안전하다.

WHILE gt_data IS NOT INITIAL.
  lv_to = nmin( val1 = pa_count val2 = lines( gt_data ) ).

  CLEAR gt_taskdata.                                       " APPEND는 덮어쓰지 않는다
  APPEND LINES OF gt_data FROM 1 TO lv_to TO gt_taskdata.  " 앞에서 꺼내고
  DELETE gt_data FROM 1 TO lv_to.                        " 원본에서 지우고

  PERFORM call_function.
ENDWHILE.

LESSON 5구문 3종 — 호출 · 콜백 · 수신

세 구문은 세트라 쪼갤 수 없다. 하나라도 빠지면 결과가 비거나 무한 대기한다.

① 호출

CALL FUNCTION 'YFM_PARALTEST'
  STARTING NEW TASK ls_task-taskname          " 비동기 — 제어권 즉시 반환
  DESTINATION IN GROUP pa_group              " 그룹 내 여유 서버에 자동 분배
  PERFORMING receive_rfc_result ON END OF TASK  " 완료 시 실행될 콜백
  EXPORTING
    iv_taskname           = ls_task-taskname   " CHAR10 변수 — STRING 금지
  TABLES
    ct_data               = gt_taskdata
  EXCEPTIONS
    system_failure        = 1
    communication_failure = 2
    resource_failure      = 3
    OTHERS                = 4.
EXCEPTIONS 절이 없으면 SY-SUBRC가 세팅되지 않는다

이 절을 빼고 IF sy-subrc NE 0을 쓰면 그 IF문은 아무 의미가 없다. 그리고 WP가 전부 소진됐을 때 잡아줄 곳이 없어 그냥 덤프난다. resource_failure는 병렬처리에서 가장 자주 만나는 예외다.

② 콜백 폼

FORM receive_rfc_result USING p_taskname TYPE clike.
  " 시그니처 고정 — 태스크명 1개. 메인 프로그램에 있어야 하고
  " 클래스 메서드는 PERFORMING으로 못 쓴다 (CALLING을 써야 함)

  gv_recv    = gv_recv    + 1.   " 맨 앞에서
  gv_running = gv_running − 1.

③ 수신

  RECEIVE RESULTS FROM FUNCTION 'YFM_PARALTEST'
    TABLES
      ct_data               = lt_data          " 호출 때와 동일한 파라미터명
    EXCEPTIONS
      system_failure        = 1 MESSAGE lv_msg  " 원격 실패 사유를 문자열로
      communication_failure = 2 MESSAGE lv_msg
      OTHERS                = 3.

  IF sy-subrc EQ 0.
    APPEND LINES OF lt_data TO gt_result.
  ENDIF.

  " 슬롯 반납 — READ 실패 시 SY-TABIX = 0, MODIFY INDEX 0 은 덤프
  READ TABLE gt_task INTO DATA(ls_task) WITH KEY taskname = p_taskname.
  IF sy-subrc NE 0. RETURN. ENDIF.
  lv_idx = sy-tabix.                          " READ 직후에 잡아둔다

  ls_task-status = 'S'.
  MODIFY gt_task FROM ls_task INDEX lv_idx TRANSPORTING status.

MESSAGE lv_msg가 진단의 핵심이다. 이게 없으면 원격에서 뭐가 터졌는지 SUBRC 숫자 하나만 남는다.

LESSON 6WAIT UNTIL의 정체 — 대기가 아니라 실행 창

안 쓰면 뭐가 터지나. 덤프도 안 나고 에러도 없이 결과만 0건으로 나온다. 병렬 프로그램에서 가장 흔하고 가장 헷갈리는 증상이다.

콜백 폼은 커널이 아무 때나 끼워 넣는 게 아니다. 메인 프로그램이 대기 상태에 들어갔을 때만 실행된다. 그래서 DO ... ENDDO로 CPU를 태우며 기다리면 콜백이 영영 안 잡힌다.

* 전체 완료 대기 — UP TO 는 안전장치, 반드시 건다
IF gv_running GT 0.
  WAIT UNTIL gv_recv GE gv_sent UP TO pa_time SECONDS.

  IF sy-subrc NE 0.
    MESSAGE |타임아웃: { gv_recv }/{ gv_sent } 완료| TYPE 'S' DISPLAY LIKE 'W'.
  ENDIF.
ENDIF.
aRFC는 호출 시점에 DB 커밋을 유발한다

비동기 RFC 호출은 호출하는 프로그램 쪽에서 데이터베이스 커밋을 일으킨다. 메인에서 DB를 건드리다가 중간에 aRFC를 던지면 그 시점에 커밋이 끊긴다. LUW 경계를 신경 써야 하는 로직이라면 호출 위치를 반드시 확인할 것.

LESSON 7검증 순서 — 단독 → 순차 → 병렬

왜 순서가 중요한가. 처음에 DDIC·FM·프로그램·병렬로직을 한꺼번에 만들고 한꺼번에 돌렸다. 덤프가 나도 원인 후보가 넷이었다. 순서를 지키면 문제가 한 번에 하나씩만 나타난다.

Step할 일통과하면 제외되는 용의자
0RZ12 그룹 · 원천 테이블 건수 · SM50 WP 확인환경
1DDIC 구조 생성 후 DATA: ls TYPE ... 신택스 체크타입
2SE37에서 FM만 단독 실행(F8) — 값이 바뀌어 나오는지FM 본문·인터페이스
3병렬 빼고 동기 CALL FUNCTION으로 한 바퀴청크 분할 · 결과 수집 · ALV
44종 세트 투입 (호출·콜백·카운터·WAIT)— 남은 건 병렬 하나뿐
5SM50 관찰 · 태스크 수 바꿔가며 측정—
이 순서가 실제로 범인을 잡아준 방식

Step 2 단독 실행 성공 → Step 3 순차 성공 → Step 4 병렬만 결과 0건. FM 본문과 인터페이스는 이미 무죄가 확정됐으므로, 남는 건 "동기에서는 되는데 비동기에서만 안 되는 것" — 즉 원격 릴리즈 누락뿐이었다. 한꺼번에 만들었다면 이 소거법이 성립하지 않는다.

Step 3에서 순차 소요 시간을 반드시 측정해 둔다. Step 4의 비교 기준이 된다.

DATA: lv_start TYPE i, lv_end TYPE i, lv_sec TYPE p DECIMALS 3.

GET RUN TIME FIELD lv_start.   " 1회차 = 타이머 초기화, 값은 0
" ... 처리 ...
GET RUN TIME FIELD lv_end.     " 2회차 = 경과 마이크로초

lv_sec = ( lv_end − lv_start ) / 1000000.   " WRITE에 계산식은 못 쓴다
WRITE: / '소요(초):', lv_sec.

LESSON 8덤프 도감 — 이번에 밟은 6종

원격 태스크의 덤프는 화면에 뜨지 않는다

병렬 구간에서 이상하면 무조건 ST22부터 본다. 메인 화면은 멀쩡한데 원격에서 916개가 터지고 있을 수 있다. 순차 디버깅과 가장 다른 지점이다.

에러증상원인조치
CALL_FUNCTION_PARM_UNKNOWNFM 호출 즉시 파라미터명·종류가 인터페이스와 다름 SE37 인터페이스 확인. 패턴(Ctrl+F6)으로 삽입
CALL_FUNCTION_PARM_MISSINGFM 호출 즉시 필수 파라미터 누락동일
CALL_FUNCTION_CONFLICT_TYPEFM 호출 즉시 STRING을 RFC 파라미터에 직접 전달 선언된 타입의 변수에 담아서 전달
CALL_FUNCTION_NOT_REMOTE병렬에서만 발생 FM이 Regular Function Module Attributes → Remote-Enabled Module
FL039FM 활성화 거부 TABLES에 flat 구조를 TYPE으로 참조 Typing을 LIKE로
FL381FM 활성화 거부 참조 파라미터가 RFC에서 불허 Import 탭 값 전달 체크

증상별 역추적

보이는 것의심할 곳
송신 = 수신인데 결과 0건RECEIVE 실패 → ST22, MESSAGE lv_msg
수신 = 0콜백 자체가 안 불림 → PERFORMING 구문
타임아웃까지 멈춤카운터 불변식 위반
예상보다 너무 빨리 끝남처리가 아니라 덤프가 난 것 → ST22
화면이 그대로, 아무 반응 없음MESSAGE ... TYPE 'E'로 선택화면 복귀 → 상태바 확인
RESOURCE_FAILUREWP 소진 — 정상 동작. 대기 후 재시도로 처리
CALL FUNCTION은 런타임 바인딩이다

파라미터 이름이 틀리든 빠지든 신택스 체크를 통과한다. 그래서 FM 호출은 손으로 타이핑하지 말고 SE38 에디터의 패턴 버튼(Ctrl+F6) → CALL FUNCTION으로 삽입하는 게 정석이다. 이 노트의 덤프 중 3종이 손타이핑에서 나왔다.

LESSON 9SM50 · SM66 읽는 법

병렬이 실제로 돌고 있는지는 코드로 알 수 없다. 눈으로 확인해야 한다.

보이는 행정체
유형 DIA · 상태 보류 중 · 보류 사유 RFC 응답 · 프로그램 ZTEST_PARALLEL_PROCESS 메인. WAIT UNTIL로 콜백을 기다리는 상태
유형 DIA · 상태 실행 중 · 프로그램 SAPLYSTUDY_HSH 태스크. 함수그룹 YSTUDY_HSH의 런타임 프로그램명
SAPMSSY1 · RFC 응답 RFC 수신 측 디스패처. 다른 사용자 것도 여기 뜬다
함수그룹은 SAPL + 그룹명으로 보인다

SM50에서 FM 이름(YFM_PARALTEST)을 찾으면 안 나온다. 실행 중인 건 그 FM이 속한 함수그룹의 런타임 프로그램, 즉 SAPL + YSTUDY_HSH다. 이 행이 여러 개 동시에 "실행 중"이면 병렬이 붙은 것이다.

관찰 요령

1

3초짜리는 놓치기 쉽다. PA_ROWS를 30, PA_TASKS를 3으로 두면 약 6초간 지속돼 F5로 잡을 여유가 생긴다.

2

SM50은 접속한 서버 한 대만 보여준다. DESTINATION IN GROUP은 여러 인스턴스로 분산되므로, 태스크가 안 보이면 SM66(전체 서버)로 확인한다.

3

프로세스를 더블클릭하면 실행 지점이 보인다. 메뉴 Administration → Program → Debugging으로 원격 태스크 내부에 디버거를 붙일 수도 있다. FM 안의 대기 시간을 10초쯤으로 늘려두면 잡을 여유가 생긴다.

유령 태스크 확인

타임아웃이나 중단으로 회수 안 된 태스크가 남으면 다음 실행분과 합쳐져 보여서 측정값이 오염된다. 아무것도 실행하지 않은 상태에서 SM50을 새로고침했을 때 함수그룹 프로그램이 계속 남아 있으면 유령이다. 세션을 새로 열고 재측정할 것.

LESSON 10확장 — AL11 파일수신과 서버 함정

먼저 함정부터. AL11 디렉토리는 그 서버의 로컬 파일시스템이다. 그런데 DESTINATION IN GROUP은 태스크를 그룹 안의 아무 서버로나 던진다.

[서버 A]  /interface/po/in/PO_001.txt   ← 파일은 여기만 있음
[서버 B]  /interface/po/in/            ← 비어 있음

TASK-1 → 서버 A → OPEN DATASET 성공
TASK-2 → 서버 B → OPEN DATASET 실패 (sy-subrc = 8)

실행할 때마다 결과가 달라진다. 재현이 안 돼서 디버깅이 가장 어려운 유형이다.

해결방식적합도
①NFS 등 공유 마운트 디렉토리 사용운영 시스템은 대개 이미 이 구조
②IN GROUP 대신 단일 서버 고정병렬 효과가 서버 1대로 제한
③파일 I/O는 메인에서 직렬, 가공만 병렬 권장 — 서버 종속이 아예 사라진다

③을 권하는 이유는 성능 관점에서도 맞다. 파일 읽기는 I/O 바운드라 병렬화 이득이 작고, 무거운 건 파싱·검증·BAPI 호출이다. 그 부분만 병렬로 돌리면 된다.

디렉토리 목록 조회

DATA: lt_dir TYPE TABLE OF salfldir.

CALL FUNCTION 'RZL_READ_DIR_LOCAL'          " AL11과 동일한 조회
  EXPORTING name = pa_dir
  TABLES    file_tbl = lt_dir
  EXCEPTIONS argument_error = 1
             not_found      = 2
             OTHERS         = 3.

LOOP AT lt_dir INTO DATA(ls_dir).
  CHECK ls_dir-name NE '.' AND ls_dir-name NE '..'.
  CHECK ls_dir-name CP pa_mask.        " CP = Contains Pattern, *.txt 등
  " ... 처리 대상 적재 ...
ENDLOOP.

파일 읽기 — 한 건 실패가 전체를 막지 않게

LOOP AT ct_file INTO ls_file.

  ls_file-servname = sy-host.      " ★ 어느 서버에서 읽었는지 추적

  OPEN DATASET ls_file-filename
       FOR INPUT IN TEXT MODE ENCODING UTF-8
       MESSAGE lv_msg.                " 실패 사유를 문자열로 받는다

  IF sy-subrc NE 0.
    ls_file-subrc   = 8.
    ls_file-message = lv_msg.
    MODIFY ct_file FROM ls_file.
    CONTINUE.                      " ★ 한 파일 실패로 청크 전체를 잃지 않는다
  ENDIF.

  DO.
    READ DATASET ls_file-filename INTO lv_line.
    IF sy-subrc NE 0. EXIT. ENDIF.
    " === 파싱 · 검증 로직 자리 ===
  ENDDO.

  CLOSE DATASET ls_file-filename.
ENDLOOP.
sy-host를 결과에 남기는 이유

태스크가 실제로 여러 서버에 분산됐는지 ALV에서 바로 보인다. 서버 로컬 파일 문제를 의심할 때 가장 먼저 확인할 값이고, 학습 관점에서는 IN GROUP이 뭘 하는지를 눈으로 확인시켜 주는 장치다.

LESSON 11실무로 넘어갈 때 — LUW · 락 · 분할 기준

학습 프로그램의 WAIT UP TO 3 SECONDS 자리에 진짜 업무 로직을 넣는 순간 병렬 특유의 문제가 세 개 더 나타난다.

① LUW 분리

원격 태스크는 독립 LUW다. 메인의 글로벌 변수에 접근할 수 없고, BAPI_TRANSACTION_COMMIT은 태스크 안에서 호출해야 한다. 메인에서 호출해봐야 아무 효과가 없다.

따라서 실패 시 전체 롤백이 안 된다. "5개 태스크 중 3번만 실패"를 되돌리려면 보상 트랜잭션을 따로 설계해야 한다. 이건 코딩이 아니라 업무 설계 영역이다.

② ENQUEUE 락 경합

같은 자재·같은 공급처를 여러 태스크가 동시에 건드리면 락이 충돌한다. 병렬로 바꿨는데 순차보다 느려지는 전형적인 원인이다.

* 나쁜 분할 — 앞에서부터 N건씩 자르면 같은 키가 여러 태스크에 흩어진다
APPEND LINES OF gt_data FROM 1 TO lv_to TO gt_taskdata.

* 좋은 분할 — 키 기준으로 묶어 같은 키는 반드시 같은 태스크에
SORT gt_data BY matnr.
" matnr가 바뀌는 지점에서 청크를 끊는다

이 노트의 실습 코드는 인덱스 기준 분할이다. 실무에 쓰려면 키 기준 분할로 바꿔야 한다.

③ 300초 제한

aRFC는 DIA에서 돌므로 청크 하나가 rdisp/max_wprun_time을 넘기면 죽는다. 건수가 아니라 예상 소요 시간으로 청크 크기를 잡는다.

참고 — 표준 프레임워크

직접 구현 대신 SAP 표준 병렬 프레임워크(SPTA_PARA_PROCESS_START_2 계열)를 쓰는 선택지도 있다. 태스크 관리·리소스 대기·결과 회수를 대신 해준다.

확인 필요

SPTA 계열 FM의 가용 여부와 릴리즈별 인터페이스는 대상 시스템(winerp01 / MEP)에서 SE37로 직접 확인할 것. 이 노트에서는 미검증이다.

반드시 지킬 것

가용 워크프로세스를 전부 쓰지 않는다

공용 시스템에서 DIA를 다 점유하면 다른 사용자의 화면이 멈춘다. 코드에 상한을 박아두고, 작게 돌려 확인한 뒤 키운다.

EXCEPTIONS 없는 SY-SUBRC 판정은 무의미하다

STARTING NEW TASK와 RECEIVE RESULTS 모두 해당. 특히 resource_failure를 안 잡으면 WP 소진 시 그냥 덤프난다.

카운터는 성공 시 송신 · 콜백 진입 즉시 수신

이 규칙이 깨지면 무한 대기다. UP TO n SECONDS는 선택이 아니라 안전장치.

병렬 구간이 이상하면 ST22부터

원격 태스크의 덤프는 메인 화면에 뜨지 않는다. 화면이 멀쩡해도 뒤에서 수백 건이 터지고 있을 수 있다.

FM 호출은 패턴 버튼으로 삽입한다

CALL FUNCTION은 런타임 바인딩이라 이름이 틀려도 신택스 체크를 통과한다. Ctrl+F6이 덤프 3종을 막아준다.
