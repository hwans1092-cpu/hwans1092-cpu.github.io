CORE CONCEPT

멀티 에이전트 하네스 엔지니어링

"테트리스는 한 프롬프트로 되는데 팩맨은 왜 안 되는가"에서 출발해 워크스페이스 거버넌스까지
원출처: Multi-Agent Team Harness Engineering Handbook (5throck.github.io) · 도해 13장 · 실습 절차 포함

한 문장으로. 복잡도가 임계점을 넘는 순간, 좋은 프롬프트가 아니라 좋은 구조가 결과를 가른다.

테트리스(약 200줄)는 한 문장으로 던져도 돌아갑니다. 팩맨(약 1,000~1,500줄)은 같은 방식으로 던지면 코드가 엉키고 기능이 서로 물려 완성되지 않습니다. 개별 기능을 못 짜서가 아니라, 한 에이전트가 동시에 너무 많은 책임을 들고 있어서 생기는 일입니다. 이 노트는 그 한계를 출발점으로 삼아 — 역할을 어떻게 나누고(2~4장), 무엇을 못 하게 막고(5장), 어떤 도구로 구현하고(6~8장), 조직 규모에서 어떻게 관리하는가(9~13장) — 를 한 번에 따라갑니다.

맥락. 이 노트의 내용은 SAP/ABAP이 아니라 AI 에이전트 협업 방법론입니다. 다만 "표준을 위에 두고 하위가 포크된다", "되돌릴 수 없는 작업 앞에는 사람 승인 게이트를 둔다", "검증 스크립트가 통과해야 이관된다" 같은 구조는 SAP 운영·이관 거버넌스와 거의 같은 문제의식입니다. 그 대응을 각 Lesson 끝에 메모로 붙였습니다.

LESSON 1왜 하네스인가 — 테트리스는 되고 팩맨은 안 되는 이유

언제 이 이야기가 필요한가. "AI한테 시켰는데 처음엔 잘 되다가, 요구사항을 몇 개 더 붙이니까 갑자기 전체가 무너졌다" — 이 경험이 있다면 이미 임계점을 넘어본 것입니다. 안 넘어봤다면, 넘기 전에 구조를 알아두는 편이 낫습니다.

원출처 핸드북은 이 임계점을 40분짜리 체험 실습으로 먼저 겪게 합니다. 개념을 설명하기 전에 실패부터 시키는 구성입니다.

Part 1 — 테트리스 (10분)

강사가 1분 시연 — HTML Canvas 테트리스를 한 문장으로 요청

2

참가자가 각자 5분간 직접 생성

3

4분간 수정 요청 연습 — 색 변경, 점수판 확대, 다음 블록 미리보기 추가

여기서 확인하는 것

약 200줄 규모에서는 단일 프롬프트가 잘 동작합니다. 수정 요청도 구조를 무너뜨리지 않고 흡수됩니다. 이 복잡도에서는 하네스가 없어도 충분하다는 것이 이 파트의 결론입니다. 즉 이 노트의 모든 내용은 "항상 해야 하는 일"이 아니라 임계점을 넘은 작업에만 필요한 일입니다.

Part 2 — 팩맨 (25분)

Stage 1 · 의도된 실패 (2~3분). 똑같은 방식으로 팩맨을 요청합니다. 팩맨은 캐릭터 이동 · 고스트 AI · 충돌 판정 · 맵 설계 · 아이템 시스템이 서로 맞물리는 구조라 약 1,000~1,500줄로 부풀어 오릅니다.

예상되는 결과 — 코드가 엉키고, 기능이 제대로 통합되지 않고, 게임이 완성되지 않습니다. 원인은 컨텍스트 과부하(context overload)입니다. 개별 기능은 각각 구현 가능하지만, 한 에이전트가 동시에 조율하려 들면 충돌과 누락이 생깁니다.

Stage 2 · 3역할로 재시도 (단계당 7~8분). 같은 팩맨을 세 단계로 쪼갭니다.

Step역할하는 일

Step 2개발(Development)Step 1 명세서만 보고 실제 코드 작성. 설계 판단은 하지 않는다

실습의 핵심 — 수동 핸드오프

각 단계의 결과를 사람이 직접 복사해서 다음 단계에 넘깁니다. 자동 전환을 일부러 쓰지 않습니다. 워크플로 패턴을 몸으로 익힌 다음에야 자동화(서브에이전트)로 넘어가기 때문입니다 — 원출처에서는 4장에서 자동화합니다.

단일 에이전트의 구조적 한계 3가지

팩맨이 실패한 이유를 일반화하면 세 가지입니다. 이 셋은 이후 모든 장의 출발점이 됩니다.

한계증상조직 비유
컨텍스트 과부하설계·구현·테스트·문서화를 한 세션에서 처리하면 앞 단계의 세부가 뒤로 갈수록 희미해지고 일관성이 떨어진다머릿속이 뒤죽박죽
역할 충돌코드를 작성한 쪽이 자기 코드를 검토하면 놓치는 결함이 많다. 작성자 = 검토자일 때의 문제자기 코드의 허점을 못 봄
병렬성 부재서로 독립적인 하위 작업도 순서대로 처리할 수밖에 없어 시간이 선형으로 늘어난다관련 없는 일 셋을 동시에 못 함
SAP 하는 입장에서 겹쳐 읽기

요구사항 하나짜리 Z리포트는 혼자 처음부터 끝까지 짜는 게 빠릅니다. 반면 화면 여러 개 + 인터페이스 + 배치 + 권한이 물린 건은 설계서를 먼저 확정하고, 구현과 검증을 분리하죠. 여기서 말하는 임계점은 그 경계와 같은 것입니다.

LESSON 2Prompt → Context → Harness, 그리고 하네스 5층

왜 용어를 먼저 정리하는가. "프롬프트를 잘 쓰면 되는 거 아닌가"와 "하네스를 짜야 한다"는 서로 다른 층위의 주장입니다. 층위를 섞어 놓으면 이후 논의가 전부 헛돕니다.

핸드북은 셋을 대체가 아니라 누적으로 봅니다. 각 단계는 "앞 단계만으로는 부족하다"를 드러내며 위에 한 겹을 얹은 것입니다.

단계시기무엇을 다루나초점
1단계 · 프롬프트 엔지니어링2022~2024무엇을 말할 것인가행동
2단계 · 컨텍스트 엔지니어링2024~2025무엇을 알게 할 것인가이해
3단계 · 하네스 엔지니어링2026~어떻게 신뢰할 것인가신뢰성
요리 비유 — 핸드북 원문

프롬프트는 "주방장에게 어떤 말로 주문을 넣을 것인가", 컨텍스트는 "주방장 손에 어떤 재료와 레시피를 쥐여 줄 것인가", 하네스는 "이 주방이 매번 같은 맛을 내도록 검수 절차·도구·위생 규칙까지 갖춘 시스템을 만드는 것". 말을 잘하고 재료가 좋아도 주방 시스템이 엉성하면 결과는 들쭉날쭉합니다.

한 줄 요약 — "좋은 프롬프트는 한 번 잘 대답하게 만들지만, 좋은 하네스는 매번 잘 대답하게 만든다."

하네스(harness)라는 말

승마에서 말에게 씌우는 마구에서 온 표현입니다. AI가 아무 방향으로나 달리지 않고 정해진 절차·도구·권한 범위 안에서 예측 가능하게 움직이도록 잡아 주는 틀입니다.

구체적으로는 이런 장치들입니다.

  • 에이전트가 호출할 수 있는 도구 목록과, 각 도구의 위험도에 따른 승인 정책
  • 특정 이벤트(파일 저장 직후, 작업 완료 시점)에 자동 실행되는 훅(hook)
  • 반복 작업 절차를 표준화해 재사용하는 스킬(skill)
  • 이 모두를 조합해 여러 에이전트를 정해진 순서·조건으로 실행시키는 오케스트레이션

같은 요청, 다른 결과. "파일을 삭제해줘"를 받았을 때 —

✗ 하네스 없이
  • 곧바로 삭제 실행
  • 기록 없음 · 되돌릴 방법 불명
  • 결과 품질이 매번 들쭉날쭉
  • 복잡한 작업은 사실상 불가능
✓ 하네스 있이
  • 삭제가 "위험한 도구"로 분류 → 실행 전 사용자 승인 요구
  • 삭제 후 로그 기록
  • 잘못 지웠을 때 되돌릴 경로까지 절차화
  • 단계별 검증으로 오류를 조기에 발견

모델의 판단력은 똑같습니다. 안전장치의 유무가 결과의 신뢰도를 가릅니다.

에이전트와 챗봇의 차이

이 노트에서 말하는 에이전트는 단순 챗봇이 아닙니다. 세 가지가 다릅니다.

구분내용
목적 지속성"역할"로 정의된 목적을 가진다. 대화가 길어져도 자기 역할(리서처·검토자·작성자)을 잃지 않는다
도구 사용텍스트 생성뿐 아니라 파일 읽기·코드 검색·명령 실행이 가능하다 (tools 필드로 제어 — Lesson 5)
자율적 행동단일 응답이 아니라 목적 달성까지 여러 단계를 수행한다. 조건 분기·오류 재시도·결과 검증을 스스로 판단

챗봇 = 사용자 → LLM → 응답의 단일 루프. 에이전트 = 사용자 → LLM → 도구/서브에이전트 → 결과 → 재검토 → 응답의 확장 루프.

하네스 5층 구조

핸드북 전체를 관통하는 아키텍처입니다. 이 다섯 층이 갖춰져야 "일을 맡길 만한" 수준이 된다고 봅니다.

SAP 하는 입장에서 겹쳐 읽기

"에이전트 자체는 어렵지 않다. 어려운 건 하네스다" — 이 문장은 "ABAP 짜는 건 어렵지 않다. 어려운 건 이관 절차·권한·검증·롤백이다"와 같은 구조입니다. 프로그램 하나를 잘 짜는 능력과, 그 프로그램이 운영에서 매번 같은 결과를 내게 만드는 능력은 다른 문제죠.

안 갖추면 뭐가 되는가. 셋 중 하나라도 빠지면 팀이 아니라 "각자 따로 일하는 에이전트 여러 개"가 됩니다. 조율자가 없으면 순서가 무너지고, 책임이 안 좁혀지면 역할 충돌이 그대로 남고, 계약이 없으면 넘길 때마다 맥락을 다시 추측하게 됩니다.

핸드오프 계약 — 실제 형태

자연어로만 넘기면 다음 에이전트가 맥락을 다시 추측해야 합니다. 구조화된 입력으로 넘기면 바로 시작할 수 있습니다.

{
  "task": "코드 리뷰",
  "agent": "reviewer",
  "scope": {
    "target_file": "src/api/handler.ts",
    "change_description": "인증 미들웨어 추가 — JWT 토큰 검증 로직"
  },
  "deliverables": {
    "from": "code-writer",
    "files": ["src/api/handler.ts", "src/auth/verify.ts"],
    "commit_hash": "a3f7c21"
  },
  "review_criteria": [
    "보안: 토큰 만료 처리가 있는가",
    "오류 처리: 잘못된 토큰에 대한 401 응답이 있는가",
    "테스트: 관련 테스트가 추가되었는가"
  ],
  "output_format": {
    "type": "structured_comment",
    "fields": ["pass_fail", "findings", "suggestions"]
  },
  "failure_conditions": [
    "target_file이 존재하지 않으면 즉시 보고",
    "보안 기준 미충족 시 block으로 표시"
  ]
}

계약이 명시하는 다섯 가지 — 목적(task) · 범위(scope) · 기준(review_criteria) · 형식(output_format) · 예외 처리(failure_conditions).

서브에이전트 — 스페셜리스트의 구현체

스페셜리스트가 개념이라면, 서브에이전트(subagent)는 그 개념을 실제 도구 안에서 구현하는 메커니즘입니다.

서브에이전트는 메인 세션과 독립된 컨텍스트 창을 가지고, 맡겨진 좁은 작업만 처리한 뒤 결과를 요약해서 메인 세션에 돌려줍니다. 메인 세션 기록에는 세부 과정이 쌓이지 않고 최종 요약만 남으므로, Lesson 1의 컨텍스트 과부하가 구조적으로 완화됩니다.

방식대표 도구구현강점
사전 정의Claude Code / App.claude/agents/이름.md에 YAML frontmatter로 정의 → subagent_type="이름"으로 호출재사용성 · 권한 통제
동적 생성Antigravity사전 파일 없음. 오케스트레이터에게 목표를 주면 필요한 역할을 그 순간 구성유연성
언제 쓰고, 언제 쓰지 않는가

쓸 것 — 경계가 분명하고(무엇을 받아 무엇을 내놓는지 명확) 반복적이거나 병렬화가 가능한 작업. 코드 리뷰 · 테스트 실행 · 문서 검토가 좋은 후보.

쓰지 말 것 — 메인 세션과 계속 맥락을 주고받아야 하는 탐색적 작업. 서브에이전트로 분리하면 오히려 핸드오프 비용만 늘어납니다.

동적 팀 구성 — 명단은 고정, 선발은 매번 다르다

재래식 자동화 스크립트는 "A 다음 B, 항상 B 다음 C"가 코드에 박혀 있습니다. 하네스로 짜인 팀은 오케스트레이터가 매 요청마다 "이번엔 누가 필요하고 어떤 순서로 움직일지"를 다시 판단합니다.

  • "오탈자만 고쳐줘" → reviewer 하나
  • "새 기능을 설계부터 배포까지" → architect · code-writer · test-runner · security-monitor · docs-writer를 순서대로(또는 일부 동시에)

비유 — 축구팀 스쿼드 22명은 고정이어도 선발 11명은 상대와 전술에 따라 매번 다릅니다. 팀 구성은 작업이 결정한다는 것이 원칙입니다.

SAP 하는 입장에서 겹쳐 읽기

핸드오프 계약은 결국 인터페이스 명세입니다. 필드 레이아웃·필수값·에러 코드·재처리 조건을 안 정하고 "데이터 넘겨줄게요" 하면 받는 쪽이 매번 물어보게 되는 것과 똑같습니다.

LESSON 4오케스트레이션 패턴 5종과 실패 대응

고르는 기준 3가지. ① 작업 사이에 의존 관계가 있는가 ② 하위 작업을 미리 예측할 수 있는가 ③ 검증이 필요한가. 다섯 패턴은 서로 대체 관계가 아니라 골라 쓰거나 조합하는 도구 상자입니다. (출처: Anthropic, 2024.12 "Building Effective Agents")

패턴언제 쓰는가예시
프롬프트 체이닝 / 파이프라인순서가 정해져 있고 단계 사이에 검증이 필요할 때공장 조립 라인. 문서 3개를 "초안 → 검토 → 교정"으로 동시에 흘려보내기
라우팅요청 성격이 갈리고, 각각 다른 처리가 필요할 때모델 티어링 — 쉬운 질문은 haiku, 어려운 질문은 opus
병렬화 (팬아웃)서로 독립적인 하위 작업이 여러 개일 때성능·보안·가독성·테스트 커버리지 네 관점 동시 리뷰
병렬화 (투표)한 에이전트의 착각 가능성을 줄이고 싶을 때같은 버그 원인 분석을 셋에게 독립 지시 → 둘 이상이 같은 원인 지목하면 채택
오케스트레이터-워커하위 작업을 미리 예측할 수 없을 때여러 파일에 걸친 코드 변경, 여러 출처를 종합하는 리서치
평가자-최적화그럴듯하지만 틀린 결과가 통과되면 곤란할 때코드 수정 전 독립 에이전트가 반박 관점에서 재검토 → 문제없을 때만 반영

조합이 기본. 코드 리뷰 워크플로 하나만 봐도 — ① 라우팅으로 변경 규모 분류 → ② 오케스트레이터-워커가 영향 파일을 동적 분배 → ③ 팬아웃으로 네 관점 동시 검토 → ④ 파이프라인으로 문서화 → ⑤ 평가자-최적화로 반영 결정. 다섯 패턴이 한 흐름 안에 다 들어갑니다.

LESSON 5가드레일 — 권한 · 승인 게이트 · 격리 · 감사

왜 실습보다 먼저인가. 원출처 핸드북은 가드레일 장을 서브에이전트를 만드는 실습 바로 앞에 배치합니다. "이 에이전트가 무엇을 해도 되고 무엇은 안 되는가"를 먼저 정하지 않으면 실습 중에도 실무에서도 사고가 나기 때문입니다.

이 장의 한 문장

"가드레일의 목적은 에이전트를 못 미더워하는 것이 아니라, 실수의 파급력을 사람이 감당할 수 있는 크기로 미리 잘라 두는 것이다."

"할 수 있는 일"은 넓게 열어 두되, "사람 확인 없이 실행해도 되는 일"은 좁게 제한합니다. 능력과 위험을 분리하는 것이 핵심입니다.

① 위험 작업 3단계 분류

모든 작업을 똑같은 강도로 통제하면 실무에서 못 씁니다. 기준은 단 하나 — 되돌릴 수 있는가.

단계예시기본 정책
읽기 (Read)파일 읽기, 코드 검색, 웹 조회대체로 자유롭게 허용 — 되돌릴 필요가 없다
쓰기 (Write)파일 생성·수정, 로컬 커밋허용하되 결과를 검토 — git으로 되돌릴 수 있는 범위
파괴적 / 외부 영향파일·브랜치 삭제, 강제 푸시, 배포, 결제, 외부 메시지 발송사람의 명시적 승인 없이는 절대 실행 금지

② 최소 권한 원칙 — tools 필드

서브에이전트 정의에서 tools: Read, Grep처럼 허용할 도구를 명시적으로 나열하는 것이 서브에이전트 단위의 최소 권한입니다.

사고 시나리오

reviewer에게 Write까지 습관적으로 열어 뒀다면, "이 파일을 검토하고 개선해줘"처럼 살짝 모호한 요청에서 reviewer가 "개선"을 "직접 수정"으로 해석해 원본을 덮어쓸 수 있습니다.

tools에 Write가 없으면 프롬프트가 아무리 애매해도 수정할 방법 자체가 없습니다. 프롬프트 품질에 기대는 대신 구조적으로 막는 것입니다.

기준 문장. 권한은 "이 역할이 최대로 무엇까지 할 수 있는가"가 아니라 "이 역할이 정상 작동하는 데 최소로 무엇이 필요한가"로 정합니다. 나중에 넓히는 건 쉽지만, 처음부터 넓게 연 권한을 사고 이후에 좁히는 건 이미 늦습니다.

③ 사람 승인 게이트 — 어디에 둘 것인가

너무 자주 멈추면 맡기는 의미가 없고, 너무 안 멈추면 파괴적 작업이 조용히 지나갑니다. 검증된 기준은 단순합니다 — 3단계 분류의 "파괴적/외부 영향" 직전에는 항상 멈추고, 그 아래는 사후 검토로 충분하다.

④ 격리 — worktree와 sandbox

여러 에이전트가 같은 파일·같은 git 이력을 동시에 건드리면 한 에이전트의 실수가 다른 에이전트의 작업 맥락까지 오염시킵니다. 이것을 인지적 중첩(cognitive overlap)이라 부릅니다 — 한 에이전트가 다른 에이전트의 결과를 자기 작업 맥락으로 착각하는 현상입니다.

격리된 git worktree나 별도 sandbox에서 각각 실행하면 실수의 영향이 자기 작업 공간 밖으로 새어 나가지 않습니다. 병렬로 굴릴 때는 "같은 공간을 공유할 것인가, 물리적으로 나눌 것인가"를 항상 먼저 결정해야 합니다.

⑤ 감사 로그와 관측성

가드레일이 사전 예방이라면 감사 로그는 사후 추적입니다. 완벽한 가드레일은 없으므로, 사고 시 "언제, 어떤 에이전트가, 어떤 도구로, 무엇을 했는지"를 되짚을 기록이 반드시 필요합니다.

log_entry
  ├─ timestamp : ISO 8601
  ├─ agent     : reviewer
  ├─ action    : Read / Grep
  ├─ result    : ok / deny
  └─ context   : filepath …

감사 흐름
에이전트 동작(tool 호출) → 로그 기록 → audit 스크립트(검사/분석) → 규칙 위반?
   ├─ 정상 → 기록 보존
   └─ 위반 → 경고 → 사후 검토(팀 리뷰) → 피드백 루프 — 가드레일 개선

워크스페이스 훅 배선 예시(2026-08-24 기준):

반드시 확인할 것 — 훅이 내 도구에서 실제로 도는가

Claude Desktop App에서는 이런 훅이 발화하지 않습니다. Desktop 위주로 작업하는 팀이라면 "감사 로그가 돌고 있는 줄 알았는데 사실 하나도 안 돌고 있었다"는 상황이 실제로 생깁니다. 화면상으로는 CLI와 똑같이 "파일이 저장됐다"는 결과만 보이므로 알아차리기도 어렵습니다.

Codex는 훅 메커니즘 자체가 없습니다. CODEX.md 지침을 PM이 매 세션 스스로 인지하고 실행하는 방식(프롬프트 자체 강제)으로 대체합니다.

Lesson 5 한 줄 요약 — 가드레일은 네 가지 습관이다. 위험도에 따라 권한을 차등 부여하고, 돌이킬 수 없는 지점 앞에서는 사람이 확인하며, 병렬 작업은 물리적으로 격리하고, 모두 실패했을 때를 대비해 기록을 남긴다.

SAP 하는 입장에서 겹쳐 읽기

3단계 위험 분류는 조회 / 등록·변경 / 삭제·전기의 권한 설계와 그대로 겹칩니다. "reviewer에게 Write를 안 줬으니 프롬프트가 애매해도 못 고친다"는 권한 오브젝트로 막는 것이 프로그램 내부 IF문으로 막는 것보다 안전하다는 원칙과 같습니다. 그리고 "훅이 내 환경에서 실제로 도는지 확인하라"는 경고는 운영기에서 실제로 배치가 스케줄되어 도는지 확인하라와 같은 종류의 함정입니다.

bun run agent:verify가 구조를 검증합니다. 검사 항목은 ① frontmatter 필드 누락/타입 ② AGENTS.md 등록 여부 ③ 참조 스킬·스크립트 실재 여부 ④ 다른 에이전트와의 역할 중복.

자주 나는 불일치 두 가지

① "로스터에는 있는데 정의 파일이 없음" — AGENTS.md의 이름과 .claude/agents/ 파일명을 대조해 누락 항목을 추가하거나 불필요 파일을 제거.

② 고아 handoff_to — 삭제된 에이전트를 가리키고 있는 경우. 대칭성도 봐야 합니다 — researcher의 handoff_to에 writer가 있으면 writer의 handoff_from에도 researcher가 쌍으로 있어야 합니다.

SAP 하는 입장에서 겹쳐 읽기

"공통 명세 하나 + 도구별 파일"은 기능 설계서 하나 + 모듈별 기술 설계서 구조와 같습니다. 그리고 agent:verify가 잡는 "로스터-파일 불일치"는 TR에 오브젝트는 담겼는데 실제로는 없거나, 있는데 TR에 안 담긴 상황과 똑같은 종류의 사고입니다.

초기에는 L1 변경을 기존 L2 전체에 자동 반영하려 했으나 세 가지 문제가 반복됐습니다.

  2. 전파 스크립트에 variant 목록이 하드코딩되어 새 variant마다 수동 갱신 필요
  3. "의도된 차이"와 "동기화 누락으로 생긴 차이"를 구분 불가
포크 모델의 대가

의도한 차이는 보존되지만, 보안 패치나 버그 수정도 프로젝트마다 수동 반영해야 합니다. 핸드북 스스로 이것을 운영 부담으로 인정하고, "동의 기반(consent-based) 선택적 수신 모델"을 고도화 방향으로 남겨 두었습니다 — 아직 미구현입니다.

L0→L1→L2→L3은 글로벌 템플릿 → 공통 → 법인별 → 실제 시스템 구조와 같습니다. 그리고 포크 모델의 대가는 SAP에서도 익숙하죠 — 표준을 수정(Modification)해 두면 다음 업그레이드 때마다 SPAU로 수동 병합해야 하는 것과 정확히 같은 트레이드오프입니다. "의도된 차이인지 동기화 누락인지 구분 불가"도 SPAU 앞에서 매번 겪는 문제입니다.

LESSON 10생애주기 관리 — 에이전트 · 스킬 · 스크립트

예방하려는 문제 3가지. ① 미검증 구성요소가 운영에 투입됨 ② 폐기 대상이 여전히 호출됨 ③ 버전 불일치로 재현 불가.

상태(State)와 생애주기(Lifecycle)는 다른 것

구분의미비유
생애주기구성요소가 거치는 순차적 단계 전체지하철 노선도
상태특정 시점의 스냅샷. YAML frontmatter의 status 필드현재 열차가 어느 역에 있는지

상태값 — draft(미검증, 운영 투입 불가) / active(운영) / deprecated·retired(새 호출 대상 제외).
워크플로 실행 차원의 상태(Phase 0~6)는 개별 구성요소의 status와 별개입니다.

공통 원칙 3가지

1

2

3

폐기 후 보존 — 즉시 삭제하지 않고 일정 기간 보존해 복원 가능성과 폐기 근거 추적을 남김

L-A 명시적 — frontmatter의 타입화된 관계. 의도상 영구적, 1차 원천

LESSON 11워크플로우 설계 패턴

패턴과 워크플로의 관계. 오케스트레이션 패턴은 레고 블록, 워크플로는 조립 결과물입니다. 워크플로 = 패턴 조합 + 도메인 규칙 + 인간 승인 게이트.

워크플로의 6대 구성요소

구성요소설명주의
단계 (Stage)순차 실행되는 작업 단위. 이전 출력이 다음 입력—
분기 (Branch)조건에 따라 경로가 갈라지는 지점. 라우팅의 실제 적용"변경 규모가 작으면 빠른 리뷰, 크면 전체 검토"
병렬 (Fan-out)독립 하위 작업을 동시 실행. 팬아웃의 구조적 표현실행 시간은 가장 느린 하위 작업에 수렴
취합 (Fan-in)병렬 결과를 하나로 모으는 단계어떤 결과를 우선할지(투표), 어떻게 병합할지(합산/선택) 규칙이 필요
게이트 (Gate)검증 또는 인간 승인을 요구하는 지점되돌리기 어려운 작업 앞에 둔다 — 파일 수정·배포·PR 병합
루프 (Loop)거부됐을 때 이전 단계로 돌아가는 반복 구조최대 반복 횟수를 정해야 무한 루프를 막는다

· 순수 순차 워크플로는 실무에서 거의 쓰이지 않는다

  • 각 단계 필드 — id · agent_key · skill_key · output_type · description
  • 단계 간 관계 — follows(선행 의존) · enables(다음 단계 활성화) · composes_with(병렬 구성)
  • 검증 — validate-procedures.ts가 모든 agent_key/skill_key가 실제 파일로 해결되는지 확인. 실패 시 sync 중단
  • 커버리지 — procedure-coverage.ts가 에이전트의 phases: 요구가 실제 절차로 덮이는지 보고. 갭은 자동으로 안 채우고 거버넌스 티켓으로 등록되어 사람이 판단

Phase 6의 "최대 2회 반복 후 에스컬레이션"은 배치 재처리 횟수 제한과 같고, 역할 경계 매트릭스는 개발자가 자기 TR을 스스로 승인하지 못하게 하는 직무 분리와 같습니다. "팬아웃에는 반드시 취합이 따라붙는다"는 병렬 처리 후 결과 집계를 빠뜨리면 안 된다는 것과 정확히 같은 이야기입니다.

LESSON 12업그레이드와 승격 — 방향이 반대인 두 스크립트

왜 헷갈리는가. 둘 다 "템플릿과 프로젝트 사이에서 파일을 옮긴다"는 점은 같은데 방향이 정반대입니다. 어느 한쪽이 다른 쪽을 대체하지 않습니다.

업그레이드 — upgrade-project.ts

L3를 만든 뒤 상위 표준이 바뀌어도 아무 일도 일어나지 않습니다. 포크 모델이기 때문에, 반영하려면 사람이 명시적으로 실행해야 합니다.

# 1) 반드시 dry-run 먼저
bun scripts/upgrade-project.ts <project-path> --dry-run

# 2) 실제 실행
bun scripts/upgrade-project.ts <project-path>
#   선택: --variant <variant>  --platform claude|antigravity|codex|all
#         --prune-removed  --rollback

# 3) 잘못됐으면 되돌리기
bun scripts/upgrade-project.ts <project-path> --rollback
분류동작대상 예시
LOCKED항상 템플릿 내용으로 덮어씀.githooks/*, .gitattributes
LOCKED (merge-aware)템플릿을 가져오되 프로젝트 전용 허용 목록은 보존.gitleaks.toml
MERGEWORKSPACE-MANAGED 등 마커로 감싼 구간만 병합, 나머지 로컬 내용은 보존CLAUDE.md/GEMINI.md/CODEX.md, .gitignore, agents/pm.md
DOCS_MERGE문서에도 마커 구간 병합 적용. 마커 없는 문서만 통째로 덮어씀AGENTS.md, docs/phase-definitions.md
VARIANT_DOCS_SYNC각주 버전이 템플릿보다 낮을 때만 갱신docs/context.md, docs/team-configuration-guide.md
COMMANDS_SYNC해시가 다르면 플랫폼 명령 파일 동기화.claude/commands/*.md, .gemini/commands/*.md
SYNC_IF_NEWER템플릿 버전이 더 높을 때만 복사scripts/*.ts, agents/*.md, skills/*/SKILL.md
PRESERVE목록에만 표시, 전혀 손대지 않음README.md, src/
PRUNE (선택)--prune-removed 지정 시 템플릿에서 사라진 파일을 프로젝트에서도 제거scripts / agents / skills
⚠ 물어보지 않고 덮어쓴다

SYNC_IF_NEWER 대상 파일을 로컬에서 고쳤는데 템플릿 버전이 더 높으면, 스크립트는 ⚠️ CONFLICT로 표시하면서도 결국 템플릿 내용으로 덮어씁니다. "덮어쓰기 전에 물어봐 주는" 동작이 아니라 "경고만 하고 진행하는" 동작입니다. 그래서 --dry-run이 먼저입니다.

안전장치

· 실행 전 자동으로 git stash push -m pre-upgrade-snapshot-YYYYMMDD
· --rollback은 그 스태시를 찾아 git stash pop으로 복원
· 업그레이드 자체는 커밋을 만들지 않으므로 결과를 git diff로 검토하고 직접 커밋

핵심 문장 — "처음부터 만들기는 설계가 사용에 앞서고, 승격은 사용이 검증을 거쳐 설계에 앞선다." 두 경로 모두 결국 같은 templates/co-<name>/로 수렴합니다.

의사결정 기록 — 결정도 자산이다

"이 스킬은 실험적 관계로만 둔다", "이 variant는 승격 보류다" 같은 판단이 대화와 기억에만 있으면 조직은 같은 논쟁을 반복합니다. 답은 — 결정을 파일로 쓰고, 체인으로 근거를 묶고, 기계로 검증한다.

파일 경로 docs/decisions/DEC-YYYYMMDD-NN.md, 체인은 Agent → Skill → Knowledge → Evidence → Rule → Decision.

  • 필수 frontmatter — id, date, agent, decision, alternatives, status
  • 증거 장부 — docs/evidence/ledger.md. 행 ID는 EV-YYYYMMDD-NN. 결정 기록의 evidence_refs는 이 장부의 행 ID만 가리킬 수 있다
  • supersession-only — 결정 기록은 지우지 않는다. 뒤집힌 결정은 새 기록이 옛 기록을 계승(supersede)한다. 결정의 역사는 덧씌워지는 게 아니라 연결된다
  • 검증 — validate-decisions.ts가 7가지를 검사하며 fail-closed. 결정 기록이 깨진 채로는 동기화가 진행되지 않는다
"지금 결정하지 않겠다"도 기록한다 — 거버넌스 백로그

근거가 부족하면 scripts/ticket.ts로 tickets/governance/에 git 추적 티켓을 남깁니다. not_before 날짜를 달면 그 전에는 목록에 안 나옵니다(숙성 예약). 상태 기계는 backlog → waiting → review → done.

망각이 아니라 예약입니다. 기억이 아니라 티켓이 책임집니다.

Domain Operating Model — 템플릿이 실행 가능한 SOP가 되는 법

2026-09부터 정식 variant 템플릿에 적용된 기준입니다. 템플릿이 "파일 묶음"을 넘어, 무엇을 어떤 순서로 하고(스테이지), 누가 책임지며(RACI), 어떤 판정을 통과해야 다음으로 가는지(결정 게이트)를 기계가 읽을 수 있는 형태로 스스로 선언합니다.

이름 규칙 — 약어 금지

공식 명칭은 Domain Operating Model, 풀네임만 씁니다. "DOM" 금지 — 브라우저의 Document Object Model과 충돌하며, HTML·CSS를 다루는 variant에게 DOM은 이미 살아있는 용어입니다. "AOM"도 금지 — "Agent"는 이미 PM 게이트웨이의 전문 에이전트를 가리킵니다. 문서·스키마·스크립트·커밋 메시지 어디에서도 약어를 쓰지 않습니다.

그룹담당하는 것파일
ProcessStage → Activity → Skill. 업무가 어떤 순서로 흐르는지process/stages.yaml, procedures/*/schema.yaml
GovernanceRACI. 단계·활동별로 누가 책임지고 누가 실행하는지governance/raci.yaml
ExecutionArtifact · Decision. 무엇이 산출되고 어떤 판정을 통과하는지procedures/_output-types.yaml, decisions/gates.yaml
GraphDomain Execution Graph. 위 셋을 잇는 관계층docs/skill-graph.json의 DEG 프로파일

조립 라인 비유 — Process = 라인 배치도 / Governance = 각 공정 앞 담당자 명패 / Execution = 만들어내는 부품 + 품질 검사대 / Graph = 전체를 내려다보는 관제탑.
에이전트는 4그룹에 포함되지 않습니다. 에이전트는 RACI 안의 행위자 참조일 뿐이고, 실행 주체가 사람인지 AI인지는 구조가 강제하지 않습니다.

phase 축과 stage 축은 다르다

기존 phase(0~6)는 PM이 작업을 실행하는 축이지 도메인 업무 흐름이 아니었습니다. 컨설팅의 "조사→분석→보고", 발표자료의 "리서치→스토리라인→빌드→출력" 같은 도메인 진행 단계가 선언된 곳이 없었죠. 그래서 process/stages.yaml에 별도 축을 선언합니다.

# templates/co-deck/process/stages.yaml (발췌)
schema_version: '1.0'
variant: co-deck
stages:
  - id: S1
    title: Deck Source Research
    order: 1
    owner_agent: version
  - id: S2
    title: Version Export Control
    order: 2
    owner_agent: version

불변식 DEG-P-01 — "스테이지가 phase와 다르게 구별되어야 한다". 절차 수·phase 수·스테이지 수가 모두 같아 1:1 대응이면 새 축이 아니라 phase의 이름만 바꾼 것 → 위반.

# governance/raci.yaml (발췌)

    activity: procedure.co-deck.deck-build-and-export

    responsible:
      - html-build

게이트 vs 결정 기록

게이트 = 절차 속 판정 지점의 규칙 선언(사전) — "출력 전에 레이아웃 검사를 통과해야 한다"
결정 기록(DEC-*.md) = 실제 내려진 판정의 기록(사후) — "2026-09-20 판정: proceed"
record_kind: DEC가 두 세계를 잇는 다리입니다.

이 마이그레이션으로 9개 템플릿의 절차에서 서술형 quality_gates 필드가 완전히 제거됐습니다. 품질 기준이 문장으로 흩어지는 대신 이름·담당자·입력·판정 결과를 가진 데이터가 됐습니다.

등급의미템플릿
governed스테이지 축이 phase와 구별되게 존재하고, RACI·게이트가 데이터로 갖춰짐co-abap, co-consult, co-deck, co-design, co-export, co-game, co-hr, co-price, co-security (9종)

"강제 3계층"은 권한 오브젝트(기계적 차단) / 프로그램 내 체크(자기 준수) / 운영 지침(사람이 지킴)의 3단과 같습니다. 특히 "훅 없는 플랫폼에서도 위반의 성격은 같다"는 것 — 시스템이 안 막아준다고 해서 해도 되는 게 아니라는 것 — 이 실무에서 가장 자주 무너지는 지점입니다.

반드시 지킬 것

① 되돌릴 수 없는 작업 앞에는 예외 없이 사람 승인

파일·브랜치 삭제, 강제 푸시, 배포, 결제, 외부 메시지 발송. 여기에 재량을 두는 순간 가드레일이 아닙니다.

② 권한은 "최소로 무엇이 필요한가"로 정한다

"최대로 무엇까지 할 수 있는가"가 아닙니다. 나중에 넓히는 건 쉽지만, 사고 이후에 좁히는 건 이미 늦습니다. reviewer에게 Write를 주지 않으면 프롬프트가 애매해도 못 고칩니다.

③ 훅이 내 환경에서 실제로 도는지 확인한다

Claude Desktop App은 훅이 발화하지 않고, Codex는 훅 메커니즘 자체가 없습니다. 화면상으로는 CLI와 똑같아 보이므로, "감사가 돌고 있는 줄 알았는데 하나도 안 돌았다"를 알아차리기 어렵습니다.

④ 의존 관계가 있으면 "순서대로 진행해"를 명시한다

안 쓰면 병렬로 호출되어 "파일이 없다"로 실패합니다. 반대로 병렬을 원하면 "동시에"를 명시해야 합니다.

⑤ 병렬 작업은 물리적으로 격리한다

같은 폴더에 에이전트 여럿을 배정하면 인지적 중첩이 발생합니다. Workspace 또는 git worktree 단위로 나눕니다. 처음부터 완전히 분리된 파일·디렉터리를 배정하십시오.

⑥ 루프에는 반복 상한, 재시도에는 횟수 상한

평가자가 계속 "부족하다"고 판단하면 공회전합니다. 상한 없는 자동 재시도는 같은 실수를 반복할 뿐입니다. "3번 실패하면 멈추고 사람에게 보고"를 미리 정합니다.

⑦ 업그레이드는 --dry-run 먼저

SYNC_IF_NEWER 대상은 로컬 수정이 있어도 경고만 하고 덮어씁니다. 물어봐 주지 않습니다.

⑧ 우회(--no-verify)는 금지

게이트 하나를 건너뛰는 게 아니라 비밀 스캔을 포함한 모든 품질 게이트를 건너뜁니다.

⑨ 승격 파이프라인은 되돌리기 까다롭다

l3-to-variant-pipeline.ts는 실제 git 이력에 흔적을 남깁니다. 정말 공개할 의도가 있을 때만 실행하고, 흐름만 보려면 읽기만 하십시오.

⑩ 팬아웃에는 반드시 취합 규칙을 함께 정한다

어떤 결과를 우선할지(투표), 어떻게 병합할지(합산/선택)를 안 정하면 병렬 결과가 그냥 쌓이기만 합니다.
